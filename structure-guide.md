# Структура папок и файлов

Инструкция для агентов: как организовать новую тематическую папку в этом репозитории. Извлечена из существующих `algorithms-and-data-structures/` и `databases/`.

Для стиля написания текста см. [styleguide.md](styleguide.md).

---

## Иерархия директорий

Максимум 4 уровня вложенности:

```
тематическая-папка/          # уровень 1: домен (databases, ruby, rails)
├── index.md                 # мастер-индекс (обязателен)
├── shared-concept.md        # общая теория, если нужна нескольким подпапкам
├── подкатегория/            # уровень 2: логическая группа (storage, concurrency)
│   ├── 00-first-topic.md    # уровень 3: файлы заметок
│   ├── 01-second-topic.md
│   └── 02-third-topic.md
└── practice/                # опционально: прикладные сценарии
    └── scenario-name.md
```

Для технологий внутри домена добавляется ещё один уровень:

```
databases/
├── postgresql/
│   ├── index.md
│   ├── storage/
│   │   ├── 00-acid.md
│   │   └── 01-pages-and-tuples.md
│   └── concurrency/
│       ├── 00-mvcc.md
│       └── 01-anomalies.md
└── redis/
    ├── index.md
    └── architecture/
        └── 00-what-is-redis.md
```

### Когда создавать подкатегорию

- 3+ файлов по одной теме → выносить в подпапку.
- 1–2 файла → оставить в родительской директории.
- Исключение: при ветвлении последовательностей (§ниже) подкатегория создаётся для оси, даже если в ней пока 2 файла, если она является самостоятельной линией изучения и ожидается рост.
- Файлы внутри подкатегории объединяет общая тема и направление зависимостей (storage → durability → concurrency).

## Именование

### Директории

kebab-case: `query-processing`, `data-structures`, `schema-design`.

### Файлы заметок

`NN-kebab-case.md` — двузначный префикс определяет порядок чтения:

```
00-acid.md
01-pages-and-tuples.md
02-toast.md
```

Номер = порядок зависимостей: файл `02` может ссылаться на `00` и `01`, но не наоборот.

### Ветвление последовательностей

Когда от фундаментального файла расходятся несколько самостоятельных осей изучения (с собственным локальным порядком, но допускающих содержательные cross-links между собой), каждая ось оформляется как подкатегория со своей нумерацией. Общий фундамент остаётся в корне, ветки — в подпапках. В index.md ветки оформляются как отдельные подсекции «Порядка изучения» с пояснением, какой вопрос каждая ветка отвечает.

```
computer/
├── index.md
├── 00-cpu.md                    # общий фундамент
├── data-path/                   # ось: куда и как быстро ходят данные
│   ├── 00-memory-hierarchy.md
│   ├── 01-cache-coherency.md
│   └── ...
└── programmer-model/            # ось: что процессор обещает программе
    ├── 00-isa.md
    ├── 01-abi-and-data-layout.md
    └── ...
```

### Специальные файлы

| Файл | Назначение |
|------|-----------|
| `index.md` | Мастер-индекс тематической папки |
| `shared-*.md` | Общая теория, используемая несколькими подпапками |

Файлы без числового префикса — либо индексы, либо shared-концепции.

## Шаблон index.md

Каждая тематическая папка (и каждая технология внутри домена) содержит `index.md`:

```markdown
# Заголовок домена/технологии

**Предпосылки:** [концепция 1](path/to/file.md), [концепция 2](path/to/file.md), базовое знание X.

Вводный абзац: зачем эта тема существует, какие задачи решает, какие компромиссы определяют её устройство. Без мета-комментариев вроде "в этом разделе мы рассмотрим".

## Порядок изучения

Заметки сгруппированы по зависимостям: от X к Y и далее к Z.

### Подкатегория 1

Краткое пояснение, почему эти темы идут вместе.

- [Тема A](subcategory/00-topic-a.md) — одно предложение о сути
- [Тема B](subcategory/01-topic-b.md) — одно предложение о сути

### Подкатегория 2

- [Тема C](subcategory2/00-topic-c.md) — одно предложение о сути

## Как всё связано

Серия компромиссов в формате **X vs Y:**

**Durability vs Performance:** Проблема. Решение. Цена решения.

**Isolation vs Performance:** Проблема. Решение. Цена решения.

## Sources

- Автор, год, *Название*. URL
```

### Ключевые свойства index.md

- Ссылки на все файлы внутри папки, сгруппированные по подкатегориям.
- Каждая ссылка сопровождается кратким пояснением (1 предложение).
- Секция «Как всё связано» показывает trade-offs домена.
- Опционально: сводные таблицы для сравнения (как таблица выбора индексов в PostgreSQL).
- Опционально: секция «См. также» со ссылками на связанные разделы в других папках.

## Шаблон файла заметки

```markdown
# Заголовок концепции

**Предпосылки:** [зависимость 1](path.md), [зависимость 2](path.md).

← [Предыдущая тема](00-previous.md) | [Следующая тема](02-next.md) →

Вводный абзац: какую проблему решает эта концепция или зачем она нужна. Сразу в тему, без "в этой заметке мы...".

## Секция 1: проблема или контекст

Проза, объясняющая проблему. Конкретные эффекты: latency, memory, OOM, CPU.

## Секция 2: решение / механизм

Как устроено решение. Код-якоря: "страница кучи (`struct heap_page`)" — что это, где живёт, зачем нужно.

### Подсекция при необходимости

Детали механизма.

## Секция N: следствия / trade-offs

К чему приводит решение, какие ограничения вносит.

## Sources

- Автор, год, *Название* — контекст: URL

---

← [Предыдущая тема](00-previous.md) | [Следующая тема](02-next.md) →
```

### Принципы содержания

Стиль написания текста подробно описан в [styleguide.md](styleguide.md). Здесь — только то, что влияет на структуру файлов:

- **Один файл = одна концепция.** Критерий разделения: концепция имеет собственное определение, собственные зависимости и может быть целью перекрёстной ссылки. Пример: MVCC, аномалии и уровни изоляции — три разных файла, потому что у каждого свои предпосылки и на каждый ссылаются независимо.
- **Предпосылки определяют порядок файлов.** Файл не использует термины, не определённые в нём самом или в файлах из предпосылок. Числовой префикс отражает этот порядок: `02` зависит от `00` и `01`.

## Перекрёстные ссылки

Относительные пути от текущего файла:

```markdown
<!-- внутри подкатегории -->
[предыдущая тема](00-previous.md)

<!-- между подкатегориями одной папки -->
[WAL](../durability/00-wal.md)

<!-- между тематическими папками -->
[LRU-кэш](../../algorithms-and-data-structures/linear/06-lru-cache.md)

<!-- на файл теории в system-design -->
[Репликация](../../../system-design/replication.md)
```

Ссылки ставятся в том месте текста, где концепция впервые упоминается.

## Навигация между последовательными заметками

Нумерованные файлы (`00-`, `01-`, `02-`, …) образуют последовательность изучения. Чтобы читатель мог перейти к следующей или предыдущей теме без возврата в index.md, каждый нумерованный файл содержит навигационные ссылки в двух местах:

- **Хедер** — после блока «Предпосылки», перед основным текстом.
- **Футер** — после секции `## Sources`, через горизонтальную линию `---`.

Формат строки навигации:

```markdown
← [Предыдущая тема](path) | [Следующая тема](path) →
```

### Порядок навигации

Порядок определяется секцией «Порядок изучения» в index.md родительской тематической папки. Навигация переходит между подкатегориями: последний файл в одной подкатегории ссылается на первый файл следующей.

```markdown
<!-- foundations/02-expressions.md — последний в foundations, следующий — первый в querying -->
← [Типы данных и NULL](01-types-and-null.md) | [SELECT и фильтрация](../querying/00-select-and-filtering.md) →
```

### Крайние случаи

- Первый документ последовательности — только ссылка вперёд: `[Следующая тема](path) →`
- Последний документ последовательности — только ссылка назад: `← [Предыдущая тема](path)`
- Файлы без числового префикса (practice/, shared concepts) — навигация не ставится.
- **Файл-корень ветвления** — одна и та же branch-choice строка в header и footer. Текст ссылок включает имя ветки: `[Путь данных: Иерархия памяти](data-path/00-topic.md) | [Программная модель: ISA](programmer-model/00-topic.md) →`
- **Первый файл ветки** — одинаковая навигация в header и footer: `← [Процессор](../00-cpu.md) | [Следующая тема](01-next.md) →`
- **Последний файл ветки** — только обратная ссылка: `← [Предыдущая тема](NN-prev.md)`. Ветки не пересекаются через prev/next — только через содержательные cross-links.

### Пути

Относительные от текущего файла. Внутри подкатегории: `01-topic.md`. Между подкатегориями: `../querying/00-topic.md`.

## Сворачиваемые предпосылки

Когда блок предпосылок содержит 3+ элементов или занимает больше одной строки, он оборачивается в `<details>`, чтобы не отвлекать от содержания:

```html
<details>
<summary>Предпосылки</summary>

[планировщик запросов](00-planner.md) (cost model, методы доступа), [B-tree](../indexes/00-btree.md) (типы сканирования), [буферный кеш](../durability/01-buffer-cache.md) (страницы, cache hit vs read).

</details>
```

Короткие предпосылки (1–2 ссылки) остаются в однострочном формате без сворачивания:

```markdown
**Предпосылки:** [ACID](00-acid.md).
```

GitHub рендерит `<details>` как нативный dropdown. В редакторах (Zed, VS Code) HTML отображается как есть — это допустимый компромисс: основной контекст чтения — GitHub.

## Блоки самопроверки

Блоки `<details>` используются не только для предпосылок, но и для самопроверки — задач, где читатель может попробовать решить проблему до того, как увидит ответ. Шаблон:

```html
<details>
<summary>Задача: формулировка задачи</summary>

**Частая ошибка:**
```sql
SELECT ... WHERE COUNT(*) > 1;
```
WHERE работает до GROUP BY — агрегат здесь невозможен.

**Правильный вариант:**
```sql
SELECT ... GROUP BY ... HAVING COUNT(*) > 1;
```
HAVING фильтрует уже сформированные группы.

</details>
```

Правила использования:

- 1–3 блока на документ. Только в местах, где ошибка типична и контринтуитивна.
- Блок не заменяет нарратив — он дополняет его. Основное объяснение идёт в тексте, блок даёт возможность попрактиковаться.
- Внутри блока всегда три элемента: частая ошибка, объяснение почему она неверна, правильный вариант.
- Подробнее о паттерне «ошибка → осознание» — в [styleguide.md §1.9](styleguide.md).

## Общие теоретические файлы (shared concepts)

Когда одна концепция используется несколькими технологиями — она выносится на уровень абстракции, где она определена. Теория, общая для всех баз данных и брокеров сообщений, живёт в `system-design/`:

```
system-design/
├── replication.md           # общая теория: sync/async, lag, failover, split brain, кворум
├── sharding.md              # общая теория: shard key, resharding, комбинация с репликацией
└── ...

databases/
├── postgresql/
│   └── distribution/        # PostgreSQL-специфика ссылается на system-design/replication.md
└── redis/
    └── distribution/        # Redis-специфика ссылается на system-design/replication.md
```

Shared-файл содержит абстрактные понятия. Конкретные реализации (как PostgreSQL делает репликацию) — в файлах технологии. Если концепция применима не только к базам данных (например, репликация используется и в Kafka, и в etcd), она принадлежит `system-design/`, а не `databases/`.

## Практические паттерны

Для прикладных сценариев — отдельная подпапка `patterns/` или `practice/`:

```
redis/
└── patterns/
    ├── 00-caching.md
    ├── 01-rate-limiting.md
    └── 02-distributed-locks.md

rails/redis/
└── practice/
    ├── bitmap-dau-retention.md      # без числового префикса —
    ├── hash-checkout-cart.md        # порядок не важен,
    └── sorted-set-call-queue.md     # файлы независимы
```

Если файлы практики зависят друг от друга — нумеровать. Если независимы — kebab-case без префикса, имя описывает «структура-данных + сценарий».

## Чек-лист: создание новой тематической папки

1. Создать директорию в kebab-case в корне или внутри существующего домена.
2. Определить подкатегории (3+ файлов → подпапка).
3. Определить порядок зависимостей внутри каждой подкатегории и пронумеровать файлы `00-`, `01-`, ...
4. Создать `index.md` с предпосылками, порядком изучения, секцией «Как всё связано» и sources.
5. В каждом файле заметки: заголовок, предпосылки со ссылками, нарратив, sources.
6. Проверить: ни один термин не используется до определения (в этом файле или в предпосылках).
7. Проставить перекрёстные ссылки на связанные файлы в других папках.
8. Проставить навигационные ссылки prev/next в хедере и футере каждого нумерованного файла по порядку из index.md.
9. Если есть общая теория для нескольких технологий — вынести в shared-файл уровнем выше.
10. Обновить file map в `CLAUDE.md`.
