# B-tree: Основной индекс

## Название и происхождение

**B-tree** (Б-дерево) — сбалансированное дерево поиска, оптимизированное для работы с дисковой памятью.

Буква "B" не имеет официального объяснения от авторов (Rudolf Bayer и Edward McCreight, 1972, Boeing Labs). Популярные интерпретации: Balanced, Bayer, Boeing, Broad/Bushy. Любая из них работает как мнемоника.

**Важно:** B — это НЕ "binary". B-tree — противоположность бинарному дереву: вместо 2 детей у узла могут быть сотни.

---

## Мотивация: почему не BST

Проблема BST на диске — количество операций ввода-вывода (IOPS).

При поиске в BST с миллионом элементов нужно посетить ~20 узлов (log₂ 10⁶ ≈ 20). Если каждый узел — отдельная страница на диске, это 20 чтений. При 200 IOPS на HDD — всего 10 поисков в секунду.

При этом каждая страница (4KB) содержит лишь ~20-30 байт полезных данных (ключ + 2 указателя). Остальное — пустая трата.

**Идея B-tree:** раз диск всё равно читает целую страницу за один I/O, нужно использовать её целиком — хранить много ключей в одном узле.

---

## Структура узла

В отличие от BST (один ключ, два ребёнка), узел B-tree содержит **много ключей** и **много детей**.

```
┌─────────────────────────────────────────────────────┐
│  P₀ │ K₁ │ P₁ │ K₂ │ P₂ │ K₃ │ P₃ │ ... │ Kₙ │ Pₙ  │
└─────────────────────────────────────────────────────┘
```

Где:
- K₁, K₂, ... Kₙ — ключи (отсортированы по возрастанию)
- P₀, P₁, ... Pₙ — указатели на детей

**Фундаментальное соотношение:** n ключей → n+1 детей.

Ключи работают как разделители диапазонов:
- P₀ ведёт к значениям < K₁
- P₁ ведёт к значениям ≥ K₁ и < K₂
- P₂ ведёт к значениям ≥ K₂ и < K₃
- ...и так далее

---

## Параметр t (минимальная степень)

B-tree определяется параметром **t** — минимальная степень (minimum degree).

**Почему "степень":** в теории графов "степень вершины" — это количество рёбер, выходящих из неё. Для дерева это по сути количество детей. "Минимальная степень t" означает: у внутреннего узла минимум t детей.

| Характеристика | Значение |
|----------------|----------|
| Минимум ключей в узле | t − 1 |
| Максимум ключей в узле | 2t − 1 |
| Минимум детей у внутреннего узла | t |
| Максимум детей у внутреннего узла | 2t |

**Исключение:** корень может содержать от 1 до 2t−1 ключей (для только что созданного или сжавшегося дерева).

### Альтернативная терминология

В разных источниках используют разные параметры:
- **Minimum degree t** — минимум t детей (наш вариант, Cormen/CLRS)
- **Order m** — максимум m детей (Knuth), тогда m = 2t

Это одно и то же дерево, просто параметр задан по-разному. Если видишь "B-tree порядка m", то m = 2t.

### Как выбирают t на практике

Подгоняют под размер страницы диска. Например, при странице 4KB, ключе 8 байт и указателе 8 байт:

- Один узел с n ключами: n×8 + (n+1)×8 = 16n + 8 байт
- Чтобы уместить в 4096 байт: n ≤ 255
- Значит 2t − 1 ≈ 255, откуда t ≈ 128

Типичные значения: t от нескольких десятков до нескольких сотен.

---

## Инварианты B-tree

1. **Ограничение заполнения:** каждый узел содержит от t−1 до 2t−1 ключей (кроме корня).

2. **Соотношение ключей и детей:** узел с n ключами имеет ровно n+1 детей (если не лист).

3. **Баланс по глубине:** все листья находятся на одной глубине.

4. **Упорядоченность:** ключи внутри каждого узла отсортированы по возрастанию.

---

## Операция: Поиск

### Алгоритм

1. Начать с корня
2. В текущем узле бинарным поиском найти:
   - Если ключ найден — готово
   - Иначе — определить указатель на нужное поддерево
3. Перейти к ребёнку по найденному указателю
4. Повторять до нахождения ключа или достижения листа

### Сложность

| Метрика | Значение | Пояснение |
|---------|----------|-----------|
| Посещённых узлов | O(log n) | Высота дерева с основанием ~t |
| Сравнений в узле | O(log t) | Бинарный поиск, но t — константа |
| **Итого сравнений** | **O(log n)** | |
| **Чтений с диска** | **O(log n)** | Главная метрика для БД |

При t=128 и миллионе записей: ~3 чтения вместо ~20 в BST.

---

## Операция: Вставка

### Алгоритм

1. Найти листовой узел для вставки (как при поиске)
2. Вставить ключ в нужную позицию (сохраняя сортировку)
3. Если узел переполнен (> 2t−1 ключей) — выполнить **split**

### Дубликаты

Что делать, если ключ уже существует — зависит от реализации:
- **Запрет дубликатов:** вставка завершается ошибкой или игнорируется (unique index в БД)
- **Разрешение дубликатов:** одинаковые ключи хранятся рядом (мультимножество)
- **Обновление:** новые данные заменяют старые по тому же ключу

### Split (расщепление)

Когда узел содержит 2t ключей (переполнен):

1. Найти медианный ключ (позиция t)
2. Разделить узел на два:
   - Левый: ключи до медианы (t−1 штук)
   - Правый: ключи после медианы (t−1 штук)
3. Медианный ключ поднимается в родительский узел

```
До:    [... переполненный узел с 2t ключами ...]
              ↓ split
После: [левая половина]  [медиана в родителе]  [правая половина]
```

**Каскадный split:** если родитель тоже переполнился — split повторяется выше.

**Рост дерева:** если split дошёл до корня и корень переполнен:
1. Корень расщепляется на два узла
2. Создаётся новый корень с одним ключом (медианой)
3. Два узла становятся его детьми

**B-tree растёт в ширину и вверх, а не вниз:**
- Каждый split увеличивает ширину уровня (был один узел → стало два)
- Новый уровень появляется только при split корня (редко)
- В BST новые узлы добавляются как листья → глубина растёт неравномерно
- В B-tree все листья всегда на одной глубине

### Сложность вставки

| Метрика | Значение |
|---------|----------|
| Спуск до листа | O(log n) узлов |
| Каскадный split (худший случай) | O(log n) узлов |
| Работа на каждом уровне | O(1) — размер узла константа |
| **Итого время** | **O(log n)** |
| **Чтений с диска** | O(log n) |
| **Записей на диск** | O(log n) худший случай, обычно O(1) |

---

## Операция: Удаление

### Два случая по расположению ключа

**Случай 1: Ключ в листе**
Просто удаляем.

**Случай 2: Ключ во внутреннем узле**
Заменяем на predecessor (или successor) — он всегда в листе:
- Predecessor: идём в левое поддерево, потом всегда вправо до листа, берём максимальный ключ
- Successor: идём в правое поддерево, потом всегда влево до листа, берём минимальный ключ

После замены задача сводится к удалению из листа.

### Восстановление инварианта

После удаления узел может стать "бедным" (< t−1 ключей).

**Способ 1: Заимствование (borrowing/rotation)**

Если у соседнего узла (с тем же родителем) больше t−1 ключей:

```
До:     [...| P |...]        ← родитель
           /     \
      [бедный]  [богатый сосед]

После:  [...| Q |...]        ← P спустился, Q поднялся
           /     \
    [пополнен]  [отдал ключ]
```

1. Разделитель P из родителя спускается в бедный узел
2. Ближайший ключ соседа Q поднимается в родитель как новый разделитель

**Для внутренних узлов:** вместе с ключом передаётся указатель на ребёнка (чтобы сохранить соотношение n ключей → n+1 детей).

**Способ 2: Слияние (merge)**

Если у соседа тоже ровно t−1 ключей (минимум), заимствовать нельзя:

1. Объединяем бедный узел + разделитель из родителя + сосед
2. Получаем один узел с (t−2) + 1 + (t−1) = 2t−2 ключами (валидно)

```
До:     [...| P |...]
           /     \
      [t−2]     [t−1]    ← оба на минимуме

После:  [...]            ← P ушёл вниз
           |
    [объединённый: 2t−2 ключей]
```

**Merge для внутренних узлов:** объединяются не только ключи, но и дети обоих узлов.

```
До:        [...| P |...]
              /     \
         [K₁]       [K₂]      ← внутренние узлы
         / \        /  \
        A   B      C    D     ← их дети

После:     [...]
              |
        [K₁ | P | K₂]         ← объединённый узел
        /   |   |   \
       A    B   C    D        ← все дети сохранены
```

Инвариант "n ключей → n+1 детей" сохраняется: было 1+1=2 ключа и 2+2=4 ребёнка, стало 3 ключа и 4 ребёнка.

**Каскадный merge:** родитель отдал ключ и мог сам стать бедным — повторяем процесс выше.

**Сжатие дерева:** если merge дошёл до корня и корень стал пустым:
- Удаляем корень
- Единственный ребёнок становится новым корнем
- Высота дерева уменьшается на 1

### Сложность удаления

| Метрика | Значение |
|---------|----------|
| Поиск ключа | O(log n) |
| Поиск predecessor/successor | O(log n) |
| Каскадный merge (худший случай) | O(log n) |
| **Итого время** | **O(log n)** |
| **Чтений с диска** | O(log n) |
| **Записей на диск** | O(log n) худший случай, обычно O(1) |

|----------|-------|----------------|-----------------|
| Поиск | O(log n) | O(log n) | 0 |

## Симметрия операций

| Вставка | Удаление |
|---------|----------|
| Переполнение (> 2t−1) | Недозаполнение (< t−1) |
| Split (расщепление) | Merge (слияние) |
| Ключ поднимается в родителя | Ключ спускается из родителя |
| Дерево растёт в ширину (и вверх при split корня) | Дерево сужается (и вниз при пустом корне) |

---

## Почему B-tree эффективно для дисков

1. **Широкие узлы:** один узел = одна страница диска, используется полностью
2. **Малая глубина:** log по основанию ~100 вместо log₂
3. **Минимум I/O:** 2-4 чтения на поиск вместо 20
4. **Локальность:** ключи в узле расположены последовательно в памяти

# B+ tree: вариант для реальных баз данных

## Название и применение

**B+ tree** — модификация B-tree, используемая в большинстве реальных СУБД (PostgreSQL, MySQL, SQLite и др.).

"+" указывает на расширение базовой идеи B-tree.

---

## Ключевое отличие от B-tree

| B-tree | B+ tree |
|--------|---------|
| Данные хранятся во всех узлах | Данные хранятся только в листьях |
| Ключ существует в одном месте | Ключ-разделитель — копия ключа из листа |
| Поиск может завершиться на любом уровне | Поиск всегда доходит до листа |

```
B-tree:
            [17]              ← 17 здесь И ТОЛЬКО здесь
           /    \
      [5|13]    [22|30]

B+ tree:
            [17]              ← 17 здесь как разделитель (копия)
           /    \
      [5|13]    [17|22|30]    ← и 17 здесь с данными
```

---

## Преимущества B+ tree

### 1. Больше ключей во внутренних узлах

В B-tree внутренний узел хранит: ключ + указатель на данные + указатель на ребёнка.

В B+ tree внутренний узел хранит: ключ + указатель на ребёнка. Всё.

Результат: в ту же страницу помещается больше ключей → дерево шире → меньше уровней → меньше I/O.

### 2. Связанные листья

Листья B+ tree связаны в список:

```
            [17 | 35]
           /    |    \
          ↓     ↓     ↓
      [5|13] ↔ [17|22] ↔ [35|40|48]
```

**Односвязный vs двусвязный:** минимально достаточен односвязный список (только next) для range scan слева направо. Но большинство СУБД используют двусвязный (prev + next), потому что:
- Запросы с `ORDER BY ... DESC` требуют обхода справа налево
- Двунаправленный обход полезен для некоторых оптимизаций

Это позволяет делать **range scan** — сканирование диапазона:

Для запроса `WHERE age BETWEEN 20 AND 40`:
1. Один спуск до листа с ключом ≥ 20
2. Линейный проход по связному списку вправо
3. Остановка когда ключ превысил 40

Без связного списка пришлось бы делать отдельный поиск для каждого ключа или подниматься к родителям.

### 3. Предсказуемость

- Время поиска стабильное (всегда одинаковая глубина)
- Внутренние узлы не содержат данных → занимают меньше места → легче кэшировать в памяти

---

## Структура листа B+ tree

```
┌─────────────────────────────────────────────────────┐
│ prev | K₁,D₁ | K₂,D₂ | K₃,D₃ | ... | Kₙ,Dₙ | next │
└─────────────────────────────────────────────────────┘
   ↑                                              ↑
указатель                                    указатель
на левого                                   на правого
соседа                                        соседа
(опционально)                              (обязательно)
```

D — либо сами данные (строка таблицы), либо указатель на строку в отдельном файле.

Указатель prev опционален — минимально нужен только next для range scan слева направо.

---

## Отличия в операциях

### Вставка: split копирует, а не перемещает

В B-tree при split медиана **перемещается** в родителя.

В B+ tree при split листа медиана **копируется** в родителя, оставаясь в листе.

```
B-tree split:
До:     [10 | 20 | 30 | 40]
После:  [10] ← [20] → [30 | 40]
        20 ушёл наверх, в листьях его нет

B+ tree split:
До:     [10 | 20 | 30 | 40]
После:  [10 | 20] ← [30] → [30 | 40]
        30 скопирован наверх И остался в правом листе
```

**Выбор точки разделения:** при чётном количестве ключей можно взять "левую" или "правую" середину — зависит от реализации. Главное — соблюдать соглашение: если разделитель K, то левый узел содержит ключи < K, правый — ключи ≥ K.

При split внутренних узлов — как в обычном B-tree (медиана перемещается, а не копируется).

### Удаление: разделители можно не трогать

Если удалили ключ из листа, но он используется как разделитель — **можно оставить**.

```
            [20]              ← разделитель остался
           /    \
      [10|15]   [25|30]       ← ключа 20 в листьях нет
```

Это валидно. Поиск ключа 20:
- 20 ≤ 20, идём влево
- В листе [10|15] ключа 20 нет → "не найден"

Разделитель — просто "указатель направления", не обязан существовать в данных.

### Merge листьев: разделитель не спускается

При merge в B-tree разделитель спускается в объединённый узел.

При merge листьев в B+ tree разделитель **просто удаляется** — все данные уже есть в листьях.

```
До:        [...| 20 |...]
              /     \
         [10|15]   [25|30]    ← листья

После:     [...]              ← 20 просто удалён
              |
        [10|15|25|30]         ← данные объединены
```

При merge внутренних узлов — как в обычном B-tree (разделитель спускается).

---

## Range scan vs Table scan

**Index range scan** — сканирование листьев B+ tree (индекса). Получаем отсортированные ключи и указатели на строки.

**Table scan (full scan)** — сканирование таблицы напрямую, без индекса.

При широком диапазоне (например, 90% таблицы) query planner может решить, что table scan дешевле, чем прыгать из индекса в таблицу тысячи раз.

---

## Сводная таблица: B-tree vs B+ tree

| Характеристика | B-tree | B+ tree |
|----------------|--------|---------|
| Где хранятся данные | Во всех узлах | Только в листьях |
| Разделители | Уникальные ключи | Копии ключей из листьев |
| Связь между листьями | Нет | Связный список (обычно двусвязный) |
| Поиск завершается | На любом уровне | Всегда в листе |
| Split листа | Медиана перемещается | Медиана копируется (остаётся в листе) |
| Merge листьев | Разделитель спускается | Разделитель удаляется |
| Удаление разделителя | Обязательно | Можно не трогать |
| Range-запросы | Неэффективны | Эффективны (range scan) |
| Использование | Учебные примеры | Реальные СУБД |

# B* tree: максимальная плотность

## Название и происхождение

**B* tree** — модификация B-tree с минимальным заполнением 2/3 вместо 1/2.

Звёздочка (*) указывает на "улучшенную" версию. Описано Knuth и др., 1973.

---

## Мотивация: проблема полупустых узлов

В обычном B-tree после split получаем два узла, заполненных примерно наполовину. В худшем случае дерево может быть заполнено всего на ~50%.

Это значит:
- Половина дискового пространства под индекс может быть пустой
- Дерево выше, чем могло бы быть при более плотной упаковке

---

## Главная идея

Минимальное заполнение узла — **2/3** вместо **1/2**.

Чтобы поддерживать этот инвариант, изменяются алгоритмы вставки и удаления.

---

## Вставка: перераспределение перед split

**Шаг 1:** Узел переполнен. Смотрим на соседа.

**Шаг 2:** Если у соседа есть место — **перераспределяем** ключи между двумя узлами через родителя:

```
До:        [...| 30 |...]
              /     \
    [10|20|25|28]   [35|40]    ← левый переполнен, у правого есть место

После:     [...| 28 |...]
              /     \
      [10|20|25]   [30|35|40]  ← перераспределили через родителя
```

**Шаг 3:** Если у соседа тоже почти полный — split **двух узлов в три**:

```
До:        [...| 30 |...]
              /     \
    [10|20|25|28]  [35|38|40|45]   ← оба переполнены

После:     [...| 25 | 38 |...]
              /    |     \
        [10|20] [28|30|35] [40|45]  ← три узла, каждый на 2/3
```

---

## Удаление: merge трёх в два

**Шаг 1:** Узел стал слишком пустым. Смотрим на соседа.

**Шаг 2:** Если у соседа есть лишние ключи — перераспределяем (как в обычном B-tree).

**Шаг 3:** Если соседи тоже на минимуме — merge **трёх узлов в два**:

```
До:        [...| 20 | 40 |...]
              /    |     \
          [10]  [25|30]  [45]    ← все на минимуме

После:     [...| 30 |...]
              /      \
        [10|20|25]  [40|45]      ← два узла на 2/3
```

---

## Сравнение B-tree, B+ tree, B* tree

| Характеристика | B-tree | B+ tree | B* tree |
|----------------|--------|---------|---------|
| Минимальное заполнение | 1/2 | 1/2 | 2/3 |
| Данные | Во всех узлах | Только в листьях | Зависит от варианта |
| Связь листьев | Нет | Связный список (обычно двусвязный) | Зависит от варианта |
| Split | 1 → 2 узла | 1 → 2 узла | 2 → 3 узла |
| Merge | 2 → 1 узел | 2 → 1 узел | 3 → 2 узла |
| Перераспределение при вставке | Нет | Нет | Да (перед split) |
| Экономия места | ~50% заполнение | ~50% заполнение | ~67% заполнение |
| Сложность реализации | Базовая | Средняя | Высокая |
| Использование | Учебные примеры | СУБД (PostgreSQL, MySQL) | Файловые системы (NTFS, HFS+) |

---

## Когда использовать B* tree

**Преимущества:**
- Экономия ~17% дискового пространства
- Дерево чуть ниже (меньше I/O)

**Цена:**
- Сложнее реализация (координация трёх узлов)
- Больше работы при split/merge (читаем/пишем три узла вместо двух)

**Вывод:** B* tree выгодно, когда дисковое пространство критично или когда экономия высоты дерева важнее стоимости более сложных операций.

# B-tree в PostgreSQL: практическая реализация

## История и версии

PostgreSQL называет свой индекс "B-tree", но технически это **B+tree с модификациями**, основанный на статье **Lehman & Yao (1981)** — "Efficient Locking for Concurrent Operations on B-Trees".

| Версия PostgreSQL | Изменения в B-tree |
|-------------------|-------------------|
| 7.0 (2000) | Базовая реализация B-tree |
| 10 (2017) | Улучшения производительности |
| 11 (2018) | Covering indexes (INCLUDE) |
| 12 (2019) | REINDEX CONCURRENTLY |
| 13 (2020) | Дедупликация записей, индексы со смешанным порядком |

---

## Физическая структура

PostgreSQL хранит всё в **страницах по 8 КБ** (по умолчанию). Индекс — это файл, состоящий из страниц.

```
┌─────────────────────────────────────────────────────────────┐
│  Файл индекса                                               │
├─────────────────────────────────────────────────────────────┤
│  Page 0: Meta page (служебная информация)                   │
│  Page 1: Root (корень, может быть и листом для маленьких)   │
│  Page 2: Internal или Leaf                                  │
│  Page 3: Internal или Leaf                                  │
│  ...                                                        │
└─────────────────────────────────────────────────────────────┘
```

---

## Структура страницы B-tree

```
┌────────────────────────────────────────────────────────────────┐
│  Page Header (24 байта)                                        │
│  ├── pd_lsn: LSN последнего изменения (для WAL)               │
│  ├── pd_flags: флаги страницы                                  │
│  ├── pd_lower: указатель на конец массива item pointers        │
│  ├── pd_upper: указатель на начало свободного места            │
│  └── pd_special: указатель на special space                    │
├────────────────────────────────────────────────────────────────┤
│  Item Pointers (массив указателей на tuples внутри страницы)   │
│  [ItemId 1][ItemId 2][ItemId 3]...                             │
├────────────────────────────────────────────────────────────────┤
│  Free Space (свободное место, растёт навстречу)                │
├────────────────────────────────────────────────────────────────┤
│  Index Tuples (сами данные, растут снизу вверх)                │
│  [...tuple 3...][...tuple 2...][...tuple 1...]                 │
├────────────────────────────────────────────────────────────────┤
│  Special Space (специфично для B-tree)                         │
│  ├── btpo_prev: указатель на левого соседа                     │
│  ├── btpo_next: указатель на правого соседа (right-link!)      │
│  ├── btpo_level: уровень (0 = лист)                            │
│  └── btpo_flags: leaf? root? deleted?                          │
└────────────────────────────────────────────────────────────────┘
```

---

## Tuple и TID

### Tuple (кортеж)

**Tuple** — термин из реляционной алгебры и теории множеств.

**Буквальный смысл:** упорядоченный набор значений фиксированной длины.

В математике: `(a, b, c)` — это 3-tuple (тройка).

**В контексте БД:** tuple = одна строка таблицы = набор значений по всем колонкам.

```
Таблица employees:
┌────┬─────────┬────────┐
│ id │  name   │ salary │
├────┼─────────┼────────┤
│ 1  │ 'Alice' │ 50000  │  ← это один tuple: (1, 'Alice', 50000)
│ 2  │ 'Bob'   │ 60000  │  ← это другой tuple: (2, 'Bob', 60000)
└────┴─────────┴────────┘
```

### TID — Tuple Identifier

**TID** — физический адрес tuple в heap.

**Структура:** `(block_number, offset_within_block)`

```
TID = (847, 3)
        │    │
        │    └── третий tuple на этой странице (нумерация с 1)
        │
        └── страница номер 847 в файле heap
```

---

## Index Tuple — что хранится в узле

Для **листовой страницы**:

```
┌─────────────────────────────────────────┐
│  Index Tuple (лист)                     │
├─────────────────────────────────────────┤
│  t_tid: (block_number, offset)          │  ← указатель на строку в heap
│  t_info: размер и флаги                 │
│  key_data: значение ключа               │  ← например, salary=50000
└─────────────────────────────────────────┘
```

Для **внутренней страницы**:

```
┌─────────────────────────────────────────┐
│  Index Tuple (внутренний)               │
├─────────────────────────────────────────┤
│  t_tid: (child_block, offset)           │  ← указатель на дочернюю страницу
│  t_info: размер и флаги                 │
│  key_data: разделитель (pivot)          │  ← граница для навигации
└─────────────────────────────────────────┘
```

---

## High Key и Right-Link (Lehman & Yao)

Каждая страница (кроме самой правой на уровне) содержит **high key** — максимальное значение, которое может быть на этой странице.

```
Страница A                          Страница B
┌─────────────────────┐            ┌─────────────────────┐
│ high_key = 50       │───────────→│ high_key = 100      │
│ keys: 10, 20, 30, 40│            │ keys: 50, 60, 70, 80│
│ right_link ─────────────────────→│                     │
└─────────────────────┘            └─────────────────────┘
```

**Зачем это нужно?**

При конкурентной вставке страница может разделиться (split) в момент, когда другой процесс её читает. High key и right-link позволяют читателю понять: "о, страница разделилась, мне нужно пойти направо".

Это позволяет избежать блокировки всего дерева при вставках — блокируем только те страницы, которые непосредственно модифицируем.

---

## Зачем двусвязный список листьев

PostgreSQL использует **двусвязный список** (btpo_prev + btpo_next), а не односвязный.

**Причина: ORDER BY ... DESC**

```sql
SELECT * FROM employees
ORDER BY salary DESC
LIMIT 10;
```

Что происходит:
- Нужны 10 самых высоких зарплат
- Спускаемся по дереву до самого правого листа
- Идём **назад** по листьям через btpo_prev, собирая значения

В плане выполнения это отображается как:

```
Index Scan Backward using idx_salary on employees
```

---

## Heap и Index — две отдельные структуры

**Критически важно:** в PostgreSQL данные таблицы (heap) и индекс — это **разные файлы**.

```
┌─────────────────────────────────────────────────────────────────┐
│  HEAP (куча) — сама таблица                                     │
│  Данные лежат В ПОРЯДКЕ ВСТАВКИ, не отсортированы ни по чему   │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  INDEX — отдельная структура (B+tree)                          │
│  Ключи отсортированы, каждый ключ содержит указатель (TID)     │
│  на физическое расположение строки в heap                       │
└─────────────────────────────────────────────────────────────────┘
```

**Следствие:** после поиска по индексу нужно идти в heap за данными — это random I/O.

---

## Три типа сканирования индекса

### Index Scan

Классическое использование индекса:

```
1. Спуск по B-tree до нужного листа
2. Для каждого найденного ключа — поход в heap по TID
3. Возврат данных
```

**Проблема:** random I/O при походах в heap.

**Когда используется:** малая селективность (< 1-2% строк).

### Bitmap Index Scan

Двухфазное сканирование для уменьшения random I/O:

**Фаза 1:** Читаем индекс, строим bitmap страниц heap

```
Bitmap страниц:
┌─────────────────────────────────────────────────────────┐
│ Page:  0   1   2   ...  123  ...  291  ...  532  ...  847 │
│ Bit:   0   0   0   ...   1   ...   1   ...   1   ...   1  │
└─────────────────────────────────────────────────────────┘
```

**Фаза 2:** Читаем страницы heap в порядке номеров (ближе к sequential I/O)

**Когда используется:** средняя селективность (2-15% строк).

**Бонус:** можно комбинировать несколько индексов через BitmapAnd / BitmapOr.

```sql
SELECT * FROM employees
WHERE salary > 50000 AND department_id = 5;

-- План:
Bitmap Heap Scan
  →  BitmapAnd
        →  Bitmap Index Scan on idx_salary
        →  Bitmap Index Scan on idx_department
```

### Index Only Scan

Если все нужные колонки есть в индексе — не ходим в heap вообще.

```sql
CREATE INDEX idx_salary ON employees(salary);

-- Этот запрос может использовать Index Only Scan:
SELECT salary FROM employees WHERE salary > 50000;

-- А этот — нет (name не в индексе):
SELECT name, salary FROM employees WHERE salary > 50000;
```

**Ограничение:** работает только если страница heap помечена как "all-visible" в Visibility Map (связано с MVCC).

### Covering Index (INCLUDE) — PostgreSQL 11+

Решение проблемы Index Only Scan:

```sql
CREATE INDEX idx_salary_covering
ON employees(salary)
INCLUDE (name, department);
```

Теперь в листьях индекса хранится:
```
[salary=50000, TID, name="Carol", department="Sales"]
```

Запрос может получить всё из индекса без heap.

**Цена:** индекс больше по размеру.

---

## Операции модификации в PostgreSQL

### INSERT

PostgreSQL использует split по Lehman & Yao:

1. Спуск до целевого листа
2. Вставка ключа
3. Если переполнение — split:
   - Создаём новую страницу
   - Устанавливаем high_key и right_link
   - Добавляем разделитель в родителя (отдельный шаг)

Между шагами дерево "временно неконсистентно", но right-link позволяет читателям корректно работать.

### DELETE — НЕ как в учебнике!

**Учебник:** при удалении делаем borrowing или merge.

**PostgreSQL:** нет, не делаем.

```
До удаления:
Лист: [10, 20, 30, 40, 50]

Удаляем 30:

После удаления:
Лист: [10, 20, □, 40, 50]
              ↑
        dead tuple (помечен как удалённый, но физически на месте)
```

**Почему PostgreSQL не делает merge:**

1. **MVCC:** удалённая запись может быть ещё видна другим транзакциям
2. **Сложность:** merge требует много блокировок
3. **Бесполезность:** освободившееся место часто быстро занимается новыми записями

### UPDATE = DELETE + INSERT

**Важнейшая особенность PostgreSQL!**

При UPDATE PostgreSQL не изменяет строку in-place. Он создаёт новую версию:

```
Heap до UPDATE:
  Tuple 1: (id=1, status='pending')
           xmin=500, xmax=∞

Heap после UPDATE:
  Tuple 1: (id=1, status='pending')     ← помечена как мёртвая
           xmin=500, xmax=600

  Tuple 2: (id=1, status='processing')  ← новая версия
           xmin=600, xmax=∞
```

**Следствие для индексов:** каждый UPDATE создаёт dead tuple в индексе.

**Почему так:** MVCC требует сохранения старых версий для других транзакций.

## HOT — Heap-Only Tuples (PostgreSQL 8.3+)

### Название

**HOT (Heap-Only Tuples)** — оптимизация, при которой новая версия строки создаётся без обновления индексов.

**Почему "Heap-Only":** новый tuple существует только в heap, индексы продолжают указывать на старый tuple.

### Условия для HOT

1. Изменяемые колонки **не входят ни в один индекс**
2. Новая версия tuple **помещается на ту же страницу** heap

### Как работает

```
Heap до UPDATE:
┌─────────────────────────────────────────────────────────────┐
│ Page 100:                                                   │
│   Tuple 1: (id=1, price=100, description='old')            │
│            TID=(100,1)                                      │
└─────────────────────────────────────────────────────────────┘

Index по price:
[price=100, TID=(100,1)]

Heap после HOT UPDATE (изменили только description):
┌─────────────────────────────────────────────────────────────┐
│ Page 100:                                                   │
│   Tuple 1: (id=1, price=100, description='old')            │
│            DEAD, указатель → Tuple 2                        │
│                                                             │
│   Tuple 2: (id=1, price=100, description='new')            │
│            TID=(100,2), LIVE                                │
└─────────────────────────────────────────────────────────────┘

Index по price:
[price=100, TID=(100,1)]  ← НЕ ИЗМЕНИЛСЯ!
```

При поиске: индекс указывает на Tuple 1, который перенаправляет на Tuple 2.

### Мониторинг HOT

```sql
SELECT
    relname,
    n_tup_upd as total_updates,
    n_tup_hot_upd as hot_updates,
    round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) as hot_percent
FROM pg_stat_user_tables
WHERE relname = 'your_table';
```

Хороший показатель: **hot_percent > 90%**.

---

## Bloat — раздувание индекса

### Что это

После множества DELETE/UPDATE индекс содержит много dead tuples и полупустых страниц.

```
После множества DELETE:
┌─────────┐
│  Root   │
└────┬────┘
     ├────────────┬────────────┐
     ↓            ↓            ↓
┌─────────┐ ┌─────────┐ ┌─────────┐
│ Leaf 1  │↔│ Leaf 2  │↔│ Leaf 3  │  все ~10-20% заполнены
│  BLOAT! │ │  BLOAT! │ │  BLOAT! │
└─────────┘ └─────────┘ └─────────┘
```

### Почему это плохо

- Больше страниц читать при сканировании
- Больше места на диске
- Вытеснение полезных данных из кэша

### VACUUM

**VACUUM** — фоновый процесс, чистящий dead tuples.

```
До VACUUM:
Лист: [10, 20, DEAD, DEAD, 50, DEAD, 70]

После VACUUM:
Лист: [10, 20, 50, 70, □, □, □]
                      ↑ свободное место
```

**Важно:** VACUUM **не уменьшает размер файла индекса**. Он освобождает место внутри страниц для повторного использования.

### Лечение bloat

**REINDEX:**
```sql
REINDEX INDEX idx_salary;  -- блокирует таблицу
```

**REINDEX CONCURRENTLY (PostgreSQL 12+):**
```sql
REINDEX INDEX CONCURRENTLY idx_salary;  -- не блокирует
```

## Operator Classes

### Название и суть

**Operator Class (операторный класс)** — набор операторов и функций, которые говорят индексу, как работать с конкретным типом данных.

### Что нужно B-tree

B-tree требует **пять операторов сравнения**:

```
Стратегия 1: <   (меньше)
Стратегия 2: <=  (меньше или равно)
Стратегия 3: =   (равно)
Стратегия 4: >=  (больше или равно)
Стратегия 5: >   (больше)
```

И **support function** — функцию сравнения:

```
compare(a, b) → integer
  Возвращает:
    -1 если a < b
     0 если a = b
    +1 если a > b
```

### Примеры operator classes

```sql
SELECT opcname, opcintype::regtype
FROM pg_opclass
WHERE opcmethod = (SELECT oid FROM pg_am WHERE amname = 'btree')
ORDER BY opcintype::regtype::text
LIMIT 10;

-- Результат:
-- int4_ops      │ integer
-- int8_ops      │ bigint
-- text_ops      │ text
-- date_ops      │ date
-- uuid_ops      │ uuid
```

---

## Collation

### Название и суть

**Collation (правила сортировки)** — набор правил, определяющих порядок сортировки строк.

От латинского "collatio" — сравнение, сопоставление.

### Влияние на индекс

Индекс строится с конкретной collation:

```sql
-- Посмотреть collation базы
SHOW lc_collate;

-- Разные индексы с разной collation
CREATE INDEX idx_name_en ON users(name COLLATE "en_US");
CREATE INDEX idx_name_c ON users(name COLLATE "C");
```

### Collation "C" vs локализованная

**Collation "C"** — побайтовое сравнение:
- Предсказуемый порядок (по ASCII/UTF-8 кодам)
- 'Z' < 'a' (заглавные перед строчными)
- Быстрее
- Работает для LIKE 'prefix%'

**Локализованная (например, "en_US.UTF-8")**:
- Регистронезависимая сортировка
- 'a' < 'B' < 'c'
- LIKE 'prefix%' **не использует индекс**

### text_pattern_ops для LIKE

```sql
-- Обычный индекс — LIKE не работает с en_US
CREATE INDEX idx_email ON users(email);

-- Специальный operator class для паттернов
CREATE INDEX idx_email_pattern ON users(email text_pattern_ops);

-- Теперь работает:
SELECT * FROM users WHERE email LIKE 'john%';
```

## Составные индексы

### Структура

Составной индекс — один B-tree с многокомпонентным ключом.

```sql
CREATE INDEX idx_user_created ON events(user_id, created_at);
```

Сортировка: сначала по user_id, при равенстве — по created_at.

```
Отсортированный порядок:
(1, 2024-01-05)
(1, 2024-01-15)
(1, 2024-01-25)
(2, 2024-01-03)
(2, 2024-01-10)
```

### Leftmost Prefix Rule

Составной индекс `(A, B, C)` эффективен для:

```
WHERE A = ?                     ✓ использует индекс
WHERE A = ? AND B = ?           ✓ использует индекс
WHERE A = ? AND B = ? AND C = ? ✓ использует индекс
WHERE A = ? AND C = ?           △ только по A, C фильтруется
WHERE B = ?                     ✗ индекс бесполезен
WHERE C = ?                     ✗ индекс бесполезен
```

**Аналогия:** телефонный справочник отсортирован по (фамилия, имя). Можно найти всех Ивановых, всех Ивановых Иванов, но нельзя эффективно найти всех Иванов.

### ORDER BY и составные индексы

Индекс `(A, B, C)` помогает с ORDER BY если:

```
ORDER BY A                    ✓
ORDER BY A, B                 ✓
ORDER BY A, B, C              ✓
ORDER BY A DESC, B DESC       ✓ (читаем индекс назад)

ORDER BY B                    ✗
ORDER BY A, C                 ✗ (пропущен B)
ORDER BY A ASC, B DESC        ✗ (смешанные направления)*

*PostgreSQL 13+ поддерживает:
CREATE INDEX idx ON t(A ASC, B DESC);
```

## Уникальные индексы

### UNIQUE INDEX vs UNIQUE CONSTRAINT

| Аспект | UNIQUE CONSTRAINT | UNIQUE INDEX |
|--------|-------------------|--------------|
| Где хранится | pg_constraint + pg_index | только pg_index |
| FOREIGN KEY | Да | Нет |
| DEFERRABLE | Да | Нет |
| Partial (WHERE) | Нет | Да |
| INCLUDE колонки | Нет* | Да |

### DEFERRABLE

**Deferrable** — возможность отложить проверку до конца транзакции.

```sql
ALTER TABLE departments
ADD CONSTRAINT fk_head
FOREIGN KEY (head_employee_id) REFERENCES employees(id)
DEFERRABLE INITIALLY DEFERRED;

BEGIN;
INSERT INTO departments (id, head_employee_id) VALUES (1, 1);
INSERT INTO employees (id, department_id) VALUES (1, 1);
COMMIT;  -- Проверка здесь
```

### Partial Unique Index

**Partial Index** — индекс только для части строк.

```sql
-- Уникальность email только для активных пользователей
CREATE UNIQUE INDEX idx_email_active
ON users(email)
WHERE deleted_at IS NULL;
```

Позволяет:
- Реализовать soft delete с повторным использованием email
- Экономить место (индексируем только нужные строки)

# GIN — Generalized Inverted Index

## Inverted Index — ключевая концепция

### Название и происхождение

**Inverted Index (инвертированный индекс)** — структура данных, которая "переворачивает" отношение между документом и его содержимым.

**Почему "inverted" (перевёрнутый)?**

Обычный (forward) индекс отвечает на вопрос: "Что содержит документ X?"

```
Forward index:
Документ 1 → [ruby, rails, postgresql]
Документ 2 → [python, django, postgresql]
Документ 3 → [ruby, sinatra]
```

Inverted index **переворачивает** вопрос: "В каких документах встречается элемент Y?"

```
Inverted index:
ruby       → [Документ 1, Документ 3]
rails      → [Документ 1]
postgresql → [Документ 1, Документ 2]
python     → [Документ 2]
django     → [Документ 2]
sinatra    → [Документ 3]
```

**Аналогия:** предметный указатель в конце книги — это inverted index. Вместо "страница 42 содержит слова X, Y, Z" он говорит "слово X встречается на страницах 42, 87, 156".

### Почему это эффективно

Запрос: "Найти все документы со словом 'ruby'"

**Без inverted index:** читаем каждый документ, проверяем содержит ли ruby. O(n) документов.

**С inverted index:** смотрим в индекс по ключу 'ruby', сразу получаем список [Документ 1, Документ 3]. O(1) для поиска ключа + O(k) для чтения результатов, где k — количество совпадений.

## GIN — Generalized Inverted Index

### Название

**GIN (Generalized Inverted Index)** — обобщённый инвертированный индекс.

**Почему "Generalized" (обобщённый)?** Потому что работает не только с текстом, а с любыми типами данных, которые можно разбить на элементы: массивы, JSONB, полнотекстовые векторы, и другие.

Появился в **PostgreSQL 8.2 (2006)**.

### Что индексирует GIN

GIN индексирует **составные значения**, разбивая их на **элементы**:

| Тип данных | Составное значение | Элементы |
|------------|-------------------|----------|
| integer[] | {1, 2, 3} | 1, 2, 3 |
| text[] | {ruby, rails} | ruby, rails |
| jsonb | {"a": 1, "tags": ["x", "y"]} | a, 1, tags, x, y |
| tsvector | 'cat' 'dog' 'fish' | cat, dog, fish |

### Почему B-tree не подходит

B-tree требует операций сравнения: меньше, равно, больше.

Для массива `{ruby, rails, postgresql}` нельзя сказать, "меньше" он или "больше" массива `{python}`. И главное — нельзя эффективно ответить на вопрос "содержит ли массив элемент X?", потому что элемент может быть на любой позиции.

---

## Физическая структура GIN

GIN состоит из двух основных частей:

### 1. Entry Tree (дерево ключей)

B-tree, где ключи — это **отдельные элементы** (не составные значения).

```
         ┌─────────────────┐
         │   Entry Tree    │
         │    (B-tree)     │
         └────────┬────────┘
                  │
    ┌─────────────┼─────────────┐
    ↓             ↓             ↓
 [django]     [python]      [ruby]
    │             │             │
    ↓             ↓             ↓
 Posting      Posting       Posting
  List         List          List
```

### 2. Posting Lists (списки вхождений)

Для каждого ключа — отсортированный список TID (указателей на строки), где этот ключ встречается.

```
ruby → [TID(100,1), TID(200,3), TID(350,2)]
         ↓            ↓            ↓
      строка 1     строка 2     строка 3
      в heap       в heap       в heap
```

**Почему отсортированный?** Для эффективного пересечения при AND-запросах. Merge двух отсортированных списков — O(n + m), а не O(n × m).

### 3. Posting Tree (для частых ключей)

Если posting list слишком длинный (ключ встречается в тысячах строк), PostgreSQL превращает его в отдельное **B-tree по TID** — Posting Tree.

```
Редкий ключ "sinatra":
sinatra → [TID1, TID2, TID3]  (простой список, inline)

Частый ключ "the":
the → ┌──────────────────┐
      │   Posting Tree   │
      │  (B-tree по TID) │
      └──────────────────┘
      Содержит миллионы TID
```

**Что является ключом в Posting Tree?**

Сами TID. Они сравниваются лексикографически: сначала по block_number, при равенстве — по offset.

```
(100, 1) < (100, 2) < (200, 1) < (200, 5)
```

## Пример: индексирование массива

```sql
CREATE TABLE posts (
    id serial PRIMARY KEY,
    title text,
    tags text[]
);

INSERT INTO posts (title, tags) VALUES
('Ruby Basics', ARRAY['ruby', 'tutorial']),
('PostgreSQL GIN', ARRAY['postgresql', 'indexing', 'tutorial']),
('Rails API', ARRAY['ruby', 'rails', 'api']);

CREATE INDEX idx_tags ON posts USING gin(tags);
```

Что построит PostgreSQL:

```
Entry Tree (B-tree по элементам массивов):
┌─────────────────────────────────────────────────┐
│  api → indexing → postgresql → rails → ruby → tutorial │
└─────────────────────────────────────────────────┘

Posting Lists:
api        → [TID строки 3]
indexing   → [TID строки 2]
postgresql → [TID строки 2]
rails      → [TID строки 3]
ruby       → [TID строки 1, TID строки 3]
tutorial   → [TID строки 1, TID строки 2]
```

## Поиск в GIN

### Запрос: WHERE tags @> ARRAY['ruby']

"Найти посты, где tags содержит 'ruby'"

```
1. Ищем 'ruby' в Entry Tree (B-tree поиск) — O(log E)
2. Получаем posting list: [TID строки 1, TID строки 3]
3. Идём в heap за строками
```

### Запрос: WHERE tags @> ARRAY['ruby', 'tutorial']

"Найти посты, где tags содержит И 'ruby', И 'tutorial'"

```
1. Ищем 'ruby' в Entry Tree → [TID1, TID3]
2. Ищем 'tutorial' в Entry Tree → [TID1, TID2]
3. Пересечение (AND): [TID1, TID3] ∩ [TID1, TID2] = [TID1]
4. Идём в heap за строкой 1
```

### Запрос: WHERE tags && ARRAY['ruby', 'rails']

"Найти посты, где tags содержит 'ruby' ИЛИ 'rails' (хотя бы один)"

```
1. Ищем 'ruby' в Entry Tree → [TID1, TID3]
2. Ищем 'rails' в Entry Tree → [TID3]
3. Объединение (OR): [TID1, TID3] ∪ [TID3] = [TID1, TID3]
4. Идём в heap за строками 1 и 3
```

## Операторы для GIN

### Массивы (integer[], text[], и т.д.)

| Оператор | Значение | Пример |
|----------|----------|--------|
| `@>` | Содержит все элементы | `tags @> ARRAY['ruby']` |
| `<@` | Содержится в | `tags <@ ARRAY['ruby', 'rails', 'api']` |
| `&&` | Пересекается (есть общие) | `tags && ARRAY['ruby', 'python']` |
| `=` | Равны | `tags = ARRAY['ruby', 'rails']` |

### JSONB

| Оператор | Значение | Пример |
|----------|----------|--------|
| `@>` | Содержит JSON | `data @> '{"type": "post"}'` |
| `?` | Содержит ключ | `data ? 'email'` |
| `?&` | Содержит все ключи | `data ?& array['email', 'name']` |
| `?\|` | Содержит любой ключ | `data ?\| array['email', 'phone']` |

---

## JSONB: jsonb_ops vs jsonb_path_ops

PostgreSQL предлагает два operator class для JSONB:

### jsonb_ops (по умолчанию)

```sql
CREATE INDEX idx_data ON products USING gin(data);
-- эквивалентно:
CREATE INDEX idx_data ON products USING gin(data jsonb_ops);
```

**Что индексирует:** каждый ключ и каждое значение отдельно.

**Поддерживает:** `@>`, `?`, `?&`, `?\|`, `@?`, `@@`

### jsonb_path_ops

```sql
CREATE INDEX idx_data ON products USING gin(data jsonb_path_ops);
```

**Что индексирует:** пути от корня до значения (хеши путей).

**Поддерживает:** только `@>`, `@?`, `@@`

### Сравнение

| Аспект | jsonb_ops | jsonb_path_ops |
|--------|-----------|----------------|
| Размер индекса | Больше | Меньше (~30%) |
| Оператор `?` (наличие ключа) | Да | Нет |
| Оператор `@>` (containment) | Да | Да, быстрее |
| Когда использовать | Нужны `?`, `?&`, `?\|` | Только `@>` запросы |

## Полнотекстовый поиск: tsvector и tsquery

### Проблема

```sql
SELECT * FROM articles WHERE body LIKE '%database%';
```

Проблемы:
- Full table scan (LIKE с `%` в начале не использует B-tree)
- Не находит "databases", "Database", "DATABASE"
- Не понимает словоформы: "running" vs "run"

### Решение: tsvector и tsquery

**tsvector (text search vector)** — представление текста в виде отсортированного списка **лексем** (нормализованных слов).

**Лексема (lexeme)** — нормализованная форма слова: без окончаний, в нижнем регистре.

```sql
SELECT to_tsvector('english', 'The quick brown foxes are running fast');

-- Результат:
'brown':3 'fast':7 'fox':4 'quick':2 'run':6
```

Что произошло:
- "The", "are" — удалены (стоп-слова)
- "foxes" → "fox" (стемминг: отсечение окончания)
- "running" → "run" (стемминг)
- Числа — позиции слов в оригинале

**tsquery (text search query)** — запрос для поиска по tsvector.

```sql
SELECT to_tsquery('english', 'running & fox');

-- Результат:
'run' & 'fox'
```

### Оператор @@

```sql
SELECT * FROM articles
WHERE to_tsvector('english', body) @@ to_tsquery('english', 'database');
```

Оператор `@@` — "tsvector соответствует tsquery".

### GIN индекс для полнотекстового поиска

**Способ 1: индекс на выражение**

```sql
CREATE INDEX idx_body_fts ON articles
USING gin(to_tsvector('english', body));

-- Запрос должен точно соответствовать выражению:
SELECT * FROM articles
WHERE to_tsvector('english', body) @@ to_tsquery('english', 'database');
```

**Способ 2: отдельная колонка tsvector (рекомендуется)**

```sql
ALTER TABLE articles ADD COLUMN body_tsv tsvector
GENERATED ALWAYS AS (to_tsvector('english', body)) STORED;

CREATE INDEX idx_body_tsv ON articles USING gin(body_tsv);

-- Запрос проще:
SELECT * FROM articles
WHERE body_tsv @@ to_tsquery('english', 'database');
```

## Pending List (Fast Update)

### Проблема записи в GIN

INSERT одной строки с 200 лексемами требует 200 модификаций индекса — много random I/O.

### Решение: отложенная вставка

**Pending List (список ожидания)** — временное хранилище для новых записей.

```
INSERT статьи с лексемами [postgresql, gin, index]

С pending list:
→ Записываем всё в конец pending list (1 sequential write)
→ Готово!

┌─────────────────────────────────────────────────────────────┐
│  Pending List (несортированный, append-only)               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ (postgresql, TID1) (gin, TID1) (index, TID1) ...    │   │
│  │ (database, TID2) (query, TID2) ...                  │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  Entry Tree + Posting Lists (основная структура)           │
│  (обновляется позже, batch-ом)                             │
└─────────────────────────────────────────────────────────────┘
```

### Когда pending list сливается

1. При переполнении: `gin_pending_list_limit` (по умолчанию 4MB)
2. При `VACUUM` таблицы
3. Вручную: `SELECT gin_clean_pending_list('idx_name')`

### Влияние на поиск

При поиске PostgreSQL проверяет **обе структуры**:

```
1. Ищем в Entry Tree → получаем posting list
2. Сканируем весь Pending List
3. Объединяем результаты
```

**Компромисс:** INSERT быстрее, SELECT медленнее.

### Отключение Fast Update

```sql
CREATE INDEX idx_body_tsv ON articles USING gin(body_tsv)
WITH (fastupdate = off);
```

Теперь INSERT сразу модифицирует основную структуру.

## Составные GIN индексы

GIN поддерживает составные индексы:

```sql
CREATE INDEX idx_tags_attrs ON products USING gin(tags, attributes);
```

**Важное отличие от B-tree:** нет "leftmost prefix rule". Каждая колонка индексируется независимо.

```sql
-- Все три запроса используют idx_tags_attrs:
WHERE tags @> ARRAY['electronics']              -- ✓
WHERE attributes @> '{"color": "black"}'        -- ✓
WHERE tags @> ARRAY['phone'] AND attributes ? 'storage'  -- ✓
```

GIN хранит элементы из всех колонок в одном Entry Tree, помечая, из какой колонки каждый элемент.

## Сложность операций GIN

| Операция | Сложность | Примечание |
|----------|-----------|------------|
| Поиск одного ключа | O(log E + P) | E = уникальных ключей, P = размер posting list |
| Поиск с AND | O(log E × k + merge) | merge = O(P1 + P2 + ...) |
| Поиск с OR | O(log E × k + union) | union = O(P1 + P2 + ...) |
| INSERT (fastupdate=on) | O(1) amortized | Append в pending list |
| INSERT (fastupdate=off) | O(k × log E) | k = элементов в значении |

|--------|---------------|

## Терминология GIN

| Термин | Значение |
|--------|----------|
| Inverted Index | Индекс "элемент → список документов" |
| Entry Tree | B-tree по элементам (ключам) |
| Posting List | Список TID для одного ключа |
| Posting Tree | B-tree по TID для частого ключа |
| Pending List | Буфер для отложенной вставки |
| Fast Update | Режим с pending list (по умолчанию включён) |
| tsvector | Нормализованное представление текста для поиска |
| tsquery | Запрос для полнотекстового поиска |
| Лексема (lexeme) | Нормализованная форма слова |
| jsonb_ops | Operator class для JSONB, все операторы |
| jsonb_path_ops | Operator class для JSONB, только @>, компактнее |
