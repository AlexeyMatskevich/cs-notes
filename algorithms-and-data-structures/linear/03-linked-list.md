# Связный список

**Предпосылки:** [массив](01-array.md) (непрерывность, кэш-локальность), [динамический массив](02-dynamic-array.md) (проблема O(n) вставки).

Хотим вставлять и удалять элементы в произвольных местах за O(1), не сдвигая остальные.

## ADT: Sequence

| Операция | Сигнатура | Сложность |
|----------|-----------|-----------|
| Вставить в позицию | `insertAt(i, value)` | O(1)* |
| Удалить из позиции | `removeAt(i) → value` | O(1)* |
| Получить элемент | `get(i) → value` | O(n) |

`*` — если уже есть указатель на место вставки

**Компромисс:** теряем O(1) доступ по индексу в обмен на O(1) вставку.

## Реализация: Связный список (Linked List)

**Этимология:** "Linked List" — буквально "связанный список". Элементы связаны указателями, образуя цепочку.

**Образ:** вагоны поезда. Каждый вагон соединён со следующим сцепкой (указателем). Чтобы добраться до вагона 500, нужно пройти через все предыдущие. Но отцепить вагон из середины — быстро, если ты уже на месте.

**Определение:** структура данных из узлов, где каждый узел содержит данные и указатель(и) на другие узлы, образуя последовательность.

В отличие от массива, элементы не обязаны лежать в памяти подряд — они связаны указателями. Из-за этого формулы адреса по индексу нет: чтобы дойти до элемента, нужно пройти по цепочке от начала.

### Варианты

**Односвязный (Singly Linked List):**

```
head → [A|•] → [B|•] → [C|•] → nil
```

Каждый узел знает только следующий. Движение только вперёд.

**Двусвязный (Doubly Linked List):**

```
nil ← [•|A|•] ⇄ [•|B|•] ⇄ [•|C|•] → nil
       ↑                       ↑
     head                    tail
```

Каждый узел знает и предыдущий, и следующий. Движение в обе стороны.

**Кольцевой (Circular):** последний указывает на первый.

### Структура узла

**Односвязный:**

```ruby
class Node
  attr_accessor :data, :next
end
```

**Двусвязный:**

```ruby
class Node
  attr_accessor :data, :prev, :next
end
```

### Ключевое различие: удаление узла

**Двусвязный:** O(1) — читаем `prev`, обновляем соседей.

**Односвязный:** O(n) — нужно найти предыдущий узел, а он неизвестен.

Это главная причина существования двусвязного списка: когда нужно удалять из середины, имея только указатель на узел. Полная реализация операций двусвязного списка (`remove_node`, `add_to_head`) показана в контексте [LRU-кэша](06-lru-cache.md), где эти операции составляют ядро структуры.

### Операции и сложность

| Операция | Односвязный | Двусвязный |
|----------|-------------|------------|
| Доступ по индексу | O(n) | O(n) |
| Вставка в начало | O(1) | O(1) |
| Вставка в конец (с tail) | O(1) | O(1) |
| Вставка после известного узла | O(1) | O(1) |
| Удаление из начала | O(1) | O(1) |
| Удаление из конца | O(n) | O(1) |
| Удаление известного узла | O(n)* | O(1) |

`*` — нужен предыдущий узел

### Накладные расходы памяти

**Односвязный:** минимум +1 указатель (`next`) на узел (обычно 8 байт на 64-bit системе) + возможный padding из-за выравнивания.

**Двусвязный:** минимум +2 указателя (`prev`, `next`) (обычно 16 байт на 64-bit системе) + возможный padding.

Для маленьких значений (например, `int` на 4 байта) накладные расходы могут доминировать. Например, на 64-bit структура вроде этой часто занимает 16 байт из-за выравнивания:

```c
struct Node {
  int value;
  struct Node *next;
};
```

В языках с GC (Ruby, Java) ещё хуже: каждый узел — отдельный объект в куче со своим заголовком, что увеличивает и расход памяти, и нагрузку на сборщик мусора.

### Реализация односвязного списка (Ruby)

```ruby
class Node
  attr_accessor :value, :next

  def initialize(value, node = nil)
    @value = value
    @next = node
  end
end

class List
  def initialize
    @head = nil
    @tail = nil
  end

  def prepend(value)
    new_node = Node.new(value, @head)
    @tail = new_node unless @head
    @head = new_node
  end

  def append(value)
    new_node = Node.new(value)
    if @tail
      @tail.next = new_node
      @tail = new_node
    else
      @tail = @head = new_node
    end
  end

  def remove_first
    return nil unless @head
    value = @head.value
    @head = @head.next
    @tail = nil unless @head  # критично: обнулить tail при опустошении!
    value
  end
end
```

**Типичный баг:** забыть обнулить `@tail` при удалении последнего элемента. После этого `append` сломается — будет писать через "мёртвый" указатель.

### Локальность и выбор структуры

Вставка в начало — O(1). Но доступ по индексу — O(n): нужно пройти по цепочке от начала. Ещё хуже — **плохая локальность данных**: узлы разбросаны по куче, каждый переход — потенциальный cache miss. Последовательный обход больших объёмов данных в массиве часто в несколько раз быстрее, чем в списке, из-за последовательного чтения кэш-линий вместо случайных прыжков по памяти.

| Критерий | Массив | Связный список |
|----------|--------|----------------|
| Произвольный доступ по индексу | O(1) | O(n) |
| Вставка/удаление в начало | O(n) | O(1) |
| Вставка/удаление в середину | O(n) | O(1)* |
| Обход всех элементов | Быстрый (локальность) | Медленный (cache miss) |
| "Сращивание" двух коллекций | O(n) | O(1) |

`*` — если есть указатель на место вставки

### Проблема: избыточная свобода интерфейса

Массив и список дают полную свободу: доступ по индексу, вставка и удаление в любом месте. Но иногда именно эта свобода опасна. Парсер выражений работает по LIFO: скобка открылась — положили, закрылась — сняли. Если использовать массив напрямую, ничто не мешает удалить элемент из середины и сломать порядок вычислений. [Стек, очередь, дек](04-stack-queue-deque.md) физически запрещают лишние операции — и этим предотвращают ошибки.
