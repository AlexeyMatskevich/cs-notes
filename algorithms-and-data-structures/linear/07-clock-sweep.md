# Clock-Sweep

**Предпосылки:** [LRU-кэш](06-lru-cache.md) (проблема contention), атомарные операции (инкремент без блокировки общей структуры).

Хотим кэш с вытеснением, но без contention при чтении. Готовы пожертвовать точностью вытеснения ради масштабируемости.

## ADT: ApproximateCache

Кэш с приблизительной политикой вытеснения:

| Операция | Сигнатура | Сложность | Contention |
|----------|-----------|-----------|------------|
| Получить значение | `get(key) → value` | O(1) | Нет* |
| Записать значение | `put(key, value)` | O(1) | При вытеснении |

`*` — атомарный инкремент вместо манипуляций со списком

**Компромисс:** менее точное вытеснение в обмен на масштабируемость.

## Реализация: Clock-Sweep

**Этимология:**
- "Clock" — часы. Указатель движется по кругу, как стрелка.
- "Sweep" — подметать. Стрелка "сметает" единицы со счётчиков.

**Альтернативное название:** Second-Chance Algorithm — элемент с ненулевым счётчиком получает "второй шанс".

**Идея:** откажемся от точного порядка. Вместо этого:

1. Каждый элемент хранит `usage_count`
2. При обращении: инкрементируем счётчик (атомарно, без блокировок общих структур)
3. При вытеснении: стрелка идёт по кругу, уменьшает счётчики, вытесняет первый с нулевым

```
        [buf 0]
           ↑
    [buf 7]   [buf 1]

  [buf 6]   ↻   [buf 2]    ← стрелка движется по кругу

    [buf 5]   [buf 3]

        [buf 4]
```

### Алгоритм

**При обращении (cache hit):**

```ruby
element.usage_count += 1  # атомарный инкремент
element.usage_count = [element.usage_count, MAX_COUNT].min
```

Никаких блокировок общих структур — только запись в своё поле.

**При поиске жертвы (cache miss):**

```ruby
def find_victim
  loop do
    element = buffer[@clock_hand]

    if element.usage_count == 0
      return element                    # нашли жертву
    else
      element.usage_count -= 1          # даём "второй шанс"
      @clock_hand = (@clock_hand + 1) % capacity
    end
  end
end
```

### Пример timeline

```
T=0: элемент загружен,      usage_count = 1
T=1: обращение,             usage_count = 2
T=2: обращение,             usage_count = 3
T=3: стрелка прошла,        usage_count = 2
T=4: стрелка прошла,        usage_count = 1
T=5: обращение,             usage_count = 2
T=6: стрелка прошла,        usage_count = 1
T=7: стрелка прошла,        usage_count = 0 → кандидат на вытеснение
```

### Почему лимит счётчика — маленькое число

PostgreSQL использует `BM_MAX_USAGE_COUNT = 5` для буферного кэша.

Без лимита элемент с `usage_count = 1000` требует 1000 проходов стрелки для вытеснения. Даже если он уже не нужен — "застревает" (та же проблема cache pollution, что у LFU).

С лимитом 5: максимум 5 проходов → быстрая адаптация к изменению паттерна доступа.

### Где теряется точность

```
Два элемента, оба usage_count = 1:

Элемент A: последнее обращение 10 секунд назад
Элемент B: последнее обращение 1 секунду назад

LRU знает: вытеснить A
Clock-sweep: видит только счётчики, выберет того, до кого дойдёт первой
```

Clock-sweep не различает элементы с одинаковым счётчиком. Это приемлемая потеря точности в обмен на масштабируемость.

### Сравнение подходов

| Аспект | LRU | LFU | Clock-Sweep |
|--------|-----|-----|-------------|
| При обращении | 4 записи + блокировка | Обновление счётчика | Атомарный инкремент |
| Точность | Точный порядок по времени | Точный счётчик за всё время | Приблизительный |
| Cache pollution | Нет | Да | Нет (затухание) |
| Contention | При каждом обращении | При каждом обращении | Только при вытеснении |
| Масштабируемость | Хуже | Хуже | Лучше |

Clock-sweep добавляет **затухание**: счётчик уменьшается при проходах стрелки. Прошлая популярность не защищает навечно — если элемент перестал использоваться, его счётчик постепенно дойдёт до нуля.

### Сложность

| Операция | LRU | Clock-Sweep |
|----------|-----|-------------|
| Обращение | O(1) + блокировка | O(1) атомарный инкремент |
| Вытеснение | O(1) | O(n) в худшем* |

`*` — на практике при нормальной нагрузке обходит несколько элементов.

### Где используется

- PostgreSQL — shared buffers
- Операционные системы — page replacement
- Другие СУБД и кэши с высокой конкурентностью

### Классификация алгоритмов вытеснения

```
              Алгоритмы вытеснения
                      │
       ┌──────────────┼──────────────┐
       │              │              │
      LRU            LFU          Random
       │
       ├── Точный LRU (список + хеш)
       │   └── Проблема: contention
       │
       └── Аппроксимации LRU

           ├── CLOCK (оригинальный)
           └── ARC, 2Q, LIRS...
```
