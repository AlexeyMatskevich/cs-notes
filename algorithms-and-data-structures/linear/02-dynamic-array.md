# Динамический массив

**Предпосылки:** [массив](01-array.md) (формула адреса, непрерывность, O(1) доступ по индексу).

Массив даёт O(1) доступ по индексу, но размер фиксирован при создании. Динамический массив снимает это ограничение: он позволяет добавлять элементы, не зная заранее сколько их будет, сохраняя при этом O(1) доступ по индексу.

| Операция | Сигнатура | Сложность |
|----------|-----------|-----------|
| Получить элемент | `get(i) → value` | O(1) |
| Записать элемент | `set(i, value)` | O(1) |
| Добавить в конец | `append(value)` | O(1) амортизировано |
| Узнать размер | `size() → n` | O(1) |

В отличие от обычного массива, размер может расти.

## Два параметра вместо одного

Внутри динамического массива — обычный статический массив, но с двумя величинами вместо одной: `capacity` (сколько места выделено) и `length` (сколько элементов реально используется).

Пока `length < capacity`, вставка в конец — O(1). Когда `length == capacity` — делаем **resize**.

### Resize: механизм

```
Было:   capacity=4, length=4
        [A][B][C][D]    — массив полон

Хотим добавить E.

Шаг 1: Выделяем новый массив (обычно × 2)
        [_][_][_][_][_][_][_][_]   — capacity=8

Шаг 2: Копируем старые элементы
        [A][B][C][D][_][_][_][_]

Шаг 3: Освобождаем старый массив

Шаг 4: Добавляем новый элемент
        [A][B][C][D][E][_][_][_]   — length=5, capacity=8
```

### Амортизированный анализ

Амортизация — термин из финансов: "растягиваем" большой разовый расход на много маленьких платежей.

После `n` вставок суммарно скопировали: `1 + 2 + 4 + 8 + ... < 2n` элементов.

На `n` операций потратили O(n) работы → в среднем на одну вставку O(1).

### Почему мультипликативный рост

При удвоении после resize есть `n` свободных слотов. Следующий resize через `n` вставок. Баланс расходов и доходов.

При увеличении на 1: каждая вставка вызывает resize. За `n` вставок — O(n²) суммарно.

Главное — **мультипликативный** рост (×2, ×1.5), а не аддитивный (+1, +10).

### Коэффициент роста в реализациях

Конкретный коэффициент — деталь реализации. Java `ArrayList` растёт примерно на 50% (≈ 1.5×). CPython `list` использует over-allocation — выделяет чуть больше, чем нужно (порядка `n + n/8 + const`), чтобы реже копировать. `std::vector` тоже растёт мультипликативно, но стандарт не фиксирует точный коэффициент — он зависит от реализации.

Смысл один: больший рост реже копирует, но увеличивает пик памяти; меньший рост чаще копирует, но экономит память.

### Накладные расходы памяти

В худшем случае после resize массив заполнен наполовину: до 50% памяти — пустые слоты. Для небольших массивов это незаметно, но для массива на гигабайт — полгигабайта впустую, что может вызвать давление на память процесса или даже OOM.

Компромисс: меньший коэффициент — меньше памяти, чаще копируем; больший коэффициент — больше памяти, реже копируем.

### Уменьшение: shrink

Массив умеет расти, но уменьшается ли он при удалении элементов? Зависит от реализации. Некоторые (Java `ArrayList`) не уменьшают capacity автоматически — нужен явный вызов вроде `trimToSize()`. Другие уменьшают буфер, когда заполненность падает ниже некоторого порога. Если этого не делать, массив, из которого удалили большинство элементов, продолжает занимать память под пиковый размер.

### Проблема: O(n) вставка в начало

Доступ по индексу — O(1). Добавление в конец — O(1) амортизированно. Но вставка в начало — по-прежнему O(n): нужно сдвинуть все элементы.

Если задача — часто вставлять в начало или середину, динамический массив неэффективен. [Связный список](03-linked-list.md) решает эту проблему.
