## 1. Массив (Array)

### Этимология

**Array** (англ.) — буквально "ряд", "строй", "расстановка". Военный термин: солдаты выстроены в ряд, плечом к плечу, без промежутков. Элементы стоят подряд, вплотную, в определённом порядке.

### Строгое определение

Массив — это структура данных, которая хранит фиксированное количество элементов одного типа в непрерывном блоке памяти, где каждый элемент доступен по целочисленному индексу за константное время.

Ключевые свойства:
- **Фиксированное количество** — размер задаётся при создании
- **Одного типа** — все элементы занимают одинаковое количество байт
- **Непрерывный блок** — между элементами нет "дыр"
- **Доступ по индексу за O(1)** — следствие трёх предыдущих свойств

### Почему O(1) — вывод, а не магия

Пусть массив начинается с адреса `base`, каждый элемент занимает `size` байт. Тогда элемент с индексом `i` лежит по адресу:

```
address(i) = base + i × size
```

Одно умножение, одно сложение — количество операций не зависит от `n`. Отсюда O(1).

**Важно:** Формула работает только потому, что все элементы одного размера. Если элементы разного размера, формула ломается.

### Представление в памяти

```
┌─────────────────────────────────────────────────────┐
│  base                                               │
│   ↓                                                 │
│  [elem 0][elem 1][elem 2][elem 3]...[elem n-1]      │
│   ←size→ ←size→  ←size→                             │
└─────────────────────────────────────────────────────┘
```

Три параметра определяют массив:
- `base` — адрес начала
- `size` — размер одного элемента в байтах
- `n` (или `length`) — количество элементов

### Инварианты массива

1. **Непрерывность:** элементы занимают адреса от `base` до `base + n × size - 1` без пропусков
2. **Однородность:** каждый элемент занимает ровно `size` байт
3. **Границы:** допустимые индексы — от `0` до `n-1` включительно

Нарушение инварианта 3 — **выход за границы массива** (buffer overflow/underflow). В C это неопределённое поведение, в Ruby/Rust — исключение или паника.

### Операции и сложность

| Операция | Время | Почему |
|----------|-------|--------|
| Чтение по индексу | O(1) | Формула адреса |
| Запись по индексу | O(1) | Формула адреса |
| Поиск по значению | O(n) | Нужно проверить каждый элемент |
| Вставка в конец (есть место) | O(1) | Просто кладём |
| Вставка в позицию i | O(n) | Сдвиг элементов |
| Удаление из позиции i | O(n) | Сдвиг элементов |

**Асимметрия массива:** конец — дешёвый (O(1)), начало — дорогое (O(n)).

### Что если элементы разного размера?

Два решения:

**1. Padding (выравнивание)** — добавляем пустые байты, чтобы все элементы занимали одинаковое место. Так работают структуры в C. Платим памятью.

**2. Массив указателей** — сам массив хранит указатели одинакового размера, а данные лежат отдельно в куче. Так устроены массивы в Ruby, Python, Java. Формула работает для указателей, но теряем **локальность данных**.

**Примечание об указателях:** указатель — это адрес в памяти, не обязательно в куче. Может указывать на стек, статическую память, куда угодно. "Куча" здесь — типичный случай для динамически создаваемых объектов.

### Локальность данных

Процессор читает память **кэш-линиями** — блоками по 64 байта. Когда просишь один байт, загружаются все 64 вокруг него.

В "честном" массиве (элементы подряд) обход — последовательное чтение. Кэш работает идеально.

В массиве указателей каждый указатель ведёт в случайное место кучи. Каждый прыжок — потенциальный **cache miss** (в 50–200 раз медленнее попадания в кэш).

## 2. Динамический массив (Dynamic Array)

### Этимология

"Dynamic" — от греческого *dynamis* (сила, способность к изменению). Массив, способный менять свой размер.

### Боль, которую решает

Статический массив требует знать размер заранее. Динамический массив растёт по мере добавления элементов.

### Идея

Храним обычный статический массив внутри, но отслеживаем две величины:
- `capacity` — сколько места выделено
- `length` — сколько элементов реально используется

Пока `length < capacity`, вставка в конец — O(1). Когда `length == capacity` — делаем **resize**.

### Resize: механизм

```
Было:   capacity=4, length=4
        [A][B][C][D]    — массив полон

Хотим добавить E.

Шаг 1: Выделяем новый массив (обычно × 2)
        [_][_][_][_][_][_][_][_]   — capacity=8

Шаг 2: Копируем старые элементы
        [A][B][C][D][_][_][_][_]

Шаг 3: Освобождаем старый массив

Шаг 4: Добавляем новый элемент
        [A][B][C][D][E][_][_][_]   — length=5, capacity=8
```

### Амортизированный анализ

**Амортизация** — из финансов: "растягиваем" большой разовый расход на много маленьких платежей.

После `n` вставок суммарно скопировали: `1 + 2 + 4 + 8 + ... + n/2 ≈ n` элементов.

На `n` операций потратили O(n) работы → в среднем на одну вставку O(1).

**Почему именно удвоение?**

При удвоении после resize есть `n` свободных слотов. Следующий resize через `n` вставок. Баланс расходов и доходов.

При увеличении на 1: каждая вставка вызывает resize. За `n` вставок — O(n²) суммарно.

Главное — **мультипликативный** рост (×2, ×1.5), а не аддитивный (+1, +10).

### Накладные расходы памяти

В худшем случае после resize массив заполнен наполовину: до 50% памяти — пустые слоты.

Компромисс: ×1.5 — меньше памяти, чаще копируем. ×2 — больше памяти, реже копируем.

## 3. Связный список (Linked List)

### Этимология

**Linked List** — буквально "связанный список". Элементы связаны указателями, образуя цепочку.

**Образ:** вагоны поезда. Каждый вагон соединён с следующим сцепкой (указателем). Чтобы добраться до вагона 500, нужно пройти через все предыдущие. Но отцепить вагон из середины — быстро, если ты уже на месте.

### Боль, которую решает

Массив: вставка в начало/середину — O(n) из-за сдвига. Если задача — часто вставлять в начало, массив неудобен.

Связный список: вставка в начало — O(1). Никаких сдвигов.

### Строгое определение

Связный список — структура данных из узлов, где каждый узел содержит данные и указатель(и) на другие узлы, образуя последовательность.

Ключевые свойства:
- Элементы не обязаны лежать в памяти подряд
- Связь через указатели
- Нет формулы для адреса по индексу

### Варианты

**Односвязный (Singly Linked List):**

```
head → [A|•] → [B|•] → [C|•] → nil
```

Каждый узел знает только следующий. Движение только вперёд.

**Двусвязный (Doubly Linked List):**

```
nil ← [•|A|•] ⇄ [•|B|•] ⇄ [•|C|•] → nil
       ↑                       ↑
     head                    tail
```

Каждый узел знает и предыдущий, и следующий. Движение в обе стороны.

**Кольцевой (Circular):** последний указывает на первый.

### Структура узла

**Односвязный:**

```ruby
class Node
  attr_accessor :data, :next
end
```

**Двусвязный:**

```ruby
class Node
  attr_accessor :data, :prev, :next
end
```

### Ключевое различие: удаление узла

**Двусвязный:** O(1) — читаем `prev`, обновляем соседей.

**Односвязный:** O(n) — нужно найти предыдущий узел, а он неизвестен.

Это главная причина существования двусвязного списка: когда нужно удалять из середины, имея только указатель на узел.

### Операции и сложность

| Операция | Односвязный | Двусвязный |
|----------|-------------|------------|
| Доступ по индексу | O(n) | O(n) |
| Вставка в начало | O(1) | O(1) |
| Вставка в конец (с tail) | O(1) | O(1) |
| Вставка после известного узла | O(1) | O(1) |
| Удаление из начала | O(1) | O(1) |
| Удаление из конца | O(n) | O(1) |
| Удаление известного узла | O(n)* | O(1) |

`*` — нужен предыдущий узел

### Накладные расходы памяти

**Односвязный:** +8 байт на узел (указатель на 64-bit системе).

**Двусвязный:** +16 байт на узел.

Для списка из `n` int'ов (4 байта): 12 байт на элемент вместо 4. Overhead 200%.

Плюс каждый узел — отдельная аллокация. Нагрузка на GC или много malloc/free.

### Когда что выбирать

**Массив лучше:**
- Нужен произвольный доступ по индексу
- Основные операции — чтение и запись
- Важна локальность (обход всех элементов)
- Вставки/удаления в основном в конец

**Связный список лучше:**
- Частые вставки/удаления в начало
- Частые вставки/удаления в середину (если есть указатель)
- Нужно "сращивать" или "разрезать" списки за O(1)

**На практике:** динамический массив выигрывает в большинстве случаев из-за кэш-локальности.

### Ring Buffer (Кольцевой буфер)

**Боль:** очередь на наивном массиве — `dequeue` оставляет "мёртвую зону" в начале.

**Решение:** кольцевой буфер. Два указателя (`head`, `tail`) ходят по кругу.

```
Физически:   [_][_][A][B][C][D][_][_]
                    ↑           ↑
                  head        tail

Переход через край: next = (current + 1) % capacity
```

Обе операции O(1). "Мёртвая зона" становится свободным местом для новых элементов.

### Реализация односвязного списка (Ruby)

```ruby
class Node
  attr_accessor :value, :next

  def initialize(value, node = nil)
    @value = value
    @next = node
  end
end

class List
  def initialize
    @head = nil
    @tail = nil
  end

  def prepend(value)
    new_node = Node.new(value, @head)
    @tail = new_node unless @head
    @head = new_node
  end

  def append(value)
    new_node = Node.new(value)
    if @tail
      @tail.next = new_node
      @tail = new_node
    else
      @tail = @head = new_node
    end
  end

  def remove_first
    return nil unless @head
    value = @head.value
    @head = @head.next
    @tail = nil unless @head  # критично: обнулить tail при опустошении!
    value
  end
end
```

**Типичный баг:** забыть обнулить `@tail` при удалении последнего элемента. После этого `append` сломается — будет писать через "мёртвый" указатель.

## 4. Абстрактные типы данных (ADT)

### Что такое ADT

**ADT — Abstract Data Type** (абстрактный тип данных).

**Этимология:** "Abstract" — от латинского *abstrahere* ("отвлекать, отделять"). Отделяем *что* структура делает от *как* устроена.

**Определение:** спецификация через набор операций и их поведение, без указания реализации.

### Зачем ограничивать операции

1. **Гарантии корректности** — если код использует стек, никто не лезет в середину
2. **Свобода реализации** — можно поменять массив на список, не ломая код
3. **Документация намерения** — читающий сразу понимает: "здесь важен LIFO"

### Стек (Stack)

**LIFO** — Last In, First Out. Последним пришёл — первым вышел.

**Образ:** стопка тарелок. Берёшь верхнюю, которую положил последней.

**Операции:**
- `push(x)` — положить на вершину
- `pop()` — снять с вершины
- `peek()` / `top()` — посмотреть вершину без удаления
- `empty?` — проверить пустоту

**Реализации:**

| Реализация | push | pop | Особенности |
|------------|------|-----|-------------|
| Динамический массив | O(1)* | O(1) | Лучшая локальность |
| Односвязный список | O(1) | O(1) | Нет resize |

На практике почти всегда массив.

**Call stack** работает по LIFO: последняя вызванная функция завершается первой.

### Очередь (Queue)

**FIFO** — First In, First Out. Первым пришёл — первым вышел.

**Образ:** очередь в магазине. Кто раньше встал, тот раньше обслужен.

**Операции:**
- `enqueue(x)` — добавить в конец
- `dequeue()` — забрать из начала
- `front()` — посмотреть первый
- `empty?`

**Реализации:**

| Реализация | enqueue | dequeue | Особенности |
|------------|---------|---------|-------------|
| Ring buffer | O(1)* | O(1) | Локальность |
| Односвязный список с tail | O(1) | O(1) | Проще код |

### Дек (Deque)

**Deque** — Double-Ended Queue. Произносится как "deck" (колода карт).

**Операции с обоих концов:**
- `push_front(x)`, `push_back(x)`
- `pop_front()`, `pop_back()`

**Почему односвязный список не подходит:** `pop_back` требует предыдущий узел — O(n).

**Реализации:** ring buffer или двусвязный список.

### Сводка: три уровня свободы

| ADT | Добавление | Удаление | Минимальная структура |
|-----|-----------|----------|----------------------|
| Стек | один конец | тот же | массив или односвязный |
| Очередь | один конец | противоположный | ring buffer или односвязный с tail |
| Дек | оба конца | оба конца | ring buffer или двусвязный |

### Реализация стека на односвязном списке (Ruby)

```ruby
# Используем тот же класс Node, что и для List
class Stack
  def initialize
    @head = nil
  end

  def push(value)
    @head = Node.new(value, @head)
  end

  def pop
    return nil unless @head
    value = @head.value
    @head = @head.next
    value
  end

  def peek
    @head&.value  # safe navigation: nil если пусто
  end

  def empty?
    @head.nil?
  end
end
```

**Почему работаем с head, а не tail:** в односвязном списке `pop` с tail требует предыдущий узел — O(n). С head — O(1).

## 5. Хеш-таблица (Hash Table)

### Боль, которую решает

Массив: O(1) доступ, но только по числовому индексу 0..n-1.

Хотим O(1) доступ по **произвольному ключу** — строке, объекту, чему угодно.

### Этимология

**Hash** (англ.) — "рубить, крошить, мелко резать". Кулинарный термин: блюдо из мелко нарезанного мяса.

**Почему подходит:** хеш-функция "рубит" входные данные, перемешивает, выдаёт результат, в котором исходная структура неузнаваема.

### Идея

1. Превратить произвольный ключ в число (хеш-функция)
2. Использовать как индекс в массиве
3. Получить O(1) в среднем

### Хеш-функция: требования

1. **Детерминированность:** один вход → всегда один и тот же выход
2. **Равномерность:** выходы распределены равномерно
3. **Быстрота:** O(длина ключа) или лучше

**НЕ требуется:** криптостойкость, уникальность выхода.

### Пример хеш-функции для строки

**Плохая (не учитывает порядок):**

```ruby
def bad_hash(str)
  str.chars.sum(&:ord)  # "ab" и "ba" дадут одинаковый хеш
end
```

**Хорошая (классическая, как в Java):**

```ruby
def good_hash(str)
  hash = 0
  str.each_char { |c| hash = hash * 31 + c.ord }
  hash
end
```

Умножение на 31 делает хеш зависимым от порядка символов.

```
"ab": (0*31 + 97)*31 + 98 = 3105
"ba": (0*31 + 98)*31 + 97 = 3135
```

### От хеша к индексу

```ruby
index = hash(key) % capacity
```

Если `capacity = 16` и `hash("alice") = 3105`, то `index = 3105 % 16 = 1`.

### Коллизия

Данных бесконечно много, индексов — ограниченное количество. Разные ключи могут получить одинаковый индекс. Это **коллизия** (столкновение).

### Стратегия 1: Chaining (цепочки)

**Этимология:** "Chain" — цепь. Элементы с одинаковым индексом связаны в цепочку (список).

Каждая ячейка хранит список элементов с одинаковым индексом.

```
┌───┬─────────────────────────────────────┐
│ 0 │ [("bob", data)]                     │
│ 1 │ [("alice", data) → ("charlie", data)]│  ← коллизия
│ 2 │ []                                  │
└───┴─────────────────────────────────────┘
```

**get(key):** вычисляем индекс, идём по списку, сравниваем ключи.

**put(key, value):** вычисляем индекс, ищем в списке, обновляем или добавляем.

### Стратегия 2: Open Addressing (открытая адресация)

**Этимология:** "Open" — весь массив "открыт" для размещения любого элемента, не только того, чей хеш указывает на эту ячейку.

Все элементы живут прямо в массиве. Если ячейка занята — ищем следующую свободную.

**Linear Probing:** если ячейка `i` занята, пробуем `i+1`, `i+2`, ...

```
put("alice"), hash % 8 = 1 → кладём в 1
put("charlie"), hash % 8 = 1 → занято, пробуем 2, кладём
put("dave"), hash % 8 = 2 → занято, пробуем 3, кладём
```

**Проблема: кластеризация.** Группы занятых ячеек растут, поиск замедляется.

### Tombstones (надгробия)

**Этимология:** "Tombstone" — надгробие. Маркер на месте "умершего" (удалённого) элемента, показывающий что здесь что-то было.

При удалении в open addressing нельзя просто поставить nil — это сломает поиск элементов, которые "перепрыгнули" эту ячейку.

**Решение:** ставим специальный маркер tombstone. При поиске — "продолжай искать", при вставке — "можно занять".

### Load Factor (коэффициент заполнения)

**Этимология:** "Load" — нагрузка, заполненность. Показывает насколько "нагружена" таблица.

```
load_factor = n / capacity
```

Где `n` — количество элементов.

**Chaining:** может быть > 1 (списки любой длины).

**Open addressing:** должен быть < 1 (физически нельзя разместить больше элементов, чем ячеек). На практике держат ≤ 0.7.

### Rehashing (перехеширование)

**Этимология:** "Re-" — заново, "hashing" — хеширование. Пересчитываем хеши для новой таблицы.

Когда load factor превышает порог (обычно 0.75):

1. Выделяем новый массив большего размера (×2)
2. Перехешируем все элементы (hash % новый_capacity ≠ hash % старый_capacity)
3. Освобождаем старый массив

Стоит O(n), но происходит редко → амортизированно O(1) на операцию.

### Сложность операций

| Операция | В среднем | В худшем |
|----------|-----------|----------|
| get | O(1) | O(n) |
| put | O(1)* | O(n) |
| delete | O(1) | O(n) |

`*` — амортизированно с учётом rehashing

**Худший случай:** все ключи в одной ячейке (плохая хеш-функция или атака).

### Сравнение стратегий

| Аспект | Chaining | Open Addressing |
|--------|----------|-----------------|
| Память | Указатели на списки | Только массив |
| Локальность | Хуже | Лучше |
| Load factor | Может быть > 1 | Должен быть < 1 |
| Удаление | Простое | Нужны tombstones |
| Код | Проще | Сложнее |

## 6. LRU-кэш

### Что это

**LRU** — Least Recently Used, "наименее недавно использованный".

Кэш с ограниченной ёмкостью. При переполнении вытесняет элемент, к которому дольше всего не обращались.

### Операции

- `get(key)` — вернуть значение. Если есть — элемент становится "свежим". Если нет — nil.
- `put(key, value)` — записать. Элемент становится "свежим". При переполнении — вытеснить самый старый.

**Требование:** обе операции O(1).

### Пример работы (capacity = 2)

```
put("a", 1) → [a]           
put("b", 2) → [b, a]        
get("a")    → [a, b]        a стал свежим
put("c", 3) → [c, a]        b вытеснен (был tail)
get("b")    → nil           b уже нет в кэше
```

### Почему нужны две структуры

**Только хеш-таблица:** O(1) доступ по ключу, но как отслеживать порядок использования?

**Только двусвязный список:** O(1) перемещение в начало, но как найти элемент по ключу за O(1)?

**Решение:** комбинация.

### Структура

```
HashMap: key → Node

Doubly Linked List: head (свежий) ⇄ ... ⇄ tail (старый)

Узел хранит: key, value, prev, next
```

**Почему ключ в узле?** При вытеснении берём tail, нужно удалить из хеша по ключу.

### Класс узла для LRU

```ruby
class Node
  attr_accessor :key, :value, :prev, :next

  def initialize(key, value)
    @key = key
    @value = value
    @prev = nil
    @next = nil
  end
end
```

### Вспомогательные методы

```ruby
# Отцепить узел из текущего места
def remove_node(node)
  if node.prev
    node.prev.next = node.next
  else
    @head = node.next
  end

  if node.next
    node.next.prev = node.prev
  else
    @tail = node.prev
  end
end

# Вставить в начало (сделать свежим)
def add_to_head(node)
  node.prev = nil
  node.next = @head

  if @head
    @head.prev = node
  else
    @tail = node
  end

  @head = node
end
```

### Операции

```ruby
def get(key)
  node = @hash[key]
  return nil unless node
  return node.value if node == @head  # уже свежий

  remove_node(node)
  add_to_head(node)
  node.value
end

def put(key, value)
  if @hash.key?(key)
    node = @hash[key]
    node.value = value
    remove_node(node)
    add_to_head(node)
  else
    node = Node.new(key, value)
    @hash[key] = node
    add_to_head(node)

    if @hash.size > @capacity
      # Важен порядок! Сначала удаляем из хеша, потом из списка
      @hash.delete(@tail.key)
      remove_node(@tail)
    end
  end
end
```

### Критичный баг с порядком операций

```ruby
# НЕПРАВИЛЬНО:
remove_node(@tail)         # @tail обновляется на предпоследний!
@hash.delete(@tail.key)    # удаляем ключ НОВОГО tail!

# ПРАВИЛЬНО:
@hash.delete(@tail.key)    # сначала берём ключ старого tail
remove_node(@tail)         # потом удаляем узел
```

### Сложность

| Операция | Время | Почему |
|----------|-------|--------|
| get | O(1) | Хеш O(1) + манипуляции O(1) |
| put | O(1) | Хеш O(1) + манипуляции O(1) |

## 7. LFU-кэш

### Что это

**LFU** — Least Frequently Used, "наименее часто используемый".

Кэш, который при вытеснении удаляет элемент с наименьшим количеством обращений за всё время.

### Отличие от LRU

**LRU** смотрит на **время** последнего обращения: "кто дольше всего не использовался?"

**LFU** смотрит на **частоту** обращений: "к кому обращались реже всего?"

### Проблема LFU: Cache Pollution

**Cache pollution** (загрязнение кэша) — когда бесполезные данные занимают место полезных.

```
T=0-100: страница A читается 1000 раз, count=1000
T=101:   страница A больше никому не нужна
T=102:   страница B нужна, count=1
T=103:   нужно вытеснить кого-то

LFU выберет B (count=1), хотя A уже бесполезна.
```

Элемент, который был очень популярен в прошлом, но больше не нужен, "застревает" в кэше из-за высокого счётчика. Он вытесняет новые элементы, которые могли бы быть полезны.

### Когда LFU лучше LRU

LFU работает лучше, когда:
- Паттерн доступа стабилен (одни и те же элементы популярны долго)
- Есть чёткое разделение на "горячие" и "холодные" данные

LRU работает лучше, когда:
- Паттерн доступа меняется со временем
- Недавнее обращение — хороший предиктор будущего обращения

### Почему Clock-Sweep лучше чистого LFU

Clock-Sweep добавляет **затухание** (decay): счётчик уменьшается при проходах стрелки. Прошлая популярность не защищает навечно — если элемент перестал использоваться, его счётчик постепенно дойдёт до нуля.

## 8. Clock-Sweep

### Боль, которую решает

LRU идеален по сложности, но в **многопоточной среде** есть проблема: при каждом обращении нужно переместить элемент в начало списка — 4 записи в указатели.

Эти записи должны быть атомарными → нужна блокировка на весь список.

```
Поток 1: хочет переместить элемент A → ждёт блокировку
Поток 2: хочет переместить элемент B → ждёт блокировку
...
1000 потоков ждут одну блокировку → bottleneck
```

### Этимология

**Clock** — часы. Указатель движется по кругу, как стрелка.

**Sweep** — подметать. Стрелка "сметает" единицы со счётчиков.

**Альтернативное название:** Second-Chance Algorithm — элемент с ненулевым счётчиком получает "второй шанс".

### Идея

Откажемся от точного порядка. Вместо этого:

1. Каждый элемент хранит `usage_count`
2. При обращении: инкрементируем счётчик (атомарно, без блокировок)
3. При вытеснении: стрелка идёт по кругу, уменьшает счётчики, вытесняет первый с нулевым

```
        [buf 0]
           ↑
    [buf 7]   [buf 1]
           
  [buf 6]   ↻   [buf 2]    ← стрелка движется по кругу
           
    [buf 5]   [buf 3]
           
        [buf 4]
```

### Алгоритм

**При обращении (cache hit):**

```ruby
element.usage_count += 1  # атомарный инкремент
element.usage_count = [element.usage_count, MAX_COUNT].min
```

Никаких блокировок общих структур.

**При поиске жертвы (cache miss):**

```ruby
def find_victim
  loop do
    element = buffer[@clock_hand]

    if element.usage_count == 0
      return element                    # нашли жертву
    else
      element.usage_count -= 1          # даём "второй шанс"
      @clock_hand = (@clock_hand + 1) % capacity
    end
  end
end
```

### Пример timeline

```
T=0: элемент загружен,      usage_count = 1
T=1: обращение,             usage_count = 2
T=2: обращение,             usage_count = 3
T=3: стрелка прошла,        usage_count = 2
T=4: стрелка прошла,        usage_count = 1
T=5: обращение,             usage_count = 2
T=6: стрелка прошла,        usage_count = 1
T=7: стрелка прошла,        usage_count = 0 → кандидат на вытеснение
```

### Почему лимит 5, а не 1000

Без лимита элемент с `usage_count = 1000` требует 1000 проходов стрелки для вытеснения. Даже если он уже не нужен — "застревает".

С лимитом 5: максимум 5 проходов → быстрая адаптация.

### Сравнение с LRU и LFU

**LRU:** точный порядок по времени, но contention при каждом обращении.

**LFU (Least Frequently Used):** вытесняем с минимальным счётчиком за всё время. Проблема: **cache pollution** — элемент, популярный час назад, не вытесняется из-за высокого счётчика.

**Clock-Sweep:** аппроксимация LRU с затуханием. Счётчик уменьшается при проходах стрелки → прошлая популярность не защищает навечно.

### Где теряется точность

```
Две элемента, оба usage_count = 1:

Элемент A: последнее обращение 10 секунд назад
Элемент B: последнее обращение 1 секунду назад

LRU знает: вытеснить A
Clock-sweep: видит только счётчики, выберет того, до кого дойдёт первой
```

### Сложность

| Операция | LRU | Clock-Sweep |
|----------|-----|-------------|
| Обращение | O(1) + блокировка | O(1) атомарный инкремент |
| Вытеснение | O(1) | O(n) в худшем* |

`*` — на практике при нормальной нагрузке обходит несколько элементов.

### Классификация

```
              Алгоритмы вытеснения
                      │
       ┌──────────────┼──────────────┐
       │              │              │
      LRU            LFU          Random
       │
       ├── Точный LRU (список + хеш)
       │   └── Проблема: contention
       │
       └── Аппроксимации LRU
           ├── Clock-Sweep (PostgreSQL)
           ├── CLOCK (оригинальный)
           └── ARC, 2Q, LIRS...
```

### Где используется

- PostgreSQL — shared buffers
- Операционные системы — page replacement
- Другие СУБД и кэши с высокой конкурентностью

## 9. Сводные таблицы

### Массив vs Связный список

| Операция | Массив | Односвязный список | Двусвязный список |
|----------|--------|-------------------|-------------------|
| Доступ по индексу | O(1) | O(n) | O(n) |
| Поиск по значению | O(n) | O(n) | O(n) |
| Вставка в начало | O(n) | O(1) | O(1) |
| Вставка в конец | O(1)* | O(1)** | O(1)** |
| Вставка в середину | O(n) | O(1)*** | O(1)*** |
| Удаление из начала | O(n) | O(1) | O(1) |
| Удаление из конца | O(1) | O(n) | O(1)** |
| Удаление из середины | O(n) | O(1)*** | O(1)*** |

`*` — амортизировано
`**` — при наличии tail указателя
`***` — если уже есть указатель на место; иначе +O(n) на поиск

### ADT: Стек, Очередь, Дек

| ADT | Порядок | Операции | Лучшая реализация |
|-----|---------|----------|-------------------|
| Стек | LIFO | push/pop с одного конца | Динамический массив |
| Очередь | FIFO | enqueue в конец, dequeue из начала | Ring buffer |
| Дек | Оба | Все операции с обоих концов | Ring buffer или двусвязный список |

### Хеш-таблица

| Операция | В среднем | В худшем |
|----------|-----------|----------|
| get | O(1) | O(n) |
| put | O(1)* | O(n) |
| delete | O(1) | O(n) |

`*` — амортизировано

### LRU-кэш

| Операция | Время | Структуры |
|----------|-------|-----------|
| get | O(1) | Хеш-таблица + двусвязный список |
| put | O(1) | |

### LFU vs LRU

| Аспект | LRU | LFU |
|--------|-----|-----|
| Критерий вытеснения | Время последнего обращения | Количество обращений |
| Cache pollution | Нет | Да (старые популярные элементы застревают) |
| Адаптация к изменениям | Быстрая | Медленная |
| Лучше для | Меняющиеся паттерны доступа | Стабильные паттерны доступа |

### Clock-Sweep vs LRU vs LFU

| Аспект | LRU | LFU | Clock-Sweep |
|--------|-----|-----|-------------|
| Критерий | Время | Частота | Частота + затухание |
| Точность | Точный порядок | Точный счётчик | Приблизительный |
| Cache pollution | Нет | Да | Нет (затухание) |
| Contention | При каждом обращении | При каждом обращении | Только при вытеснении |
| Масштабируемость | Хуже | Хуже | Лучше |
