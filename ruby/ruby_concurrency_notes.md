# Конкурентность, параллелизм и асинхронность в Ruby

## Базовая модель: конкурентность, параллелизм, async

### 1. Две причины, почему программа «не делает работу»

Если убрать маркетинговые термины, у программы есть два базовых режима: она либо **исполняет инструкции на CPU** (полезная работа), либо **ждёт** (не делает полезной работы).

Ждать можно по двум фундаментальным причинам:

**(A) Ждём внешнее событие (I/O).** Сеть, диск, таймер, процесс-ребёнок, DNS — всё это может занимать миллисекунды и секунды. CPU в этот момент свободен, но поток исполнения «спит».

**(B) Ждём доступ к общим данным.** Когда у нас несколько потоков/задач, они неизбежно начинают делить что-то общее: память, очередь, мьютекс (механизм взаимного исключения для защиты общих данных), пул соединений. Тогда часть времени уходит на ожидание синхронизации.

Конкурентность и асинхронность — это способы сделать так, чтобы пока одна часть работы ждёт, другая могла продолжать прогресс.

### 2. Термины: конкурентность, параллелизм, вытеснение, кооперация

Одна задача исполняется, другая ждёт — но как именно они чередуются? Без точных терминов легко спутать "чередование на одном ядре" и "реальное выполнение на разных ядрах".

**Задача (task)** — кусок работы, который можно рассматривать отдельно: «обработать запрос», «прочитать файл», «посчитать хэш», «подождать таймер».

**Конкурентность (concurrency)** — одна задача выполняется, пока другая ждёт, потом они меняются местами. На одном ядре это выглядит как быстрое переключение — задачи чередуются так часто, что кажутся одновременными.

**Параллелизм (parallelism)** — *буквально одновременное* выполнение задач на разных ядрах. Технология SMT (Simultaneous Multithreading, например Intel Hyper-Threading) позволяет одному ядру выполнять несколько потоков — это тоже форма параллелизма.

Мини-карта во времени:

```text
Конкурентно (1 core):   A A A A A
                        B B B B B
                        └─ чередуются во времени

Параллельно (2 cores):  core0: A A A A A
                        core1: B B B B B
```

Чтобы конкурентность работала, выполнение задачи должно быть **прерываемым**: её можно остановить и позже продолжить. Прерывание реализуется двумя способами.

**Вытесняющая (preemptive) многозадачность** — планировщик (обычно ОС) может остановить поток в любой момент (по таймеру или событию) и отдать CPU другому. Это хорошо для справедливости, но усложняет правильность: если поток может быть остановлен «везде», доступ к общим данным надо синхронизировать.

**Кооперативная (cooperative) многозадачность** — задача сама явно отдаёт управление в известных местах (yield/await). Это упрощает рассуждения (точки переключения видны), но есть риск **starvation (голодания)**: одна задача, которая никогда не уступает, блокирует все остальные. Пользователь видит это как "зависание" — запросы накапливаются в очереди, timeout через 30 секунд, сервис перестаёт отвечать.

### 3. ОС: процессы и системные потоки как фундамент параллелизма

Конкурентность и параллелизм — это абстракции. Как они реализуются на практике? Современные ОС планируют выполнение **системных потоков (OS threads)** вытесняюще. У потока есть стек, регистры и статус, и ОС может переключать его на другое ядро или приостанавливать/возобновлять.

**POSIX (Portable Operating System Interface)** — стандарт API для Unix-подобных ОС. Часть стандарта — **pthread (POSIX threads)** — определяет интерфейс для работы с системными потоками: `pthread_create`, `pthread_mutex_lock`, `pthread_cond_wait` и т.д.

Важно: pthread — это не отдельный вид потоков, а API для обычных системных потоков. Стандарт описывает *что* функции делают, а каждая ОС реализует *как*: Linux использует futex (механизм эффективного засыпания потоков при конкуренции), macOS — Mach threads, FreeBSD — `_umtx_op`. Ruby использует pthread API для создания потоков и синхронизации.

Отсюда две базовые единицы изоляции:

**Процесс (process)** — отдельное адресное пространство. Изоляция сильная: нельзя случайно «поделить память»; падение одного процесса обычно не рушит другой. Цена — дорогостоящие границы: IPC (Inter-Process Communication — общение между процессами через пайпы, сокеты, shared memory, файлы), копирование данных, отдельные кучи/GC, больше памяти.

**Поток (thread)** — несколько потоков в одном процессе делят память. Это позволяет дешёвое общение: объекты просто лежат в куче, и несколько потоков к ним обращаются.

Но разделяемая память создаёт главную проблему конкурентности: когда два потока одновременно читают и пишут одну переменную, возникают гонки. Нужна синхронизация.

**Системный вызов (syscall)** — способ программы попросить ядро ОС сделать что-то привилегированное: создать поток, прочитать файл, отправить данные в сеть, выделить память. Программа не может сама напрямую работать с железом или ресурсами ОС — она должна "попросить" ядро через syscall.

```text
Твоя программа (userspace)
        │
        │ syscall: read(fd, buf, size)
        ▼
┌─────────────────────────────┐
│       Ядро ОС (kernel)      │
│  - проверяет права          │
│  - работает с железом       │
│  - копирует данные          │
└─────────────────────────────┘
        │
        ▼
Результат возвращается в программу
```

Syscall — дорогая операция (переключение контекста user→kernel→user), поэтому многие оптимизации направлены на то чтобы делать syscall'ы реже. Например, futex (Fast Userspace Mutex — syscall Linux для эффективного засыпания потоков) делает syscall только при конкуренции, а не при каждом захвате mutex.

Практический эффект для приложений выражается через две метрики. **Latency (задержки)** — время ответа на один запрос: если поток ждал синхронизации 50ms, пользователь видит это как "подвисание" интерфейса или timeout в API-вызове. **Throughput (пропускная способность)** — сколько запросов система обрабатывает в секунду: если потоки часто блокируются на mutex, CPU простаивает, а RPS падает.

Вытесняющая модель ОС помогает, чтобы система оставалась живой даже если один поток «завис» в бесконечном цикле: CPU у него отберут. Но из-за вытеснения мы не можем «по-человечески» указать, где возможна пауза: она возможна везде.

Потоки выглядят как хорошее решение: ОС управляет ими, распределяет по ядрам. Но потоки внутри одного процесса делят память — и это порождает три класса проблем.

### 4. Почему shared-memory многопоточность сложная

Когда два потока пишут/читают одну и ту же память без синхронизации, возникают проблемы — от аппаратного уровня до логики приложения.

**Атомарная операция** — операция, которая выполняется целиком без возможности прерывания. Либо она полностью завершена, либо не началась. Промежуточное состояние невозможно.

#### 4.1 Torn reads/writes (разорванные операции)

**Что это:** Чтение "половины старого + половины нового" значения, когда запись не атомарна.

**Актуально для Ruby? НЕТ.** На x86/x86_64 все выровненные операции до 8 байт атомарны, а в Ruby ты работаешь с указателями на объекты (64 бита). Плюс механизм **GVL** в MRI (Global VM Lock — глобальная блокировка, гарантирующая что только один тред выполняет Ruby-код), плюс гарантии JVM в JRuby. Это теоретическая проблема для понимания многопоточности, но не практическая для Ruby.

#### 4.2 Race conditions (гонки): когда порядок операций ломает логику

Torn reads в Ruby не проблема. Но есть более коварная проблема: даже если каждая отдельная операция атомарна, **последовательность операций** — нет. Классический пример — проверка и изменение:

```ruby
# Thread 1                    # Thread 2
if @counter < 100             if @counter < 100
  @counter += 1                 @counter += 1
end                           end
```

Между проверкой `@counter < 100` и выполнением `@counter += 1` может вклиниться другой тред. Более того, `@counter += 1` — это несколько операций: read, increment, write.

Это проблема атомарности составных операций — нужна «критическая секция» (участок кода, выполняемый только одним потоком), которую никто не прервёт.

Чтобы понять, как именно race conditions проявляются в Ruby, нужно разобраться с механизмом GVL.

##### Как GVL переключается в Ruby

В Ruby Thread переключение происходит на двух уровнях.

На первом уровне ОС переключает pthread (вытесняющее): Ruby Thread — это pthread (системный поток), и ОС может вытеснить его в *любой* момент, посреди любой C-инструкции. Но если вытесненный pthread держит GVL, другой Ruby-тред не может выполнять Ruby-код — он заблокирован на GVL и просто ждёт.

На втором уровне GVL переключает право выполнять Ruby-код (в контролируемых точках).

**Байткод** — промежуточное представление кода. Ruby компилирует твой `.rb` файл в байткод (инструкции YARV VM), который потом выполняет виртуальная машина. Одна строка Ruby может стать несколькими байткод-инструкциями.

GVL — это mutex, не планировщик. Планировщик ОС не «опрашивает Ruby threads» на предмет “можно ли уже работать”: поток либо runnable, либо blocked. Если поток не может взять GVL, он блокируется на примитиве синхронизации (mutex/condvar; на Linux под капотом обычно futex) и **выпадает из runnable** до пробуждения.

Никакого «все потоки сразу усыпили» здесь нет: каждый pthread засыпает только когда доходит до точки, где ему нужен GVL. Типичная траектория для конкурирующего потока: runnable → попытка взять GVL → блокировка → сон. При освобождении GVL Ruby будит одного ожидающего, остальные продолжают спать. Возможны спонтанные пробуждения, поэтому логика всегда “проснулся → попробовал → если не вышло, снова блокировка”.

В MRI есть timer thread, который периодически (порядка каждых 10ms) ставит «таймерное прерывание» для активных threads. Thread, который держит GVL и исполняет байткод, обрабатывает эти прерывания в безопасных точках VM (между байткод‑инструкциями): на каждом “тике” он увеличивает счётчик времени, и когда счётчик достигает кванта — он отдаёт GVL и будит одного ожидающего. Квант по умолчанию — 100ms; в Ruby 3.4+ его можно менять через `RUBY_THREAD_TIMESLICE` (в миллисекундах).

```text
ОС (вытесняющее):        pthread A ──вытеснен──► pthread B (пытается взять GVL)
                                                 └── GVL занят → блокировка (futex) → не runnable

GVL (контролируемые точки): Thread A выполняет Ruby ──(каждые ~10ms)──► timer interrupt
                                                                      между инструкциями
                                                                          │
                                                      (накопил квант) ──► отдаёт GVL ─► Thread B получает GVL
```

##### Почему race condition возможен даже с GVL

Переключение GVL происходит между **байткод-инструкциями**, а не между Ruby-выражениями. Одно Ruby-выражение — несколько инструкций:

```ruby
# Выглядит как одна операция:
counter += 1

# Но это несколько байткод-инструкций:
# 1. getlocal counter    (read)
# 2. putobject 1         
# 3. opt_plus            (add)
# 4. setlocal counter    (write)
# GVL может переключиться между любыми из них!

# Thread 1:                    # Thread 2:
# getlocal counter (= 5)       
#    --- GVL переключился ---   
#                              # getlocal counter (= 5)
#                              # opt_plus (= 6)
#                              # setlocal counter (= 6)
#    --- GVL вернулся ---
# opt_plus (= 6)               
# setlocal counter (= 6)       # Результат: 6, а не 7!
```

Это не классическое вытеснение "где угодно" — GVL переключается в контролируемых точках. Но этих точек много (между каждой байткод-инструкцией), и Ruby-программист не видит их напрямую.

#### 4.3 Memory ordering / visibility (видимость памяти между потоками)

Допустим, мы защитили race condition через mutex. Другая проблема скрывается в многоядерности: один поток пишет `@data = 42`, другой читает старое значение — потому что запись "застряла" в кеше CPU и не долетела до общей памяти.

##### Проблема видимости: кеши CPU

```text
         Thread 1 (CPU 0)              Thread 2 (CPU 1)
              ↓                             ↓
        ┌──────────┐                  ┌──────────┐
        │ L1 Cache │                  │ L1 Cache │
        │ data=42  │                  │ data=??? │ ← старое значение!
        │ ready=T  │                  │ ready=F  │
        └──────────┘                  └──────────┘
              ↓                             ↓
        ─────────────────────────────────────────────
                          RAM
                     (когда-нибудь синхронизируется)
```

Thread 1 записал `data = 42`, но значение застряло в кеше CPU 0. Thread 2 на CPU 1 читает из своего кеша и видит старое значение. **Записи одного ядра не сразу видны другому.**

На практике это выглядит так: один поток читает `@data = nil` вместо `@data = 42`, потому что запись ещё "в пути". Логика "если данные готовы — обработай" срабатывает с пустым значением. Результат: падение с ошибкой или молчаливая потеря данных.

**В MRI с GVL это решено автоматически:** GVL реализован через pthread_mutex, а mutex по стандарту включает memory barriers (барьеры памяти — специальные инструкции, гарантирующие видимость записей между потоками). При освобождении GVL — все записи "сбрасываются" (release barrier). При захвате GVL — видны все записи до освобождения (acquire barrier). Без этих барьеров потоки могли бы читать устаревшие значения из кеша CPU — классическая ошибка visibility, которую в Ruby не увидишь благодаря GVL.

В JRuby/TruffleRuby (без GVL) visibility — реальная проблема, нужна явная синхронизация.

##### Reordering: ещё один источник проблем

Даже если один поток "пишет данные, потом ставит флаг", другой поток не обязан наблюдать это в таком же порядке. Причины — кеши, буферы записи и переупорядочивание операций на уровне CPU/JIT.

Типичный антипаттерн — публикация данных через "ready flag":

```ruby
# Thread 1 (producer)
@data = 42
@ready = true

# Thread 2 (consumer)
puts @data if @ready
```

Это не протокол. На реализациях, где Ruby‑код реально выполняется параллельно (JRuby, TruffleRuby), `@ready` и `@data` могут стать видимыми в другом порядке, и consumer иногда увидит `@ready == true`, но старое значение `@data`.

Рабочие варианты публикации (happens-before через синхронизацию):
- `Mutex` + `ConditionVariable` (один поток сигналит, другой ждёт в цикле)
- `Queue` (передавать данные сообщением)
- атомарные примитивы (`concurrent-ruby`), если нужно без блокировок

##### Почему архитектура важна: x86 vs ARM

x86_64 обычно "прощает" больше ошибок, чем ARM: один и тот же баг синхронизации может годами не проявляться на x86 и всплыть на ARM. Правило простое: если между потоками есть обмен состоянием, делай его через синхронизацию.

#### 4.4 Синхронизационные примитивы

Для защиты от race conditions и visibility проблем существуют примитивы синхронизации. **Mutex и RwLock** делают критическую секцию взаимно исключающей — только один поток выполняет защищённый код. **Condition variables и семафоры** позволяют потокам ждать наступления условий и сигнализировать друг другу. **Каналы и очереди** структурируют передачу данных как сообщения — вместо общей памяти потоки обмениваются копиями. **Атомарные операции** позволяют строить протоколы без блокировок, но требуют понимания модели памяти.

#### 4.5 Потоки ОС: runnable vs sleeping (и где тут Ruby)

У ОС есть простая модель: поток либо **runnable** (планировщик может дать ему CPU), либо **blocked/sleeping** (ждёт событие и исключён из runnable очереди). Важно: blocked поток **не крутится** и **не “проверяет готовность”** в цикле — он спит, пока ядро не разбудит.

В Ruby (MRI) поверх этого появляется ещё один “внутренний ресурс” — GVL: даже если поток runnable, он может **ждать GVL** и снова быстро уснуть. Но это всё равно ожидание через ОС (mutex/condvar), а не spin.

Два коротких эксперимента (смотри на `Thread#status`):

**Blocking I/O = поток спит в ядре**

```ruby
r, w = IO.pipe

t = Thread.new do
  r.read(1)  # blocking read: пока байт не пришёл, поток спит
end

sleep 0.05
p t.status   # обычно "sleep"

w.write("x") # событие приходит → ядро будит поток
t.join
```

**Ожидание лока = поток спит, а не крутится**

```ruby
mutex = Mutex.new
mutex.lock

t = Thread.new do
  mutex.synchronize { :ok } # ждём пока лок освободят
end

sleep 0.05
p t.status   # обычно "sleep"

mutex.unlock
t.join
```

То же самое происходит, когда поток ждёт GVL: он не “сжигает CPU”, он ждёт на примитиве синхронизации, и ядро его будит, когда появляется шанс продолжить.

### 5. Общая память: блокировки, атомики и «куда девается CPU»

Когда два потока делят изменяемые данные, есть два принципиально разных способа делать это корректно:

- **Блокировки (lock-based):** один выполняет, остальные ждут.
- **Атомики/lock-free:** пытаемся обновлять данные “за один шаг”, чтобы не засыпать на блокировке.

Важно не путать “правильность” и “параллелизм”: и блокировки, и атомики могут быть корректными. Разница — в том, **как выглядит ожидание** и во что оно превращается по ресурсу.

#### 5.1 Блокировки: ожидание через сон (не spin)

Когда поток не может продолжить из‑за лока (GVL, `Mutex`, ожидание на `Queue#pop`), он обычно **паркуется**: уходит в sleeping/blocked и исчезает из runnable очереди. CPU в этот момент отдаётся другим runnable потокам. Это даёт хороший профиль CPU, но создаёт очередь: под нагрузкой растёт p95/p99 latency (кто-то “просто ждёт своей очереди”).

Ментальная модель:

```text
Thread A: [ lock ]──[ work ]──[ unlock ]
Thread B:        └──── wait ────┘[ work ]
```

#### 5.2 Атомики: ожидание может стать активным

Атомик — это операция “прочитал‑изменил‑записал как одно целое”. Идея: не засыпать на локе, а сделать обновление за один неделимый шаг.

Цена: при высокой конкуренции ожидание часто превращается в **активные попытки** (повтор “пока не получилось”), то есть CPU может начать расходоваться на борьбу за одно и то же место.

Ruby как язык не даёт прямых атомиков на уровне переменных. Если они нужны, это обычно делается через библиотеки/рантайм (например, `concurrent-ruby`), которые дают одинаковые гарантии на MRI/JRuby/TruffleRuby.

#### 5.3 Что это значит для Ruby и GVL

- В MRI (внутри одного ractor) Ruby‑код не выполняется параллельно: все потоки по очереди держат GVL. Поэтому “контеншн” часто выглядит как очередь за GVL.
- GVL делает внутренности интерпретатора безопасными, но не делает твой протокол атомарным: `@x += 1`, `@hash[:k] ||= ...`, “check‑then‑act” всё ещё гонки.
- На JRuby/TruffleRuby потоковость “настоящая”: параллелизм CPU появляется, но любые shared mutable структуры требуют явного протокола (локи/очереди/атомики). Не полагайся на то, что “в MRI работало”.

### 6. Асинхронность как реакция на I/O-ожидание

Lock-based и lock-free подходы решают вопрос *как защитить общие данные*. Но остаётся другой вопрос: что если задач тысячи, и большую часть времени они ждут I/O? Потоки дорогие: у каждого thread есть стек. Даже если поток в основном спит, стек остаётся зарезервированным/выделенным — и тысячи потоков превращаются в гигабайты памяти. Плюс планировщик ОС тратит время на переключения между тысячами потоков.

Асинхронность — альтернативный подход: один поток обслуживает много задач, переключаясь между ними при ожидании I/O.

#### 6.1 Механизмы мультиплексирования I/O: epoll, kqueue, IOCP

Когда программе нужно ждать события на множестве ресурсов (сокеты, файлы, таймеры), ОС предоставляет специальные механизмы. Без них пришлось бы либо создавать по потоку на каждый ресурс (дорого), либо в цикле опрашивать все ресурсы (неэффективно — busy waiting).

**Файловый дескриптор (fd)** — целое число, которое ядро присваивает открытому ресурсу. Когда программа открывает файл, сокет или pipe, ядро возвращает fd. Все операции с ресурсом идут через этот номер: `read(fd, ...)`, `write(fd, ...)`, `close(fd)`.

Механизмы мультиплексирования позволяют одним вызовом ждать события на множестве fd:

**epoll (Linux)** — масштабируемый механизм для Linux. Работает в три шага:
1. `epoll_create()` — создать экземпляр epoll
2. `epoll_ctl(epfd, ADD, fd, events)` — зарегистрировать интерес к событиям на fd (чтение готово, запись готова, ошибка)
3. `epoll_wait(epfd, events, timeout)` — заблокироваться пока хотя бы один fd не станет готов

```text
                    ┌─────────────────────────────────┐
                    │         epoll instance          │
                    │                                 │
   epoll_ctl ADD ──►│  fd=5 (socket): READ            │
   epoll_ctl ADD ──►│  fd=7 (socket): READ, WRITE     │
   epoll_ctl ADD ──►│  fd=9 (timer):  READ            │
                    │                                 │
                    └─────────────────────────────────┘
                                    │
                                    │ epoll_wait()
                                    ▼
                    поток спит, ядро разбудит когда
                    любой из fd станет готов
```

**kqueue (BSD, macOS)** — аналог epoll для BSD-систем. Концептуально похож: регистрируешь интерес к событиям, потом ждёшь. Отличия в API и возможностях (kqueue умеет следить не только за fd, но и за файловой системой, процессами, сигналами).

**IOCP (Windows)** — I/O Completion Ports. Другая модель: вместо "сообщи когда готов читать" используется "начни читать, сообщи когда закончишь" (completion-based vs readiness-based). Но идея та же — один поток эффективно обслуживает много операций.

Все три механизма решают одну задачу: **позволить одному потоку эффективно ждать события на тысячах ресурсов**. Без них высоконагруженные серверы были бы невозможны — потоки слишком дорогие для "по потоку на соединение".

#### 6.2 Два способа ждать I/O

**Блокирующий I/O** — вызываешь `read(fd)`, поток блокируется в ядре пока данные не придут. Один поток ждёт один ресурс.

**Мультиплексированный I/O** — регистрируешь интерес к множеству дескрипторов, потом один вызов (epoll_wait/kevent) ждёт события на любом из них. Один поток ждёт много ресурсов.

```text
Блокирующий I/O:
Thread 1: read(socket_A)  → спит на socket_A
Thread 2: read(socket_B)  → спит на socket_B
Thread 3: read(socket_C)  → спит на socket_C
// Нужно N потоков для N соединений

Мультиплексированный I/O:
Thread 1: epoll_wait([socket_A, socket_B, socket_C])
          → спит, просыпается когда ЛЮБОЙ готов
// Один поток для N соединений
```

#### 6.3 Проблема: блокирующий I/O не масштабируется

Самый простой способ обработки соединений — «по потоку на соединение». Работает пока соединений мало. Когда соединений тысячи, начинаются проблемы.

Память: стек каждого потока ограничен снизу `PTHREAD_STACK_MIN` (часто 16KB), а дефолт в ОС обычно измеряется мегабайтами. При 10,000 соединений это легко превращается в десятки гигабайт только на стеки — может не влезть в RAM.

Планировщик: ОС тратит время на переключения контекста между тысячами потоков. При переключении — cache miss, данные потока вытесняются из L1/L2 кеша. Это проявляется как "хвостовые задержки" (tail latency): p50 запроса 5ms, но p99 — 200ms, потому что поток прождал своей очереди у планировщика.

#### 6.4 Решение: event loop на базе мультиплексированного I/O

Идея async:

1. Перевести I/O в **неблокирующий режим** — операции возвращают «пока не готово» вместо блокировки
2. **Event loop (реактор)** — один поток ждёт события на множестве дескрипторов через epoll/kqueue
3. **Исполнитель** — возобновляет задачи когда их событие готово

#### 6.5 Ruby по умолчанию — блокирующий I/O

Когда ты пишешь обычный Ruby-код:

```ruby
data = socket.read(1024)
```

Это простой syscall `read()`, который блокирует поток в ядре до прихода данных. Никакого epoll здесь нет. Ruby отпускает GVL на время этого ожидания, чтобы другие Ruby-потоки могли работать.

epoll появляется когда ты явно используешь async-подход: Fiber Scheduler (Ruby 3+), гем Async, Falcon. Они реализуют event loop поверх epoll/kqueue.

Ключевой компромисс async — кооперативность: переключение происходит в точках `.await` (или в местах, где runtime «перехватил» блокирующую операцию). Поэтому CPU-тяжёлая задача без yield/await способна «заморозить» прогресс остальных задач на том же потоке.

### 7. Акторная модель как реакция на shared mutable state

Threads и async решают проблему *как исполнять* код конкурентно. Но остаётся проблема *как управлять состоянием*. Если главная боль многопоточности — разделяемая память, то альтернативная идея звучит так: **не делить память, а делиться сообщениями**.

В акторной модели актор хранит своё состояние «внутри себя», и другой актор не может напрямую менять это состояние. Взаимодействие происходит через **почтовые ящики (mailboxes)** и сообщения.

Это сдвигает характер сложности: гонок на общих данных становится меньше (потому что общих данных меньше), но появляется необходимость проектировать протоколы сообщений, управлять очередями и **backpressure** (механизм замедления производителя когда потребитель не успевает), а также учитывать стоимость копирования данных между акторами.

Ruby `Ractor` — это именно актороподобная абстракция: параллелизм достигается через изоляцию и обмен сообщениями.

---

Конкурентность — это абстракция: потоки, async, акторы — разные способы её реализовать. Ruby выбирает конкретные механизмы для каждого подхода.

## Конкурентность в Ruby (MRI/CRuby, JRuby, TruffleRuby)

### 1. Слои исполнения: `Process → Ractor → Thread → Fiber`

MRI разделяет выполнение на четыре уровня, каждый со своей задачей:

```text
Process (адресное пространство, ОС)
  Ractor (изолированное состояние + per-ractor GVL)
    Thread (native thread, вытесняется ОС)
      Fiber (кооперативная корутина, точки переключения в коде/рантайме)
```

**Корутина** — функция, которая умеет приостановиться (yield) и продолжиться с того же места, сохраняя своё состояние между вызовами. В отличие от обычной функции, корутина не "забывает" где остановилась.

Параллелизм CPU возможен между процессами и между ractors. Переключение задач происходит на двух уровнях: ОС вытесняет threads, а Ruby-код кооперативно переключает fibers.

### 2. Процессы: «самый простой параллелизм» ценой изоляции

Процесс даёт параллелизм почти «по умолчанию»: разные процессы выполняются независимо, и ОС распределяет их по ядрам.

Компромисс процесса — в цене границ: данные не разделяются напрямую (нужен IPC через пайпы/сокеты/shared memory/файлы), память не общая (своя куча, свой GC, свои кеши), а перенос крупных объёмов данных означает копирование. Если таких пересылок много, они легко становятся узким горлышком.

Процессы удобны, когда важна изоляция: «пусть воркер упадёт, но мастер живёт», или когда нужно обойти ограничения внутри одного интерпретатора.

### 3. Ractor: параллельный Ruby без общей изменяемой памяти

#### 3.1 Зачем Ractor появился именно в MRI

MRI исторически строился вокруг **GVL** (Global VM Lock). Это упрощает жизнь интерпретатору и C-расширениям: внутри одного VM-контекста Ruby-код выполняется последовательно, и многим структурам не нужна тонкая блокировка на каждый объект.

Цена этой простоты — слабый CPU-параллелизм через `Thread`. Если у тебя 4 CPU-bound задачи и 4 ядра, создание 4 Thread не даст ускорения: потоки выполняют Ruby-код по очереди, каждый получает ~100ms, потом отдаёт GVL. Общее время — как будто выполнял последовательно, плюс overhead переключений.

Ractor меняет точку компромисса: вместо того чтобы пытаться сделать весь мир «thread-safe», Ruby вводит **изоляцию**:

- каждый ractor — независимая единица исполнения, которая может работать параллельно с другими ractors;
- объекты по умолчанию **не разделяются** между ractors (они «принадлежат» одному ractor);
- синхронизация и обмен данными делаются через сообщения.

#### 3.2 Потоки внутри ractor и per-ractor GVL

Один ractor содержит один или несколько `Thread`. Важное ограничение MRI: threads внутри одного ractor делят **ractor-wide GVL**, поэтому они не могут исполнять Ruby-код параллельно друг с другом (если только не отпускают GVL в C-расширении). Threads из разных ractors могут исполняться параллельно — именно это даёт CPU-параллелизм.

Отсюда практическая эвристика: **CPU-bound Ruby-код распараллеливается через ractors или процессы, но не через threads внутри одного ractor**.

#### 3.3 Shareable vs unshareable: что можно передавать между ractors

Если ractors должны быть изолированы, возникает вопрос: «а как тогда обмениваться данными?».

Ruby делит объекты на две категории. **Shareable** объекты безопасны для совместного использования — это числа, замороженные строки/структуры без ссылок на изменяемые внутренности, и сами объекты `Ractor`. **Unshareable** — большинство обычных объектов: массивы, хеши, пользовательские классы — по умолчанию они принадлежат одному ractor.

Проверка и превращение:

```ruby
Ractor.shareable?(obj)        # проверка
Ractor.make_shareable(obj)    # попытка сделать объект shareable (обычно через deep-freeze)
```

Это похоже на перенос идеи Rust в runtime: в Rust типы `Send/Sync` решают «можно ли делить/передавать между потоками» на этапе компиляции; в Ruby это решается проверками и протоколом передачи.

##### 3.3.1 Классы: shareable объект ≠ свободный shared state

`Class` и `Module` объекты всегда считаются shareable, поэтому *определения классов/модулей общие для всех ractors*: если `C` определён как константа, не-main ractors могут обращаться к `C` и вызывать его методы.

Но класс — это объект, у которого есть «глобальное» состояние, и Ractor вводит на него отдельные ограничения:

- **Class variables (`@@cv`) доступны только в main ractor.** Попытка прочитать/изменить `@@cv` в non-main ractor приводит к `Ractor::IsolationError`.
- **Class instance variables (`@iv` на уровне класса) в non-main ractor:**
  - чтение разрешено только если значение shareable;
  - запись запрещена даже для shareable значений.
- **Константы должны ссылаться на shareable объекты**, иначе non-main ractors не смогут их читать.

Минимальный пример (Ruby 3.0+: в Ruby 4.0 есть `value`, в Ruby 3.0–3.4 — `take`):

```ruby
class C
  @@cv = 1
  @iv = 1
  GOOD = "good".freeze
  BAD  = "bad".dup
end

r = Ractor.new do
  class C
    begin
      p @iv
      p GOOD
      p @@cv
    rescue => e
      p [e.class, e.message]
    end

    begin
      @iv = 42
    rescue => e
      p [e.class, e.message]
    end

    begin
      p BAD
    rescue => e
      p [e.class, e.message]
    end
  end

  :done
end

if r.respond_to?(:value) # Ruby 4.0+
  r.value
else
  r.take                 # Ruby 3.0-3.4: возврат из ractor читается через `take`
end
```

#### 3.4 Сообщения: default port и `Ractor::Port`

> **Примечание о версиях Ruby:** в Ruby 3.0–3.4 у ractors были два канала: входящий (`Ractor#send`/`Ractor.receive`) и исходящий (`Ractor.yield`/`Ractor#take`). В Ruby 4.0 `Ractor.yield`/`Ractor#take` удалены, вместо них добавлены `Ractor::Port`, `Ractor#default_port`, `Ractor#join` и `Ractor#value`.

У ractor есть **mailbox** (очередь входящих сообщений). В Ruby 4.0 mailbox представлен объектом `Ractor::Port` и доступен как `r.default_port`. В Ruby 3.0–3.4 этот объектный API отсутствует, но `r.send` и `Ractor.receive` работают по той же идее: `send` кладёт сообщение в mailbox получателя, `receive` читает из mailbox текущего ractor.

**`Ractor::Port`** (Ruby 4.0+) — отдельный объект-очередь, который создаётся вызовом `Ractor::Port.new` и **принадлежит ractor'у-создателю**.

Ключевое правило владения:

- **получать (`port.receive`) и закрывать (`port.close`) может только ractor, который создал port;**
- **отправлять (`port.send` / `port <<`) может любой ractor, у которого есть ссылка на port.**

Это не «ограничение по месту, где лежит переменная», а ограничение по **owner ractor**, выбранному при `Port.new`.

Отсюда следует паттерн MPSC (multi-producer / single-consumer): один потребитель (создатель), много производителей (все, кому отдали ссылку).

Есть ещё один важный эффект: `Port#send` не блокирует отправителя (очередь концептуально бесконечная), а `Port#receive` блокирует текущий thread, если сообщений нет. Это значит, что backpressure приходится реализовывать протоколом (например, «не посылай больше N сообщений без ack»), иначе очередь может разрастись до OOM.

#### 3.5 Двустороннее общение: кому нужен port и кто его создаёт

У «однонаправленного» port простая логика: **порт создаёт тот, кто будет получать**.

Поэтому для двусторонней связи обычно нужны два канала «туда» и «обратно»:

- если `main` должен получать от `worker`, то `main` создаёт `reply_port`, передаёт его `worker`, и `worker` делает `reply_port.send(...)`;
- если `worker` должен получать от `main` *через port*, то `worker` должен создать свой входящий port, передать его `main`, и `main` будет в него `send`.

При этом для многих сценариев ports вообще не нужны: можно общаться через mailbox'ы ractor-ов (`send/receive`), если у сторон есть ссылки друг на друга.

Пример «main → worker → main» через mailbox'ы (`send/receive`):

```ruby
main = Ractor.current

worker = Ractor.new(main) do |main|
  req = Ractor.receive        # читаем из mailbox worker
  main.send([:ok, req])       # пишем в mailbox main
  :done
end

worker.send("ping")
p Ractor.receive              # читаем из mailbox main

if worker.respond_to?(:value) # Ruby 4.0+
  worker.value
else
  worker.take                 # Ruby 3.0-3.4
end
```

Пример «много воркеров → один consumer» (`Ractor::Port` в Ruby 4.0+, иначе mailbox main):

```ruby
results = Ractor.const_defined?(:Port) ? Ractor::Port.new : nil # owner: main (Ruby 4.0+)
main = Ractor.current

workers = 4.times.map do |i|
  if results
    Ractor.new(results, i) do |results, i|
      results << [:done, i, Process.pid]
      :done
    end
  else
    Ractor.new(main, i) do |main, i|
      main.send([:done, i, Process.pid])
      :done
    end
  end
end

4.times do
  msg = results ? results.receive : Ractor.receive
  p msg
end

workers.each do |w|
  if w.respond_to?(:value) # Ruby 4.0+
    w.value
  else
    w.take                 # Ruby 3.0-3.4
  end
end
```

#### 3.6 Общение между двумя non-main ractors без участия main «в доставке»

После того как два ractor'а получили ссылки друг на друга (или ссылки на нужные ports), они могут переписываться напрямую: сообщения идут в mailbox/port получателя, а `main` больше не пересылает их.

Но «стыковка» (bootstrap) всё равно должна откуда-то взяться: кто-то должен передать контакт. Это может быть `main`, или один ractor может создать другой и передать ссылку сразу.

#### 3.7 Copy vs move при отправке сообщений

Когда отправляется shareable объект, передаётся ссылка (дёшево).

Когда отправляется unshareable объект, Ruby должен сохранить гарантию «в один момент времени доступен только в одном ractor». Для этого используются два режима:

- **copy** (по умолчанию): объект глубоко копируется в другой ractor (может быть дорого);
- **move**: передача владения — отправитель теряет доступ к объекту, получатель получает эксклюзивное право (как move-семантика в Rust).

Следствие: стоимость сообщений определяется тем, нужно ли копировать объект. Shareable/immutable передаются как ссылка. Unshareable либо копируются (copy), либо перемещаются (move) — и в обоих случаях протокол должен учитывать цену копирования и цену потери владения.

### 4. Thread: нативные потоки, GVL и модели 1:1 vs M:N

#### 4.1 Ruby Thread = нативный pthread (по умолчанию)

В main ractor (типичный случай) MRI использует 1:1 модель: Ruby `Thread` — это **native thread**, созданный через `pthread_create`. Когда ты создаёшь 4 Ruby потока, у тебя реально создаются 4 нативных потока ОС:

```text
Ruby процесс
├── pthread #1 (main thread)     → Ruby Thread.main
├── pthread #2                   → Ruby Thread #2  
├── pthread #3                   → Ruby Thread #3
├── pthread #4                   → Ruby Thread #4
└── pthread #5 (timer thread)    → внутренний, ставит флаг "пора отдать GVL" по таймеру
```

Каждый pthread — это реальный системный поток. ОС может поставить их на разные ядра CPU. Метод `Thread#native_thread_id` возвращает native thread id (может быть `nil`, если поток ещё не связан с native thread или уже отвязан; при M:N модели может меняться во времени).

Ruby использует pthread API для всей синхронизации: GVL реализован через `pthread_mutex_t` + `pthread_cond_t`. Ruby не использует futex напрямую — pthread абстрагирует это (на Linux pthread внутри использует futex).

#### 4.2 Эволюция моделей потоков в Ruby

Ruby 1.8 использовал M:1 модель (green threads) — много Ruby-потоков на одном нативном потоке, полностью в userspace, без настоящего параллелизма. С Ruby 1.9 перешли на 1:1 модель: каждый `Thread.new` создаёт нативный pthread, хотя GVL по-прежнему ограничивает выполнение Ruby-кода одним потоком одновременно.

Ruby 3.3+ добавил M:N thread scheduler. На main ractor он выключен по умолчанию, но его можно включить через `RUBY_MN_THREADS=1`. На non-main ractors M:N включён. Число нативных потоков для планирования ограничивается `RUBY_MAX_CPU=n` (по умолчанию 8). При M:N модели `native_thread_id` может быть `nil` и/или меняться во времени.

#### 4.3 Почему Ruby выбрал GVL

GVL (Global VM Lock) — это mutex на уровне интерпретатора. Только один тред может исполнять Ruby-код в один момент времени. Это автоматически решает некоторые проблемы многопоточности: **torn reads** не актуальны (только один тред пишет/читает Ruby-объекты), **memory ordering** гарантируется барьерами в GVL-операциях, а **внутренние структуры VM** защищены от параллельного доступа.

**Но GVL НЕ делает Ruby-код атомарным!** Переключение происходит между байткод-инструкциями, а одно Ruby-выражение (например `counter += 1`) — это несколько инструкций. Race conditions на уровне логики всё ещё возможны (см. раздел 4.4).

GVL даёт несколько конкретных гарантий (в пределах одного ractor в MRI):

- В каждый момент времени Ruby‑байткод исполняет только один thread.
- Переключение между threads происходит только в точках, где VM может сохранить свои инварианты.
- Вход/выход из GVL выступает как барьер памяти: записи, сделанные одним thread'ом в Ruby‑коде, становятся видимыми thread'у, который позже захватил GVL (отношение happens-before: «сделал раньше» → «наблюдается позже»).

Иногда это описывают как «GVL делает VM‑инструкции атомарными». Если под этим подразумевается “другой Ruby thread не может вклиниться посреди одной VM‑инструкции” — это близко к правде: переключение Ruby‑исполнения происходит в safe points VM (обычно между байткод‑инструкциями). Но это не “атомарность на уровне CPU”: ОС может вытеснить текущий pthread в середине выполнения C‑кода, просто другие Ruby threads в этот момент всё равно не смогут исполнять Ruby‑код, пока GVL не освободится. И важно: некоторые VM‑инструкции (например, вызов метода) могут выполнять большой кусок работы и даже отпускать GVL внутри (например, на blocking I/O) — поэтому «инструкция всегда маленькая и неделимая» как модель не работает.

GVL не даёт:

- Атомарности «составных» операций и протоколов на уровне твоей логики.
- Параллельного ускорения CPU‑bound Ruby‑кода внутри одного ractor.
- Защиты внешних ресурсов (файл, сокет, соединение с БД) от конкурентного доступа: это отдельные протоколы.

GVL выбран исторически по нескольким причинам. Ruby создавался как «язык для программиста» — Matz хотел простоту и выразительность, а заставлять программистов думать о memory ordering и атомиках противоречило бы философии языка. Ruby как динамический язык имеет тяжёлый рантайм: внутренние структуры интерпретатора (таблицы методов, constant tables, объекты) сложны, и сделать их lock-free или fine-grained — титаническая работа и источник багов. Кроме того, Ruby позволяет писать C-расширения, которые напрямую манипулируют Ruby-объектами — требование синхронизации от C-кода сломало бы совместимость. Наконец, для типичных задач (веб-серверы, I/O-bound приложения) GVL достаточно хорош: во время ожидания сети/диска он отпускается.

#### 4.4 GVL не освобождает от синхронизации!

**Важно:** GVL защищает **внутренние структуры интерпретатора**, а не твою бизнес-логику. Race conditions на уровне логики всё ещё возможны:

```ruby
# Это НЕ атомарно, даже с GVL!
if @hash[:key].nil?
  @hash[:key] = expensive_computation
end
```

Здесь три отдельные Ruby-операции: чтение из хеша, проверка на nil, запись в хеш. Между любыми из них GVL может переключиться на другой тред.

GVL переключается по тайм‑слайсу (по умолчанию 100ms: тред проверяет флаг и отдаёт GVL между байткод-инструкциями), при блокирующем I/O, при `Thread.pass`, и на границах Ruby-инструкций байткода.

Чтобы эта логика была корректной при конкурентном доступе, проверка и запись должны быть частью одного неделимого протокола (одна «критическая секция»). Например, под одним общим локом:

```ruby
@mutex.synchronize do
  if @hash[:key].nil?
    @hash[:key] = expensive_computation
  end
end
```

#### 4.5 Вытесняемость и два уровня планирования

ОС не знает про GVL. Для неё это просто N обычных pthread. Планировщик Linux переключает их по своему усмотрению.

Получается двухуровневая система:

```text
┌─────────────────────────────────────────────────────────────┐
│                    Планировщик ОС                           │
│  Решает: какому pthread дать физический CPU                 │
│  Не знает про Ruby, GVL, переключает по своим правилам      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    GVL (внутри Ruby VM)                     │
│  Решает: какой Ruby Thread может выполнять Ruby-код         │
│  Реализован через pthread_mutex + pthread_cond              │
│  (под капотом — futex на Linux)                             │
└─────────────────────────────────────────────────────────────┘
```

Что происходит когда ОС даёт CPU потоку, ожидающему GVL:
1. ОС переключает контекст на pthread
2. Pthread пытается захватить GVL (pthread_mutex_lock)
3. Если GVL занят — pthread_cond_wait → поток сразу засыпает на futex
4. Поток получил CPU на микросекунды только чтобы проверить и снова уснуть

Это не страшно: потоки на pthread_cond_wait спят в ядре (состояние SLEEPING), ОС видит их как спящие и не тратит на них CPU-время. Ruby при освобождении GVL сигнализирует конкретному следующему потоку через pthread_cond_signal.

### 5. Что происходит при I/O и sleep

#### 5.1 GVL отпускается при блокирующих операциях

Когда Thread делает `File.read("big_file.txt")` или `socket.read` или `sleep`:

```text
Время    Thread #1          Thread #2              Thread #3
─────    ─────────          ─────────              ─────────
t1       держит GVL,        ждёт GVL               ждёт GVL
         выполняет код      
         
t2       вызывает socket.read
         │
         ▼
         ОТПУСКАЕТ GVL ──► Thread #2 захватывает GVL
         │                 выполняет Ruby-код
         ▼
         read() syscall
         спит в ядре
         (ждёт данные)
         
t3       спит в ядре        выполняет код          ждёт GVL

t4       данные пришли!     
         ждёт GVL
         
t5       ← захватил GVL     ждёт GVL               ждёт GVL
         продолжает
```

Система **не зависает**! Пока Thread #1 спит в ядре ожидая диск/сеть, другие потоки спокойно выполняют Ruby-код по очереди.

Важно: блокирующий `read()` не делает «проверку в цикле». Поток заходит в syscall, и если данных нет — ядро переводит его в SLEEPING (blocked) и убирает из очереди runnable. CPU не тратится, пока поток не разбудят событием (данные пришли/таймер сработал). После пробуждения поток либо продолжает выполнение, либо упирается в ожидание синхронизации (в MRI — например, повторно ждёт GVL) и снова засыпает через mutex/condvar. Спин и сжигание CPU появляются, только если сделать non-blocking I/O и крутиться в цикле на `EAGAIN` без `select/poll/epoll`/scheduler.

Контрпример: non-blocking I/O без ожидания превращается в spin (и начинает жечь CPU):

```ruby
r, w = IO.pipe
r.nonblock = true

spins = 0
t = Thread.new do
  loop do
    begin
      r.read_nonblock(1)
      break
    rescue IO::WaitReadable
      spins += 1
    end
  end
end

sleep 0.05
p spins
w.write("x")
t.join
```

Тот же non-blocking I/O без спина: вместо повторных попыток поток засыпает в ядре до готовности fd:

```ruby
r, w = IO.pipe
r.nonblock = true

t = Thread.new do
  loop do
    begin
      r.read_nonblock(1)
      break
    rescue IO::WaitReadable
      IO.select([r])
    end
  end
end

sleep 0.05
p t.status # обычно "sleep"
w.write("x")
t.join
```

#### 5.2 Два разных вида «засыпания»

**Ожидание синхронизации (mutex, condition variable, GVL)** — поток ждёт, пока *другой поток* что-то сделает (освободит mutex, подаст сигнал). Механизм: futex — специальный системный вызов для эффективного ожидания. Поток добавляется в wait queue привязанную к адресу в памяти.

Важно: это не кооперативность и не spinlock. Поток не «обходит потоки и проверяет», и CPU не «знает про futex». Поток заходит в ядро (futex_wait / cond_wait / mutex contended) и становится **blocked**, после чего планировщик перестаёт рассматривать его как runnable — поток не выполняет инструкций, пока ядро его не разбудит.

**Ожидание I/O** — поток ждёт *внешнего события* (данные из сети, завершение записи на диск, срабатывание таймера). Механизм: wait queue ядра привязанная к ресурсу. Это **не futex** — это другие структуры ядра.

```text
Синхронизация (ждём другой поток):
  pthread_mutex_lock()     →  futex на адресе mutex
  pthread_cond_wait()      →  futex на адресе condvar
  
I/O (ждём внешнее событие):
  read(socket)             →  wait queue сокета, пробуждение от сетевой карты
  read(file)               →  ожидание DMA-контроллера диска
  sleep(n)                 →  timer queue ядра, пробуждение от прерывания таймера
```

В обоих случаях поток переходит в состояние SLEEPING и не потребляет CPU. Разница в том, *что* его разбудит: другой поток (futex_wake) или железо (прерывание).

Планировщик ОС не «обходит все потоки по кругу». Он выбирает, кому дать CPU, только из runnable очереди. Поток, который ждёт на futex или в `read()`, из runnable очереди исключён — поэтому это не кооперативная многозадачность и не "yield": это блокировка в ядре.

Ментальная модель для MRI, когда поток проснулся после I/O, но GVL сейчас занят:

```text
read()/sleep() → SLEEPING (ядро) → wakeup → RUNNABLE (ОС)
                                     ↓
                           попытка взять GVL
                                     ↓
                               SLEEPING (futex)
                                     ↓
                               RUNNING Ruby (GVL)
```

#### 5.3 Когда GVL отпускается

GVL отпускается при блокирующем I/O (сеть, диск, `sleep`), при вызове C-расширений, которые явно используют `rb_thread_call_without_gvl`, и при некоторых тяжёлых операциях в стандартной библиотеке.

#### 5.4 Когда система «зависнет»

Система зависнет (другие потоки не смогут работать) только если поток держит GVL и не отпускает его. Это происходит при чистом CPU-bound коде:

```ruby
Thread.new do
  # Этот код держит GVL ~100ms, потом проверяет флаг и отдаёт на несколько ms
  result = 0
  100_000_000.times { |i| result += i }
end

Thread.new do
  # Этот поток получает CPU только в короткие окна когда первый отдаёт GVL
  # На практике: выполнится один puts за ~100ms ожидания
  puts "Я выполняюсь урывками!"
end
```

### 6. Fiber: кооперативная конкурентность и фундамент async-рантайма

#### 6.1 Базовая механика: `resume`, `yield`, `alive?`

Fiber — это корутина: у неё есть свой стек, и она умеет «остановиться» и продолжить с того же места.

- `Fiber.new { ... }` создаёт fiber, но не запускает.
- `fiber.resume` запускает/продолжает выполнение до ближайшего `Fiber.yield` или до завершения.
- `Fiber.yield` отдаёт управление наружу (в `resume`).
- `fiber.alive?` показывает, можно ли его ещё продолжить (после завершения — `false`).

Минимальная «лестница»:

```ruby
f = Fiber.new do
  puts "A"
  Fiber.yield
  puts "B"
end

f.resume  # печатает A, останавливается на yield
f.resume  # печатает B, завершается
```

У `yield` и `resume` есть обмен значениями: аргументы `yield(...)` возвращаются из `resume`, а аргументы следующего `resume(...)` становятся результатом выражения `Fiber.yield` внутри fiber. Это удобно, чтобы строить кооперативные протоколы без общей памяти.

#### 6.2 Проблема: блокирующий I/O блокирует весь thread

Fiber переключается только в точках `yield/transfer` (кооперативность). Но если внутри fiber вызвать блокирующую операцию, весь thread заблокируется:

```ruby
f1 = Fiber.new { sleep(2); puts "fiber 1 done" }
f2 = Fiber.new { puts "fiber 2 done" }

f1.resume  # Здесь программа зависает на 2 секунды!
           # f2 не может выполниться, пока f1 спит
f2.resume  # Выполнится только после того как f1 проснётся
```

Никакой другой fiber на этом thread не побежит, пока `sleep(2)` не завершится. Это делает "наивные" fibers бесполезными для async I/O: нельзя обслужить 10000 соединений на одном thread, если каждый блокирующий вызов замораживает весь thread.

Чтобы fibers стали инструментом async, нужен механизм: «когда fiber упирается в блокирующий вызов, он не должен блокировать thread; он должен зарегистрировать ожидание и уступить управление».

В Rust это место — `.await` + runtime. В Ruby это место — **Fiber Scheduler**.

#### 6.3 Решение: Fiber Scheduler перехватывает блокирующие операции

Ruby даёт интерфейс планировщика, который можно установить на *текущий thread*:

```ruby
Fiber.set_scheduler(MyScheduler.new)
```

Дальше в специальных «non-blocking» контекстах Ruby будет вызывать hooks планировщика вместо того, чтобы реально блокировать thread на `sleep` и I/O.

Смысл hooks ровно такой же, как у reactor/executor: когда нужен I/O или таймер — зарегистрировать интерес к событию, уступить управление (fiber блокируется), и когда событие произошло — разбудить fiber и продолжить.

Минимальный контракт планировщика включает методы `io_wait`, `kernel_sleep`, `block`, `unblock` (иначе `Fiber.set_scheduler` упадёт с ошибкой). Дополнительные hooks (DNS, timeout, ожидание процессов) могут быть опциональными.

Threads дают вытесняемость и простую модель, но платят ресурсами. Fibers дают дешёвые «задачи», но требуют дисциплины (yield-точек) и планировщика, чтобы не блокировать thread.

### 7. JRuby и TruffleRuby: как работают реализации без GVL

#### 7.1 Главный вопрос: если JRuby работает без GVL, зачем GVL нужен MRI?

GVL в MRI защищает **две разные вещи**: внутренние структуры интерпретатора (method tables, constant tables, object allocation), которые написаны на C без thread-safety, и как побочный эффект — пользовательские структуры (Array, Hash), которые "случайно" работают корректно. JRuby и TruffleRuby решают первую проблему иначе.

#### 7.2 Как JRuby и TruffleRuby обходятся без GVL

**MRI: один лок (GVL) защищает вообще всё**

```text
┌─────────────────────────────────────────────┐
│                  GVL                        │
│  ┌─────────────────────────────────────┐    │
│  │  method tables                      │    │
│  │  constant tables                    │    │
│  │  object allocation                  │    │
│  │  require/autoload                   │    │
│  │  твой Array                         │    │
│  │  твой Hash                          │    │
│  │  вообще всё                         │    │
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘

Хочешь что-то сделать? Захвати GVL.
Неважно что — один лок на всё.
```

Плюс: просто реализовать, невозможно ошибиться.
Минус: нет параллелизма — все ждут один лок.

**JRuby: нативные Java threads без глобального лока**

JRuby не имеет GVL, потому что Ruby thread в JRuby — это просто Java thread, а JVM изначально проектировалась для многопоточности. Внутренние структуры интерпретатора (method tables, constant tables, require/autoload) защищены отдельными локами там, где это необходимо — JRuby использует стандартные механизмы синхронизации Java.

```text
┌─────────────────────────────────────────────┐
│              JRuby Runtime                  │
│                                             │
│  Thread 1 ──────────────┐                   │
│  Thread 2 ──────────────┼── параллельно     │
│  Thread 3 ──────────────┘   выполняют код   │
│                                             │
│  Внутренние структуры защищены              │
│  отдельными локами по необходимости         │
└─────────────────────────────────────────────┘
```

Плюс: настоящий параллелизм — потоки выполняют Ruby-код одновременно.
Минус: race conditions в пользовательском коде теперь реальная проблема, а не теоретическая.

**TruffleRuby: параллельные threads без GVL (Native/JVM)**

TruffleRuby тоже не имеет GVL и исполняет Ruby‑код параллельно. У него два режима запуска:

- **Native** (`--native`, по умолчанию): быстрее стартует и быстрее “выходит на рабочий режим”.
- **JVM** (`--jvm`): дольше стартует и прогревается, но обычно даёт лучшую peak‑производительность и более удобен для Java‑интеропа.

Отсутствие GVL означает то же самое, что и для JRuby: если два threads делят изменяемые данные, нужна дисциплина синхронизации. Разница в том, что TruffleRuby постепенно делает некоторые базовые структуры более “похожими на MRI” по безопасности:

- `Hash` на современных версиях TruffleRuby сделан thread-safe (это убирает класс багов, когда `Hash` повреждается при конкурентном доступе без синхронизации).
- Есть `TruffleRuby::ConcurrentMap` — thread-safe map, ориентированный на высокую конкуренцию (обычно используется через `concurrent-ruby`).

Но thread-safe контейнер не делает протокол атомарным: `hash[:k] ||= expensive` всё равно может вычислиться дважды, если два threads одновременно увидят “ключа ещё нет”.

#### 7.3 Почему JRuby не защищает Array и Hash

JRuby защитил **только внутренности интерпретатора** — то что нужно для работы самого JRuby.

Твои `Array` и `Hash` — **твоя ответственность**. Это осознанный выбор: добавить лок на каждый Array/Hash замедлило бы однопоточный код, а это 99% Ruby-программ.

#### 7.4 Что это значит для твоего кода

```ruby
# Этот код "работает" в MRI из-за отсутствия параллелизма Ruby‑кода,
# но в реализациях без GVL это уже shared mutable state.

array = []
10.times.map do 
  Thread.new { 1000.times { array << 1 } }
end.each(&:join)

array.size
```

В MRI `Array#<<` "атомарен" только потому что **нет параллелизма** — GVL не даёт двум потокам выполнять Ruby-код одновременно.

В JRuby потоки **реально параллельны**, и `Array` не обязан быть thread-safe — конкурентная запись без протокола означает гонку.

В TruffleRuby потоки тоже параллельны. Даже если часть стандартных структур сделана thread-safe, это не отменяет требований к протоколам: shared mutable state без синхронизации остаётся источником логических гонок.

#### 7.5 Видимость памяти и "volatile"

В многопоточном коде важно не только «кто первый записал», но и «когда другой поток это увидит». CPU‑кеши и переупорядочивание инструкций могут дать ситуацию: один поток уже записал "готово", другой увидел флаг, но не увидел данные.

- **Volatile** — это про *видимость и порядок*, а не про атомарность: запись volatile работает как “release” (всё, что записано «до», станет видимым другим потокам), а чтение volatile — как “acquire” (после чтения видны записи, сделанные «до» соответствующего release). Это помогает корректно публиковать данные (happens-before), но **не делает** `x += 1` атомарным.

Ruby как язык не задаёт "volatile" семантики для instance variables, поэтому pattern "data + ready flag" без синхронизации не должен использоваться. В MRI GVL сериализует выполнение Ruby‑кода, и на практике многие visibility‑проблемы маскируются, но логические гонки остаются. В JRuby/TruffleRuby Ruby‑код выполняется параллельно, поэтому visibility становится реальной проблемой.

```ruby
# Thread 1
@data = 42
@ready = true

# Thread 2
if @ready
  puts @data
end
```

Чтобы это было корректным, между записью данных и чтением должен быть happens-before. Его даёт только синхронизация: лок/очередь (сообщение)/атомики с барьерами.

#### 7.6 TruffleRuby: явные барьеры и атомики

TruffleRuby предоставляет явные примитивы:
```ruby
# Явный memory barrier
TruffleRuby.full_memory_barrier

# Атомарные ссылки с барьерами
ref = TruffleRuby::AtomicReference.new(value)
ref.set(new_value)                    # включает barrier
ref.compare_and_set(old, new)         # CAS с barrier

# Синхронизация на объекте
TruffleRuby.synchronized(object) { ... }
```

#### 7.7 concurrent-ruby: единое решение для всех реализаций

Гем `concurrent-ruby` предоставляет одинаковое поведение на MRI, JRuby и TruffleRuby:

```ruby
require 'concurrent'

# Thread-safe коллекции
map = Concurrent::Map.new

# Атомарные примитивы
ref = Concurrent::AtomicReference.new(initial_value)
ref.compare_and_set(old_value, new_value)
```

#### 7.8 Сводная таблица

| Что | MRI (GVL) | JRuby | TruffleRuby |
|-----|-----------|-------|-------------|
| Интерпретатор защищён? | ✅ GVL | ✅ механизмы JVM | ✅ механизмы Truffle | 
| Ruby-код в `Thread` параллелен? | ❌ (внутри одного ractor) | ✅ да | ✅ да |
| Shared mutable state без синхронизации | ❌ нет | ❌ нет | ❌ нет |

#### 7.9 Гарантии и переносимость

Одна и та же программа может «казаться правильной» в MRI и ломаться в JRuby/TruffleRuby — не потому что MRI «правильнее», а потому что GVL убирает параллелизм Ruby‑кода и тем самым меняет вероятность проявления гонок.

Переносимая ментальная модель такая: **shared mutable state между потоками без протокола — всегда ошибка**, просто в MRI она чаще маскируется очередностью выполнения.

### 8. Сравнение веб-серверов: Puma vs Falcon

Оба сервера решают одну задачу — обрабатывать HTTP-запросы эффективно. Но используют разные подходы к конкурентности. Понимание их архитектуры связывает теорию (процессы, потоки, fibers, I/O мультиплексирование) с практикой.

#### 8.1 Проблема: blocking I/O не масштабируется

Наивный подход "один поток на соединение":

```ruby
# Простейший сервер
loop do
  client = server.accept          # блокируемся, ждём соединения
  Thread.new do
    request = client.read         # блокируемся, ждём данные
    response = app.call(request)
    client.write(response)        # блокируемся, ждём отправки
  end
end
```

Проблема: 10,000 клиентов = 10,000 потоков = гигабайты/десятки гигабайт памяти только на стеки (зависит от настроек ОС). Плюс накладные расходы на переключение контекста в ядре ОС.

Решение — **I/O мультиплексирование**: один системный вызов спрашивает ядро "какие из этих 10,000 сокетов готовы к чтению/записи?"

#### 8.2 I/O мультиплексирование: select → poll → epoll/kqueue

```text
select (1983)     →    poll (1986)    →    epoll/kqueue (2002+)
     ↓                      ↓                      ↓
O(n) каждый раз      O(n) каждый раз       O(1) для событий
лимит ~1024 fd       нет лимита            нет лимита
копирует туда-сюда   копирует туда-сюда    ядро хранит состояние
```

**epoll** (Linux) и **kqueue** (macOS/BSD) — современные механизмы:

```text
epoll_create(...)
epoll_ctl(epfd, ADD, fd, events)
epoll_wait(epfd, ..., timeout)  # блокируется и возвращает только готовые fd
```

Ключевое отличие: ядро само отслеживает состояние и возвращает только готовые дескрипторы, не перебирая все 10,000.

#### 8.3 Puma: Reactor + Thread Pool + Forked Workers

Puma использует **гибридную архитектуру** в clustered mode:

```text
                    ┌─────────────────────────────────────────┐
                    │            Master Process               │
                    │  - не обрабатывает запросы              │
                    │  - roles: spawn workers, reap dead workers│
                    └─────────────────┬───────────────────────┘
                                      │ fork()
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
    ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
    │    Worker 0     │     │    Worker 1     │     │    Worker 2     │
    │   (процесс)     │     │   (процесс)     │     │   (процесс)     │
    │                 │     │                 │     │                 │
    │  ┌───────────┐  │     │  ┌───────────┐  │     │  ┌───────────┐  │
    │  │  Reactor  │  │     │  │  Reactor  │  │     │  │  Reactor  │  │
    │  │  Thread   │  │     │  │  Thread   │  │     │  │  Thread   │  │
    │  └─────┬─────┘  │     │  └─────┬─────┘  │     │  └─────┬─────┘  │
    │        │        │     │        │        │     │        │        │
    │        ▼        │     │        ▼        │     │        ▼        │
    │  ┌───────────┐  │     │  ┌───────────┐  │     │  ┌───────────┐  │
    │  │Thread Pool│  │     │  │Thread Pool│  │     │  │Thread Pool│  │
    │  │ 5 threads │  │     │  │ 5 threads │  │     │  │ 5 threads │  │
    │  └───────────┘  │     │  └───────────┘  │     │  └───────────┘  │
    │                 │     │                 │     │                 │
    │  свой GVL       │     │  свой GVL       │     │  свой GVL       │
    └─────────────────┘     └─────────────────┘     └─────────────────┘
```

**Три уровня конкурентности:**

1. **Workers (процессы)** — настоящий параллелизм CPU, каждый со своим GVL
2. **Reactor thread** — I/O мультиплексирование через nio4r (обёртка над epoll/kqueue)
3. **Thread pool** — конкурентность для выполнения Ruby-кода приложения

#### 8.4 Reactor в Puma: разделение ответственности

```text
┌────────────────────────────────────────────────────────────────────┐
│                         Puma Worker                                │
│                                                                    │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │                     Reactor Thread                           │  │
│  │                                                              │  │
│  │  Использует nio4r (Ruby обёртка над epoll/kqueue)            │  │
│  │                                                              │  │
│  │  Задачи:                                                     │  │
│  │  - accept() новых TCP соединений                             │  │
│  │  - читать HTTP request (может быть медленно — slow client!)  │  │
│  │  - парсить HTTP headers/body                                 │  │
│  │  - НЕ выполняет Ruby app код                                 │  │
│  │                                                              │  │
│  └────────────────────────────┬─────────────────────────────────┘  │
│                               │                                    │
│                    request полностью прочитан                      │
│                    кладём в очередь                                │
│                               │                                    │
│                               ▼                                    │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │                     Thread Pool                              │  │
│  │                                                              │  │
│  │  Задачи:                                                     │  │
│  │  - взять request из очереди                                  │  │
│  │  - вызвать app.call(env) — тут выполняется Rails             │  │
│  │  - отдать response                                           │  │
│  │                                                              │  │
│  │  Thread 1: [────── app.call(env) ──────]                     │  │
│  │  Thread 2: [── app.call(env) ──]                             │  │
│  │  Thread 3: [waiting...]                                      │  │
│  │                                                              │  │
│  └──────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────────┘
```

**Ключевая идея:** Reactor защищает Thread Pool от slow clients.

#### 8.5 Жизненный цикл запроса в Puma

```text
1. TCP соединение приходит на сокет
              ↓
2. Reactor thread: accept() — принимает соединение
              ↓
3. Reactor: регистрирует сокет в selector (epoll/kqueue)
              ↓
4. Reactor: ждёт готовности через select() — НЕ блокирует другие соединения
              ↓
5. Reactor: читает данные (non-blocking read)
   - если данные неполные → остаёмся в selector, ждём ещё
   - если клиент медленный (3G) → reactor обслуживает других, пока ждёт
              ↓
6. Reactor: HTTP request полный, парсинг завершён
              ↓
7. Reactor: снимает сокет с мониторинга, кладёт request в очередь Thread Pool
              ↓
8. Worker thread: берёт request из очереди
              ↓
9. Worker thread: вызывает app.call(env) — тут Rails код
              ↓
10. Worker thread: получает [status, headers, body]
              ↓
11. Worker thread: отправляет response клиенту
              ↓
12. Worker thread: свободен для следующего request
```

**Без Reactor (наивный подход):**
```text
Thread: [accept]──[read 5 sec от 3G клиента]──[Rails 50ms]──[write 5 sec]
        └───────────────── thread занят ~10 секунд ─────────────────────┘
```

**С Reactor:**
```text
Reactor: [accept]──[ждём в epoll, обслуживаем других]──[read готов]──▶ Thread Pool
Thread:  ──────────────────────────────────────────────[Rails 50ms]──[write]
         └── thread занят только на время обработки ──┘
```

#### 8.6 Конфигурация Puma и её смысл

```ruby
# config/puma.rb

# Workers = количество форкнутых процессов
# Правило: примерно равно количеству CPU cores
# Каждый worker = отдельный процесс = отдельный GVL = реальный параллелизм
workers ENV.fetch("WEB_CONCURRENCY") { 2 }

# Threads = размер thread pool в каждом worker
# min, max — пул может расти динамически
# Типичные значения: 5-16 для I/O-bound приложений (Rails)
threads_count = ENV.fetch("RAILS_MAX_THREADS") { 5 }
threads threads_count, threads_count

# Загрузить приложение ДО fork — экономия памяти через Copy-on-Write
preload_app!

# Колбэки для управления ресурсами при fork
on_worker_boot do
  ActiveRecord::Base.establish_connection  # новый connection pool
end
```

**Почему workers = CPU cores?**

Больше workers чем ядер → context switching overhead, workers конкурируют за CPU.
Меньше workers → не используем все ядра.

**Почему threads = 5 (типично)?**

Это не про параллелизм CPU (GVL не даёт), а про **I/O конкурентность**:

```text
Thread 1: [request]──[ждём PostgreSQL]────────────[обработка]──[response]
Thread 2:     [request]──[ждём PostgreSQL]──[обработка]──[response]
Thread 3:         [request]────[ждём Redis]────[обработка]──[response]
```

Пока thread 1 ждёт БД → GVL свободен → threads 2, 3 могут работать.

**Связь с database pool:**

```yaml
# config/database.yml
production:
  pool: <%= ENV.fetch("RAILS_MAX_THREADS") { 5 } %>
```

`pool size >= threads per worker`, иначе threads будут ждать соединений друг у друга.

#### 8.7 Falcon: Fiber Scheduler + Event Loop

Falcon использует принципиально другой подход — **один поток, много fibers**:

```text
┌─────────────────────────────────────────────────────────────────────┐
│                         Falcon Process                              │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │                    Event Loop Thread                          │  │
│  │                                                               │  │
│  │   ┌─────────────────────────────────────────────────────┐     │  │
│  │   │              Fiber Scheduler                        │     │  │
│  │   │         (io-event: epoll/kqueue/select)             │     │  │
│  │   │                                                     │     │  │
│  │   │  Fiber 1: [Rails code]──yield──[Rails code]         │     │  │
│  │   │  Fiber 2: ──────[waiting I/O]──────[Rails code]     │     │  │
│  │   │  Fiber 3: [Rails code]──[waiting I/O]───────        │     │  │
│  │   │  ...                                                │     │  │
│  │   │  Fiber N: ────────[waiting I/O]─────────────        │     │  │
│  │   │                                                     │     │  │
│  │   │  Все fibers на одном потоке                         │     │  │
│  │   └─────────────────────────────────────────────────────┘     │  │
│  │                                                               │  │
│  └───────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
```

**Стек библиотек Falcon:**

```text
┌─────────────────────────────────────────┐
│              Falcon                      │  ← HTTP-сервер
├─────────────────────────────────────────┤
│         async / async-http               │  ← async runtime
├─────────────────────────────────────────┤
│            io-event                      │  ← Fiber Scheduler implementation
├─────────────────────────────────────────┤
│  epoll (Linux) / kqueue (macOS/BSD)      │  ← системный механизм
│  select (fallback)                       │
└─────────────────────────────────────────┘
```

#### 8.8 Как Fiber Scheduler работает в Falcon

Когда Fiber делает blocking операцию (`sleep`, `IO#read`, `Net::HTTP.get`):

```ruby
# Внутри Falcon request handler (упрощённо)
Fiber.schedule do
  # 1. Fiber выполняет код
  data = socket.read  # ← blocking операция
  
  # Что происходит под капотом:
  # 2. Fiber Scheduler перехватывает read()
  # 3. Переводит сокет в non-blocking режим
  # 4. Регистрирует интерес к событию в epoll/kqueue
  # 5. Fiber УСТУПАЕТ управление (yield)
  # 6. Event loop продолжает другие fibers
  # 7. Когда данные готовы — epoll сигнализирует
  # 8. Scheduler ВОЗОБНОВЛЯЕТ этот fiber
  # 9. read() возвращает данные
  
  process(data)
end
```

Это прозрачно для кода — тот же `socket.read`, но не блокирует поток.

#### 8.9 Сравнение архитектур

| Аспект | Puma | Falcon |
|--------|------|--------|
| Модель конкурентности | Процессы + Threads | Fibers на одном потоке |
| I/O мультиплексирование | nio4r (Reactor thread) | io-event (Fiber Scheduler) |
| Память на соединение | выше (threads) | ниже (fibers) |
| CPU параллелизм | Workers (процессы) | Несколько процессов (опционально) |
| GVL impact | Thread pool ограничен GVL | Один поток, GVL не мешает |
| Совместимость с гемами | Высокая (blocking I/O OK) | Требует async-совместимых гемов |
| Зрелость | Production-ready, широко используется | Менее распространён |

#### 8.10 Когда что выбирать

**Puma подходит когда:**
- Стандартное Rails приложение
- Используются гемы с blocking I/O (большинство)
- Нужна проверенная, стабильная архитектура
- Команда не хочет думать об async

**Falcon подходит когда:**
- Много одновременных соединений (WebSockets, SSE, long polling)
- I/O-intensive приложение с async-совместимыми гемами
- Хочется минимизировать потребление памяти
- Готовы к более новой, менее распространённой технологии

#### 8.11 Практический пример: Falcon

```ruby
# Gemfile
gem 'falcon'
gem 'async-http'  # async HTTP клиент

# config.ru
run lambda { |env|
  # Этот код выполняется в Fiber
  # I/O операции не блокируют — переключаются через scheduler
  
  [200, {'Content-Type' => 'text/plain'}, ['Hello from Falcon!']]
}
```

```bash
falcon serve --bind http://localhost:9292

# Falcon автоматически:
# 1. Устанавливает Fiber Scheduler (io-event)
# 2. Каждый request = отдельный Fiber
# 3. I/O операции yield'ят в event loop
```

#### 8.12 Ключевое различие в ментальной модели

**Puma:** "У нас пул потоков, каждый поток обрабатывает один request за раз. Reactor защищает от slow clients. Параллелизм через fork."

**Falcon:** "У нас один event loop с тысячами fibers. Каждый fiber — это request. Когда fiber ждёт I/O, другие работают. Это как async/await."

Оба используют I/O мультиплексирование (epoll/kqueue), но на разных уровнях:
- Puma: Reactor thread отдельно от worker threads
- Falcon: Fiber Scheduler интегрирован в Ruby runtime

---

Process, Ractor, Thread, Fiber — каждый инструмент имеет свои компромиссы. Выбор зависит от того, где программа проводит время и какой уровень изоляции нужен.

## Карта компромиссов: Process/Ractor/Thread/Fiber

| Инструмент | Даёт | Цена |
| --- | --- | --- |
| `Process` | параллелизм + сильная изоляция | IPC/память/стоимость границ |
| `Ractor` | параллелизм Ruby-кода + изоляция объектов | протокол сообщений, shareable/copy/move |
| `Thread` | конкурентность в одном процессе | shared-state протоколы, GVL для Ruby CPU в MRI |
| `Fiber` | дешёвые кооперативные задачи | нужен scheduler для I/O, риск starvation |

Несколько инвариантов, которые помогают не путаться:

- В MRI `Thread` не даёт параллелизма Ruby‑кода внутри одного ractor: потоки по очереди держат GVL. Смысл threads чаще в I/O‑ожидании и в блокирующих внешних вызовах, где GVL отпускается.
- `Fiber` перекрывает ожидание только там, где рантайм/библиотека умеют отдавать управление scheduler'у. Блокирующий вызов без интеграции со scheduler блокирует весь thread.
- CPU‑параллелизм для Ruby‑кода в MRI достигается через `Process` или `Ractor` (между ними разница в изоляции и цене обмена данными).
