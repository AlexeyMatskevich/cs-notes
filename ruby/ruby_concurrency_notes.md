# Конкурентность, параллелизм и асинхронность в Ruby

**Предпосылки:** читатель понимает что такое переменная, функция, условие, цикл. Знает что программа выполняется процессором, данные хранятся в памяти.

# Часть I: Общая теория конкурентности, параллелизма и async

## 1. Две причины, почему программа «не делает работу»

Если убрать маркетинговые термины, у программы есть два базовых режима:

1) она **исполняет инструкции на CPU** (полезная работа);
2) она **ждёт** (не делает полезной работы).

Ждать можно по двум фундаментальным причинам:

**(A) Ждём внешнее событие (I/O).** Сеть, диск, таймер, процесс-ребёнок, DNS — всё это может занимать миллисекунды и секунды. CPU в этот момент свободен, но поток исполнения «спит».

**(B) Ждём доступ к общим данным.** Когда у нас несколько потоков/задач, они неизбежно начинают делить что-то общее: память, очередь, мьютекс, пул соединений. Тогда часть времени уходит на ожидание синхронизации.

Конкурентность и асинхронность — это способы сделать так, чтобы пока одна часть работы ждёт, другая могла продолжать прогресс.

## 2. Термины: конкурентность, параллелизм, вытеснение, кооперация

**Задача (task)** — кусок работы, который можно рассматривать отдельно: «обработать запрос», «прочитать файл», «посчитать хэш», «подождать таймер».

**Конкурентность (concurrency)** — способность держать *несколько задач в прогрессе одновременно*: сегодня эта задача исполняется, через миллисекунду — другая, потом опять первая. Конкурентность возможна и на одном ядре.

**Параллелизм (parallelism)** — *буквально одновременное* выполнение задач: два независимых потока инструкций реально идут в один момент времени на разных ядрах (или SMT — Simultaneous Multithreading, технология типа Intel Hyper-Threading, позволяющая одному ядру выполнять несколько потоков).

Мини-карта во времени:

```text
Конкурентно (1 core):   A A A A A
                        B B B B B
                        └─ чередуются во времени

Параллельно (2 cores):  core0: A A A A A
                        core1: B B B B B
```

Чтобы конкурентность работала, выполнение задачи должно быть **прерываемым**: её можно остановить и позже продолжить.

Есть два способа «прерывать»:

**Вытесняющая (preemptive) многозадачность.** Планировщик (обычно ОС) может остановить поток в любой момент (по таймеру или событию) и отдать CPU другому. Это хорошо для справедливости, но усложняет правильность: если поток может быть остановлен «везде», доступ к общим данным надо синхронизировать.

**Кооперативная (cooperative) многозадачность.** Задача сама явно отдаёт управление в известных местах (yield/await). Это упрощает рассуждения (точки переключения видны), но есть риск starvation: если задача никогда не уступает, остальные «умирают от голода».

## 3. ОС: процессы и системные потоки как фундамент параллелизма

Современные ОС планируют выполнение **системных потоков (OS threads)** вытесняюще. У потока есть стек, регистры и статус, и ОС может переключать его на другое ядро или приостанавливать/возобновлять.

**POSIX (Portable Operating System Interface)** — это стандарт API для Unix-подобных ОС. Часть этого стандарта — **pthread (POSIX threads)** — определяет интерфейс для работы с системными потоками (OS threads): `pthread_create`, `pthread_mutex_lock`, `pthread_cond_wait` и т.д. Это не отдельный вид потоков, а стандартизированный API для создания и управления теми самыми системными потоками которые планирует ОС. Стандарт описывает *что* функции делают, а каждая ОС реализует *как*: Linux использует futex, macOS — Mach threads, FreeBSD — `_umtx_op`. Ruby использует pthread API для создания потоков и синхронизации.

Отсюда две базовые единицы изоляции:

**Процесс (process)** — отдельное адресное пространство. Изоляция сильная: нельзя случайно «поделить память»; падение одного процесса обычно не рушит другой. Цена — дорогостоящие границы: IPC (Inter-Process Communication — общение между процессами через пайпы, сокеты, shared memory, файлы), копирование данных, отдельные кучи/GC, больше памяти.

**Поток (thread)** — несколько потоков в одном процессе делят память. Это позволяет дешёвое общение через общие структуры данных, но создаёт главную проблему конкурентности: **разделяемая изменяемая память (shared mutable state)** порождает гонки и необходимость синхронизации.

**Системный вызов (syscall)** — способ программы попросить ядро ОС сделать что-то привилегированное: создать поток, прочитать файл, отправить данные в сеть, выделить память. Программа не может сама напрямую работать с железом или ресурсами ОС — она должна "попросить" ядро через syscall.

```
Твоя программа (userspace)
        │
        │ syscall: read(fd, buf, size)
        ▼
┌─────────────────────────────┐
│       Ядро ОС (kernel)      │
│  - проверяет права          │
│  - работает с железом       │
│  - копирует данные          │
└─────────────────────────────┘
        │
        ▼
Результат возвращается в программу
```

Syscall — дорогая операция (переключение контекста user→kernel→user), поэтому многие оптимизации направлены на то чтобы делать syscall'ы реже. Например, futex (механизм эффективных блокировок в Linux, разберём позже) делает syscall только при конкуренции, а не при каждом захвате mutex.

Практический эффект для приложений почти всегда выражается через две метрики:

- **latency** (задержки): как быстро отвечает один запрос/операция;
- **throughput** (пропускная способность): сколько запросов/операций в секунду.

Вытесняющая модель ОС помогает, чтобы система оставалась живой даже если один поток «завис» в бесконечном цикле: CPU у него отберут. Но из-за вытеснения мы не можем «по-человечески» указать, где возможна пауза: она возможна везде.

## 4. Почему shared-memory многопоточность сложная: три класса проблем

Когда два потока пишут/читают одну и ту же память без синхронизации, возникают три разных класса проблем:

### 4.1 Torn reads/writes (разорванные операции)

**Что это:** Чтение "половины старого + половины нового" значения, когда запись не атомарна.

**Актуально для Ruby? НЕТ.** На x86/x86_64 все выровненные операции до 8 байт атомарны, а в Ruby ты работаешь с указателями на объекты (64 бита). Плюс GVL в MRI, плюс гарантии JVM в JRuby. Это теоретическая проблема для понимания многопоточности, но не практическая для Ruby.

### 4.2 Race conditions на уровне логики

Даже если каждая отдельная операция атомарна, **последовательность операций** — нет. Классический пример — проверка и изменение:

```ruby
# Thread 1                    # Thread 2
if @counter < 100             if @counter < 100
  @counter += 1                 @counter += 1
end                           end
```

Между проверкой `@counter < 100` и выполнением `@counter += 1` может вклиниться другой тред. Более того, `@counter += 1` — это несколько операций: read, increment, write.

Это проблема атомарности составных операций — нужна «критическая секция», которую никто не прервёт.

#### Как GVL переключается в Ruby

В Ruby Thread есть **два уровня** переключения:

**Уровень 1: ОС переключает pthread (вытесняющее)**
- Ruby Thread = pthread (системный поток)
- ОС может вытеснить pthread в *любой* момент — посреди любой C-инструкции
- Но! Если вытесненный pthread держит GVL, другой Ruby-тред не может выполнять Ruby-код — он заблокирован на GVL

**Уровень 2: GVL переключает право выполнять Ruby-код (в контролируемых точках)**
- GVL — это mutex, не планировщик
- Есть таймер (~100ms): если тред держит GVL слишком долго, VM ставит флаг "пора отдать"
- Тред проверяет флаг **между инструкциями байткода** и отдаёт GVL
- Переключение GVL происходит в безопасных точках, не посреди байткод-инструкции

**Байткод** — промежуточное представление кода. Ruby компилирует твой `.rb` файл в байткод (инструкции YARV VM), который потом выполняет виртуальная машина. Одна строка Ruby может стать несколькими байткод-инструкциями.

```
ОС (вытесняющее):        pthread A ──вытеснен──► pthread B (ждёт GVL) ──не может работать──► ...
                                                 └── GVL занят, просто ждёт и засыпает

GVL (контролируемые точки): Thread A выполняет Ruby ──таймер 100ms──► проверяет флаг 
                                                                      между инструкциями
                                                                          │
                                                            ──отдаёт GVL──► Thread B получает GVL
```

#### Почему race condition возможен даже с GVL

Переключение GVL происходит между **байткод-инструкциями**, а не между Ruby-выражениями. Одно Ruby-выражение — несколько инструкций:

```ruby
# Выглядит как одна операция:
counter += 1

# Но это несколько байткод-инструкций:
# 1. getlocal counter    (read)
# 2. putobject 1         
# 3. opt_plus            (add)
# 4. setlocal counter    (write)
# GVL может переключиться между любыми из них!

# Thread 1:                    # Thread 2:
# getlocal counter (= 5)       
#    --- GVL переключился ---   
#                              # getlocal counter (= 5)
#                              # opt_plus (= 6)
#                              # setlocal counter (= 6)
#    --- GVL вернулся ---
# opt_plus (= 6)               
# setlocal counter (= 6)       # Результат: 6, а не 7!
```

Это не классическое вытеснение "где угодно" — GVL переключается в контролируемых точках. Но этих точек много (между каждой байткод-инструкцией), и Ruby-программист не видит их напрямую.

### 4.3 Memory ordering / visibility (видимость памяти между потоками)

Это **другая** проблема, не связанная с race conditions. Она существует из-за многоядерности CPU:

```
         Thread 1 (CPU 0)              Thread 2 (CPU 1)
              ↓                             ↓
        ┌──────────┐                  ┌──────────┐
        │ L1 Cache │                  │ L1 Cache │
        │ data=42  │                  │ data=??? │ ← старое значение!
        │ ready=T  │                  │ ready=F  │
        └──────────┘                  └──────────┘
              ↓                             ↓
        ─────────────────────────────────────────────
                          RAM
                     (когда-нибудь синхронизируется)
```

Thread 1 записал `data = 42`, но значение застряло в кеше CPU 0. Thread 2 на CPU 1 читает из своего кеша и видит старое значение. **Записи одного ядра не сразу видны другому.**

**В MRI с GVL это решено автоматически:** GVL реализован через pthread_mutex, а mutex по стандарту включает memory barriers. При освобождении GVL — все записи "сбрасываются" (release barrier). При захвате GVL — видны все записи до освобождения (acquire barrier).

В JRuby/TruffleRuby (без GVL) visibility — реальная проблема, нужна явная синхронизация.

#### Reordering: ещё один источник проблем

Помимо кешей, CPU и компилятор могут **переставлять инструкции** ради производительности. Рассмотрим C-код:

```c
// Thread 1
data = 42;        // (1) запись данных
ready = true;     // (2) сигнал "готово"

// Thread 2
if (ready) {      // (3) проверка сигнала
  print(data);    // (4) чтение данных
}
```

Интуиция говорит: если Thread 2 видит `ready == true`, значит Thread 1 уже записал `data = 42`. **Но в C/C++ без барьеров это не гарантировано!**

Компилятор может переставить (1) и (2), потому что в однопоточном контексте это не меняет результат. CPU может выполнить (2) раньше (1) из-за out-of-order execution или буферизации записей (store buffer). Thread 2 может увидеть `ready = true`, но `data` всё ещё равно мусору.

**Почему в Ruby это не проблема?** Ruby VM выполняет байткод последовательно, инструкция за инструкцией. GVL гарантирует, что в момент переключения на другой тред все записи «видны». При захвате/освобождении GVL происходят memory barriers. Поэтому Ruby-программисту не нужно думать о memory ordering — GVL решает эту проблему автоматически.

Именно для многопоточного C-кода нужны **memory barriers (барьеры памяти)** — они запрещают определённые перестановки. Барьер — это как «забор» между инструкциями: инструкции до забора не могут «перепрыгнуть» через него и оказаться после.

На x86_64 модель памяти относительно строгая (Total Store Order), большинство «опасных» перестановок запрещены по умолчанию. На ARM память упорядочена слабее, и там барьеры нужны чаще. Это объясняет, почему C-код может работать на x86 и ломаться на ARM — x86 «прощает» некоторые ошибки синхронизации.

### 4.4 Синхронизационные примитивы

Отсюда появляются примитивы синхронизации:

- **Mutex/RwLock**: делают критическую секцию взаимно исключающей.
- **Condvar/Semaphore**: дают ожидание условий и сигнализацию.
- **Channels/Queues**: структурируют передачу данных как сообщения.
- **Atomics**: позволяют строить протоколы без блокировок, но требуют аккуратной модели памяти.

### 4.5 POSIX threads (pthread) — стандартные примитивы

POSIX определяет набор функций для многопоточности. Основные примитивы:

**Потоки:**
- `pthread_create` — создать новый поток (именно это вызывает Ruby при `Thread.new`)
- `pthread_join` — дождаться завершения потока

**Mutex (взаимное исключение):**
- `pthread_mutex_lock` — захватить mutex (заблокируется если занят)
- `pthread_mutex_unlock` — освободить mutex
- `pthread_mutex_trylock` — попробовать захватить без блокировки

**Condition variables (условные переменные):**
- `pthread_cond_wait` — атомарно освободить mutex и заснуть, ждать сигнала
- `pthread_cond_signal` — разбудить один поток, ждущий на condvar
- `pthread_cond_broadcast` — разбудить все потоки

Condition variables используются по паттерну «ждать пока условие станет истинным»:

```
pthread_mutex_lock(&mutex);
while (!condition_is_true) {           // while, не if — из-за spurious wakeups
    pthread_cond_wait(&cond, &mutex);  // освобождает mutex, спит, при пробуждении снова захватывает
}
// условие истинно, mutex захвачен — делаем работу
pthread_mutex_unlock(&mutex);
```

Почему `while`, а не `if`? POSIX разрешает **spurious wakeups** — поток может проснуться без явного signal. Также между signal и пробуждением другой поток может изменить состояние.

**Read-write locks:**
- `pthread_rwlock_rdlock` — захватить на чтение (несколько читателей одновременно)
- `pthread_rwlock_wrlock` — захватить на запись (эксклюзивно)

GVL в Ruby реализован через `pthread_mutex_t` + `pthread_cond_t`.

## 5. Lock-based vs Lock-free: два подхода к синхронизации

Есть два фундаментально разных подхода к многопоточным структурам данных.

### 5.1 Lock-based (на основе блокировок)

Используем mutex для защиты критических секций. Просто в реализации, но потоки могут ждать друг друга:

```ruby
@mutex.synchronize do
  @counter += 1
end
```

**Как устроен mutex внутри?**

Mutex — это переменная-флаг (например, 0 = свободен, 1 = занят) плюс механизм ожидания. Проблема: как атомарно проверить флаг и установить его?

Обычная последовательность `if (flag == 0) flag = 1` не работает — между проверкой и записью другой поток может вклиниться. Нужна атомарная операция, которая делает «проверку и запись» за один шаг.

**Атомарные операции CPU:**

Процессоры предоставляют специальные инструкции. Например, **compare-and-swap (CAS)** делает следующее атомарно:
1. Читает текущее значение по адресу
2. Сравнивает с ожидаемым
3. Если совпало — записывает новое значение и возвращает «успех»
4. Если не совпало — ничего не делает и возвращает «неудача»

На x86 это инструкция `CMPXCHG` (с префиксом `LOCK`). Пример простейшего захвата:

```
Поток хочет захватить mutex (ожидает 0, хочет записать 1):
  CAS(mutex, expected=0, new=1)
    → если mutex был 0: теперь 1, поток захватил лок
    → если mutex был 1: ничего не изменилось, кто-то другой держит лок
```

**Что делать если mutex занят?**

Можно крутиться в цикле (spinlock) — плохо, тратим CPU. Лучше — заснуть и разбудиться когда mutex освободится.

**Futex (Fast Userspace Mutex)** — механизм Linux для эффективного засыпания. Это системный вызов с двумя основными операциями:

`FUTEX_WAIT(адрес, ожидаемое_значение)`:
1. Атомарно проверяет: значение по адресу равно ожидаемому?
2. Если да — поток засыпает (переходит в состояние SLEEPING, убирается из очереди планировщика)
3. Если нет — немедленно возвращается (значит mutex уже освободили)

`FUTEX_WAKE(адрес, сколько_разбудить)`:
1. Будит указанное количество потоков, ждущих на этом адресе

Атомарность «проверки и засыпания» критична — иначе возможна гонка: проверили (mutex занят), кто-то освободил mutex и вызвал wake (никого нет в очереди), мы заснули навечно.

**Типичная реализация pthread_mutex:**

```
lock():
  if CAS(mutex, 0, 1) == success:   # Быстрый путь — никого нет
    return                           # Захватили без syscall!
  
  # Медленный путь — есть конкуренция
  loop:
    mutex = 2                        # Пометить "есть ожидающие"
    FUTEX_WAIT(mutex, 2)             # Заснуть
    if CAS(mutex, 0, 2) == success:  # После пробуждения — попробовать снова
      return

unlock():
  old = exchange(mutex, 0)           # Освободить
  if old == 2:                       # Если были ожидающие
    FUTEX_WAKE(mutex, 1)             # Разбудить одного
```

**Ключевой момент:** когда mutex свободен — захват полностью в userspace, один атомарный CAS, никакого системного вызова. Syscall нужен только при конкуренции (несколько потоков хотят mutex одновременно).

**Спящие потоки не тратят CPU.** Поток в состоянии SLEEPING убран из run queue планировщика. Ядро просто не даёт ему CPU. Можно иметь тысячи спящих потоков — они потребляют только память (стек ~8KB каждый).

### 5.2 Lock-free (без блокировок)

Вместо mutex используем только атомарные операции напрямую. Нет засыпания — потоки всегда делают прогресс (хотя могут «крутиться» при высокой конкуренции):

```rust
// Rust: атомарный инкремент счётчика
counter.fetch_add(1, Ordering::Relaxed);
```

Это одна CPU-инструкция `LOCK XADD` — атомарно прибавляет 1 и возвращает старое значение. Никакого mutex, никакого ожидания других потоков.

Lock-free структуры данных сложнее в реализации. Например, lock-free очередь требует аккуратной работы с указателями через CAS, чтобы несколько потоков могли одновременно добавлять/извлекать элементы без блокировок.

### 5.3 Разница в стоимости

```
Атомарный инкремент:    [одна инструкция LOCK XADD]
                        └── ~5-50 наносекунд (зависит от конкуренции за cache line)

Mutex-защищённый код:   [lock] → [твой код] → [unlock]
                        └── минимум ~20-100 нс без конкуренции
                            микросекунды при конкуренции (futex wake/wait)
```

Для простых операций типа счётчика — mutex это перебор. Разница может быть в 10-100 раз.

### 5.4 Где какой язык на спектре

```
Lock-free первичен              Lock-based первичен
←───────────────────────────────────────────────────→

Erlang    Rust     Java        Go         Ruby    Python
(actors,  (atomics (AtomicXxx, (channels, (GVL,   (GIL,
 no       + Mutex  concurrent  mutex,     Mutex)  Lock)
 shared   выбор)   collections атомики)
 state)            + locks)
```

**Ruby — это lock-based система.** Сам GVL — это mutex. Весь Ruby-код выполняется «под локом». Ruby не даёт прямого доступа к атомикам из языка.

Для lock-free структур в Ruby используется гем `concurrent-ruby`, который реализует атомарные примитивы через C-расширения:

```ruby
require 'concurrent-ruby'

counter = Concurrent::AtomicFixnum.new(0)
counter.increment  # Атомарно, без mutex

ref = Concurrent::AtomicReference.new({name: "Alice"})
ref.compare_and_set(old_value, new_value)  # CAS операция

map = Concurrent::Map.new  # Thread-safe hash без глобального лока
```

## 6. Асинхронность как реакция на I/O-ожидание

### 6.1 Механизмы мультиплексирования I/O: epoll, kqueue, IOCP

Когда программе нужно ждать события на множестве ресурсов (сокеты, файлы, таймеры), ОС предоставляет специальные механизмы. Без них пришлось бы либо создавать по потоку на каждый ресурс (дорого), либо в цикле опрашивать все ресурсы (неэффективно — busy waiting).

**Файловый дескриптор (fd)** — целое число, которое ядро присваивает открытому ресурсу. Когда программа открывает файл, сокет или pipe, ядро возвращает fd. Все операции с ресурсом идут через этот номер: `read(fd, ...)`, `write(fd, ...)`, `close(fd)`.

Механизмы мультиплексирования позволяют одним вызовом ждать события на множестве fd:

**epoll (Linux)** — масштабируемый механизм для Linux. Работает в три шага:
1. `epoll_create()` — создать экземпляр epoll
2. `epoll_ctl(epfd, ADD, fd, events)` — зарегистрировать интерес к событиям на fd (чтение готово, запись готова, ошибка)
3. `epoll_wait(epfd, events, timeout)` — заблокироваться пока хотя бы один fd не станет готов

```
                    ┌─────────────────────────────────┐
                    │         epoll instance          │
                    │                                 │
   epoll_ctl ADD ──►│  fd=5 (socket): READ            │
   epoll_ctl ADD ──►│  fd=7 (socket): READ, WRITE     │
   epoll_ctl ADD ──►│  fd=9 (timer):  READ            │
                    │                                 │
                    └─────────────────────────────────┘
                                    │
                                    │ epoll_wait()
                                    ▼
                    поток спит, ядро разбудит когда
                    любой из fd станет готов
```

**kqueue (BSD, macOS)** — аналог epoll для BSD-систем. Концептуально похож: регистрируешь интерес к событиям, потом ждёшь. Отличия в API и возможностях (kqueue умеет следить не только за fd, но и за файловой системой, процессами, сигналами).

**IOCP (Windows)** — I/O Completion Ports. Другая модель: вместо "сообщи когда готов читать" используется "начни читать, сообщи когда закончишь" (completion-based vs readiness-based). Но идея та же — один поток эффективно обслуживает много операций.

Все три механизма решают одну задачу: **позволить одному потоку эффективно ждать события на тысячах ресурсов**. Без них высоконагруженные серверы были бы невозможны — потоки слишком дорогие для "по потоку на соединение".

### 6.2 Два способа ждать I/O

**Блокирующий I/O** — вызываешь `read(fd)`, поток блокируется в ядре пока данные не придут. Один поток ждёт один ресурс.

**Мультиплексированный I/O** — регистрируешь интерес к множеству дескрипторов, потом один вызов (epoll_wait/kevent) ждёт события на любом из них. Один поток ждёт много ресурсов.

```
Блокирующий I/O:
Thread 1: read(socket_A)  → спит на socket_A
Thread 2: read(socket_B)  → спит на socket_B
Thread 3: read(socket_C)  → спит на socket_C
// Нужно N потоков для N соединений

Мультиплексированный I/O:
Thread 1: epoll_wait([socket_A, socket_B, socket_C])
          → спит, просыпается когда ЛЮБОЙ готов
// Один поток для N соединений
```

### 6.3 Проблема: блокирующий I/O не масштабируется

Самый простой способ обработки соединений — «по потоку на соединение». Работает пока соединений мало. Когда соединений тысячи:

- стеки потоков занимают память (~8KB на поток × 10000 = 80MB только на стеки);
- планировщик ОС тратит время на переключения между тысячами потоков;
- увеличиваются хвостовые задержки (tail latency — задержки в "хвосте" распределения, например 99-й перцентиль).

### 6.4 Решение: event loop на базе мультиплексированного I/O

Идея async:

1. Перевести I/O в **неблокирующий режим** — операции возвращают «пока не готово» вместо блокировки
2. **Event loop (реактор)** — один поток ждёт события на множестве дескрипторов через epoll/kqueue
3. **Исполнитель** — возобновляет задачи когда их событие готово

### 6.5 Ruby по умолчанию — блокирующий I/O

Когда ты пишешь обычный Ruby-код:

```ruby
data = socket.read(1024)
```

Это простой syscall `read()`, который блокирует поток в ядре до прихода данных. Никакого epoll здесь нет. Ruby отпускает GVL на время этого ожидания, чтобы другие Ruby-потоки могли работать.

epoll появляется когда ты явно используешь async-подход: Fiber Scheduler (Ruby 3+), гем Async, Falcon. Они реализуют event loop поверх epoll/kqueue.

Ключевой компромисс async — кооперативность: переключение происходит в точках `.await` (или в местах, где runtime «перехватил» блокирующую операцию). Поэтому CPU-тяжёлая задача без yield/await способна «заморозить» прогресс остальных задач на том же потоке.

## 7. Акторная модель как реакция на shared mutable state

Если главная боль многопоточности — разделяемая память, то альтернативная идея звучит так: **не делить память, а делиться сообщениями**.

В акторной модели:

- актор хранит своё состояние «внутри себя»;
- другой актор не может напрямую менять это состояние;
- взаимодействие происходит через **почтовые ящики (mailboxes)** и сообщения.

Это сдвигает сложность:

- меньше гонок на общих данных, потому что общих данных меньше;
- больше внимания к протоколам сообщений, очередям, backpressure (механизм замедления производителя когда потребитель не успевает обрабатывать) и стоимости копирования.

Ruby `Ractor` — это именно актороподобная абстракция: параллелизм достигается через изоляцию и обмен сообщениями.

# Часть II: Модель конкурентности в Ruby (MRI/CRuby)

## 1. Слои исполнения: `Process → Ractor → Thread → Fiber`

В MRI удобно держать в голове такую вложенность:

```text
Process (адресное пространство, ОС)
  Ractor (изолированное состояние + per-ractor GVL)
    Thread (native thread, вытесняется ОС)
      Fiber (кооперативная корутина, точки переключения в коде/рантайме)
```

**Корутина** — функция, которая умеет приостановиться (yield) и продолжиться с того же места, сохраняя своё состояние между вызовами. В отличие от обычной функции, корутина не "забывает" где остановилась.

Эта схема отвечает на два вопроса:

1) **где возможен параллелизм CPU** (между процессами, и между ractors);
2) **где происходит переключение задач** (ОС между thread'ами; Ruby-код кооперативно между fibers).

## 2. Процессы: «самый простой параллелизм» ценой изоляции

Процесс даёт параллелизм почти «по умолчанию»: разные процессы выполняются независимо, и ОС распределяет их по ядрам.

Компромисс процесса — в цене границ:

- данные не разделяются напрямую, нужен IPC (пайпы/сокеты/шары/файлы);
- память не общая: своя куча, свой GC, свои кеши;
- перенос крупных объёмов данных между процессами означает копирование (или сложные схемы вроде shared memory).

Процессы удобны, когда важна изоляция: «пусть воркер упадёт, но мастер живёт», или когда нужно обойти ограничения внутри одного интерпретатора.

## 3. Ractor: параллельный Ruby без общей изменяемой памяти

### 3.1 Зачем Ractor появился именно в MRI

MRI исторически строился вокруг **GVL** (Global VM Lock). Это упрощает жизнь интерпретатору и C-расширениям: внутри одного VM-контекста Ruby-код выполняется последовательно, и многим структурам не нужна тонкая блокировка на каждый объект.

Цена этой простоты — слабый CPU-параллелизм через `Thread`: потоки есть, но они не могут одновременно исполнять Ruby-код.

Ractor меняет точку компромисса: вместо того чтобы пытаться сделать весь мир «thread-safe», Ruby вводит **изоляцию**:

- каждый ractor — независимая единица исполнения, которая может работать параллельно с другими ractors;
- объекты по умолчанию **не разделяются** между ractors (они «принадлежат» одному ractor);
- синхронизация и обмен данными делаются через сообщения.

### 3.2 Потоки внутри ractor и per-ractor GVL

Один ractor содержит один или несколько `Thread`. Важное ограничение MRI:

- threads внутри одного ractor делят **ractor-wide GVL** (в терминологии MRI — GVL на уровне ractor),
- поэтому они не могут исполнять Ruby-код параллельно друг с другом (если только не отпускают GVL в C-расширении),
- threads из разных ractors могут исполняться параллельно.

Отсюда практическая эвристика: **CPU-bound Ruby-код распараллеливается через ractors или процессы, но не через threads внутри одного ractor**.

### 3.3 Shareable vs unshareable: что можно передавать между ractors

Если ractors должны быть изолированы, возникает вопрос: «а как тогда обмениваться данными?».

Ruby делит объекты на:

**Shareable** — безопасны для совместного использования (например, числа; замороженные строки/структуры без ссылок на изменяемые внутренности; сами объекты `Ractor`).

**Unshareable** — большинство обычных объектов, которые по умолчанию принадлежат одному ractor.

Проверка и превращение:

```ruby
Ractor.shareable?(obj)        # проверка
Ractor.make_shareable(obj)    # попытка сделать объект shareable (обычно через deep-freeze)
```

Это похоже на перенос идеи Rust в runtime: в Rust типы `Send/Sync` решают «можно ли делить/передавать между потоками» на этапе компиляции; в Ruby это решается проверками и протоколом передачи.

### 3.4 Сообщения: default port и `Ractor::Port`

У ractors есть два связанных, но разных механизма приёма сообщений.

**Default port** (порт по умолчанию, `Ractor#default_port`) есть у каждого ractor. Он используется «обычными» API:

- `r.send(obj)` отправляет `obj` в default port ractor `r`;
- `Ractor.receive` читает сообщение из default port *текущего* ractor (`Ractor.current`).

Это самый прямой аналог mailbox в акторной модели: каждый актор сам читает из своего почтового ящика.

**`Ractor::Port`** — это отдельный объект-очередь, который создаётся вызовом `Ractor::Port.new` и **принадлежит ractor'у-создателю**.

Ключевое правило владения:

- **получать (`port.receive`) и закрывать (`port.close`) может только ractor, который создал port;**
- **отправлять (`port.send` / `port <<`) может любой ractor, у которого есть ссылка на port.**

Это не «ограничение по месту, где лежит переменная», а ограничение по **owner ractor**, выбранному при `Port.new`.

Отсюда следует паттерн MPSC (multi-producer / single-consumer): один потребитель (создатель), много производителей (все, кому отдали ссылку).

Есть ещё один важный эффект: `Port#send` не блокирует отправителя (очередь концептуально бесконечная), а `Port#receive` блокирует текущий thread, если сообщений нет. Это значит, что backpressure приходится реализовывать протоколом (например, «не посылай больше N сообщений без ack»), иначе очередь может разрастись до OOM.

### 3.5 Двустороннее общение: кому нужен port и кто его создаёт

У «однонаправленного» port простая логика: **порт создаёт тот, кто будет получать**.

Поэтому для двусторонней связи обычно нужны два канала «туда» и «обратно»:

- если `main` должен получать от `worker`, то `main` создаёт `reply_port`, передаёт его `worker`, и `worker` делает `reply_port.send(...)`;
- если `worker` должен получать от `main` *через port*, то `worker` должен создать свой входящий port, передать его `main`, и `main` будет в него `send`.

При этом для многих сценариев ports вообще не нужны: можно общаться через default ports, если у сторон есть ссылки друг на друга.

Пример «main → worker → main» через default ports (mailboxes):

```ruby
main = Ractor.current

worker = Ractor.new(main) do |main|
  req = Ractor.receive        # читаем из default port worker
  main.send([:ok, req])       # пишем в default port main
end

worker.send("ping")
p Ractor.receive              # читаем из default port main
worker.join
```

Пример «много воркеров → один consumer» через `Ractor::Port`:

```ruby
results = Ractor::Port.new    # owner: main

workers = 4.times.map do |i|
  Ractor.new(results, i) do |results, i|
    results << [:done, i, Process.pid]
  end
end

4.times { p results.receive } # читать может только main
workers.each(&:join)
```

### 3.6 Общение между двумя non-main ractors без участия main «в доставке»

После того как два ractor'а получили ссылки друг на друга (или ссылки на нужные ports), они могут переписываться напрямую: сообщения идут в mailbox/port получателя, а `main` больше не пересылает их.

Но «стыковка» (bootstrap) всё равно должна откуда-то взяться: кто-то должен передать контакт. Это может быть `main`, или один ractor может создать другой и передать ссылку сразу.

### 3.7 Copy vs move при отправке сообщений

Когда отправляется shareable объект, передаётся ссылка (дёшево).

Когда отправляется unshareable объект, Ruby должен сохранить гарантию «в один момент времени доступен только в одном ractor». Для этого используются два режима:

- **copy** (по умолчанию): объект глубоко копируется в другой ractor (может быть дорого);
- **move**: объект «переезжает» в другой ractor, и отправитель больше не имеет права к нему обращаться (похоже на move-семантику владения в Rust).

Практический вывод: если хочется быстрых сообщений — протокол и данные лучше строить вокруг shareable/immutable форматов (числа, символы, замороженные структуры, байтовые буферы, которые можно передавать move'ом).

## 4. Thread: нативные потоки, GVL и модели 1:1 vs M:N

### 4.1 Ruby Thread = нативный pthread (по умолчанию)

Ruby `Thread` в MRI — это **native thread**, созданный через `pthread_create`. Когда ты создаёшь 4 Ruby потока, у тебя реально создаются 4 нативных потока ОС:

```
Ruby процесс
├── pthread #1 (main thread)     → Ruby Thread.main
├── pthread #2                   → Ruby Thread #2  
├── pthread #3                   → Ruby Thread #3
├── pthread #4                   → Ruby Thread #4
└── pthread #5 (timer thread)    → внутренний, ставит флаг "пора отдать GVL" по таймеру
```

Каждый pthread — это реальный системный поток. ОС может поставить их на разные ядра CPU. Метод `Thread#native_thread_id` возвращает реальный TID из ядра (на Linux — результат `gettid(2)`).

Ruby использует pthread API для всей синхронизации: GVL реализован через `pthread_mutex_t` + `pthread_cond_t`. Ruby не использует futex напрямую — pthread абстрагирует это (на Linux pthread внутри использует futex).

### 4.2 Эволюция моделей потоков в Ruby

**Ruby 1.8 и раньше:** M:1 (green threads) — много Ruby-потоков на одном нативном потоке. Полностью в userspace, нет настоящего параллелизма.

**Ruby 1.9 – 3.2:** 1:1 — каждый `Thread.new` создаёт нативный pthread. GVL ограничивает выполнение Ruby-кода одним потоком одновременно.

**Ruby 3.3+:** Гибридная модель — 1:1 по умолчанию для main Ractor, M:N для Ractors:

- `RUBY_MN_THREADS=1` включает M:N scheduler для main Ractor
- `RUBY_MAX_CPU=n` задаёт максимум нативных потоков для M:N (по умолчанию 8)

При M:N модели `native_thread_id` **может меняться** во время жизни Ruby Thread, потому что один Ruby Thread может «перепрыгивать» между разными нативными потоками.

### 4.3 Почему Ruby выбрал GVL

GVL (Global VM Lock) — это mutex на уровне интерпретатора. Только один тред может исполнять Ruby-код в один момент времени. Это автоматически решает некоторые проблемы многопоточности:

1. **Torn reads** — не актуально, только один тред пишет/читает Ruby-объекты
2. **Memory ordering** — барьеры в GVL-операциях (mutex включает memory barriers)
3. **Внутренние структуры VM** — защищены от параллельного доступа

**Но GVL НЕ делает Ruby-код атомарным!** Переключение происходит между байткод-инструкциями, а одно Ruby-выражение (например `counter += 1`) — это несколько инструкций. Race conditions на уровне логики всё ещё возможны (см. раздел 4.4).

Исторические причины выбора GVL:

1. **Ruby создавался как «язык для программиста».** Matz хотел простоту и выразительность. Заставлять программистов думать о memory ordering и атомиках — против философии Ruby.

2. **Ruby — динамический язык с тяжёлым рантаймом.** Внутренние структуры интерпретатора (таблицы методов, constant tables, объекты) очень сложные. Сделать их lock-free или fine-grained locking — титаническая работа и источник багов.

3. **C-расширения.** Ruby позволяет писать C-расширения, которые напрямую манипулируют Ruby-объектами. Если бы Ruby требовал синхронизации от C-кода, это сломало бы совместимость и усложнило экосистему.

4. **«Достаточно хорошо» для типичных задач.** Большинство Ruby-приложений — это веб-серверы, которые I/O-bound. Для них GVL не проблема: во время ожидания сети/диска GVL отпускается.

### 4.4 GVL не освобождает от синхронизации!

**Важно:** GVL защищает **внутренние структуры интерпретатора**, а не твою бизнес-логику. Race conditions на уровне логики всё ещё возможны:

```ruby
# Это НЕ атомарно, даже с GVL!
if @hash[:key].nil?
  @hash[:key] = expensive_computation
end
```

Здесь три отдельные Ruby-операции: чтение из хеша, проверка на nil, запись в хеш. Между любыми из них GVL может переключиться на другой тред.

GVL переключается:
- По таймеру (~100ms) — тред проверяет флаг и отдаёт GVL между байткод-инструкциями
- При блокирующем I/O
- При `Thread.pass`
- На границах Ruby-инструкций байткода

Правильное решение:

```ruby
@mutex.synchronize do
  if @hash[:key].nil?
    @hash[:key] = expensive_computation
  end
end
```

### 4.5 Вытесняемость и два уровня планирования

ОС не знает про GVL. Для неё это просто N обычных pthread. Планировщик Linux переключает их по своему усмотрению.

Получается двухуровневая система:

```
┌─────────────────────────────────────────────────────────────┐
│                    Планировщик ОС                           │
│  Решает: какому pthread дать физический CPU                 │
│  Не знает про Ruby, GVL, переключает по своим правилам      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    GVL (внутри Ruby VM)                     │
│  Решает: какой Ruby Thread может выполнять Ruby-код         │
│  Реализован через pthread_mutex + pthread_cond              │
│  (под капотом — futex на Linux)                             │
└─────────────────────────────────────────────────────────────┘
```

Что происходит когда ОС даёт CPU потоку, ожидающему GVL:
1. ОС переключает контекст на pthread
2. Pthread пытается захватить GVL (pthread_mutex_lock)
3. Если GVL занят — pthread_cond_wait → поток сразу засыпает на futex
4. Поток получил CPU на микросекунды только чтобы проверить и снова уснуть

Это не страшно: потоки на pthread_cond_wait спят в ядре (состояние SLEEPING), ОС видит их как спящие и не тратит на них CPU-время. Ruby при освобождении GVL сигнализирует конкретному следующему потоку через pthread_cond_signal.

## 5. Что происходит при I/O и sleep

### 5.1 GVL отпускается при блокирующих операциях

Когда Thread делает `File.read("big_file.txt")` или `socket.read` или `sleep`:

```
Время    Thread #1          Thread #2              Thread #3
─────    ─────────          ─────────              ─────────
t1       держит GVL,        ждёт GVL               ждёт GVL
         выполняет код      
         
t2       вызывает socket.read
         │
         ▼
         ОТПУСКАЕТ GVL ──► Thread #2 захватывает GVL
         │                 выполняет Ruby-код
         ▼
         read() syscall
         спит в ядре
         (ждёт данные)
         
t3       спит в ядре        выполняет код          ждёт GVL

t4       данные пришли!     
         ждёт GVL
         
t5       ← захватил GVL     ждёт GVL               ждёт GVL
         продолжает
```

Система **не зависает**! Пока Thread #1 спит в ядре ожидая диск/сеть, другие потоки спокойно выполняют Ruby-код по очереди.

### 5.2 Два разных вида «засыпания»

**Ожидание синхронизации (mutex, condition variable, GVL)** — поток ждёт, пока *другой поток* что-то сделает (освободит mutex, подаст сигнал). Механизм: futex — специальный системный вызов для эффективного ожидания. Поток добавляется в wait queue привязанную к адресу в памяти.

**Ожидание I/O** — поток ждёт *внешнего события* (данные из сети, завершение записи на диск, срабатывание таймера). Механизм: wait queue ядра привязанная к ресурсу. Это **не futex** — это другие структуры ядра.

```
Синхронизация (ждём другой поток):
  pthread_mutex_lock()     →  futex на адресе mutex
  pthread_cond_wait()      →  futex на адресе condvar
  
I/O (ждём внешнее событие):
  read(socket)             →  wait queue сокета, пробуждение от сетевой карты
  read(file)               →  ожидание DMA-контроллера диска
  sleep(n)                 →  timer queue ядра, пробуждение от прерывания таймера
```

В обоих случаях поток переходит в состояние SLEEPING и не потребляет CPU. Разница в том, *что* его разбудит: другой поток (futex_wake) или железо (прерывание).

### 5.3 Когда GVL отпускается

- Блокирующий I/O (сеть, диск, `sleep`)
- C-расширения, которые явно вызывают `rb_thread_call_without_gvl`
- Некоторые тяжёлые операции в стандартной библиотеке

### 5.4 Когда система «зависнет»

Система зависнет (другие потоки не смогут работать) только если поток держит GVL и не отпускает его. Это происходит при чистом CPU-bound коде:

```ruby
Thread.new do
  # Этот код держит GVL всё время (кроме моментов когда таймер сигнализирует отдать GVL ~100ms)
  result = 0
  100_000_000.times { |i| result += i }
end

Thread.new do
  # Этот поток будет получать CPU только когда первый проверит флаг таймера и отдаст GVL
  puts "Я почти не выполняюсь!"
end
```

## 6. JRuby и TruffleRuby: как работают реализации без GVL

### 6.1 Главный вопрос: если JRuby работает без GVL, зачем GVL нужен MRI?

GVL в MRI защищает **две разные вещи**:

1. **Внутренние структуры интерпретатора** (method tables, constant tables, object allocation) — написаны на C без thread-safety
2. **Как побочный эффект** — пользовательские структуры (Array, Hash) "случайно" работают корректно

JRuby и TruffleRuby решают первую проблему иначе — **много мелких локов вместо одного глобального**.

### 6.2 Один лок на всё vs отдельный лок на каждую структуру

**MRI: один лок (GVL) защищает вообще всё**

```
┌─────────────────────────────────────────────┐
│                  GVL                        │
│  ┌─────────────────────────────────────┐    │
│  │  method tables                      │    │
│  │  constant tables                    │    │
│  │  object allocation                  │    │
│  │  require/autoload                   │    │
│  │  твой Array                         │    │
│  │  твой Hash                          │    │
│  │  вообще всё                         │    │
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘

Хочешь что-то сделать? Захвати GVL.
Неважно что — один лок на всё.
```

Плюс: просто реализовать, невозможно ошибиться.
Минус: нет параллелизма — все ждут один лок.

**JRuby: ~50 отдельных локов, каждый защищает свою структуру**

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ lock #1      │  │ lock #2      │  │ lock #3      │
│ method       │  │ constant     │  │ autoload     │
│ tables       │  │ tables       │  │              │
└──────────────┘  └──────────────┘  └──────────────┘

┌──────────────┐  ┌──────────────┐  
│ lock #4      │  │ lock #5      │  ... ещё ~45 локов
│ require      │  │ class vars   │  
└──────────────┘  └──────────────┘  

Хочешь добавить метод? Захвати lock #1.
Хочешь прочитать константу? Захвати lock #2.
Разные операции — разные локи.
```

Плюс: параллелизм! Пока Thread A держит lock #1, Thread B может работать с lock #2.
Минус: сложнее реализовать, риск deadlock (взаимная блокировка — когда Thread A ждёт lock #2 который держит Thread B, а Thread B ждёт lock #1 который держит Thread A — оба ждут вечно).

**Аналогия:** GVL — это один ключ от всего здания. Хочешь в туалет — возьми ключ. Хочешь в столовую — тот же ключ. Все ждут в очереди. JRuby — отдельный ключ от каждой комнаты. Один человек в туалете, другой параллельно в столовой.

### 6.3 Почему JRuby не защищает Array и Hash

JRuby защитил **только внутренности интерпретатора** — то что нужно для работы самого JRuby.

Твои `Array` и `Hash` — **твоя ответственность**. Это осознанный выбор: добавить лок на каждый Array/Hash замедлило бы однопоточный код, а это 99% Ruby-программ.

### 6.4 Что это значит для твоего кода

```ruby
# Этот код "работает" в MRI, но СЛОМАН в JRuby/TruffleRuby!

array = []
10.times.map do 
  Thread.new { 1000.times { array << 1 } }
end.each(&:join)

array.size
# MRI:     всегда 10000 (нет параллелизма, GVL защищает)
# JRuby:   может быть меньше, или Exception!
# TruffleRuby: то же самое
```

В MRI `Array#<<` "атомарен" только потому что **нет параллелизма** — GVL не даёт двум потокам выполнять Ruby-код одновременно.

В JRuby/TruffleRuby потоки **реально параллельны**. Два потока могут одновременно вызвать `array << x`, и внутренняя структура массива будет повреждена.

### 6.5 Volatile и видимость памяти

В MRI переключение GVL включает memory barriers — записи одного потока гарантированно видны другому после переключения.

В JRuby **instance variables не volatile**. Из документации JRuby:

> "The following operations are NOT volatile, and there is potential for threads to see inconsistent views of memory:
> - Modifying an instance variable
> - Modifying any of the non-threadsafe core data structures"

Что это значит на практике:

```ruby
# Thread 1
@data = 42
@ready = true

# Thread 2
if @ready
  puts @data  # В JRuby может увидеть nil!
end
```

Thread 2 может увидеть `@ready = true`, но `@data` ещё "не долетел" из кеша CPU в общую память. Это классическая проблема visibility.

**Volatile** — это свойство переменной которое гарантирует:
- При записи: значение сразу "сбрасывается" в RAM (не застревает в кеше CPU)
- При чтении: значение берётся из RAM (не из локального кеша)
- Плюс memory barrier — запрет на переупорядочивание инструкций вокруг этой точки

В MRI это неактуально (GVL включает барьеры). В JRuby/TruffleRuby нужно явно синхронизировать.

### 6.6 Что гарантируют JRuby и TruffleRuby

**JRuby гарантирует volatile/барьеры для:**
- `Mutex#synchronize` — да (это Java synchronized)
- Инициализация классов и констант — да
- `require` / `autoload` — да (только один поток загружает)
- Рост таблицы instance variables — да (но не сами значения!)

**TruffleRuby предоставляет явные примитивы:**
```ruby
# Явный memory barrier
TruffleRuby.full_memory_barrier

# Атомарные ссылки с барьерами
ref = TruffleRuby::AtomicReference.new(value)
ref.set(new_value)                    # включает barrier
ref.compare_and_set(old, new)         # CAS с barrier

# Синхронизация на объекте
TruffleRuby.synchronized(object) { ... }
```

### 6.7 concurrent-ruby: единое решение для всех реализаций

Гем `concurrent-ruby` предоставляет одинаковое поведение на MRI, JRuby и TruffleRuby:

```ruby
require 'concurrent-ruby'

# Thread-safe collections
map = Concurrent::Map.new
# На MRI: обычный Hash (GVL защищает)
# На JRuby: hash + mutex
# На TruffleRuby: ConcurrentMap

# Атомарные ссылки
ref = Concurrent::AtomicReference.new(initial_value)
ref.compare_and_set(old_value, new_value)

# Базовый класс с volatile fields
class MyClass < Concurrent::Synchronization::Object
  attr_volatile :my_field  # Гарантирует volatile на всех реализациях
end
```

### 6.8 Сводная таблица

| Что | MRI (GVL) | JRuby | TruffleRuby |
|-----|-----------|-------|-------------|
| Интерпретатор защищён? | ✅ GVL | ✅ ~50 мелких локов | ✅ ~50 мелких локов |
| `Array#<<` concurrent-safe? | ✅ "случайно" | ❌ может крашнуть | ❌ может крашнуть |
| Instance vars volatile? | ✅ (через GVL) | ❌ нет | ❌ нет |
| Твоя бизнес-логика safe? | ❌ нет | ❌ нет | ❌ нет |
| Параллелизм CPU? | ❌ нет | ✅ да | ✅ да |

### 6.9 Практический вывод

**Код который "работает" в MRI может быть сломан** — GVL маскирует race conditions. При миграции на JRuby/TruffleRuby эти баги проявятся.

**Пиши код так, будто GVL нет:**
- Используй `Mutex` для критических секций
- Используй `concurrent-ruby` для thread-safe структур
- Не полагайся на "атомарность" отдельных операций

Тогда код будет работать на всех реализациях Ruby.

## 7. Fiber: кооперативная конкурентность и фундамент async-рантайма

### 7.1 Базовая механика: `resume`, `yield`, `alive?`

Fiber — это корутина: у неё есть свой стек, и она умеет «остановиться» и продолжить с того же места.

- `Fiber.new { ... }` создаёт fiber, но не запускает.
- `fiber.resume` запускает/продолжает выполнение до ближайшего `Fiber.yield` или до завершения.
- `Fiber.yield` отдаёт управление наружу (в `resume`).
- `fiber.alive?` показывает, можно ли его ещё продолжить (после завершения — `false`).

Минимальная «лестница»:

```ruby
f = Fiber.new do
  puts "A"
  Fiber.yield
  puts "B"
end

f.resume  # печатает A, останавливается на yield
f.resume  # печатает B, завершается
```

У `yield` и `resume` есть обмен значениями: аргументы `yield(...)` возвращаются из `resume`, а аргументы следующего `resume(...)` становятся результатом выражения `Fiber.yield` внутри fiber. Это удобно, чтобы строить кооперативные протоколы без общей памяти.

### 7.2 Почему fibers «не дают асинхронности сами по себе»

Fiber переключается только в точках `yield/transfer` (кооперативность). Но если внутри fiber вызвать блокирующую операцию, например `sleep(1)`, то блокируется **весь thread**, а значит никакой другой fiber на этом thread не побежит.

Чтобы fibers стали инструментом async, нужен механизм: «когда fiber упирается в блокирующий вызов, он не должен блокировать thread; он должен зарегистрировать ожидание и уступить управление».

В Rust это место — `.await` + runtime. В Ruby это место — **Fiber Scheduler**.

### 7.3 Fiber Scheduler: перехват блокирующих операций

Ruby даёт интерфейс планировщика, который можно установить на *текущий thread*:

```ruby
Fiber.set_scheduler(MyScheduler.new)
```

Дальше в специальных «non-blocking» контекстах Ruby будет вызывать hooks планировщика вместо того, чтобы реально блокировать thread на `sleep` и I/O.

Смысл hooks ровно такой же, как у reactor/executor:

1) когда нужен I/O или таймер — зарегистрировать интерес к событию;
2) уступить управление (fiber блокируется);
3) когда событие произошло — разбудить fiber и продолжить.

Минимальный контракт планировщика включает методы `io_wait`, `kernel_sleep`, `block`, `unblock` (иначе `Fiber.set_scheduler` упадёт с ошибкой). Дополнительные hooks (DNS, timeout, ожидание процессов) могут быть опциональными.

Отсюда появляется важный практический разделение:

- threads дают вытесняемость и простую модель, но платят ресурсами;
- fibers дают дешёвые «задачи», но требуют дисциплины (yield-точек) и планировщика, чтобы не блокировать thread.

## 8. Сравнение веб-серверов: Puma vs Falcon

**Puma** использует гибридный подход: пул потоков, каждый поток делает блокирующий I/O на своём соединении. Простой и надёжный подход.

```
Puma архитектура:
                    ┌─────────────────────┐
                    │   Accept thread     │
                    └──────────┬──────────┘
                               │
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
┌───────────────┐      ┌───────────────┐      ┌───────────────┐
│   Worker 1    │      │   Worker 2    │      │   Worker N    │
│ (thread pool) │      │ (thread pool) │      │ (thread pool) │
└───────────────┘      └───────────────┘      └───────────────┘

Каждый worker thread делает блокирующий I/O
```

**Falcon** использует Fiber Scheduler с epoll — один поток может обслуживать тысячи соединений:

```
Falcon архитектура:
┌─────────────────────────────────────────┐
│            Event Loop (epoll)           │
│  Fiber 1 ──┐                            │
│  Fiber 2 ──┼── все на одном потоке,     │
│  Fiber 3 ──┤   мультиплексируются       │
│  Fiber N ──┘   через epoll              │
└─────────────────────────────────────────┘
```

### 8.1 Стек библиотек Falcon

Falcon построен на экосистеме async-библиотек:

```
┌─────────────────────────────────────────┐
│              Falcon                      │  ← HTTP-сервер
├─────────────────────────────────────────┤
│         async / async-http               │  ← async runtime, HTTP клиент/сервер
├─────────────────────────────────────────┤
│            io-event                      │  ← низкоуровневый I/O, выбор механизма
├─────────────────────────────────────────┤
│     epoll (Linux) / kqueue (macOS)       │  ← системный механизм
│            / IOCP (Windows)              │
└─────────────────────────────────────────┘
```

**io-event** — гем, который абстрагирует механизм ожидания событий. Он автоматически выбирает лучший доступный механизм:
- Linux → epoll
- macOS / BSD → kqueue  
- Windows → IOCP

Благодаря этому Falcon работает на всех платформах без изменения кода.

### 8.2 Пример: Falcon в действии

```ruby
# Gemfile
gem 'falcon'

# config.ru — обычное Rack-приложение
run lambda { |env|
  # Внутри этого блока можно делать async I/O:
  # HTTP-запросы, чтение файлов, sleep — всё будет
  # неблокирующим благодаря Fiber Scheduler
  
  [200, {'Content-Type' => 'text/plain'}, ['Hello from Falcon!']]
}
```

```bash
# Запуск
falcon serve --bind http://localhost:9292

# Falcon автоматически:
# 1. Устанавливает Fiber Scheduler на основе io-event
# 2. Каждый входящий запрос обрабатывается в отдельном Fiber
# 3. I/O операции внутри Fiber не блокируют — переключаются через epoll/kqueue
```

Когда Fiber внутри Falcon делает `sleep(1)` или `Net::HTTP.get(...)`, он не блокирует поток. Вместо этого:
1. Fiber регистрирует интерес к событию (таймер / сокет готов)
2. Fiber уступает управление
3. Event loop продолжает обрабатывать другие Fiber'ы
4. Когда событие происходит — Fiber возобновляется

Это позволяет одному потоку обслуживать тысячи одновременных соединений с минимальным потреблением памяти.

# Часть III: Как этим пользоваться на практике

## 1. Начинать с вопроса: CPU или I/O?

Почти все практические решения сводятся к диагностике «где время»:

**CPU-bound**: считаем, парсим, сжимаем, криптография, большие преобразования данных.

**I/O-bound**: ждём сеть/диск/таймеры, делаем много маленьких запросов, держим тысячи соединений.

Дальше выбор инструментов в Ruby обычно такой:

- **CPU-bound и нужен параллелизм Ruby-кода** → `Ractor` или `Process`.
- **I/O-bound и задач не очень много** → `Thread` (проще всего).
- **I/O-bound и задач очень много** → `Fiber` + scheduler (обычно через готовый гем/рантайм).

## 2. Процессы vs ractors: когда что

Процессы выбирают, когда важна «тяжёлая изоляция»:

- безопасность: падение воркера не рушит мастер;
- разные зависимости/настройки;
- проще «не думать» о shareability объектов.

Ractors выбирают, когда нужен параллелизм *внутри одного процесса* и хочется акторную модель:

- меньше накладных расходов на IPC;
- обмен сообщениями встроен в модель;
- изоляция на уровне объектов помогает избежать shared-memory гонок.

Компромисс ractors — в том, что нужно проектировать данные и протокол так, чтобы сообщения были shareable/дешёвыми, иначе копирование/перемещения станут бутылочным горлышком.

## 3. Threads в MRI: простота, но помнить про GVL и синхронизацию

Для I/O и для «сходить в сторонний блокирующий API» threads часто лучший инструмент, потому что:

- код выглядит линейно;
- вытесняемость ОС даёт хорошую отзывчивость;
- многие блокирующие операции отпускают GVL, и другие threads могут прогрессировать.

Но как только threads начинают делить изменяемые данные, возвращается классическая проблема: нужны `Mutex`, `Queue`, `ConditionVariable` и аккуратные протоколы.

## 4. Fibers + scheduler: когда нужна высокая I/O-конкурентность

Fibers обычно берут, когда хочется «тысячи задач» без «тысяч потоков».

Ключевой нюанс: сами по себе fibers ничего не ускоряют. Они становятся async-инструментом только если:

- выполняются в non-blocking контексте (`Fiber.schedule` / `Fiber.new(blocking: false)`),
- установлен scheduler, который перехватывает `sleep` и I/O.

Похожее ощущение, как в Rust: `.await` работает только потому, что runtime под капотом делает event loop и возобновление задач.

Из этого следует практическое правило: если библиотека делает «честный блокирующий вызов» (например, C-расширение без интеграции со scheduler), то fiber не спасёт — будет блокироваться весь thread. В таких местах обычно используют отдельный thread pool или оборачивают куски в `Fiber.blocking { ... }`, чтобы явно признать «это блокирующая зона».

## 5. Типичные ошибки и «скользкие места»

**Ошибка: ожидать ускорения CPU-bound кода от `Thread`.** В MRI чистый Ruby под GVL не распараллеливается. Если нужен CPU-параллелизм — ractors/processes (или C, который отпускает GVL).

**Ошибка: думать, что GVL защищает от race conditions.** GVL защищает интерпретатор, не твою логику. Составные операции (check-then-act) требуют mutex.

**Ошибка: думать, что `Ractor::Port` можно `receive` «в любом месте».** `receive` привязан к owner ractor (кто сделал `Port.new`). Передача объекта порта не переносит право чтения.

**Ошибка: строить протокол ractors вокруг больших изменяемых структур.** Дорогие копии/глубокая заморозка быстро съедают выигрыш параллелизма. Лучше проектировать сообщения как «маленькие immutable команды и результаты».

**Ошибка: использовать fibers без scheduler и ждать перекрытия I/O.** Без перехвата блокирующих операций `sleep`/`read` блокируют thread, и fibers выполняются последовательно.

**Ошибка: забыть, что кооперативность требует yield-точек.** В fiber-рантайме CPU-тяжёлая функция без yield способна заморозить прогресс остальных задач на этом thread.

## 6. Итоговая карта: что где даёт

Если свести всё к одной таблице, получится не «что лучше», а «какой компромисс выбираем»:

| Инструмент | Даёт | Цена |
| --- | --- | --- |
| `Process` | параллелизм + сильная изоляция | IPC/память/стоимость границ |
| `Ractor` | параллелизм Ruby-кода + изоляция объектов | протокол сообщений, shareable/copy/move |
| `Thread` | простая конкурентность, хорошая для I/O | shared-state синхронизация, GVL для Ruby CPU |
| `Fiber` | дешёвые кооперативные задачи | нужен scheduler для I/O, риск starvation |

Эта карта полезнее всего, когда её применять «сверху вниз»: сначала выбрать уровень изоляции (процесс/рактер), затем способ I/O-конкурентности (threads/fibers), и только потом думать про конкретные API.
