# JIT-компиляция

**Предпосылки:** [Компиляция](vm/01-compilation.md) — ISeq, YARV-байткод, `iseq_encoded`. [Исполнение](vm/02-execution.md) — фреймы (`rb_control_frame_t`), PC, SP, CFP, цикл VM. [Диспетчеризация методов](methods/00-method-dispatch.md) — инлайн-кеш, callable method entry (`rb_callable_method_entry_t`), инвалидация кеша. [Формы](object-model/02-shapes.md) — `shape_id`, инлайн-кеш переменных.

В [заметке об исполнении](vm/02-execution.md) мы видели, как VM выполняет байткод: читает инструкцию, декодирует, вызывает обработчик, передвигает PC. Этот цикл работает корректно при любой нагрузке, но каждый шаг стоит процессорного времени — непрямое ветвление при диспетчеризации, обслуживание стека значений, проверки типов. Пока метод вызывается редко, overhead незаметен. Но представим метод `Product#match?(query)`, который проверяет `@name`, `@category` и `@tags` на каждом из 1000 товаров, 200 раз в секунду — 200 000 вызовов/сек. При такой частоте интерпретатор тратит заметную долю времени не на саму проверку полей, а на обслуживание факта интерпретации. В профиле это видно как доминирование `vm_exec_core` — цикла VM.

JIT-компиляция (just-in-time) решает эту проблему: когда VM обнаруживает, что метод вызывается достаточно часто, она компилирует его байткод в машинный код [процессора](../../computer/00-cpu.md). Следующий вызов выполняет машинные инструкции напрямую, без dispatch-цикла. В CRuby встроены два JIT-компилятора — YJIT (с Ruby 3.1) и ZJIT (экспериментальный, с Ruby 4.0). Оба работают поверх того же YARV-байткода, который создаёт [компилятор](vm/01-compilation.md), но используют разные стратегии генерации машинного кода.

## Когда интерпретация становится узким местом

Не всякий код стоит компилировать. Компиляция сама требует процессорного времени и памяти для хранения сгенерированного кода. Чтобы JIT был выгоден, ускорение от машинного кода должно «отбить» стоимость компиляции. Поэтому VM компилирует только **горячий код** — методы и блоки, которые выполняются достаточно часто.

Механизм обнаружения горячего кода встроен в саму структуру [ISeq](vm/01-compilation.md). Когда Ruby собран с поддержкой JIT, в `rb_iseq_constant_body` появляются три группы полей. Указатель на скомпилированный код (`jit_entry`, тип `rb_jit_func_t`) — изначально `NULL`, он заполняется после компиляции. Счётчик вызовов (`jit_entry_calls`) — сколько раз VM пыталась войти в этот ISeq. И отдельная пара `jit_exception` / `jit_exception_calls` — для входа из обработки исключений (`vm_exec_handle_exception`).

Логика решения о компиляции проста:

```
if (body->jit_entry == NULL) {
    body->jit_entry_calls++;
    if (body->jit_entry_calls >= threshold) {
        body->jit_entry = compile(iseq);
    }
}
// следующий вход: if (body->jit_entry) goto jit_entry;
```

Пока `jit_entry == NULL`, метод `match?` выполняется интерпретатором. С каждым вызовом `jit_entry_calls` растёт. Когда счётчик достигает порога — VM компилирует ISeq и записывает адрес машинного кода в `jit_entry`. Следующий вход в `match?` проверяет `jit_entry`, видит ненулевой указатель и передаёт управление JIT-коду.

Порог — это экономический параметр, а не магическое число. Слишком низкий порог — VM компилирует методы, которые вызываются десять раз за всю жизнь процесса, впустую тратя CPU и память на код, который почти не используется. Слишком высокий — горячий метод долго остаётся в интерпретаторе, а ускорение приходит поздно. YJIT дополнительно использует фильтр холодного кода (`rb_yjit_cold_threshold`): если ISeq набирает вызовы слишком медленно относительно общего потока, его можно не компилировать — это экономит память на инициализационном коде и редких путях. ZJIT разделяет процесс на два порога: `rb_zjit_profile_threshold` (когда начать собирать профиль) и `rb_zjit_call_threshold` (когда компилировать) — об этом подробнее в секции про ZJIT.

## Специализация: предположения и охранные проверки

Компиляция байткода в машинный код убирает overhead диспетчеризации, но самый большой выигрыш приходит от **специализации** — генерации кода, оптимизированного под конкретные типы и формы объектов, которые JIT наблюдает в runtime.

Вернёмся к `Product#match?`. Метод читает `@name` у receiver'а. В интерпретаторе это инструкция `getinstancevariable`, которая каждый раз проходит через инлайн-кеш форм — проверяет `shape_id` объекта, ищет смещение переменной в массиве `ivar_array` (этот механизм мы видели в [заметке о формах](object-model/02-shapes.md)). JIT может сделать лучше: если все объекты `Product`, приходящие в `match?`, имеют одну и ту же форму (один `shape_id`), JIT генерирует машинный код, который предполагает эту форму и читает `@name` по фиксированному смещению — одна инструкция `mov` вместо цепочки проверок.

Но предположение «все объекты Product имеют `shape_id` = 47» — это именно предположение, не гарантия. Завтра кто-то добавит `@cached_score` к части объектов, и у них будет другой `shape_id`. Или метод `String#include?`, который `match?` вызывает внутри, будет переопределён. Чтобы специализированный код оставался корректным, JIT добавляет три механизма.

**Охранная проверка (guard)** — проверка в машинном коде, которая подтверждает предположение перед выполнением специализированного пути. Для `match?` это `cmp [receiver + shape_offset], 47; jne side_exit` — одна машинная инструкция сравнения. Если `shape_id` совпадает — JIT-код продолжает по быстрому пути. Если нет — нужен безопасный выход.

**Выход в интерпретатор (side exit)** — код, который возвращает управление интерпретатору, когда guard не прошёл. Выход должен восстановить состояние VM так, чтобы интерпретатор мог продолжить с той инструкции, на которой JIT остановился. Для этого side exit записывает три значения в текущий [фрейм](vm/02-execution.md): PC (какую инструкцию выполнять дальше), SP (вершину стека значений) и передаёт управление обратно в `vm_exec_core`. Важная деталь: выход привязывается к границам YARV-инструкций — JIT не может «прыгнуть в side exit» посередине операции, которая уже изменила модель стека, иначе восстановление состояния станет неоднозначным.

**Инвалидация** — механизм для случаев, когда предположение ломается не из-за конкретного объекта, а из-за глобального изменения в программе (переопределение метода, изменение константы, `include` модуля). В этом случае весь скомпилированный код, опирающийся на это предположение, помечается недействительным — подробнее об этом в секции «Инвалидация».

Эта тройка — guard, side exit, invalidation — фундамент любого JIT в динамическом языке. Различаются конкретные реализации: что именно JIT компилирует за один раз, как выбирает предположения, сколько специализированных версий допускает.

## YJIT: компиляция базовых блоков

Тройка guard/side exit/invalidation — общий механизм. Теперь посмотрим, как конкретные JIT-компиляторы CRuby реализуют его и какую стратегию компиляции выбирают. YJIT — первый встроенный JIT в CRuby, написанный на Rust и интегрированный через интерфейс вызовов между C и Rust. Его ключевая идея — **Basic Block Versioning (BBV)**: вместо компиляции метода целиком YJIT компилирует **базовые блоки** (участки кода без ветвлений) по одному, причём каждый блок может существовать в нескольких версиях, специализированных под разные контексты.

Когда `match?` достигает порога, C-сторона VM вызывает `rb_yjit_compile_iseq(iseq, ec, jit_exception)`. YJIT генерирует точку входа — машинный код для первого базового блока ISeq — и возвращает адрес, который записывается в `body->jit_entry`. Остальные блоки компилируются по мере необходимости: когда исполнение JIT-кода достигает ещё не скомпилированного перехода, YJIT генерирует следующий блок на лету. Практический смысл: YJIT начинает с малого и расширяет покрытие постепенно, не платя сразу стоимость компиляции всего метода.

Чтобы описать место в байткоде, YJIT использует `BlockId` — пару (ISeq, `insn_idx`), где `insn_idx` — индекс инструкции в `iseq_encoded`. Чтобы описать, под какие предположения сгенерирован код, используется `Context` — компактное описание состояния в этой точке: типы значений на стеке, тип `self`, состояние регистров JIT. Одна и та же позиция в байткоде может иметь несколько скомпилированных версий с разными контекстами.

Метаданные о скомпилированных блоках YJIT хранит в поле `yjit_payload` на `rb_iseq_constant_body`. В Rust это структура `IseqPayload`, и её ключевое поле — `version_map`: массив, индексируемый по `insn_idx`. На каждой позиции — список версий блока, каждая помечена своим `Context`. Когда YJIT ищет подходящую версию, он сравнивает текущий контекст с контекстом каждой версии и выбирает ближайшую по специализации.

Вернёмся к сценарию. `match?` всегда получает `Product` с одним `shape_id` — YJIT генерирует версию блока с контекстом «self = Product, shape_id = 47». Но если появляется подкласс `PremiumProduct` с дополнительным полем `@discount`, у него другой `shape_id`. Когда `PremiumProduct` впервые попадает в `match?`, guard на `shape_id` не проходит, срабатывает side exit, и YJIT генерирует **вторую версию** того же блока — с контекстом «self = PremiumProduct, shape_id = 52». Теперь оба пути работают в машинном коде.

Если бы вариантов было бесконечно много, `version_map` разрастался бы без предела — это взрыв числа версий. YJIT защищается лимитом: когда количество версий блока достигает максимума, следующая генерируется с **обобщённым контекстом**, который хуже оптимизирует (больше проверок в runtime), но подходит для любых входных данных. Это осознанный компромисс: лучше медленный, но единственный fallback, чем неограниченный рост памяти.

## ZJIT: метод целиком через профилирование

Если YJIT делает ставку на быструю, постепенную компиляцию маленьких кусков, ZJIT устроен иначе — как method-based JIT, который компилирует метод целиком, но только после сбора профиля.

Процесс запускается в два этапа. Когда ISeq достигает порога `rb_zjit_profile_threshold`, VM переписывает часть байткода: в `iseq_encoded` адреса некоторых YARV-инструкций заменяются на адреса `zjit_*`-обёрток. Каждая такая обёртка делает две вещи: вызывает `rb_zjit_profile_insn(opcode, ec)` (собирает информацию о типах, формах, результатах вызовов) и затем выполняет оригинальную инструкцию как обычно. Это замедляет исполнение — профилирование имеет цену — но собирает данные, которые позволят сгенерировать более эффективный код.

Когда счётчик достигает второго порога `rb_zjit_call_threshold`, VM компилирует ISeq через `rb_zjit_compile_iseq(iseq, jit_exception)`. В отличие от YJIT, вход в ZJIT-код проходит через промежуточную функцию `rb_zjit_entry(ec, cfp, jit_entry)`, которая согласовывает соглашения о вызовах между C-стеком VM и сгенерированным кодом — без неё VM не может корректно передать управление в JIT-код и получить результат обратно.

Внутри ZJIT ближе к классическим оптимизирующим компиляторам. Он строит промежуточные представления: HIR (high-level IR, близкий к семантике Ruby) и LIR (low-level IR, близкий к машинному коду). Промежуточное представление — это [граф](../../algorithms-and-data-structures/non-linear/00-graph.md), где узлы — операции, а рёбра — зависимости по данным и управлению. На уровне HIR ZJIT применяет оптимизации, используя собранный профиль: если профиль показывает, что `@name` всегда читается у объекта с одной формой, ZJIT может встроить прямой доступ с guard'ом. На уровне LIR представление трансформируется в машинные инструкции с распределением регистров.

Контраст с YJIT: YJIT компилирует быстро (один базовый блок за раз, минимальный анализ), поэтому warmup короче и ускорение появляется раньше, но код менее оптимален. ZJIT тратит больше времени на анализ и оптимизацию, поэтому warmup длиннее, но потенциально генерирует более быстрый код для горячих методов. Это классический компромисс JIT-компиляции: скорость старта vs качество кода.

## Инвалидация: когда мир меняется

Guard'ы защищают от неожиданных данных — объект пришёл с другой формой, и side exit вернул управление интерпретатору. Но в Ruby мир может измениться не из-за данных, а из-за кода: метод переопределили, константу изменили, включили модуль. В этом случае guard'ы бесполезны — JIT-код может стать некорректным, даже если текущие объекты выглядят «правильно», потому что предположение касалось результата поиска метода, а не типа данных.

Вернёмся к сценарию. Разработчик выполняет `Product.include(Searchable)`, и модуль `Searchable` определяет собственный `match?`. [Цепочка поиска метода](methods/00-method-dispatch.md) изменилась: callable method entry (CME, `rb_callable_method_entry_t`) для старого `match?` становится недействительной. Если JIT-код продолжит вызывать старую версию метода — результат будет неправильным.

VM решает это через хуки инвалидации. Когда callable method entry становится недействительной, VM вызывает `rb_yjit_cme_invalidate(cme)` и `rb_zjit_cme_invalidate(cme)`. JIT-компилятор находит все скомпилированные блоки, которые опирались на эту CME, и помечает их недействительными — следующий вход в эти методы уйдёт обратно в интерпретатор (или будет перекомпилирован).

Аналогичный механизм работает для констант. При изменении значения константы VM вызывает `rb_yjit_constant_state_changed(id)` и `rb_zjit_constant_state_changed(id)`. Если JIT-код встроил значение константы прямо в машинные инструкции (например, заменил `THRESHOLD` на число `100`), это значение может стать устаревшим.

Отдельный триггер — переопределение базовых операций. Инструкции вроде `opt_plus` в интерпретаторе предполагают, что `Integer#+` не переопределён, и выполняют арифметику напрямую. JIT использует то же предположение. Когда кто-то определяет `class Integer; def +(other) ... end; end`, VM вызывает `rb_yjit_bop_redefined(...)` / `rb_zjit_bop_redefined(...)` — и все скомпилированные быстрые пути для этой операции инвалидируются. Переопределение базовых операторов — редкость, но [метапрограммирование](metaprogramming.md) (через `define_method`, `eval`, refinements) может вызывать аналогичные инвалидации.

## Кеш кода и его сборка

Инвалидация убирает некорректный код из исполнения, но не освобождает память — машинные инструкции продолжают занимать место в кеше кода. JIT-код живёт в памяти процесса в специальной области — кеше кода (code cache). Это регион с правами на исполнение, куда YJIT записывает сгенерированные машинные инструкции. Если приложение активно компилирует — сотни контроллеров, моделей, сервисных объектов с горячими методами — кеш кода растёт и может заметно увеличить потребление памяти процесса.

YJIT решает это механизмом сборки кеша кода (code GC), который срабатывает, когда кеш заполняется — достигает лимита, заданного через `--yjit-exec-mem-size` (по умолчанию 128 MiB). Идея аналогична обычному GC: найти код, который больше не нужен, и освободить занятую им память. «Не нужен» здесь означает: ISeq, для которого сгенерирован этот код, не находится ни на одном стеке вызовов (не выполняется прямо сейчас). Связь между страницами кеша кода и ISeq'ами отслеживается через множество `pages` в `IseqPayload` — для каждого ISeq известно, какие страницы с машинным кодом ему принадлежат.

Сборка кеша кода проходит в два шага. Сначала YJIT инвалидирует все входы и переходы в блоки, принадлежащие освобождаемым страницам — чтобы VM больше не пыталась прыгнуть в код, который будет перезаписан. Затем страницы помечаются свободными и могут быть переиспользованы для компиляции новых методов. Если освобождённый метод снова станет горячим — он будет скомпилирован заново.

Сборку можно вызвать вручную через `RubyVM::YJIT.code_gc` — это полезно для экспериментов и диагностики.

## Наблюдаемость

Чтобы JIT не был чёрным ящиком, CRuby предоставляет API для интроспекции. Для YJIT — модуль `RubyVM::YJIT` с методами `enabled?` (включён ли), `runtime_stats` (статистика компиляций и side exit'ов), `log` (лог компиляций, если включён флагом запуска) и `code_gc` (ручная сборка кеша). Для ZJIT — модуль `RubyVM::ZJIT` с `enabled?`, `stats` / `reset_stats!` и `exit_locations` (трассировка side exit'ов).

В нашем сценарии разработчик, увидевший доминирование `vm_exec_core` в профиле, включает YJIT (`--yjit`), и после прогрева проверяет `RubyVM::YJIT.runtime_stats`. Статистика показывает: `match?` скомпилирован, side exit'ов мало (большинство объектов имеют одну форму), объём кеша кода в пределах нормы. Если side exit'ов неожиданно много — это сигнал, что JIT не может эффективно специализировать метод (слишком много форм или частые инвалидации), и стоит пересмотреть дизайн объектов.

MRI разрешает включить только один JIT одновременно: если активен YJIT, включение ZJIT будет отвергнуто, и наоборот. Это упрощает модель исполнения — один набор порогов, один кеш кода, один набор правил инвалидации.
