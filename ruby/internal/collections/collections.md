# Коллекции: внутреннее устройство Array, Hash, String

> [!info]- Предпосылки
> [Объекты и классы](../object-model/objects-and-classes.md) (VALUE, RBasic, klass), [GC](../gc.md) (VWA, слоты, страницы, write barrier), [динамический массив](../../../algorithms-and-data-structures/linear/dynamic-array.md), [хеш-таблица](../../../algorithms-and-data-structures/linear/hash-table.md).

Для пользовательских [объектов](../object-model/objects-and-classes.md) Ruby хранит инстанс-переменные в обобщённой структуре `RObject`. Но встроенные типы — Array, Hash, String — работают с данными настолько часто, что обобщённое представление было бы расточительным. Каждый из них получил собственную C-структуру (`RArray`, `RHash`, `RString`), оптимизированную под конкретный паттерн доступа: последовательный, ассоциативный, текстовый.

Все три структуры начинаются с одного и того же заголовка `RBasic` (flags + klass) и разделяют общий приём: если данных мало, они хранятся прямо в слоте [объекта](../object-model/objects-and-classes.md) (embedded-режим), без отдельной аллокации. Когда данных становится больше, чем вмещает слот, Ruby выделяет внешний буфер через malloc (heap-режим). [Variable Width Allocation](../gc.md) расширяет embedded-ёмкость: слоты бывают 40, 80, 160, 320, 640 байт, и чем крупнее слот, тем больше данных помещается без malloc.

## Порядок изучения

- [Array](array.md) — `RArray`: embedded/heap-хранение элементов, стратегия роста (×1.5), shared-массивы (Copy-on-Write)
- [Hash](./hash.md) — `RHash`: AR table для маленьких хешей (≤8), ST table для больших, переход между ними, сохранение порядка вставки
- [String](string.md) — `RString`: embedded/heap для символов, кодировки, Copy-on-Write, frozen strings и интернирование (fstring)

Array вводит паттерн embedded/heap, который повторяется в String. Hash демонстрирует другой подход — адаптивный выбор между двумя представлениями в зависимости от размера.

## Как всё связано

*Этот раздел — итоговая карта для тех, кто прочитал заметки выше. Термины здесь не объясняются — они определены в соответствующих файлах.*

**Embedded vs Heap:** данные рядом с заголовком (один cache miss, без malloc) vs отдельный буфер (два cache miss, malloc + free). Цена embedded — ограниченная ёмкость слота: массив из 4 элементов не помещается в 40-байтный слот. [VWA](../gc.md) смягчает это: слоты до 640 байт вмещают 78 элементов массива или ~135 символов строки без malloc. Hash использует аналогичную идею, но переключается между двумя разными структурами данных (AR table и ST table) вместо двух режимов одного буфера.

**Компактность vs Скорость:** AR table экономит память для маленьких хешей (~136 байт, два cache lines), но линейный поиск деградирует с ростом. ST table добавляет массив бакетов и косвенное обращение, но даёт O(1) поиск. Порог — 8 элементов: при типичных размерах Ruby-хешей (3–7 ключей) AR table быстрее и компактнее.

**Изменяемость vs Дедупликация:** строки изменяемы по умолчанию — удобно (`<<`, `gsub!`), но каждый литерал `"id"` создаёт новый объект. Frozen strings запрещают мутации, а fstrings дедуплицируют одинаковые frozen строки до единственного экземпляра. Цена — потеря мутабельности; выгода — сотни одинаковых строк в Rails-приложении сжимаются до одного объекта.

**Copy-on-Write в массивах и строках:** создание подмассива (`ary[1..3]`) или подстроки (`str[0..4]`) не копирует данные — дочерний объект разделяет буфер родителя. Копирование откладывается до момента модификации. Хеши не используют CoW — их структура данных не допускает простого разделения буфера.

**GC и коллекции:** при записи ссылки в массив или хеш срабатывает [write barrier](../gc.md) для корректной работы generational и incremental GC. Shared-корни (массивы и строки, чей буфер разделяется) закрепляются как pinned — GC compaction не может их переместить, пока на них есть ссылки.
