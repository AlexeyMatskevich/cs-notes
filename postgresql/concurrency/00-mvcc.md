# MVCC — версионирование вместо блокировок

**Предпосылки:** [страницы и кортежи](../storage/01-pages-and-tuples.md), [WAL](../durability/00-wal.md).

Даже если данные не теряются при сбое, параллельные транзакции всё ещё могут ломать инварианты. Isolation отвечает за то, что именно видно и когда, не превращая чтения в очередь блокировок.

## Проблема: блокировки убивают производительность

Классический подход к изоляции — блокировки. Читаешь строку — блокируешь её. Другие ждут.

**Проблема:** Читателей много, писателей мало. Если читатели блокируют друг друга — пропускная способность падает катастрофически.

## Решение: MVCC — версионирование вместо блокировок чтения

**MVCC (Multi-Version Concurrency Control)** — храним несколько версий каждой строки. Читатели видят «свою» версию, не блокируя писателей.

**Принцип:** Читатели не блокируют писателей. Писатели не блокируют читателей. Блокируются только писатели между собой (при записи в одну строку).

## Три обязательных компонента MVCC

Чтобы версионирование работало, нужно ответить на три вопроса о каждой версии строки:

1. **КТО** создал/удалил эту версию? (какая транзакция)
2. **ЗАВЕРШИЛАСЬ ли** эта транзакция? (committed, aborted, или ещё выполняется)
3. **КОГДА** она завершилась относительно меня? (до или после моего «старта»)

Без ответа на любой из этих вопросов MVCC не работает. Поэтому PostgreSQL использует три структуры — каждая отвечает на свой вопрос:

```text
┌─────────────────────────────────────────────────────────────────┐
│                    ПРОВЕРКА ВИДИМОСТИ                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Tuple (версия строки)                                          │
│  ┌──────────────────┐                                           │
│  │ xmin = 120       │ ─── КТО создал? Транзакция 120            │
│  │ xmax = 0         │ ─── КТО удалил? Никто (версия актуальна)  │
│  │ data = 'Alice'   │                                           │
│  └──────────────────┘                                           │
│           │                                                     │
│           ▼                                                     │
│  CLOG (pg_xact/)                                                │
│  ┌──────────────────┐                                           │
│  │ XID 120 = ?      │ ─── ЗАВЕРШИЛАСЬ ли? COMMITTED/ABORTED/    │
│  └──────────────────┘     IN_PROGRESS                           │
│           │                                                     │
│           ▼                                                     │
│  Snapshot (в памяти транзакции)                                 │
│  ┌──────────────────┐                                           │
│  │ xmin, xmax, xip  │ ─── КОГДА относительно меня?              │
│  └──────────────────┘     До моего старта или после?            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## Компонент 1: xmin/xmax — КТО создал и удалил версию

Каждая транзакция получает уникальный номер — **XID (Transaction ID)**. Это 32-битный счётчик.

**Почему счётчик, а не timestamp?** Timestamp ненадёжен: две транзакции могут начаться в одну микросекунду, часы на серверах расходятся. Счётчик прост: транзакция 100 точно началась раньше 150.

При создании версии строки PostgreSQL записывает в её заголовок:
- **xmin** — ID транзакции, создавшей версию
- **xmax** — ID транзакции, «удалившей» версию (или 0, если версия актуальна)

```text
UPDATE users SET name = 'Bob' WHERE id = 1;

До UPDATE (транзакция 100 создала строку):
  Tuple1 [xmin=100, xmax=0, data='Alice']

После UPDATE (транзакция 150):
  Tuple1 [xmin=100, xmax=150, data='Alice']  ← старая версия, «удалена» T150
  Tuple2 [xmin=150, xmax=0,   data='Bob']    ← новая версия
```

DELETE работает так же: ставит xmax, не создавая новую версию.

**Проблема 32-битного счётчика:** 2³² ≈ 4 миллиарда транзакций. При высокой нагрузке это конечное число. Когда счётчик переполняется — **transaction ID wraparound**. PostgreSQL использует «заморозку» старых транзакций (freezing). Это одна из причин, почему VACUUM критически важен.

## Компонент 2: CLOG — ЗАВЕРШИЛАСЬ ли транзакция

xmin=100 говорит КТО создал. Но закоммитилась ли транзакция 100? Если откатилась — версии «никогда не было».

**Почему не хранить статус в самом tuple?** При COMMIT нужно обновить ВСЕ созданные строки. Транзакция создала миллион строк на разных страницах — миллион random write. Вспомним: HDD даёт ~100 IOPS. Миллион операций при 100 IOPS = 10000 секунд ≈ 3 часа на один COMMIT. Это убивает производительность. Плюс проблема атомарности: что если сервер упал посередине обновления флагов?

**Решение: CLOG (Commit Log)** — централизованная битовая карта в файлах `pg_xact/`. Каждая транзакция занимает 2 бита:
- `IN_PROGRESS` (00) — выполняется
- `COMMITTED` (01) — закоммичена
- `ABORTED` (10) — откатилась

При COMMIT — изменить 2 бита + fsync. Быстро и атомарно.

## Компонент 3: Snapshot — КОГДА завершилась относительно меня

CLOG говорит ЧТО (committed). Но не говорит КОГДА.

**Проблема:**
```text
Timeline:
     T=1              T=2              T=3
      │                │                │
      ▼                ▼                ▼
 Ты стартуешь    Транзакция 120    Ты читаешь
 (XID=115)       делает COMMIT     tuple с xmin=120
```

Допустим, твой мир «заморожен» на момент T=1 — ты должен видеть данные так, как они были в этот момент. Транзакция 120 закоммитилась в T=2 — после твоего старта. CLOG говорит COMMITTED, но ты не должен видеть эту версию — её не было в твоём «замороженном» мире.

**Решение: Snapshot** — фиксация состояния на момент «старта». Snapshot запоминает: какие транзакции были активны (не завершены) в момент его создания.

Snapshot содержит:
- `xmin` — все транзакции < xmin точно завершены до моего старта
- `xmax` — следующий XID, который будет назначен; транзакций >= xmax ещё не существует
- `xip[]` — список транзакций между xmin и xmax, которые были активны на момент старта

## Как три компонента работают вместе

Полная проверка видимости для tuple с xmin=120:

```text
Мой snapshot: xmin=100, xmax=118, xip=[105, 110]

Шаг 1 (xmin/xmax): Кто создал версию?
  Транзакция 120

Шаг 2 (Snapshot): Существовала ли транзакция 120 на момент моего старта?
  120 >= snapshot.xmax (118) → НЕТ, ещё не существовала
  → НЕВИДИМ. Стоп.
```

Другой пример — tuple с xmin=107:

```text
Шаг 1 (xmin/xmax): Кто создал версию?
  Транзакция 107

Шаг 2 (Snapshot): Существовала ли?
  107 < snapshot.xmax (118) → ДА

Шаг 3 (Snapshot): Была ли активна на момент моего старта?
  107 в xip[]? → НЕТ, значит уже завершилась ДО моего старта

Шаг 4 (CLOG): Как завершилась?
  COMMITTED → ВИДИМ
  ABORTED → НЕВИДИМ (откатилась)
```

## Когда создаётся snapshot — вопрос политики

Snapshot можно создавать с разной частотой:

**Вариант 1: Перед каждым оператором.** Каждый SELECT видит свежие закоммиченные данные. Между двумя SELECT в одной транзакции можно увидеть изменения от других транзакций.

**Вариант 2: Один раз на всю транзакцию.** Все операторы видят одну «замороженную» картину мира. Даже если другие транзакции коммитят — мы их не видим.

Это и есть разные **уровни изоляции** — политики использования snapshot. Каждый вариант даёт определённые гарантии и допускает определённые аномалии.

## Оптимизация: Hint bits — кэширование статуса CLOG

**Проблема:** При каждой проверке видимости обращаемся к CLOG. Миллион строк — миллион обращений. Если CLOG не в кэше — random I/O к диску.

**Решение:** После первой проверки результат кэшируется в заголовке tuple:

```text
HEAP_XMIN_COMMITTED — создатель точно закоммичен
HEAP_XMIN_INVALID   — создатель откатился
HEAP_XMAX_COMMITTED — удалитель точно закоммичен
HEAP_XMAX_INVALID   — удалитель откатился
```

Следующая транзакция видит hint bits и не ходит в CLOG.

**Побочный эффект:** SELECT может порождать запись! Установка hint bits меняет страницу, она становится dirty.

## Цена MVCC: Dead tuples

MVCC дал нам «читатели не блокируют писателей». Но бесплатного не бывает.

Старые версии строк занимают место. После UPDATE старая версия не исчезает — она остаётся с заполненным xmax. PostgreSQL не может удалить её сразу: вдруг какая-то транзакция ещё видит эту версию через свой snapshot?

**Dead tuple** — версия, невидимая ни одной активной транзакции. Мусор.

Если не убирать:
- Таблица разбухает (**bloat**)
- Sequential scan читает больше страниц
- Индексы указывают на мёртвые версии

**VACUUM** — процесс очистки. Он освобождает место, занятое dead tuples. Это обязательная часть эксплуатации PostgreSQL — цена за MVCC.

Snapshot определяет, что видно транзакции, но не определяет, какие аномалии допустимы. [Аномалии транзакций](01-anomalies.md) описывают конкретные проблемы, которые могут возникнуть при недостаточной изоляции.
