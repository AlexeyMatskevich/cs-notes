# Аномалии транзакций

**Предпосылки:** [MVCC](00-mvcc.md).

PostgreSQL реализует изоляцию через MVCC, snapshot, версии строк. Но ЧТО именно эта изоляция гарантирует? И какие проблемы возникают, если гарантии недостаточны?

## Сериализуемость — идеал параллельного выполнения

**Определение:** Результат параллельного выполнения транзакций **сериализуем**, если он совпадает с результатом какого-то последовательного выполнения тех же транзакций.

Не важно, какого именно порядка — любого допустимого. Если T1 и T2 работают параллельно, результат должен быть таким, как будто выполнилась сначала T1, потом T2, или наоборот.

**Почему это важно:** Если гарантирована сериализуемость, программист пишет код, как будто его транзакция единственная. Тестирует — работает. В production параллельные транзакции не создадут результат, невозможный при последовательном выполнении.

**Цена:** Полная сериализуемость требует либо блокировок (транзакции ждут друг друга), либо откатов при конфликтах. Это снижает производительность. Поэтому SQL-стандарт предлагает компромиссные уровни изоляции, допускающие определённые **аномалии**.

## Аномалия — результат, невозможный при последовательном выполнении

Каждая аномалия — это конкретный сценарий, когда параллельное выполнение даёт результат, который не мог бы получиться, если бы транзакции выполнялись одна за другой.

## Аномалия 1: Dirty Read (грязное чтение)

**Сценарий:** Транзакция читает данные, которые другая транзакция изменила, но ещё не закоммитила.

```ruby
# Начальное состояние: Account.find(1).balance = 1000

# === Транзакция T1 (перевод денег) ===
ActiveRecord::Base.transaction do
  account = Account.find(1)
  account.update!(balance: account.balance - 500)  # balance = 500

  # ... длительная операция ...
  # T1 ещё не закоммитила!

  raise "Ошибка валидации!"  # T1 откатывается
end

# === Транзакция T2 (параллельно, читает во время T1) ===
ActiveRecord::Base.transaction do
  account = Account.find(1)
  puts account.balance  # Видит 500 — незакоммиченное значение!

  # T2 принимает решение на основе balance = 500
  # Но T1 откатилась, реальный balance = 1000
end
```

**Сгенерированный SQL:**

```sql
-- T1
BEGIN;
SELECT * FROM accounts WHERE id = 1;        -- balance = 1000
UPDATE accounts SET balance = 500 WHERE id = 1;
-- T1 ещё не COMMIT

-- T2 (параллельно)
BEGIN;
SELECT * FROM accounts WHERE id = 1;        -- Dirty read: видит balance = 500
COMMIT;

-- T1
ROLLBACK;                                    -- balance возвращается к 1000
```

**Timeline:**

```text
T1: BEGIN ──── UPDATE(500) ─────────────────── ROLLBACK
                    │
T2:          BEGIN ─┼─ SELECT ── COMMIT
                    │
                    └─ T2 видит 500, но это значение
                       никогда не существовало!
```

**Почему это плохо:** T2 прочитала данные, которых «никогда не было». T1 откатилась — значение 500 не должно было существовать. Любое решение T2, основанное на этом значении, ошибочно.

**Это самая грубая аномалия:** Ты видишь данные, которые никогда не были валидны. Даже промежуточное состояние — ложь.

## Аномалия 2: Non-Repeatable Read (неповторяемое чтение)

**Сценарий:** Транзакция дважды читает одну строку и получает разные значения, потому что другая транзакция изменила и закоммитила данные между чтениями.

```ruby
# Начальное состояние: Account.find(1).balance = 1000

# === Транзакция T1 (проверка и действие) ===
ActiveRecord::Base.transaction do
  account = Account.find(1)
  puts account.balance  # 1000

  # Проверяем: достаточно ли денег для крупной операции?
  if account.balance >= 1000
    # ... подготовка к операции ...
    sleep(2)  # Симуляция задержки

    # Перечитываем для надёжности
    account.reload
    puts account.balance  # 500 — другое значение!

    # Условие уже не выполняется, но мы уже начали операцию
  end
end

# === Транзакция T2 (параллельно) ===
ActiveRecord::Base.transaction do
  account = Account.find(1)
  account.update!(balance: account.balance - 500)  # 1000 → 500
end  # COMMIT между двумя SELECT в T1
```

**Сгенерированный SQL:**

```sql
-- T1
BEGIN;
SELECT * FROM accounts WHERE id = 1;        -- balance = 1000

-- T2 (между SELECT'ами T1)
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;
COMMIT;

-- T1 (продолжение)
SELECT * FROM accounts WHERE id = 1;        -- balance = 500 (другое!)
COMMIT;
```

**Timeline:**

```text
T1: BEGIN ── SELECT(1000) ─────────────── SELECT(500) ── COMMIT
                              │
T2:                    BEGIN ─┼─ UPDATE ── COMMIT
                              │
                              └─ T2 закоммитила между
                                 двумя SELECT в T1
```

**Почему это плохо:** T1 видит мир непоследовательно. Первый SELECT говорит одно, второй — другое. Если T1 принимала решение на основе первого чтения, это решение может быть неверным.

**Чем отличается от dirty read:** Данные, которые видит T1 во втором SELECT, реальны — T2 закоммитила. Но внутри одной транзакции T1 видит два разных состояния мира.

## Аномалия 3: Phantom Read (фантомное чтение)

**Сценарий:** Транзакция дважды выполняет запрос с условием и получает разные наборы строк, потому что другая транзакция вставила новые строки.

```ruby
# Начальное состояние:
# Account id=1, balance=500
# Account id=2, balance=300

# === Транзакция T1 (подсчёт для отчёта) ===
ActiveRecord::Base.transaction do
  # Сколько счетов с balance > 200?
  count1 = Account.where("balance > 200").count
  puts count1  # 2 счёта

  # ... формируем отчёт ...
  sleep(2)

  # Проверяем ещё раз
  count2 = Account.where("balance > 200").count
  puts count2  # 3 счёта — появился фантом!
end

# === Транзакция T2 (параллельно) ===
ActiveRecord::Base.transaction do
  Account.create!(id: 3, balance: 400)  # Новая строка
end  # COMMIT между двумя SELECT в T1
```

**Сгенерированный SQL:**

```sql
-- T1
BEGIN;
SELECT COUNT(*) FROM accounts WHERE balance > 200;  -- 2

-- T2 (между SELECT'ами T1)
BEGIN;
INSERT INTO accounts (id, balance) VALUES (3, 400);
COMMIT;

-- T1 (продолжение)
SELECT COUNT(*) FROM accounts WHERE balance > 200;  -- 3 (фантом!)
COMMIT;
```

**Timeline:**

```text
T1: BEGIN ── SELECT(count=2) ─────────────── SELECT(count=3) ── COMMIT
                                  │
T2:                        BEGIN ─┼─ INSERT ── COMMIT
                                  │
                                  └─ Новая строка появилась
                                     между запросами T1
```

**Почему это плохо:** T1 работает с набором данных, который меняется «под ногами». Отчёт, построенный на первом запросе, не соответствует второму.

**Чем отличается от non-repeatable read:** Существующие строки не изменились — появились новые. Это тоньше: даже если заблокировать все прочитанные строки, новых строк ещё не было — их нечего было блокировать.

## Аномалия 4: Lost Update (потерянное обновление)

**Сценарий:** Две транзакции читают одно значение, вычисляют новое на его основе и записывают. Одно из изменений теряется.

```ruby
# Начальное состояние: Account.find(1).balance = 1000

# === Транзакция T1 (списание 100) ===
ActiveRecord::Base.transaction do
  account = Account.find(1)           # Читает balance = 1000
  new_balance = account.balance - 100 # Вычисляет: 1000 - 100 = 900
  sleep(1)                            # Задержка
  account.update!(balance: new_balance)  # Записывает 900
end

# === Транзакция T2 (списание 200, параллельно) ===
ActiveRecord::Base.transaction do
  account = Account.find(1)           # Тоже читает balance = 1000
  new_balance = account.balance - 200 # Вычисляет: 1000 - 200 = 800
  account.update!(balance: new_balance)  # Записывает 800
end
```

**Сгенерированный SQL:**

```sql
-- T1
BEGIN;
SELECT * FROM accounts WHERE id = 1;        -- balance = 1000
-- T1 вычисляет: 1000 - 100 = 900

-- T2 (параллельно)
BEGIN;
SELECT * FROM accounts WHERE id = 1;        -- balance = 1000
-- T2 вычисляет: 1000 - 200 = 800
UPDATE accounts SET balance = 800 WHERE id = 1;
COMMIT;

-- T1 (продолжение)
UPDATE accounts SET balance = 900 WHERE id = 1;  -- Перезаписывает!
COMMIT;
```

**Timeline:**

```text
T1: BEGIN ── SELECT(1000) ──────────────────────── UPDATE(900) ── COMMIT
                 │                                      │
T2:       BEGIN ─┼─ SELECT(1000) ── UPDATE(800) ── COMMIT
                 │                       │              │
                 └───────────────────────┴──────────────┘
                   Оба читают 1000        T1 перезаписывает
                                          изменение T2
```

**Результат:** balance = 900, хотя должно быть 1000 - 100 - 200 = 700. Списание T2 (200) потеряно.

**Почему это плохо:** Это паттерн **read-modify-write**. Каждая транзакция корректна сама по себе: прочитала, вычислила, записала. Но вместе они теряют данные.

**Важно:** SQL-стандарт не упоминает lost update явно. Эта аномалия возникает из-за паттерна в приложении, а не из-за самой СУБД.

## Аномалия 5: Write Skew (перекос записи)

**Сценарий:** Две транзакции читают пересекающиеся данные, принимают решения на основе прочитанного, и записывают в разные строки. Каждая транзакция корректна, но вместе они нарушают инвариант.

```ruby
# Бизнес-правило: минимум 1 врач должен быть на дежурстве
# Начальное состояние:
# Doctor id=1, name='Alice', on_call=true
# Doctor id=2, name='Bob',   on_call=true

# === Транзакция T1 (Alice хочет уйти с дежурства) ===
ActiveRecord::Base.transaction do
  on_call_count = Doctor.where(on_call: true).count
  puts on_call_count  # 2 врача на дежурстве

  if on_call_count >= 2  # Можно уйти, останется минимум 1
    Doctor.find(1).update!(on_call: false)  # Alice уходит
  end
end

# === Транзакция T2 (Bob тоже хочет уйти, параллельно) ===
ActiveRecord::Base.transaction do
  on_call_count = Doctor.where(on_call: true).count
  puts on_call_count  # Тоже видит 2 врача!

  if on_call_count >= 2  # Можно уйти, останется минимум 1
    Doctor.find(2).update!(on_call: false)  # Bob уходит
  end
end
```

**Сгенерированный SQL:**

```sql
-- T1
BEGIN;
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- 2
-- Условие выполняется: 2 >= 2
UPDATE doctors SET on_call = false WHERE id = 1;     -- Alice уходит
COMMIT;

-- T2 (параллельно)
BEGIN;
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- 2 (T1 ещё не закоммитила)
-- Условие выполняется: 2 >= 2
UPDATE doctors SET on_call = false WHERE id = 2;     -- Bob уходит
COMMIT;
```

**Timeline:**

```text
T1: BEGIN ── SELECT(count=2) ── UPDATE(Alice) ── COMMIT
                  │                   │
T2: BEGIN ────────┼─ SELECT(count=2) ─┼── UPDATE(Bob) ── COMMIT
                  │                   │
                  └───────────────────┘
                  Оба видят 2 врача, оба решают что можно уйти
```

**Результат:** 0 врачей на дежурстве. Инвариант нарушен.

**Почему это самая коварная аномалия:**
1. Каждая транзакция корректна по отдельности
2. Они пишут в разные строки — нет конфликта записи
3. Проблема только в их комбинации
4. Обычные механизмы защиты (блокировка изменяемой строки) не помогают

## Уровни изоляции SQL-стандарта

SQL-стандарт определяет четыре уровня изоляции через допускаемые аномалии:

| Уровень | Dirty Read | Non-Repeatable Read | Phantom Read |
|---------|------------|---------------------|--------------|
| READ UNCOMMITTED | Возможен | Возможен | Возможен |
| READ COMMITTED | Невозможен | Возможен | Возможен |
| REPEATABLE READ | Невозможен | Невозможен | Возможен |
| SERIALIZABLE | Невозможен | Невозможен | Невозможен |

**Что стандарт НЕ упоминает:** Lost update и write skew. Эти аномалии не укладываются в простую таблицу, потому что зависят от паттернов в приложении (read-modify-write) и структуры данных (пересекающиеся чтения).

**Важно:** Стандарт определяет **минимальные** требования. СУБД может давать более сильные гарантии. Например, PostgreSQL на уровне REPEATABLE READ использует Snapshot Isolation, которая предотвращает и phantom read — это сильнее стандарта.

## Связь аномалий с механизмом snapshot

Политика создания snapshot определяет, какие аномалии возможны:

**READ UNCOMMITTED:** Теоретически — нет snapshot, видим всё подряд. На практике PostgreSQL не реализует — MVCC не позволяет видеть незакоммиченные изменения.

**READ COMMITTED:** Новый snapshot перед каждым оператором. Поэтому два SELECT могут видеть разные данные — non-repeatable read возможен.

**REPEATABLE READ:** Один snapshot на всю транзакцию. Все операторы видят одну «замороженную» картину — non-repeatable read невозможен.

**SERIALIZABLE:** Один snapshot + дополнительные проверки на опасные зависимости между транзакциями.

SQL-стандарт определяет минимальные требования к уровням изоляции. PostgreSQL реализует их через MVCC-механизмы — [уровни изоляции](02-isolation-levels.md) описывают конкретную реализацию.
