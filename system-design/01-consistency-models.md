# Модели консистентности

**Предпосылки:** [CAP-теорема](00-cap-theorem.md) (strong consistency vs eventual consistency, linearizability, partition tolerance), понятие [репликации](../databases/distribution.md).

CAP-теорема описывает две крайности: strong consistency (все узлы видят одни данные сразу) и eventual consistency (данные синхронизируются когда-нибудь). Между ними — спектр промежуточных моделей. Реальные системы выбирают точку на этом спектре, которая даёт достаточно гарантий для конкретного сценария без переплаты за ненужную строгость.

```
Strong (Linearizability)
    │
    │   Sequential consistency
    │
    │   Causal consistency
    │
    │   Read-your-writes
    │
    │   Monotonic reads
    │
    ▼
Eventual consistency
```

## Eventual consistency: минимальная гарантия

Если новых записей нет, то рано или поздно все узлы вернут одно и то же значение. Когда именно это произойдёт — не определено: может через 10ms, может через 5 секунд. Нет гарантии, что клиент прочитает собственную запись, и нет гарантии единого порядка операций для разных клиентов.

```
Клиент:  POST "новый пост"     → Node A
Клиент:  GET  список постов    → Node B
Результат: поста нет в списке
```

Node B ещё не получил данные от Node A. Для ленты новостей это терпимо — пост появится через мгновение. Для корзины покупок — раздражает: пользователь добавил товар, а его нет.

## Monotonic reads: время не откатывается назад

Гарантия: если клиент прочитал значение версии V, последующие чтения никогда не вернут значение старее V.

Без этой гарантии возникает проблема «прыгающего значения»:

```
Чтение 1 (Node A): balance = 100
Чтение 2 (Node B): balance = 50    ← более старое значение
```

Пользователь видит, что баланс уменьшился, хотя никаких списаний не было — просто Node B отстаёт от Node A. Monotonic reads гарантирует: увидел 100 → следующее чтение вернёт 100 или больше, но не 50.

Реализуется через отслеживание «версии» последнего прочитанного значения. Следующий запрос направляется только на узлы с версией не ниже.

## Read-your-writes: видишь собственные изменения

Гарантия: после записи тот же клиент гарантированно видит свою запись при последующих чтениях. Другие клиенты могут ещё какое-то время видеть старое значение.

Типичная реализация — sticky sessions (клиент привязан к одному узлу) или read-from-primary-after-write (после записи следующие N секунд читать с primary, потом можно с реплики).

```
Sticky sessions:
    Клиент ──────────────────► Node A (всегда)
    Записал на A → читает с A → видит свою запись

Read from primary after write:
    Клиент ── WRITE ──► Primary
    Клиент ── READ  ──► Primary  (следующие N секунд)
    Клиент ── READ  ──► Replica  (потом, когда реплика догонит)
```

Пользователь меняет аватарку — read-your-writes гарантирует, что он сам сразу видит новую. Другие пользователи могут ещё несколько секунд видеть старую, и это допустимо.

Для данных, принадлежащих одному пользователю (корзина, профиль, настройки), read-your-writes часто достаточно — нет конкуренции за одни и те же данные между разными клиентами.

## Causal consistency: причина перед следствием

Гарантия: если операция B причинно зависит от операции A, то все узлы увидят A перед B. Причинная зависимость означает: клиент прочитал результат A, а потом на основе этого записал B; или записал A, а потом записал B в той же сессии.

Без causal consistency возникают нарушения порядка:

```
Alice:   POST "Кто хочет пиццу?"               (сообщение 1)
Bob:     читает сообщение 1
Bob:     POST "Я хочу!"                        (сообщение 2, ответ на 1)

Charlie на другом узле видит:
    "Я хочу!"              ← сообщение 2
    "Кто хочет пиццу?"     ← сообщение 1
```

Bob ответил на вопрос Alice, но Charlie видит ответ раньше вопроса. Causal consistency гарантирует: если сообщение 2 причинно зависит от сообщения 1, все увидят их в правильном порядке.

Независимые операции causal consistency не упорядочивает. Если Alice и Dave одновременно пишут несвязанные сообщения — их порядок на разных узлах может отличаться, и это нормально.

## Linearizability: как одна машина

Самая строгая модель. Система ведёт себя так, будто существует одна копия данных и все операции выполняются атомарно в некотором порядке. Если запись завершилась — любое последующее чтение с любого узла любым клиентом увидит это значение или более новое.

Это то поведение, которое даёт PostgreSQL на одной машине: записал — прочитал — увидел. Внутри одного узла PostgreSQL реализует это через [уровни изоляции](../databases/postgresql/concurrency/02-isolation-levels.md) — SERIALIZABLE использует SSI (Serializable Snapshot Isolation) вместо сетевого кворума. В распределённой системе linearizability стоит дорого: запись требует подтверждения от кворума (latency), а при partition часть узлов становится недоступной.

## Выбор модели определяется сценарием

Каждая модель — компромисс между строгостью гарантий и стоимостью (latency, доступность).

Персональные данные одного пользователя (корзина, профиль) — read-your-writes достаточно. Чат или лента комментариев — causal consistency, чтобы ответы не опережали вопросы. Финансовые операции — linearizability, потому что цена ошибки несопоставимо выше цены задержки.

Разные части одной системы могут использовать разные модели: отображение баланса — eventual (допустимо показать данные секундной давности), списание средств — linearizability (недопустимо списать дважды).
