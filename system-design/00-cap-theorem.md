# CAP-теорема

**Предпосылки:** базовое понимание [репликации](../databases/distribution.md) (leader/follower, синхронная и асинхронная), понятие network partition, [ACID](../databases/postgresql/storage/00-acid.md) (достаточно знать, что Consistency в ACID — это про constraints).

Пока база данных живёт на одной машине, всё просто: записал — прочитал — увидел то же значение. Проблемы начинаются, когда данные распределяются по нескольким узлам, связанным сетью. Сеть ненадёжна: кабель перережут, роутер зависнет, датацентр потеряет связь. Это не вопрос «если», а вопрос «когда».

CAP-теорема формулирует ограничение, с которым сталкивается любая распределённая система в момент сетевого сбоя.

## Три буквы

### Consistency (линеаризуемость)

CAP Consistency — это **не** ACID Consistency. ACID Consistency означает, что транзакция переводит базу из одного валидного состояния в другое, не нарушая constraints (NOT NULL, FOREIGN KEY, CHECK). Это правила внутри одной базы.

CAP Consistency (она же linearizability) — требование к распределённой системе: после завершения записи любое последующее чтение с любого узла вернёт это значение или более новое. Система ведёт себя так, будто копия данных одна.

```
Запись на Node A: balance = 100
         │
         ▼
С CAP Consistency: чтение с любого узла → 100
```

### Availability (ответ от каждого узла)

CAP Availability — это **не** SLA availability (99.9% uptime за период). CAP Availability означает: каждый запрос к работающему узлу получает ответ с данными. Не ошибку, не таймаут — ответ. Узел не имеет права сказать «подожди, пока я свяжусь с остальными».

### Partition Tolerance (устойчивость к разделению сети)

Network partition — это **не** partitioning (шардирование данных). Network partition — ситуация, когда узлы системы не могут общаться друг с другом: сеть разделилась на изолированные части.

```
ДО partition:                 ПОСЛЕ partition:

Node A ←──────→ Node B        Node A    ✕    Node B
   │               │             │               │
   └───────┬───────┘             │               │
           │                     │               │
        Node C                Node C         (изолирован)
```

Partition Tolerance означает: система продолжает работать при сетевом разделении, а не падает целиком.

## Partition — не выбор, а данность

В распределённой системе partition неизбежен. Отказаться от P и «выбрать CA» нельзя — если данные на нескольких машинах, сеть между ними может разорваться, и система должна как-то себя вести в этот момент.

Поэтому реальный выбор: **когда происходит network partition, сохранить Consistency или Availability. Оба сохранить невозможно.**

«Выбери 2 из 3» — распространённое, но неверное упрощение. CAP — это не меню, а ограничение при сбое.

## Почему невозможно и то, и другое

Два узла: San Francisco и New York. Оба хранят `balance = 100`. Клиент в San Francisco делает `UPDATE balance = 50`. В этот момент связь между городами рвётся.

```
    San Francisco                New York
    ┌─────────────┐      ✕      ┌─────────────┐
    │ balance=50  │             │ balance=100 │
    └─────────────┘  partition  └─────────────┘
```

Клиент в New York хочет прочитать `balance`. Узел в New York должен решить: сохранить **C**onsistency (пожертвовав Availability) — **CP**-система, или сохранить **A**vailability (пожертвовав Consistency) — **AP**-система. **P** (Partition tolerance) остаётся в обоих случаях — partition уже произошёл, от него не откажешься.

**Вариант CP** — отказать: «Я не могу связаться с San Francisco. Возможно, там были изменения. Отдавать потенциально устаревшие данные я не имею права.» Клиент получает ошибку. Данные остаются консистентными, но доступность потеряна.

**Вариант AP** — ответить: «Отдам то, что знаю: `balance = 100`.» Клиент получает ответ, но значение устаревшее (реальное — 50). Доступность сохранена, консистентность потеряна.

Третьего варианта нет. Нельзя одновременно отдать правильные данные и отдать хоть какие-то данные, когда неизвестно, какие данные правильные.

## Кворум: как узлы определяют, кто изолирован

При partition каждый узел видит только свою часть сети. Node1 думает «Node2 и Node3 пропали», а Node2 и Node3 думают «Node1 пропал». Кто прав — объективно неизвестно.

Решение — правило большинства (кворум): узел имеет право обслуживать запросы, только если он связан с **большинством** узлов кластера. В кластере из N узлов большинство = ⌈N/2⌉ + 1 (при нечётном N это (N+1)/2).

```
DC1 (изолирован)           DC2 ←────→ DC3
┌───────┐         ✕        ┌───────┐  ┌───────┐
│ Node1 │                  │ Node2 │  │ Node3 │
└───────┘                  └───────┘  └───────┘

Node1 видит: 1 узел (себя)     Node2 видит: 2 узла
1 < 2 (большинство из 3)       2 ≥ 2 (большинство из 3)
→ В меньшинстве                → В большинстве
→ Отказывает в записи          → Продолжают работать
```

Большинство может быть только одно — невозможно, чтобы две изолированные группы обе имели большинство. Поэтому кластеры обычно нечётные (3, 5, 7): при чётном числе узлов возможна ситуация 2-2, когда большинства нет ни у кого — и система встаёт целиком.

## CP на практике: PostgreSQL с синхронной репликацией

При синхронной репликации primary не подтверждает COMMIT, пока синхронная реплика не подтвердила получение WAL.

```
Клиент           Primary              Replica
   │                │                    │
   │── INSERT ─────→│                    │
   │                │── WAL ────────────→│
   │                │←── ACK ────────────│
   │←── COMMIT OK ──│                    │
```

Если связь с репликой рвётся, primary не может получить ACK — и блокирует все записи. Клиент ждёт, получает таймаут, затем ошибку. Если падает primary — реплика read-only и записи тоже невозможны.

Система жертвует доступностью ради консистентности: данные не расходятся, но при partition записи останавливаются. Настройки, контролирующие это поведение — `synchronous_commit` и `synchronous_standby_names` — описаны в [репликации PostgreSQL](../databases/postgresql/distribution/00-replication.md).

## AP на практике: Redis

Redis-реплики получают данные от master асинхронно. При потере связи с master Sentinel выбирает новый master из доступных реплик.

```
San Francisco (изолирован)       New York
┌────────────┐         ✕         ┌────────────┐
│ Old Master │                   │  Replica1  │
│            │                   │  Replica2  │
└────────────┘                   └────────────┘
```

Sentinel в New York обнаруживает недоступность master, набирает кворум среди Sentinel-ов и промоутит одну из реплик. Как именно Sentinel обнаруживает сбой (SDOWN → ODOWN), набирает кворум и выбирает реплику — в [Sentinel](../databases/redis/distribution/01-sentinel.md). Но старый master в San Francisco не знает, что его заменили — он продолжает принимать записи от локальных клиентов.

```
San Francisco                     New York
┌──────────────┐        ✕        ┌──────────────┐
│ Old Master   │                 │  NEW Master  │
│ balance=500  │                 │ balance=100  │
└──────────────┘                 └──────────────┘
       ↑                                ↑
 клиент пишет                     клиент пишет
```

Когда сеть восстанавливается, старый master узнаёт о новом, становится репликой и **перезаписывает свои данные данными нового master**. Все записи, принятые старым master за время partition, теряются безвозвратно.

CP-система в такой ситуации отказала бы в записи изолированному узлу — клиент получил бы ошибку, но данные не потерялись бы. Redis выбирает доступность: клиент всегда получает «OK», но часть записей может исчезнуть.

## Контраст: асинхронная репликация в PostgreSQL

PostgreSQL с асинхронной репликацией ведёт себя иначе, чем с синхронной. Primary не ждёт подтверждения от реплики и отвечает «COMMIT OK» сразу. Если реплика отвалится — primary продолжает работать. Но если primary упадёт до того, как WAL дошёл до реплики — данные потеряны. Это сдвигает PostgreSQL ближе к AP-поведению.

## Спектр, а не бинарный переключатель

Реальные системы не делятся строго на «чистый CP» и «чистый AP». Они занимают точку на спектре и часто дают настройки:

- **PostgreSQL:** синхронная репликация — CP, асинхронная — ближе к AP.
- **Redis:** по умолчанию AP, но команда WAIT позволяет дождаться подтверждения от реплик.
- **Cassandra:** consistency level настраивается per-query (ONE → AP-поведение, QUORUM → ближе к CP, ALL → жёсткий CP).

Более того, разные части одной системы могут иметь разные требования. Банковская платформа может использовать CP для списаний и зачислений (ошибка в балансе — юридические и финансовые последствия), и AP для отображения истории транзакций (показать данные секундной давности допустимо). Выбор CP или AP определяется ценой ошибки в конкретной операции.

## Eventual Consistency

AP-системы принимают записи без гарантии мгновенной синхронизации между узлами. Данные **когда-нибудь** станут одинаковыми на всех узлах, но не гарантировано когда — через 10ms, через 5 секунд или позже.

```
Запись: новый пост
    │
    ▼
  Node A: видит пост сразу
  Node B: ещё не видит ──→ (100ms) ──→ видит
  Node C: ──→ ──→ (200ms) ──→ видит
```

Это и есть replication lag, видимый как свойство системы: записал на одном узле — прочитал с другого — получил устаревшее значение. Eventual consistency — название для гарантии «рано или поздно синхронизируется, но когда именно — не обещаем».

Когда partition заканчивается и узлы AP-системы снова видят друг друга, им нужно разрешить конфликты — ситуации, когда разные узлы приняли разные записи для одних и тех же данных. Типичные стратегии: last-write-wins (по timestamp; одна запись теряется), merge (объединение изменений; работает не для всех типов данных), передача конфликта приложению. Идеального решения нет — это цена AP.
