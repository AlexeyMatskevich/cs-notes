# System Design

**Предпосылки:** базовое понимание клиент-серверной архитектуры, сетевых протоколов ([networking](../networking/networking.md)), структур данных ([algorithms-and-data-structures/index.md](../algorithms-and-data-structures/algorithms-and-data-structures.md)), баз данных ([databases/](../databases/)).

Проектирование систем — это поиск компромиссов между надёжностью, производительностью, стоимостью и сложностью. Каждое архитектурное решение сдвигает баланс: увеличивая пропускную способность, мы усложняем консистентность; добавляя отказоустойчивость, платим задержкой и деньгами.

## Порядок изучения

Заметки выстроены по зависимостям: фундаментальные ограничения распределённых систем → модели и механизмы → строительные блоки → паттерны проектирования.

## Как всё связано

**Репликация vs Шардинг:** репликация создаёт копии данных — масштабирует чтение и обеспечивает доступность, но все записи идут на один primary. Шардинг делит данные между узлами — масштабирует запись и ёмкость, но ломает глобальные гарантии (JOIN, транзакции, уникальность между шардами). На практике это два слоя одного решения: шардинг между узлами, репликация внутри каждого шарда.

**Consistency vs Availability:** сетевое разделение неизбежно; жёсткая консистентность блокирует записи при partition, eventual consistency сохраняет доступность ценой временных расхождений данных. Выбор зависит от цены ошибки в конкретной операции.

**Строгость гарантий vs Latency:** linearizability требует подтверждения от кворума на каждую операцию — это задержка. Ослабление до causal или read-your-writes снижает latency, сохраняя достаточные гарантии для большинства сценариев.

**Автоматическое слияние vs Универсальность:** CRDT разрешают конфликты без потерь, но работают только для определённых типов данных (счётчики, множества). Произвольные данные требуют vector clocks с ручным разрешением или LWW с допустимой потерей.

**Read throughput vs Write throughput:** индексы и кэш ускоряют чтение, но замедляют запись. Read replicas масштабируют чтение, sharding — запись. B-tree оптимизирован для чтения, LSM-tree — для записи. Профиль нагрузки определяет, какой набор компромиссов выбрать.

**Stateless vs Stateful серверы:** load balancer свободно распределяет запросы, если серверы не хранят состояние. Состояние в памяти сервера (сессии, кэш) привязывает клиента к конкретному серверу и ломает масштабирование. Вынос состояния во внешнее хранилище (Redis, БД) возвращает свободу.

**Latency vs Consistency в кэше:** локальный in-process кэш даёт минимальную latency (нет сетевого RTT), но создаёт проблему когерентности — N копий данных в N процессах рассинхронизируются. Внешний кэш (Redis) решает когерентность ценой RTT на каждый запрос.

**Простота хеширования vs стоимость ребалансировки:** `hash % N` распределяет ключи равномерно, но при добавлении сервера ~75% ключей меняют адрес — массовый cache miss. Consistent hashing минимизирует миграцию до 1/N ключей ценой сложности реализации и необходимости virtual nodes для равномерности.

**Retry vs перегрузка:** retry с backoff помогает при transient failures, но при permanent failure каждый клиент делает N запросов вместо одного — нагрузка на сломанный сервис растёт в N раз. Circuit breaker разрывает этот цикл: после N ошибок — прекратить попытки, дать сервису восстановиться.

**Потеря vs дубликат:** at-most-once теряет сообщения при сбое, at-least-once гарантирует доставку ценой возможных дубликатов. Exactly-once на транспортном уровне невозможна — окно между обработкой и подтверждением неустранимо. Единственный путь — at-least-once + idempotency на стороне получателя. Цена ошибки определяет выбор: потеря аналитического события незаметна, двойное списание денег — инцидент.

**Синхронный вызов vs очередь:** синхронный HTTP-вызов прост в реализации и даёт немедленный результат, но создаёт coupling по доступности — если зависимость недоступна, вызывающий блокируется. Очередь развязывает сервисы по времени, но добавляет сложность (брокер, idempotency, мониторинг) и убирает немедленный ответ. Начинай синхронно, переходи к очереди когда появляется конкретная проблема.

**Очередь сообщений vs лог:** очередь удаляет сообщение после подтверждения — подходит для задач, которые нужно выполнить и забыть. Лог хранит сообщения и позволяет replay — подходит для событий, которые могут понадобиться новым consumers или для аудита. Выбор определяется тем, нужна ли история.

**Универсальность хранилища vs эффективность под паттерн:** PostgreSQL справляется с большинством задач, но физическая организация данных, оптимальная для одного паттерна доступа (OLTP — построчная), неизбежно субоптимальна для другого (OLAP — поколоночная, поиск — инвертированный индекс). Специализированное хранилище даёт порядки по производительности, но каждое — это деплой, мониторинг, экспертиза и data pipeline.

**Читаемость vs эффективность API:** REST с JSON читаем (curl, браузер, логи), но текстовая сериализация и HTTP/1.1 overhead стоят дорого при тысячах вызовов в секунду. gRPC с Protobuf на порядок эффективнее, но бинарный формат непрозрачен для отладки. Выбор определяется тем, кто клиент: человек с curl или сервис в том же датацентре.

**Монолит vs микросервисы:** монолит даёт бесплатную консистентность (одна транзакция) и простоту (один деплой, один процесс), но при росте команды стоимость координации превышает стоимость разработки. Микросервисы дают независимость команд ценой распределённой сложности: сетевые вызовы вместо методов, saga вместо транзакции, eventual consistency вместо ACID. Модульный монолит — промежуточный шаг: границы в коде без цены сети.

**Оркестрация vs хореография:** оркестратор управляет цепочкой зависимых шагов — логика в одном месте, но координатор становится bottleneck для изменений. Хореография через события даёт независимость подписчиков, но размазывает логику и усложняет отладку. Тест: если удаление подписчика ломает процесс — это зависимый шаг для оркестратора; если нет — независимая реакция для хореографии.

**Одна модель vs разделение чтения и записи (CQRS):** пока паттерны чтения и записи совпадают, одна модель — проще и надёжнее (ACID, нет рассинхронизации). Когда запись хочет минимум индексов, а чтение — денормализацию и специализированные хранилища, одна модель обслуживает оба паттерна с компромиссами. CQRS разделяет модели ценой eventual consistency и инфраструктурной сложности.

**Мутабельное состояние vs event sourcing:** UPDATE перезаписывает — текущее состояние известно, история потеряна. Audit log (Logidze) записывает дифы, но остаётся побочным продуктом. Event sourcing делает историю источником истины: состояние вычисляется из событий, проекцию можно пересоздать с нуля. Цена — версионирование событий, snapshots, размер хранилища.
