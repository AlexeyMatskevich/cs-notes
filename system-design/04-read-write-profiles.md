# Профили нагрузки: read-heavy и write-heavy

**Предпосылки:** [CAP-теорема](00-cap-theorem.md) (репликация, partition, CP/AP), [модели консистентности](01-consistency-models.md) (eventual, read-your-writes), базовое понимание [индексов](../databases/postgresql/indexes/) (B-tree ускоряет чтение, но замедляет запись), понятие репликации ([distribution.md](../databases/distribution.md)).

Прежде чем выбирать базу данных, схему репликации или стратегию кэширования, нужно понять характер нагрузки: что преобладает — чтения или записи. Это соотношение определяет, где система упрётся в потолок первой, и какие оптимизации имеют смысл.

## Что такое read-heavy и write-heavy

Профиль нагрузки — это соотношение операций чтения к операциям записи за единицу времени.

В read-heavy системах чтений на порядки больше, чем записей. URL shortener: ссылку создают один раз, переходят по ней тысячи раз. Wikipedia: статью редактируют десятки авторов, читают миллионы пользователей. Лента Twitter/X: пост публикуется один раз, но отображается в лентах тысяч подписчиков. CDN: контент загружается один раз, отдаётся миллионам.

В write-heavy системах записей больше или они сопоставимы с чтениями. Системы логирования: тысячи сервисов непрерывно пишут логи, читают их редко — только при расследовании инцидентов. Сбор метрик и телеметрии: IoT-сенсоры отправляют показания каждую секунду, агрегированные отчёты запрашиваются раз в минуту. Аналитические пайплайны: данные поступают потоком, а запросы к ним — периодические batch-джобы.

Balanced-системы — чтений и записей примерно поровну. Чаты: каждое отправленное сообщение — запись, каждое прочитанное — чтение; в групповом чате одно сообщение порождает столько чтений, сколько участников. Collaborative editing: каждое нажатие клавиши — запись, каждый участник непрерывно читает изменения остальных.

## Почему профиль определяет архитектуру

Разные соотношения упираются в разные бутылочные горлышки, и оптимизация одного типа операций часто ухудшает другой.

### Индексы: ускоряют чтение, замедляют запись

B-tree индекс ускоряет поиск с O(N) до O(log N) — для read-heavy системы это критично. Но каждый индекс — дополнительная структура, которую нужно обновлять при каждой записи. INSERT в таблицу с пятью индексами — это шесть записей на диск вместо одной: сама строка плюс обновление каждого индекса.

В read-heavy системе (URL shortener, каталог товаров) создание дополнительных индексов оправдано: записи редки, а каждое чтение должно быть быстрым. В write-heavy системе (логирование, метрики) каждый индекс — прямой удар по пропускной способности записи. Системы сбора метрик вроде ClickHouse и TimescaleDB минимизируют количество индексов и используют другие стратегии ускорения чтения: сортировку данных при записи, партиционирование по времени, колоночное хранение.

### Storage engine: B-tree vs LSM-tree

Минимизировать индексы — полумера. Более фундаментальный выбор — сам storage engine, определяющий, как данные физически попадают на диск.

**B-tree** (PostgreSQL, MySQL InnoDB) оптимизирован для чтения: данные отсортированы, поиск за O(log N), чтение диапазонов — последовательное. Цена — запись требует random I/O: каждый INSERT ищет нужную страницу на диске, читает, модифицирует и записывает обратно.

**LSM-tree** (Cassandra, RocksDB, LevelDB, HBase) оптимизирован для записи: данные сначала копятся в памяти, затем сбрасываются на диск последовательно (sequential I/O). Sequential I/O на HDD быстрее random примерно в 100 раз, на SSD — в 4–10 раз. Цена — чтение медленнее: данные разбросаны по нескольким файлам на диске, и для поиска одной строки может потребоваться проверить несколько из них. Вторая цена — write amplification: данные перезаписываются многократно при фоновом уплотнении (compaction), на практике 10–30x.

| | B-tree | LSM-tree |
|--|--------|----------|
| Запись | Random I/O (медленнее) | Sequential I/O (быстрее) |
| Чтение | O(log N), одно обращение | Поиск по нескольким файлам |
| Цена | Медленная запись | Write amplification, медленное чтение |
| Системы | PostgreSQL, MySQL | Cassandra, RocksDB, HBase |

### Репликация: read replicas vs sharding

Read-heavy система масштабируется через read replicas: один primary принимает записи, несколько реплик обслуживают чтения. Добавление реплик линейно увеличивает пропускную способность чтения, при этом запись не замедляется (за исключением стоимости репликации).

```
Read-heavy: масштабирование чтения

    ┌─────────┐
    │ Primary │ ← все записи
    └────┬────┘
         │ репликация
    ┌────┴─────┬──────────┐
    ▼          ▼          ▼
┌────────┐ ┌────────┐ ┌────────┐
│Replica │ │Replica │ │Replica │ ← чтения распределены
└────────┘ └────────┘ └────────┘
```

Для write-heavy системы read replicas не помогают: все записи всё равно идут на один primary. Масштабирование записи требует sharding — разделения данных между несколькими независимыми узлами, каждый из которых принимает записи для своего подмножества данных.

```
Write-heavy: масштабирование записи

    ┌────────┐  ┌────────┐  ┌────────┐
    │Shard 1 │  │Shard 2 │  │Shard 3 │
    │ A–H    │  │ I–P    │  │ Q–Z    │
    └────────┘  └────────┘  └────────┘
         ↑           ↑           ↑
    записи для   записи для  записи для
    ключей A–H   ключей I–P  ключей Q–Z
```

Sharding сложнее: появляются вопросы выбора ключа шардирования, перебалансировки при добавлении узлов, cross-shard запросов. Read replicas проще в эксплуатации, но решают только проблему чтения.

### Кэширование: эффективно для read-heavy

[Кэш](07-caching.md) (Redis, Memcached, CDN) хранит результат вычисления или запроса, чтобы не повторять его при следующем обращении. Эффективность кэша напрямую зависит от профиля нагрузки.

В read-heavy системе один и тот же ключ запрашивается многократно. Кэш с TTL 60 секунд при 1000 RPS означает: одна запись в БД, 59999 ответов из кэша. Cache hit rate приближается к 100%, нагрузка на БД падает на порядки.

В write-heavy системе данные постоянно меняются. Закэшированное значение быстро устаревает, кэш нужно инвалидировать при каждой записи. Если записи происходят чаще, чем чтения, кэш не успевает окупить себя: каждое значение инвалидируется до того, как его кто-то прочитает. Cache hit rate падает, а overhead на запись (обновление кэша) остаётся.

```
Read-heavy (URL shortener, 1 запись : 10000 чтений):
    Запись slug → кэш, TTL 24h
    10000 чтений → все из кэша
    Hit rate ≈ 99.99%

Write-heavy (счётчик просмотров, 1000 записей/сек):
    Каждая запись инвалидирует кэш
    Чтение: кэш почти всегда пустой
    Hit rate ≈ 0%
    Решение: буферизация записей (накопить N, записать разом)
```

### Консистентность: связь с профилем нагрузки

Read-heavy системы с репликами неизбежно сталкиваются с replication lag: данные записаны на primary, но ещё не дошли до реплики, с которой читает пользователь. Для большинства read-heavy сценариев eventual consistency допустима — пользователь увидит обновлённую статью через секунду, а не мгновенно. Read-your-writes решает проблему «не вижу свою правку» через sticky sessions или read-after-write с primary.

Write-heavy системы чаще сталкиваются с конфликтами записей, особенно при sharding: два клиента обновляют один и тот же ключ на разных шардах (если шардирование допускает это) или пишут данные, которые нарушают глобальные ограничения. Здесь выбор между CP и AP из [CAP-теоремы](00-cap-theorem.md) проявляется острее.

## Буферизация и батчинг: приём для write-heavy

Когда записей слишком много для обработки по одной, их накапливают и обрабатывают пачками.

Вместо 1000 INSERT в секунду — один bulk INSERT из 1000 строк раз в секунду. Это эффективнее: меньше round-trip до базы, меньше обновлений индексов (batch может оптимизировать), меньше вызовов fsync (принудительный сброс данных из буфера ОС на диск). Цена — данные доступны не мгновенно, а с задержкой буферизации.

Очередь сообщений (Kafka, RabbitMQ) играет роль буфера между источником записей и хранилищем. Продюсеры пишут в очередь с максимальной скоростью, консьюмеры читают из неё и пишут в БД в контролируемом темпе. Это защищает БД от пиков нагрузки: вместо 100 000 записей в секунду во время пика база получает стабильные 10 000, а остальные ждут в очереди.

```
Без буферизации:
    Клиенты ──(100K/сек)──► БД  → перегрузка

С буфером (очередь):
    Клиенты ──(100K/сек)──► Kafka ──(10K/сек)──► БД  → стабильная нагрузка
                               │
                          данные ждут в очереди
                          (задержка секунды-минуты)
```

## Как определить профиль своей системы

На этапе проектирования профиль оценивается из бизнес-логики. Сколько пользователей читают на одного пишущего? Как часто данные обновляются? Допустима ли задержка между записью и видимостью?

На работающей системе профиль измеряется: соотношение SELECT к INSERT/UPDATE/DELETE в PostgreSQL (`pg_stat_statements`), количество GET к SET в Redis (`INFO commandstats`), read IOPS к write IOPS на уровне диска.

Профиль может меняться со временем и отличаться для разных частей системы. Лента соцсети — read-heavy (посты читаются чаще, чем создаются), но подсистема уведомлений — write-heavy (каждое действие порождает десятки записей уведомлений). Каталог товаров — read-heavy днём (пользователи просматривают), но write-heavy ночью (импорт обновлений от поставщиков).

## Сводка архитектурных решений

| Решение | Read-heavy | Write-heavy |
|---------|-----------|-------------|
| Индексы | Больше индексов — быстрее поиск | Минимум индексов — быстрее запись |
| Storage engine | B-tree (PostgreSQL, MySQL) | LSM-tree (Cassandra, RocksDB) |
| Масштабирование | Read replicas | Sharding |
| Кэширование | Высокий hit rate, большой эффект | Низкий hit rate, буферизация записей |
| Консистентность | Eventual / read-your-writes достаточно | Конфликты записей — CP или CRDT |
| Буферизация | Редко нужна | Батчинг, очереди — стандартный приём |
