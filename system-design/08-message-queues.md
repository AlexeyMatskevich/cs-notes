# Message Queues: асинхронная коммуникация между сервисами

**Предпосылки:** [паттерны надёжности](06-reliability-patterns.md) (idempotency, retry, timeout).

## Три проблемы прямого вызова

Пользователь оформляет заказ в интернет-магазине. Система должна зарезервировать товар на складе, списать деньги с карты, отправить подтверждение на email, записать событие в аналитику. Простейший подход — синхронные HTTP-вызовы из обработчика заказа:

```
POST /orders
  → warehouse.reserve()
  → billing.charge()
  → email.send()
  → analytics.record()
  → return "Заказ оформлен"
```

При небольшой нагрузке и надёжных сервисах это работает. Проблемы появляются при росте.

**Coupling по доступности.** Если склад недоступен — весь заказ не оформляется. Четыре сервиса означают четыре точки отказа: любой упавший блокирует всю операцию. Доступность системы — произведение доступностей всех зависимостей: 99.9% × 99.9% × 99.9% × 99.9% = 99.6%.

**Потеря работы при падении.** Сервер начал обработку, вызвал склад и биллинг, но упал до отправки email. Пользователь заплатил, товар зарезервирован — но подтверждение не пришло. При перезапуске сервера состояние потеряно: непонятно, что было сделано, а что нет.

**Разница в скорости.** Склад отвечает за 50ms, биллинг — за 500ms, email — за 2 секунды. Пользователь ждёт суммарные 2.5 секунды, хотя для ответа «заказ принят» достаточно было бы 50ms. В пиковые часы аналитика не справляется с потоком и начинает таймаутить, блокируя все заказы.

## Message broker: посредник между producer и consumer

Решение — вынести коммуникацию в отдельный компонент. **Message broker** (брокер сообщений) принимает сообщения от отправителей (producers), хранит их и доставляет получателям (consumers).

```
Producer (обработчик заказа)
    ↓ publish
[Message Broker]
    ↓ consume
Consumer (warehouse / billing / email / analytics)
```

Почему отдельный сервис, а не структура данных в памяти приложения?

**Переживает падение producer и consumer.** Producer положил сообщение — оно живёт в брокере независимо от судьбы producer. Consumer упал — сообщение дождётся нового consumer.

**Развязывает деплои.** Producer и consumer — разные приложения (или разные версии одного). Можно передеплоить consumer, не останавливая producer. Сообщения накопятся в брокере и обработаются после деплоя.

**Предоставляет гарантии.** Persistence, acknowledgment, retry, ordering — ответственность брокера, а не прикладного кода.

## Acknowledgment и гарантии доставки

Центральный вопрос при проектировании очередей: что происходит с сообщением, если consumer упал во время обработки?

**Без подтверждения (acknowledgment)** брокер считает сообщение доставленным в момент отправки consumer. Если consumer упал до завершения обработки — сообщение потеряно. Это **at-most-once** delivery: сообщение обрабатывается не более одного раза (возможно, ноль раз).

**С подтверждением** consumer явно сообщает брокеру: «обработка завершена успешно». Брокер удаляет сообщение только после ACK. Если ACK не пришёл (consumer упал, сеть оборвалась) — брокер возвращает сообщение в очередь для повторной обработки. Это **at-least-once** delivery: сообщение обрабатывается минимум один раз (возможно, несколько раз).

```
[msg1, msg2, msg3] → Consumer
                       ↓ обработка
                       ↓ crash (ACK не отправлен)
[msg1, msg2, msg3] → Consumer₂  ← msg3 обрабатывается повторно
```

At-least-once создаёт проблему дубликатов. Что если consumer успел выполнить работу (списал деньги), но упал до отправки ACK? Сообщение вернётся в очередь, другой consumer спишет деньги повторно.

**Exactly-once** (ровно один раз) кажется идеальным решением. Но это фундаментально невозможно на уровне брокера: есть окно между «работа выполнена» и «ACK получен», где может произойти сбой. Брокер не может знать, что произошло на стороне consumer.

Даже Kafka, которая маркетирует «exactly-once semantics», реализует at-least-once delivery плюс идемпотентность на уровне producer/consumer.

**Exactly-once = at-least-once + idempotency.**

Consumer должен быть написан так, чтобы повторная обработка того же сообщения не ломала систему. Подробнее об идемпотентности — в [паттернах надёжности](06-reliability-patterns.md#idempotency).

## Point-to-Point vs Pub/Sub

До сих пор мы рассматривали сценарий: один producer кладёт сообщение, один consumer забирает. Это **point-to-point** (очередь задач) — каждое сообщение обрабатывается ровно одним consumer.

```
Producer → [Queue] → Consumer₁
                  → Consumer₂  (конкурируют за сообщения)
                  → Consumer₃
```

Три consumer забирают сообщения из одной очереди, но каждое конкретное сообщение достаётся только одному. Так работает [Sidekiq](../rails/sidekiq.md): воркеры конкурируют за задачи.

Другой паттерн — **Pub/Sub** (publish/subscribe). Одно сообщение доставляется всем подписчикам:

```
Publisher → [Topic] → Subscriber₁ (получает копию)
                   → Subscriber₂ (получает копию)
                   → Subscriber₃ (получает копию)
```

Вернёмся к примеру с заказом. Событие «заказ оформлен» интересует несколько систем одновременно: склад, биллинг, email, аналитику. Каждая система должна получить это событие независимо — это pub/sub.

Consumer groups в [Redis Streams](../databases/redis/data-structures/05-stream.md) и Kafka позволяют комбинировать модели. Consumers в одной группе конкурируют за сообщения (point-to-point внутри группы). Несколько групп на одном топике получают все сообщения независимо (pub/sub между группами). Группа «warehouse» из 5 воркеров (point-to-point) плюс группа «analytics» из 2 воркеров — обе получают каждое событие заказа.

## Два архетипа брокеров

Существует принципиальное разделение, которое влияет на архитектуру системы.

### Традиционная очередь

RabbitMQ, AWS SQS, Sidekiq+Redis — сообщение существует в очереди до тех пор, пока consumer не обработает и не подтвердит. После ACK сообщение удаляется навсегда. Очередь — буфер для необработанных задач.

```
Producer → [msg3, msg2, msg1] → Consumer
                                  ACK(msg1)
           [msg3, msg2]          ← msg1 удалён
```

Сообщение — это **задача**, которую нужно выполнить и забыть.

### Распределённый лог

Kafka, Redis Streams — сообщения записываются в append-only лог и не удаляются после обработки. Consumer отслеживает свою позицию (offset) в логе. Разные consumers могут читать один и тот же лог с разных позиций.

```
[msg1, msg2, msg3, msg4, msg5, ...]   ← лог только растёт
        ↑              ↑
   Consumer A     Consumer B
   (offset=2)     (offset=5)
```

Сообщение — это **факт** (событие), который произошёл. Факт не удаляется после того, как кто-то о нём узнал.

### Replay: перечитать историю

Ключевое свойство лога — **replay**: возможность воспроизвести поток событий заново.

Представим: появился новый аналитический сервис, который должен обработать все заказы за последний месяц. С традиционной очередью эти сообщения давно удалены после ACK — новый сервис не может перечитать историю. С логом сообщения на месте: новый consumer начинает с нужного offset и проходит весь лог.

Replay невозможен в традиционной очереди по определению: после ACK сообщение не существует.

### Когда какой архетип

Отправка email после регистрации — традиционная очередь. После отправки информация о задаче не нужна.

Поток событий для аналитики, аудита, или интеграции с новыми сервисами — лог. История должна сохраняться.

## Ordering и partitions

Гарантирует ли очередь порядок? В традиционной очереди с параллельной обработкой — нет.

```
Consumer A забирает msg1, обрабатывает 500ms
Consumer B забирает msg2, обрабатывает 50ms
Consumer B забирает msg3, обрабатывает 50ms

Порядок завершения: msg2, msg3, msg1
```

Даже если очередь отдаёт сообщения в порядке FIFO, параллельная обработка ломает порядок завершения. Для отправки email это неважно — каждое письмо независимо. Но что если сообщения — «пользователь сменил имя на Alice», затем «пользователь сменил имя на Bob»? При обратном порядке обработки имя останется Alice вместо Bob.

### Partition: единица ordering и параллелизма

**Partition (партиция)** — независимый сегмент топика, представляющий собой отдельный append-only лог. Топик — логическая сущность («user-events», «orders»). Физически топик состоит из нескольких партиций.

```
Topic: user-events (3 партиции)

Partition 0: [msg0, msg3, msg6, ...]  → один consumer
Partition 1: [msg1, msg4, msg7, ...]  → другой consumer
Partition 2: [msg2, msg5, msg8, ...]  → третий consumer
```

Сообщения внутри партиции строго упорядочены по времени добавления. Между партициями порядка нет.

Сообщение попадает в конкретную партицию через хеширование:

```
partition_number = hash(partition_key) % количество_партиций
```

Если partition key = user_id, все события одного пользователя попадают в одну партицию. Поэтому ordering внутри пользователя гарантирован: «rename to Alice» всегда обработается раньше «rename to Bob» для того же user_id.

Аналогия с [sharding](../databases/distribution.md#шардинг) прямая: партиция — это шард, partition key — это shard key, hash-функция распределяет данные по узлам.

### Партиции и параллелизм

Один consumer читает одну партицию. **Количество партиций — потолок параллелизма** для consumer group.

| Партиции | Consumers | Результат |
|----------|-----------|-----------|
| 4 | 2 | Каждый consumer читает 2 партиции |
| 4 | 4 | Каждый consumer читает 1 партицию |
| 4 | 6 | 4 работают, 2 простаивают |

Типичная практика: создавать партиций с запасом. Если сейчас 2 consumers справляются — делать 8–16 партиций. Когда нагрузка вырастет, добавляются consumers, и они автоматически перераспределят партиции между собой (rebalancing). Добавить партиции в существующий топик сложнее — ломается распределение ключей.

### Ordering — end-to-end свойство

Партиция гарантирует ordering только для того, что уже записано. Порядок записи — ответственность producers. Даже один producer может нарушить порядок: при асинхронной отправке батчами первый batch может уйти в retry, а второй успешно запишется. Для строгого ordering нужна дополнительная конфигурация producer.

## Backpressure

Очередь абсорбирует разницу в скорости: producer кладёт 1000 msg/sec, consumer обрабатывает 100 msg/sec, сообщения накапливаются. Но что если это не временный всплеск, а постоянное состояние?

```
Время 0:     [////] 1,000 сообщений
Время 1 мин: [////////] 55,000 сообщений
Время 1 час: [///...///] 3,240,000 сообщений
```

Память брокера конечна. В какой-то момент: брокер упадёт с OOM, latency вырастет до часов, или сообщения начнут теряться.

**Backpressure** (обратное давление) — механизм, который сообщает producer: «притормози, consumer не справляется».

**Drop (отбрасывание).** Новые сообщения отклоняются когда очередь полна. Producer получает ошибку и решает сам — retry, сохранить локально, потерять. Подходит когда потеря допустима (метрики, логи).

**Block (блокировка).** Producer блокируется на операции send() пока в очереди не появится место. Producer замедляется до скорости consumer. Опасно если producer — web-сервер: заблокированный send() = зависший HTTP-запрос.

**Overflow to slower storage.** Горячие сообщения в памяти, остальные сбрасываются на диск. Kafka так работает по умолчанию — это лог на диске, память используется как кэш. Throughput падает, но ничего не теряется и не блокируется.

Redis при заполнении памяти (достижении maxmemory) с дефолтной политикой `noeviction` возвращает ошибку на команды записи — это стратегия Drop. Producer (например, Rails-приложение) получит исключение при попытке положить сообщение в очередь.

## Dead Letter Queue

At-least-once означает: если обработка упала — сообщение возвращается в очередь и обрабатывается снова. Но что если сообщение невозможно обработать в принципе?

```ruby
# Consumer получает сообщение
{ "user_id": "abc", "amount": "not-a-number" }

# Парсинг падает
Integer("not-a-number")  # ArgumentError!
```

Сообщение возвращается в очередь. Другой consumer забирает — та же ошибка. Retry. Опять ошибка. Бесконечный цикл. Такое сообщение называют **poison message** — оно блокирует обработку остальных.

**Dead Letter Queue (DLQ)** — очередь для «мёртвых» сообщений. После N неудачных попыток сообщение перемещается в DLQ вместо основной очереди.

```
Основная очередь: [msg4, msg3, msg2]
                      ↓
                  Consumer
                      ↓ (5 failures)
Dead Letter Queue: [msg1]  ← сюда попадают "безнадёжные"
```

DLQ — диагностический инструмент. Сообщения в ней не обрабатываются автоматически. Инженер смотрит: почему упало? Баг в consumer? Невалидные данные от producer? После исправления можно вручную переложить сообщения обратно в основную очередь или удалить.

### Длинный retry перед DLQ

Sidekiq использует retry с exponential backoff: 1-я попытка через 16 сек, 2-я через ~31 сек, вплоть до 25 попыток за ~21 день. Почему такой длинный цикл?

**Transient failures.** Внешний сервис упал, сеть моргнула, rate limit сработал. Через час/день сервис вернётся — накопившиеся задачи обработаются. 3 попытки за 5 минут не помогут, если сервис лежит 2 часа.

**Изменение бизнес-условий.** Денег на счёте не хватило сегодня — клиент пополнит завтра. Платёж пройдёт без вмешательства разработчика.

**Баги в коде consumer.** За 21 день команда заметит ошибки в логах, задеплоит фикс — старые задачи обработаются новым кодом.

Но длинный retry не поможет против poison messages с невалидными данными. `Integer("not-a-number")` будет падать и через 21 день. Поэтому DLQ всё равно нужен как конечная точка.

## Мониторинг очередей

Очередь — буфер. Здоровый буфер почти пустой: сообщения приходят и быстро уходят. Проблема проявляется когда буфер растёт.

**Queue depth (глубина очереди):** количество сообщений, ожидающих обработки. Растущий тренд = consumers не справляются. Это leading indicator — показывает проблему до того, как пользователи заметят задержки.

**Consumer lag (отставание consumer):** для log-based систем — разница между последним записанным offset и текущей позицией consumer. Lag в 1,000,000 сообщений при скорости consumer 1,000 msg/sec = отставание ~17 минут.

**Processing time:** сколько времени занимает обработка одного сообщения. Рост означает проблемы с зависимостями (медленный внешний сервис) или усложнение самих сообщений.

**Error rate:** процент сообщений, уходящих в retry или DLQ.

| Метрика | Здоровая система | Проблема |
|---------|------------------|----------|
| Queue depth | ~0–100 | 50,000 и растёт |
| Consumer lag | секунды | часы и растёт |
| Error rate | <0.1% | >5% |

Характерный паттерн: queue depth вырос с 0 до 10,000 за 10 минут, потом стабилизировался и начал падать, error rate не изменился. Это всплеск нагрузки от producers — очередь абсорбировала пик, consumers постепенно разгребают накопившееся. Система работает как задумано.

## Когда очереди НЕ нужны

Добавление брокера — усложнение архитектуры. Появляется компонент, который нужно мониторить, бэкапить, масштабировать. Код становится сложнее: вместо синхронного вызова — producer, consumer, обработка ошибок, идемпотентность.

**Операция быстрая и надёжная.** Запись в локальную БД занимает 5ms и почти никогда не падает. Очередь ради этого — overhead без пользы.

**Нужен немедленный результат.** Пользователь нажал «купить», ему нужен ответ «заказ оформлен» или «ошибка оплаты» прямо сейчас. Асинхронная обработка не даст ответ вовремя.

**Объём небольшой и стабильный.** 10 запросов в минуту, один сервер справляется. Очередь добавит latency и сложность без выгоды.

**Нет требований к durability.** Если потеря задачи при падении допустима — можно обойтись in-memory очередью в том же процессе.

Правило: начинай с синхронного вызова. Добавляй очередь когда появляется конкретная проблема — ненадёжный внешний сервис, пиковые нагрузки, долгие операции блокируют HTTP-ответ.

## Применённые концепции

| Концепция | Роль в message queues |
|-----------|----------------------|
| At-most-once / at-least-once | Гарантии доставки: без ACK vs с ACK |
| Idempotency | Необходима для exactly-once поверх at-least-once |
| Point-to-point / Pub-Sub | Один consumer vs все подписчики получают сообщение |
| Традиционная очередь vs лог | Сообщение-задача (удаляется) vs сообщение-факт (хранится) |
| Replay | Перечитать историю событий в log-based системе |
| Partition | Единица ordering и параллелизма |
| Backpressure | Защита от перегрузки: drop, block, overflow |
| Dead Letter Queue | Изоляция poison messages |
