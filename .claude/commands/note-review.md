# /note-review — ревью свежего draft

Draft написан по дизайну. Эта фаза проверяет, воплотился ли дизайн в ткань текста так, чтобы заметка действительно обучала, — и исправляет расхождения. Отличия от `/deep-rework`: здесь есть design.md и draft-log.md как контекст, корни известны из дизайна, и работа сфокусирована на воплощении, а не на переосмыслении материала.

## Общие принципы (держать в голове во всех 4 фазах)

**Как читать `styleguide.md`.** Не чеклист — способ мышления. Мини-правила — финальная сверка после размышления.

**Приоритет при конфликте (§0.1).** Инварианты > дуга > полнота > форма. Editor (шаг 3) применяет эту иерархию при столкновении линз — не голосованием, а по уровню.

**Чистый язык (§0.2).** Метатермины, самореференция, следы промпта — отдельная линза (§ Проверка). Это не стилевая придирка, а инвариант.

**V-shape.** Низкие слои переиспользуются наверху как ментальные модели; проверяется линзой Integration (фокус B), а формальная механика ссылок — фокус A.

**Интегрированные ссылки на каждое содержательное упоминание** (structure-guide §6.2), включая якоря на определения внутри того же файла. Проверяется линзой Integration.

**Артефакты.** Фаза пишет `wip/<slug>-review/NN-*.md`. Durable: если сессия прервётся, следующая команда подхватит. Модель: opus.

## Вход

`$ARGUMENTS` — slug.

Обязательно прочитать:
- `wip/<slug>-design.md` — чтобы знать, что заметка **должна была** делать.
- `wip/<slug>-draft-log.md` — что было написано, какие отклонения от дизайна, какие открытые вопросы оставил автор.
- Файлы заметок из `files: [...]` в design.md / draft-log.md.
- `wip/<slug>-draft-artifacts/baseline.ref` — SHA до начала draft'а; нужен для Codex diff.

Если файлов нет или draft-log помечен неполным — остановиться.

## Фаза 0: Картография и hookify-проверка

**Артефакт:** `wip/<slug>-review/00-map.md`.

Прежде чем запускать линзы — короткая ориентировка:

- Пересчитай объём (кол-во файлов, строк).
- Проверь, что hookify-правила по всем заметкам не сработали на красный (запусти `grep`-прогон по regex из `.claude/hookify.*.local.md` на целевых файлах; механические находки — в артефакт). Если линзы смогут повторить то, что уже ловит регулярка — это пустая работа.
- Прочитай draft-log.md секцию «Открытые вопросы для review» — именно в эти точки линзы должны смотреть внимательнее.

Если hookify-правила реально сработали — сначала правишь их, потом запускаешь линзы. Линзам не нужно тратить tokens на то, что регексом ловится.

## Фаза 1: Диагностика — 7 линз параллельно

**Артефакты:** `wip/<slug>-review/01-lenses/<lens>.md`.

`TeamCreate`. 7 teammate'ов, запущенных параллельно. Каждый читает соответствующую главу styleguide **заново как способ мышления**, не как чеклист, и пишет interpretive-отчёт с аргументацией.

Каждому teammate передаётся:
- Точные пути целевых файлов.
- Путь к design.md и draft-log.md как контекст (не как ограничение).
- Пути файлов-предпосылок (для naive reader и integration).
- Обязательство читать соответствующую главу styleguide **целиком** + §0.1 + §0.2.
- Формат вывода: находки с симптомом, корнем, рекомендуемым уровнем L1-L5 (см. ниже), классом решения (correct / compress / split / relocate / rewrite).

### Уровни вмешательства

Единая шкала для editor (фаза 2):

- **L1** — точечная правка (неточный факт, битая ссылка, одно-два предложения).
- **L2** — переструктурирование раздела: материал есть, порядок или акценты неправильные.
- **L3** — переписывание заметки: нет сквозной нити, раздел писался как справка.
- **L4** — структурные изменения: перенос материала между слоями, новые shared-файлы, изменение `Предпосылки`, создание новых заметок или добавление в `wip/layer-gaps.md`.
- **L5** — re-design серии или папки.

Если находок нет или единичные — так и писать. Не изобретать проблемы ради заполнения отчёта.

### Линза: § Результат (styleguide §1)

```text
Прочитай styleguide.md §1 целиком.

Target files: [пути]
Design.md: [путь]
Draft-log.md: [путь]

Реконструируй для каждого файла:
- какой сдвиг в голове читателя заметка пытается произвести;
- что зафиксировано в design.md как сдвиг — и отличается ли реальный текст от плана;
- три стороны эффекта (в голове / в поведении системы / когда становится правильным инструментом);
- глубина и границы: потерял ли текст смысл, если убрать внутреннее устройство?

Задай тексту:
- Результат — это сдвиг или тавтология «теперь читатель знает X»?
- Три стороны эффекта очевидны к концу заметки или остались декларациями?
- Результат управляет глубиной — или автор вышел ниже пола ради полноты темы?
- Мотивация и результат различаются — или вся тяга свалена в «ты узнаешь X»?

Не делай:
- не требуй, чтобы результат был явно проговорён в тексте (должен быть очевиден, не объявлен);
- не путай «тема заметки» с «результат для читателя»;
- не вводи pass/fail по пунктам — это линза мышления.
```

### Линза: § Читатель (styleguide §2)

```text
Прочитай styleguide.md §2 целиком.

Target files: [пути]. Также прочитай файлы из Предпосылок [пути] — не для проверки, а чтобы понять, какую именно модель они оставляют в голове.

Реконструируй:
- инвентарь схем из Предпосылок: какие концепции читатель реально может использовать;
- наивная модель из design.md — выдержана ли она как рычаг мотивации в тексте?
- threshold-концепция (если дизайн так пометил) — построена ли дуга вокруг самого перехода?
- слои зависимостей (Предпосылки смотрят вниз или в тот же слой?).

Задай тексту:
- Контракт Предпосылок соблюдён? Все технические термины либо там, либо вводятся?
- Наивная модель названа и использована как рычаг — или сразу дан ответ?
- Декоративная точность — термины и числа, которые не двигают цель заметки?
- Имена без опоры (WAL, LATERAL, task_struct) без этимологии / functional gloss / кодовой привязки?
- Скрытые предпосылки вверх — место, где нужен более прикладной слой, чем объявлено?

Не делай:
- не требуй тавтологического дублирования Предпосылок в тексте;
- не расширяй Предпосылки — чаще решение это inline-расшифровка + cross-link;
- не увеличивай Предпосылки ради полноты.
```

### Линза: § Дуга (styleguide §3)

```text
Прочитай styleguide.md §3 целиком.

Target files: [пути]
Design.md: [путь] — там зафиксированы источник разрыва, тип сценария, нить, цепочка шагов.

Реконструируй для каждого файла:
- какой разрыв в модели читателя текст обещает закрыть (по дизайну и по факту — совпадают?);
- тип сценария (роль / ограничение / применение) и сквозной ли он;
- тип нити (цель→проблема→решение / цепочка компромиссов / жизненный цикл / путь данных / слои);
- для серий — продолжает ли файл нить предыдущего и оставляет ли следующему.

Прочитай текст как непрерывный поток. Задай:
- Мотивация — ощутимый разрыв или «это важно»?
- Точка входа: читатель видит ситуацию до имени — или имя раньше?
- Сценарий сквозной или декоративный? Убери все технические детали — остаётся ли связная история с вопросом и ответом?
- Мостики причинные или формульные («X решило Y. Но Z.»)?
- Микропаттерны из дизайна (worked example, productive failure, прослеживание, возврат с другого угла) применены там, где могут помочь?

Не делай:
- не хвали переходы, которые только объявляют порядок разделов;
- не ищи формальных нарушений — ищи места, где у читателя пропадает интерес или непонятно зачем ему это.
```

### Линза: § Нагрузка (styleguide §4)

```text
Прочитай styleguide.md §4 целиком.

Target files: [пути]
Design.md: [путь] — там зафиксированы пол/потолок и решение о послойном раскрытии.

Реконструируй:
- уровень абстракции заметки;
- пол и потолок (что ниже — не объясняется локально; что выше — cross-link);
- требовалось ли послойное раскрытие, и применено ли оно правильно.

Задай тексту:
- Спуск ниже пола: детали реализации, которые читатель не может использовать для цели заметки?
- Выход выше потолка: объяснение концепции, которая должна была прийти из Предпосылок?
- От крупного к мелкому: пропуски масштаба?
- Смешивание масштабов в одной секции?
- Код: минимален ли под текущий шаг? Эволюция показана, где уместно (версия 1 → проблема → версия 2)?

Не делай:
- не требуй диаграмм, где проза справляется;
- не расширяй код для полноты;
- не путай «не хватает деталей» с «ниже пола» — это разные ошибки в разных направлениях.
```

### Линза: § Проверка (styleguide §5 + §0.2)

```text
Прочитай styleguide.md §5 целиком и §0.2.

Target files: [пути]

Задай тексту:
- Метатермины styleguide'а в служебном смысле («нарратив», «мостик», «послойное раскрытие» не как TCP/IP stack)?
- Самореферентные обороты («в этой части мы разобрали», «выше дали определение»)?
- Следы промпта, повторяющие инструкцию («как вы просили», «для наглядности рассмотрим»)?
- Формульные мостики («X решило Y. Но Z.» во всех секциях подряд)?
- Шаблонные определения («X — это Y, которое Z») массовыми копиями?
- Решения без симптома — оптимизация прилетает без видимой проблемы?
- Избыточное «мы» («мы научились», «мы разобрались»)?
- 1-2 места, где читатель может остановиться и предсказать — есть?

Не делай:
- не бей по каждому «мы» или «разберём»;
- не требуй сворачиваемых блоков везде — они для типичных контринтуитивных ошибок.
```

### Линза: Naive reader

```text
Ты — ученик, знающий РОВНО следующее и НИЧЕГО больше:
- Нетехнический baseline: связный текст, простая причинность, школьная арифметика.
- Концепции из Предпосылок целевых файлов: для каждого файла-предпосылки извлеки только то, что читатель действительно мог бы использовать. Если файл что-то упоминает, но не делает usable, — не импортируй.

Target files: [пути]. Для серии — читай по порядку, модель переносится.

Читай по 5 строк за раз. ЕСЛИ ТЫ ЧИТАЕШЬ БОЛЬШЕ 5 СТРОК ЗА РАЗ — ЗАДАЧА ПРОВАЛЕНА.

Единственный вопрос: могу ли я продолжать строить рабочую модель, не догадываясь?

Правила:
- никогда не патчь пробелы внешним знанием;
- если можешь продолжать только догадываясь — отметь;
- не судишь о фактической корректности, если она прямо не ломает модель;
- не комментируешь стиль, если он не меняет рост модели.

После каждого блока:
1. Модель ДО: «я понимаю, что...».
2. Эффект: EXPANDS / LINKS / DEEPENS / DOES NOT CHANGE.
3. Проблемы — только из списка: MODEL_BREAK, HIDDEN_KNOWLEDGE, DANGLING, NO_CONNECTION, OVERLOAD, MOTIVATION_GAP.
4. Вердикт блока: CLEAR / CONCERN / BLOCKER.

После всего текста:
- Финальная модель.
- Первая точка необратимого непонимания.
- Осталось заученным vs понятым.
- Общий вердикт.

Будь adversarial. Главный враг автора — проклятие знания.
```

### Линза: Integration

```text
Прочитай styleguide.md §2 (слои зависимостей) + structure-guide.md §5 (размещение) + §6 (cross-links и якоря) целиком.

Target files: [пути]. Также читай обзорный файл домена, обзорные файлы соседних доменов, top-level index.md.
Design.md: [путь] — там V-shape план и план интегрированных ссылок.

Два фокуса — держи раздельно в отчёте.

**Фокус A: reference integration.**
- Integrated links при каждом содержательном употреблении концепции из Предпосылок (§6.2)?
- Внутренние якоря: концепции, определённые в том же файле (в разделах с заголовком), при упоминании в других разделах линкуются на якорь раздела-определения?
- Якоря: если целевой файл широкий — якорь на конкретный подраздел? Якорь — точный текст заголовка, не slug? Wikilink, а не markdown (§6.3)?
- Формат: ссылка в подпапку текущего каталога — wikilink (§6.5)? Остальные случаи — markdown?
- Недостающие концепции: термин, который не объяснён, не в Предпосылках, и для которого нет заметки в репо — кандидат в wip/layer-gaps.md. Запиши: файл, термин, ожидаемый слой, зачем нужен.

**Фокус B: conceptual integration (V-shape).**
Сверь V-shape план из design.md с реальным текстом.
- Для заметок system-design: опирается ли текст на ментальные модели из низких слоёв там, где дизайн это планировал? Где мог бы опереться, но не опирается?
- Для заметок ниже system-design: есть ли мотивирующие upward-link'и там, где они были запланированы?
- V-shape — это узкие точки реального переиспользования модели, не универсальный призыв тянуть всё вниз или вверх. Проверяй именно точки.

Не делай:
- не расширяй Предпосылки — чаще решение это integrated link и якорь;
- не добавляй ссылки ради ссылок;
- не путай фокус A (механика линков) с фокусом B (содержание моста между слоями).

Формат: по каждому файлу → фокус A findings + фокус B findings + wip-queue кандидаты отдельной секцией.
```

## Фаза 2: Editor — синтез корневых причин

**Артефакт:** `wip/<slug>-review/02-roots.md`.

Editor teammate в той же команде (opus). Читает все 7 отчётов + styleguide.md целиком + design.md + draft-log.md + целевые файлы. Если что-то в отчёте линзы неубедительно — спрашивает автора отчёта через `SendMessage`. Не додумывает.

Группирует findings по общему корню. Часто 5-7 симптомов из разных линз — одна причина: раздел писался как справка, а не объяснение; мостик между секциями декоративный; пол протечён из-за желания «быть точным». Фиксится корень, не симптомы.

**§0.1 priority hierarchy.** При конфликте между линзами работает иерархия. Нарушение инварианта (Предпосылки, чистый язык §0.2, причинная корректность) перевешивает вопросы дуги и эстетики. Нарушение дуги перевешивает полноту. Editor решает по уровню, не голосованием.

Для каждого корня: уровень вмешательства (L1-L5), класс решения (correct / compress / split / relocate / rewrite), предлагаемые стратегии — столько, сколько реально имеет смысл (обычно одна, если решение очевидно; несколько, если развилка с trade-offs).

Отдельной секцией — `layer-gaps`: концепции, нужные, но отсутствующие в репо. Пойдут в `wip/layer-gaps.md` при правках.

Формат артефакта:

```markdown
## Root cause 1: <краткое название>
**Симптомы:** (из каких линз, какие файлы, строки)
**Корень:** (что на самом деле сломано)
**Уровень:** L3
**Стратегии:**
- A: (что делать) — trade-off A
- B: (что делать) — trade-off B
**Рекомендация:** A — <одна фраза почему>, или «вопрос пользователю».

## Layer gaps
- <slug концепции> (<слой>) — нужна для <файл:строка>, пока нет в репо
```

После записи артефакта — `TeamDelete`. Команда фазы 1-2 своё отработала; фаза 4 при необходимости создаст новую. Держать две команды параллельно нельзя (одна команда на сессию), и если фаза 4 пойдёт через writer-teammate'ов, они должны стартовать в чистой команде.

## Фаза 3: Чекпоинт с автором

**Артефакт:** `wip/<slug>-review/03-plan.md`.

Покажи автору короткое резюме: сколько корней, их уровни, какие стратегии. Одна большая проблема перекрывает десяток симптомов — их не показывать. Не раздувать до «5 главных» ради круглого числа.

Для очевидных правок (L1-L2 без trade-off'ов) — план предлагается сразу, автор утверждает одним ответом.

Для развилок L3+ — `AskUserQuestion` с вариантами и последствиями для читателя. Автор пользуется LLM, потому что материал ему до конца не знаком; «как лучше?» без вариантов — пустой вопрос. Формулируй последствия не только архитектурно («изменим структуру»), но через читателя («новичок быстрее поймёт X, но эксперт на этом моменте заскучает»).

`03-plan.md` фиксирует: какие файлы меняются, на каком уровне, какой стратегией; какие каскады ожидаются; что уходит в layer-gaps.

## Фаза 4: Правки

**Артефакт:** `wip/<slug>-review/04-fix-log.md`.

- **L1-L2** любого объёма: main agent правит напрямую, без writer-teammate'ов.
- **L3+ на 2+ независимых файлах**: `TeamCreate` с writer teammate'ами, каждый owns непересекающийся набор файлов. Файлы с каскадными связями (обзорный файл домена, `system-design/*`, top-level `index.md`) — на main agent, не на teammate'ов. Перед `TeamCreate` в этой фазе — убедиться, что команда фазы 1-2 уже закрыта (см. конец фазы 2).
- **L4-L5** структурные: main agent owns перемещения файлов, создание новых, обновление плана изучения, добавление в `wip/layer-gaps.md`.

Каждый writer teammate (opus):
- Получает свой набор файлов и соответствующие корни из `02-roots.md`.
- Читает файлы целиком + styleguide.md §1-§5 целиком, не выборочно.
- Пишет по выбранной стратегии.
- Перед сохранением перечитывает собственный текст как читатель с только Предпосылками (§5 styleguide). Находит свои огрехи, правит.
- Отчитывается в log.

Main agent после teammate'ов:
- Сводит каскадные правки (обзорный файл, prev/next соседей, cross-links из других папок).
- Обновляет `wip/layer-gaps.md` новыми записями.
- Записывает `04-fix-log.md`.

## Фаза 5: Верификация

**Артефакт:** `wip/<slug>-review/05-verify.md`.

Две проверки, по возможности параллельно:

**Naive reader повторный** (opus, тот же промпт из фазы 1) на целевых файлах после правок. Не обязательно на весь текст — если правки точечные, можно гонять по секциям. Цель: убедиться, что правки не сломали модель.

**Regression (main agent).** Regex/grep-проверки:
- битые Unicode (U+FFFD);
- широкие Unicode-стрелки в ASCII-диаграммах (`▼`/`▲`/`►`/`◄`/`▶`);
- неэкранированные `$N` в прозе вне code-блоков (structure-guide §8.5);
- markdown-ссылки с якорем (`\[[^\]]+\]\([^)]*\.md#[^)]*\)`) — должны быть wikilink;
- markdown-ссылки в подпапку текущего каталога без `../`-префикса — тоже wikilink;
- оборванные предложения, copy-paste артефакты;
- ссылки на несуществующие файлы и якоря.

Итеративно: находка → фикс → следующий прогон. Два прохода без находок → верификация закрыта.

`TeamDelete` для команды фазы 4, если она создавалась. Для сценариев L1-L2 без writer-teammate'ов эта операция пропускается. Codex в фазе 6 — внешний процесс, не teammate.

## Фаза 6: Codex — опциональный независимый взгляд на diff

**Артефакты:** `wip/<slug>-review/06-codex-styleguide.md`, `wip/<slug>-review/06-codex-factcheck.md`.

Если серия большая или содержит сложные технические утверждения — стоит дать Codex финальный проход по diff'у. Для короткой одиночной заметки с L1-L2 правками фаза пропускается; пользователь утверждает явно.

Два параллельных запуска Codex через `codex-companion task --background`. Codex видит финальный diff после всех Claude-фаз.

**Запуск 1 — styleguide compliance.**
Задача: прочитать `styleguide.md` целиком + diff (`git diff $(cat wip/<slug>-draft-artifacts/baseline.ref)..HEAD -- <пути файлов>`). Для каждого нарушения — файл, строка, правило styleguide по §-номеру (§1 / §2 / §3 / §4 / §5 / §0.1 / §0.2), класс правки (correct / compress / split / relocate / rewrite). §0.1 priority hierarchy: инварианты (Предпосылки, чистый язык, причинность) сначала, потом дуга, полнота, форма.

**Запуск 2 — factcheck.**
Задача: для каждого нового или изменённого технического утверждения в том же diff — сверка с первичными источниками (официальная документация, стандарты, RFC, vendor docs). Приоритет: числа, default'ы, имена параметров, причинные связи «X вызывает Y», примеры кода (синтаксис, семантика, ожидаемый вывод), упрощения, которые могут создать неправильную модель. Для каждого расхождения — файл, строка, утверждение в тексте, что говорит источник, ссылка на источник, класс правки (correct / weaker wording / version scoping / explicit simplification).

Команды:

```bash
node "${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/cache/openai-codex/codex/1.0.3}/scripts/codex-companion.mjs" task --background "<полный prompt styleguide-роли>"
node "${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/cache/openai-codex/codex/1.0.3}/scripts/codex-companion.mjs" task --background "<полный prompt factcheck-роли>"
```

Каждая команда возвращает jobId. Статусы — через `/codex:status <jobId>` не чаще раза в несколько минут. Результаты — через `/codex:result <jobId>`. Когда оба прогона завершены — сохрани отчёты в артефакты.

Codex read-only; правки по его отчётам делает main agent. После правок — один повторный прогон с теми же ролями. Если повторный прогон критических находок не даёт — фаза закрыта.
