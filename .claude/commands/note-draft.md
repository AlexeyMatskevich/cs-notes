# /note-draft — написание по дизайну

Ты пишешь учебный материал по утверждённому педагогическому дизайну.

## Входные данные

Slug: `$ARGUMENTS`
Прочитай:
- `wip/<slug>-design.md` — утверждённый дизайн (следуй ему точно)
- **Файлы предпосылок** (перечислены в design.md) — чтобы знать, что знает читатель

## Перед началом написания

Прочитай из styleguide.md эти секции (не пересказывай — интернализируй):
- **§1.2** — термин только после зависимостей + антипаттерн «декоративная точность»
- **§1.3** — этимология при первом вводе + кодовые якоря (что + где + зачем)
- **§4.2** — мостики: «зачем мы сейчас туда идём» + «решение без симптома = ошибка»
- **§4.3** — детали подчинены сценарию, не порядку документации
- **§4.5** — паттерны: ошибка→осознание, до→после, растущие структуры, контекст при возврате
- **§5.1-5.2** — послойное раскрытие (3+ взаимозависимых → сначала карта) + уровни масштаба
- **§6** — три эффекта: для читателя (какой вопрос закрывается), в системе (наблюдаемое, не тавтология), решения (когда применять)
- **§7.2** — кодовые примеры: реальный vs псевдокод, длина, аннотации, эволюция

Прочитай из structure-guide.md:
- **§4** — шаблон заметки: один `#`, Предпосылки, prev/next, Sources
- **§8.1** — формат блока Предпосылки (короткий → inline, длинный → `<details>`)

## Порядок написания

Для каждого файла из design.md:

### 1. Написать заметку

- Начни с точки входа из design.md (можешь доработать прозу, но суть и порядок «роль→имя» сохранить)
- Следуй дуге — каждое звено дуги = секция
- Вводи детали из карты деталей на нужных шагах
- Не опускайся ниже «пола» документа (из design.md)

**Во время написания каждой секции помни:**

- **Мостик перед ##:** если причинный переход неочевиден, 1-2 предложения: «мы решили X, но это создало проблему Y» (styleguide §4.2). Заголовок — не мостик.
- **Термины:** каждый новый термин — либо объяснён тут же, либо в Предпосылках. Непрозрачный англоязычный термин при первом появлении получает смысловую опору (перевод, расшифровку, functional gloss) (styleguide §1.3).
- **Кодовые имена** (`task_struct`, `vm_area_struct`): привязка к понятию — «что это + где живёт + зачем сейчас» (styleguide §1.3).
- **Паттерн «ошибка→осознание»:** где ошибка типична — попробуем X → неожиданный результат → тут же причина (styleguide §4.5).
- **Контраст «до→после»:** при введении нового инструмента — сначала рабочий пример старым способом, потом новый. Один раз при введении, старый способ — полноценный код (styleguide §4.5).
- **Код:** реальный код когда важен синтаксис, псевдокод когда алгоритм не привязан к языку. Не смешивать. Минимальная длина. «Что делает» = комментарий, «почему» = проза (styleguide §7.2).
- **Эффекты:** заметка должна (хотя бы неявно) отвечать на три «зачем»: какой вопрос теперь понятен, какое наблюдаемое явление объяснено, когда это правильный инструмент (styleguide §6).

### 2. Самопроверка

Перечитай написанное и проверь:
- [ ] Каждый термин либо объяснён выше, либо в Предпосылках?
- [ ] Нет декоративно точных терминов, которые читатель не может использовать?
- [ ] Непрозрачные имена получили смысловую опору при первом вводе?
- [ ] Есть мостики где причинный переход неочевиден?
- [ ] Нет решений/оптимизаций без предшествующего симптома?
- [ ] Читатель видит назначение подсистемы до внутреннего устройства?
- [ ] Детали вводятся когда сценарий их требует, не раньше?
- [ ] Эффект для читателя: понятно какой вопрос заметка закрывает?
- [ ] Эффект в системе: наблюдаемое явление, не тавтология?
- [ ] Код минимален, аннотирован, «почему» — в прозе?
- [ ] Нет метаязыка styleguide, самореференции, протечки промпта?
- [ ] Текст не опускается ниже «пола» документа?

Если нашёл проблемы — исправь и проверь снова.

### 3. Стыковка (для последовательностей)

После каждого файла: вход следующего файла стыкуется с концом текущего? Ограничение текущего → мотивация следующего?

## Вычитка серии на шаблонность (только для мультифайловых серий)

После написания всех файлов, до интеграции — перечитай серию как единый поток. Собери в список:
1. **Все мосты** (последний абзац каждого файла, переходящий к следующему)
2. **Все определения** (фразы вида «X — это Y»)
3. **Все открывающие абзацы**

Проверь каждый список на повторы:
- Одна и та же синтаксическая конструкция использована 2+ раза подряд? Перепиши.
- Мосты следуют формуле «X решило проблему. Но Y.»? Варьируй: вопрос, сценарий, контраст, одно предложение, вообще убрать (если вход следующего файла самодостаточен).
- Определения все через «X — это Y, которое Z»? Часть можно ввести через пример, через роль, через контраст.
- Избыточное «мы» / «мы научились» / «мы разобрались»? Убрать или заменить безличной формой.
- Антропоморфизм программы («программа общается», «данные рассказывают»)? Допустим один раз за серию, не чаще.

Это не стилистическая полировка — это проверка на механические повторы, которые накапливаются при последовательном написании и делают текст роботизированным.

## Интеграционные правки

После написания всех файлов выполни план интеграции из секции «Integration plan» в `wip/<slug>-design.md`:
- Обнови index.md
- Проставь prev/next
- Добавь cross-links в существующие файлы
- Обнови Предпосылки в затронутых файлах
- Добавь мотивационные ссылки вверх/вниз по слоям

Покажи пользователю краткое резюме: что написано, что обновлено. Предложи `/note-review <slug>`.
