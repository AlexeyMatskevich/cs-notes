# /note-draft — написание по дизайну

Дизайн утверждён. Теперь пишем текст, сохраняя причинную связность дуги, контракт `Предпосылки`, пол/потолок и интегрированные ссылки.

## Общие принципы (держать в голове во всех 4 фазах)

**Как читать `styleguide.md`.** Не чеклист — способ мышления. Мини-правила — финальная сверка после размышления.

**Приоритет при конфликте (§0.1).** Инварианты > дуга > полнота > форма. Контракт `Предпосылки`, чистый язык §0.2 и причинная корректность перевешивают любую эстетику.

**Чистый язык (§0.2).** Готовая заметка не должна выглядеть так, будто styleguide существовал. Метатермины, самореференция, следы промпта — протечка.

**V-shape.** Низкие слои (чаще всего — алгоритмы, network, computer, linux, но не только) переиспользуются наверху как ментальные модели; system-design тянет вниз; нижние слои могут получать мотивирующий upward-link без обязательной базы.

**Интегрированные ссылки на каждое содержательное упоминание** (structure-guide §6.2). При каждом содержательном употреблении — ссылка, в том числе на якоря внутри того же файла (если концепция определяется в разделе с заголовком, то вне этого раздела — ссылка на якорь). Максимум одна на концепцию в строке; на следующей — снова.

**Артефакты.** Фаза пишет файлы заметок + `wip/<slug>-draft-log.md` + `wip/<slug>-baseline.ref`. Модель: opus.

## Вход

`$ARGUMENTS` — slug.

Обязательно прочитать:
- `wip/<slug>-design.md` целиком. Особенно: сдвиг, мотивационный черновик, точку входа, цепочку шагов, пол/потолок, V-shape план, план интегрированных ссылок, file structure, integration plan.
- Все файлы-предпосылки из design.md **целиком**, чтобы знать, что читатель реально усвоил, а не в каком порядке называются заголовки.

Если design.md отсутствует или `status != approved` — остановиться.

## Шаг 0: Baseline SHA

Перед первой правкой:

```bash
mkdir -p wip/<slug>-draft-artifacts
git rev-parse HEAD > wip/<slug>-draft-artifacts/baseline.ref
```

Этот SHA пригодится для `/note-review`: Codex-прогон на diff увидит ровно то, что команда изменила, а не случайные предшествующие правки.

## Шаг 1: Подготовка

Прочитай из `styleguide.md`:
- §0.1 (приоритет) и §0.2 (чистый язык) — инварианты, которые нельзя нарушать.
- §1 (результат), §2 (читатель), §3 (дуга), §4 (нагрузка), §5 (проверка) — каждую главу **целиком**, не выборочно. В draft ссылаться на них уже поздно — они должны стоять в голове при каждом абзаце.

Прочитай из `structure-guide.md`:
- §4 (шаблон заметки), §6 (cross-links и якоря целиком, включая §6.3 про формат якоря, §6.5 про wikilink), §8.1 (блок `Предпосылки`), §8.5 (экранирование `$`).

## Шаг 2: Написание файла — итеративный цикл по звеньям

Для каждого файла из design.md работай **по звеньям дуги**, а не монолитно. Каждое звено — мини-цикл:

### 2.1 Что читатель понимает прямо сейчас?

Сформулируй состояние модели читателя на входе в звено:
- Для первой секции файла = инвентарь схем из `Предпосылки` + (для серий) усвоенное в предыдущих файлах серии.
- Для последующих секций = состояние после предыдущей секции.

Это не декоративное упражнение — это стартовая точка для шага 2.3. Если не можешь сформулировать состояние — значит предыдущая секция сработала не так, как планировалось в дизайне; вернись и пересмотри.

### 2.2 Какие утверждения делаем и откуда уверены?

Перечисли содержательные технические claims звена. Для каждого:
- Уверен ли в нём? Если нет — верифицируй **прямо сейчас** через Context7 (для библиотек, фреймворков) или WebSearch + официальные источники (стандарты, RFC, vendor docs).
- Это claim про числа/пороги/default'ы/имена параметров — сверь буквально.
- Это причинная связь «X вызывает Y» — сверь механизм, не только факт.

Не полагайся на training data. Если факт неочевиден и дизайн на нём строится — проверь первоисточник.

### 2.3 Напиши секцию

Читатель пришёл из состояния (2.1) и должен прийти к пониманию, которое создаёт потребность в следующем звене. Форма каждого абзаца решается заново исходя из мысли, которую передаёшь, и состояния читателя — не по шаблону.

**Стиль прозы.** После каждого абзаца задай себе один тест: **«если бы я объяснял это коллеге устно, я бы сказал именно так?»** Если нет — перепиши, как сказал бы. Устное объяснение начинается с ситуации, которую собеседник узнаёт, не с технического артефакта. Не пакует шесть деталей в одно предложение. Даёт модель, потом оговорки — не наоборот. Конкретная форма каждый раз разная.

**Для первой секции файла** возьми точку входа из design.md. Сохрани порядок «роль/работа → имя → устройство»; не больше 1-2 новых сущностей; никаких сравнений производительности до того, как объект стал видимым.

**Для последующих секций** мостик отвечает на вопрос «зачем мы сейчас туда идём» внутри темы. Заголовок мостом не считается. Мостик должен быть **причинным**, не формульным:
- ❌ «Дальше пройдём по структуре разделов…»
- ✅ «Задержку мы уменьшили — но что это стоило по пропускной способности?»

**Секция не начинается с решения без симптома.** Если раздел вводит оптимизацию, перед ним должен быть виден сценарий, в котором операция становится болезненной.

### 2.4 Интегрированные ссылки

Проставь integrated links на ключевые концепции **в момент написания**, не отдельным проходом потом. Правила — из `structure-guide.md` §6 и плана ссылок в design.md:

- **При каждом содержательном употреблении** — ссылка, не только при первом. Максимум одна на концепцию в одной строке; на следующей строке — можно снова.
- **Формат.** Markdown для внешних ссылок без якоря (`[очередь блокировок](../postgresql/concurrency/locks.md)`). Wikilink для ссылок с якорем (`[[databases/postgresql/concurrency/locks#ACCESS EXCLUSIVE|блокировка уровня таблицы]]`). Wikilink для ссылок в подпапку текущего каталога (`[[computer/data-path/cache-coherency|когерентность кешей]]` из `computer/atomic-instructions.md`).
- **Якорь — точный текст заголовка**, не slug. `#Структура B-tree`, не `#struktura-b-tree`. Пробелы, двоеточия, регистр сохраняются.
- **Внутренние якоря того же файла.** Если концепция определяется в разделе с заголовком и позже упоминается в других разделах — при первом содержательном упоминании в каждой такой секции даётся ссылка на якорь раздела-определения. Если определение и упоминание стоят в соседних абзацах одного раздела — ссылка избыточна, читатель только что прошёл через определение.
- **V-shape ссылки из design.md.** Там, где заметка переиспользует ментальную модель из низкого слоя — integrated link при первом содержательном упоминании и при каждом последующем. Upward-link'и — где дизайн их запланировал, интегрируй в ткань абзаца («эта модель вернётся в X»), не отдельным блоком «см. также».
- **Не добавляй ссылок ради ссылок.** Каждая ссылка закрывает локальную неопределённость или открывает путь к углублению.

### 2.5 Инварианты (механическая сверка после секции)

Пройдись глазами:

- **Контракт `Предпосылки`.** Каждый технический термин в секции — либо объяснён выше в этом файле, либо объясняется прямо сейчас, либо явно в `Предпосылки`. Одноразовое упоминание непонятного термина хуже его отсутствия.
- **Имена без опоры.** Непрозрачный термин при первом вводе получает смысловую опору — короткая этимология или functional gloss («WAL = write-ahead log: журнал, который пишется заранее, до изменённых страниц»). Кодовые имена из реализации (`task_struct`, `heap_page`) привязаны: что + где + зачем.
- **Декоративная точность.** Число или термин вставлен ради «глубины», но не работает на цель секции? Убери. Тест: убери термин или число — если предложение не теряет смысл для читателя, оно лишнее.
- **Пол и потолок.** Не залез ниже пола (деталь реализации, которую читатель не использует)? Не вышел выше потолка (объяснение концепции, которая должна была прийти из `Предпосылки` или cross-link)?
- **Масштаб.** Не перескочил через уровень (назначение → поля без промежуточного «части»)? В одной секции — один шаг масштаба.
- **Чистый язык (§0.2).** Нет метатерминов инструкции, самореферентных оборотов, следов промпта?
- **Мостик к следующей секции.** Причинная связь очевидна? Если нет — мостик на уровне предметной причинности.
- **Тест вслух.** Если бы объяснял это коллеге, сказал бы именно так?

Если что-то не сходится — правь прямо сейчас, до следующего звена.

### 2.6 (Для серий) Параллельная разведка следующего звена

Пока пишешь звено N, можешь запустить `researcher` в фоне (subagent, run_in_background) для верификации фактов звена N+1. Промпт: «Тема звена, ключевые claims, источники для сверки». Это экономит время на последовательной верификации.

## Шаг 3: Проверка файла наивным читателем

После того как все звенья файла написаны и внутренние инварианты сошлись, запусти агента (name: `reader-draft`, opus):

```text
Ты — ученик, знающий РОВНО следующее и НИЧЕГО больше:
- Нетехнический baseline: связный текст, простая причинность, школьная арифметика.
- Концепции из Предпосылок: для каждого файла-предпосылки [пути] извлеки только то, что он действительно делает usable. Если файл что-то упоминает, но не делает usable, — не импортируй в модель автоматически.
- (Если это не первый файл серии) Концепции из предыдущих файлов серии: для каждого [пути] — то же извлечение.

Ты НЕ знаешь ничего технического, чего нет выше.

Читаемый файл: <путь>

Читай по 5 строк за раз. ЕСЛИ ТЫ ЧИТАЕШЬ БОЛЬШЕ 5 СТРОК ЗА РАЗ — ЗАДАЧА ПРОВАЛЕНА.

Единственный вопрос: могу ли я продолжать строить рабочую модель, не догадываясь?

Правила:
- никогда не патчь пробелы внешним знанием;
- если можешь продолжать только догадываясь — отметь;
- не судишь о фактической корректности, если она прямо не ломает модель;
- не комментируешь стиль, если он не меняет, растёт ли модель.

После каждого блока:
1. Модель ДО блока: набор «я понимаю, что...».
2. Эффект: EXPANDS / LINKS / DEEPENS / DOES NOT CHANGE.
3. Проблемы — только из списка: MODEL_BREAK, HIDDEN_KNOWLEDGE, DANGLING, NO_CONNECTION, OVERLOAD, MOTIVATION_GAP.
4. Вердикт блока: CLEAR / CONCERN / BLOCKER.

После всего файла:
- Финальная модель.
- Первая точка необратимого непонимания (если есть).
- Осталось ли что-то заученным, а не понятым.
- Закрылась ли мотивация из начала файла.
- Общий вердикт.

Будь adversarial. Главный враг автора — проклятие знания.
```

BLOCKER или HIDDEN_KNOWLEDGE или MODEL_BREAK → фикс → перезапуск reader'a на исправленные участки (не обязательно на весь файл, если правка точечная). CONCERN → правка по усмотрению автора.

### Для серий — параллельность

Пока `reader-draft` проверяет файл N, можешь начинать писать файл N+1 (subagent в foreground, main agent пишет). Но не переходить к стыковке между N и N+1 до закрытия reader'а по N — исправления могут изменить то, что передаётся читателю на входе в N+1.

## Шаг 4: Вычитка серии на формульность

Если файлов больше одного — после завершения всех и закрытия всех reader'ов, собери параллельные списки:

1. Все **мостики** между последним и первым абзацами соседних секций во всех файлах.
2. Все **определения** концепций («X — это Y, которое…»).
3. Все **открывающие абзацы** каждого файла.

Правило из `styleguide.md` §5 про формульные паттерны:
- Если в списке одна конструкция повторяется 2+ раза подряд — разнообразь форму. Варианты: вопрос, контраст, прожитая боль, роль, одно предложение, убрать.
- Если все секции заканчиваются одинаковой формулой («X решило Y. Но Z.») — перепиши повторы.

Формульность — сигнал, что нарратив не выстроен на содержании, переходы формируются механически. Частый источник — длинные серии, где автор копирует шаблон между файлами.

## Шаг 5: Интеграция

Выполни integration plan из design.md:

- **Обзорный файл домена** (`postgresql.md`, `linux.md` и т.д.) — новая запись в «Порядок изучения» + «Как всё связано», если появляется новый trade-off.
- **prev/next** в соседних файлах серии обновлены.
- **Cross-links** в соседних файлах — integrated links при содержательных упоминаниях, с якорями если нужен конкретный раздел, wikilink для якорей и для подпапок.
- **`Предпосылки` в затронутых файлах** — если новая заметка меняет контракт знания для соседей.
- **Top-level `index.md`** и `knowledge-map.canvas` — если появляется новая связь между доменами.
- **Мотивационные upward-link'и** — в низких слоях, где дизайн их запланировал.

Каскадные изменения — main agent owns, не reader-агенты. Reader-агенты видят только целевой файл, не соседей.

## Шаг 6: Log артефакт

Запиши `wip/<slug>-draft-log.md`:

```markdown
---
phase: draft
status: written
topic: <тема>
slug: <slug>
baseline: <SHA из wip/<slug>-draft-artifacts/baseline.ref>
files: [список написанных файлов с путями]
---

# Draft log: <тема>

## Созданные файлы
<пути + кратко о чём каждый>

## Ключевые решения, отошедшие от design.md
<если были отклонения: что изменилось и почему>

## Verifications (что сверял с первоисточниками)
<список проверенных claims + источники>

## Reader-агент: что поймано и исправлено
<по каждому файлу: BLOCKER/HIDDEN_KNOWLEDGE/MODEL_BREAK + фикс>

## Проверки формульности серии
<если серия: что перефразировано после параллельных списков>

## Интеграционные правки
<какие соседние файлы тронуты и как>

## Открытые вопросы для review
<то, что заметил в процессе, но не уверен — в /note-review разберётся>
```

Предложи пользователю `/note-review <slug>`.
