# /note-design — педагогический дизайн + структура + интеграция

**Самая важная фаза.** Здесь решается, будет заметка учить или просто информировать. Файловая структура выводится ИЗ педагогического дизайна, а не наоборот.

Порядок: грубый эскиз → педагогика (8 вопросов) → структура из дуги → интеграция.

## Входные данные

Slug: `$ARGUMENTS`
Прочитай:
- `wip/<slug>-research.md` — видение автора, зависимости, слой, паттерны
- **Сами файлы предпосылок** из research.md — прочитай их содержание, чтобы понимать что РЕАЛЬНО знает читатель

## Шаг 1: Грубый структурный эскиз

Определи то, что НЕ зависит от педагогики:
- Домен/папка (куда класть)
- Слой знания (фундамент / механизм / технология / прикладной)
- Примерный scope (одна тема или серия)
- **Пол и потолок документа:** что ниже нас (спускаться только если объясняет наблюдаемый эффект текущего уровня), что выше нас (только cross-link, не повторять). Прочитай styleguide.md секцию «Уровень абстракции документа» для деталей.

## Шаг 2: Педагогический дизайн (8 вопросов)

Отвечай для **всей темы целиком**, не разбивая на файлы — разбиение будет на шаге 3 из дуги.

**Перед каждым вопросом — прочитай указанную секцию styleguide.md.** Не пересказывай — интернализируй.

---

### 1. Граница знаний

**Прочитай:** styleguide.md §1.1 (Предпосылки как контракт).

Что знает читатель (baseline + Предпосылки). **Явный список того, чего он НЕ знает** — критично для предотвращения проклятия знания.

**Антипаттерн:** список предпосылок, скопированный из оглавления домена. Предпосылки — не навигация, а контракт: ТОЛЬКО то, что текст действительно использует без объяснения.

---

### 2. Слой заметки

Фундамент / механизм / реализация в технологии / прикладное использование. От этого зависит тип сценария (вопрос 5) и пол/потолок (шаг 1).

---

### 3. Мотивация

**Прочитай:** styleguide.md §3.1 (Мотивация) — целиком, включая антипаттерны.

Какой из 4 источников?
- Недостающее звено — знакомое действие без объясняющей части
- Ломающаяся наивная модель — простое объяснение перестаёт работать
- Наблюдаемая странность — эффект, который выглядит магией
- Мост вверх — без этой темы позже останется слепая зона

**Напиши конкретную формулировку** (2-3 предложения), не просто тип.

**Антипаттерны (из styleguide):**
- ❌ Фраза «это важно» — не мотивация
- ❌ Далёкое обещание «когда-нибудь пригодится» — не создаёт интерес сейчас
- ❌ Сравнение неизвестных объектов (`X быстрее Y`, если X ещё не в картине)
- ❌ Искусственная загадка, не вытекающая из Предпосылок

**Тест:** после прочтения мотивации читатель хочет узнать ответ ПРЯМО СЕЙЧАС, а не «может когда-нибудь»?

---

### 4. Точка входа

**Прочитай:** styleguide.md §3.2 (Точка входа: роль раньше имени).

Ситуация ДО названия термина. **Напиши 2-3 предложения** — черновик первого абзаца.

Правило «роль раньше имени»:
1. Наблюдаемая ситуация
2. Недостающая роль/работа
3. Название сущности
4. Только потом внутреннее устройство

**Антипаттерн:** начать с определения или названия. «Хеш-таблица хранит пары ключ-значение…» — если читатель ещё не понял, зачем нужен быстрый поиск.

**Ограничения:** не больше 1-2 новых сущностей; никаких сравнений производительности до того, как объект стал видимым.

---

### 5. Тип сценария

**Прочитай:** styleguide.md §3.3 (Типы сценариев).

- Роль (фундамент): какая работа должна быть выполнена?
- Ограничение (механизм): где известное решение перестаёт работать?
- Применение (прикладной): какая задача заставляет выбрать инструмент?

**Антипаттерн:** натягивать бизнес-кейс с QPS на низкоуровневую тему. Для фундамента сценарий строится вокруг базовой работы системы, не вокруг benchmark'ов.

**Тест:** убрать все технические детали — остаётся связная история с вопросом, ограничением и ответом?

---

### 6. Дуга

**Прочитай:** styleguide.md §4.1 (Выбор нити) и §4.3 (Детали подчинены сценарию).

Цепочка вопрос→ответ: «ситуация X → нужен механизм A → ограничение B → механизм C → …»
Каждое звено = потенциальная секция текста.

**Ключевой принцип:** каждый шаг дуги СОЗДАЁТ НЕОБХОДИМОСТЬ в следующем. Не «A, потом B, потом C» — а «A работает, пока не X → тогда нужен B → B решает X, но создаёт Y → нужен C».

**Антипаттерн:** порядок из официальной документации. Если дуга совпадает с порядком API reference — вероятно, это список фич, а не история.

**Тест:** дуга читается как связная story без технических деталей? Если нет — сценарий декоративный.

---

### 7. Карта деталей

Какая конкретная команда/структура/параметр появляется на каком шаге дуги.

**Антипаттерн:** деталь без привязки к конкретному шагу = кандидат на удаление или вынос в конец. Деталь ниже «пола» документа = декоративная точность.

---

### 8. Связи

- Предпосылки (вниз/тот же слой — НИКОГДА вверх)
- Мотивационные ссылки (вверх — допустимы, но не создают скрытых баз)
- prev в последовательности
- Соседи, требующие обновления (из research.md)

---

### Валидация

1. **Тест первых двух абзацев:** перечитай точку входа. Понятна ли она из ТОЛЬКО baseline + Предпосылки? Нет ли скрытого знания?
2. **Тест дуги:** перепиши дугу простым языком без терминов. Связная история? Если нет — сценарий декоративный.
3. **Тест на порядок документации:** порядок отличается от офдоков? Если совпадает — дуга подогнана под факты.

## Шаг 3: Файловая структура ИЗ ДУГИ

**Прочитай:** structure-guide.md §1-2 (иерархия, именование), §4.1 (разбиение заметок).

Дуга определяет структуру:
- **Естественные разрывы** → границы файлов. Где сценарий доходит до устойчивого состояния и нужно новое ограничение — разрыв.
- **Ветвление сценариев** → подпапки. Независимые оси от базового механизма — это ветви дуги.
- **Порядок нарратива** → нумерация. 00 — начало истории. 01 — где 00 упирается в ограничение.
- **Предпосылки** файла = то, что раскрыто в предыдущих звеньях дуги.

Правила structure-guide: kebab-case, NN-префиксы, макс. 4 уровня, 3+ файлов → подпапка.

**Для мультифайловых последовательностей:**
- Как заканчивается файл N → мотивация для входа N+1
- Какие детали отложены из N в N+1
- Общая дуга серии
- **Перенести 8 вопросов на уровень каждого файла:** уточнить мотивацию, вход, под-дугу

## Шаг 4: Интеграция с репозиторием

**Прочитай:** structure-guide.md §11 (Каскадные изменения), styleguide.md §8.5.

**Если тема НИЖЕ** — заметки выше могут заменить inline на ссылку, добавить в Предпосылки.
**Если тема ВЫШЕ** — заметки ниже могут получить мотивационную ссылку вверх.

Для КАЖДОГО затронутого файла — конкретно что меняется.

## Чекпоинт — САМЫЙ КРИТИЧНЫЙ

### Этап A: Открытый диалог

- «Если бы вы объясняли другу за обедом, с чего бы начали?» — сравни с точкой входа
- «Что делает наивный подход и почему не работает?» — может подсказать лучший сценарий
- «Какое знание кажется очевидным, но не-очевидно для новичка?» — ловит проклятие знания

### Этап B: Валидация

1. «Граница знаний: вот ВСЁ, что знает читатель. Это действительно всё?»
2. «Мотивация создаёт любопытство или декоративная?»
3. «Точка входа доступна при ТОЛЬКО предпосылках?»
4. «Дуга — история или список фич?»
5. «Файловая структура — правильные ли разрывы?»
6. «План интеграции — одобрить?»

## Запись результатов

Запиши в `wip/<slug>-design.md` со структурой:
- YAML frontmatter (phase: design, status: approved, topic, files[])
- Грубый эскиз (домен, слой, scope, пол/потолок)
- Педагогический дизайн (8 вопросов с конкретными ответами)
- Валидация (3 теста: PASS/FAIL)
- Файловая структура из дуги (пути, нумерация, предпосылки, prev/next)
- (если мультифайл) Дизайн каждого файла (под-дуга, вход, мотивация)
- Integration plan (для каждого файла — что меняется)

Предложи перейти к `/note-draft <slug>`.
