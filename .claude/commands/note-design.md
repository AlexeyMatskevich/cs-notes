# /note-design — педагогический дизайн

Самая важная фаза. Здесь решается, будет заметка учить или информировать. Файловая структура выводится ИЗ дизайна.

## Входные данные

Slug: `$ARGUMENTS`
Прочитай:
- `wip/<slug>-research.md` — видение автора, зависимости, слой, паттерны
- **Сами файлы предпосылок** из research.md — прочитай содержание целиком

## Шаг 1: Черновик объяснения

Если тема связана с конкретной технологией — перед черновиком верифицируй ключевые механизмы через context7/WebSearch. Цель: убедиться, что твоё понимание темы точно, а не полагаться только на training data. Обрати внимание на секцию «Внешние источники» в research.md.

Используя ТОЛЬКО содержание прочитанных файлов-предпосылок как базу знаний читателя:

1. **Объяснение**: как объяснить эту тему человеку, который знает ровно то, что в предпосылках? Конкретные слова, конкретные примеры из его багажа знаний.

2. **Главная сложность**: что конкретно делает тему трудной для человека с этими предпосылками? Какое заблуждение у него вероятнее всего? (привязка к конкретным местам в предпосылках, где его знание заканчивается)

3. **Момент понимания**: после какого объяснения/примера/связки тема встаёт на место?

## Шаг 2: Перспектива читателя (агент)

Запусти агента (name: "reader"):

```
Ты знаешь РОВНО следующее:
- Нетехнический baseline: связный текст, простая причинность, школьная арифметика
- Концепции из предпосылок:
  [прочитай каждый файл-предпосылку и извлеки список: какие концепции, термины и механизмы читатель из него усвоил]

Тебе говорят: следующая тема — [тема].

1. Что ты ожидаешь узнать? Какая у тебя модель этой темы?
2. Какие вопросы у тебя сейчас?
3. Какой один вопрос ты бы задал автору?
4. Какие слова из темы ты слышал, но не понимаешь?
```

Прочитай результат. Где ожидания читателя расходятся с твоим объяснением из шага 1 — места для проработки.

## Шаг 3: Грубый эскиз

- Домен/папка
- Слой знания (фундамент / механизм / технология / прикладной)
- Scope (одна тема или серия)
- **Пол и потолок:** прочитай styleguide.md «Уровень абстракции документа»

## Шаг 4: Педагогический дизайн

Прочитай styleguide.md §1.1, §3.1-3.3, §4.1, §4.3.

Используя черновик из шага 1, перспективу читателя из шага 2 и свои знания темы, последовательно реши:

**Граница знаний.** Возьми список концепций из предпосылок (шаг 2) и список вопросов читателя. Какие концепции нужны для понимания темы, но отсутствуют в предпосылках? Где именно знание читателя заканчивается и начинается новое?

**Мотивация.** Напиши текст, после которого читатель захочет узнать ответ. Используй то, что узнал о его ожиданиях из шага 2 — где его модель неполна или ошибочна? Прочитай styleguide.md §3.1 для антипаттернов.

**Точка входа.** Напиши первый абзац: ситуация, понятная читателю ДО ключевого термина. Сравни с объяснением из шага 1 — если они сильно расходятся, подумай почему. Прочитай styleguide.md §3.2.

**Сценарий.** Опиши ситуацию, которая создаёт потребность в теме. Проверка: можешь ли описать её без использования ключевого термина? Если нет — сценарий ещё не найден. Прочитай styleguide.md §3.3.

**Дуга.** Построй цепочку: каждый шаг создаёт проблему, которую решает следующий. Верифицируй причинно-следственные связи: если утверждаешь «A вызывает B» — проверь через WebSearch/context7, что это действительно так. Перепиши цепочку простым языком — если не получается связная история, дуга декоративная. Если порядок совпадает с документацией — это список фич. Прочитай styleguide.md §4.1 и §4.3.

**Карта деталей.** Привяжи каждую команду/структуру/параметр к конкретному шагу дуги. Деталь без привязки к шагу — кандидат на удаление.

**Связи.** Какие файлы станут предпосылками? Какие соседние заметки потребуют обновления? Где prev в последовательности?

### Валидация

Перечитай точку входа и мотивацию. Понятны ли они из ТОЛЬКО baseline + Предпосылки? Перечитай дугу без терминов — связная история?

## Шаг 5: Файловая структура ИЗ ДУГИ

Прочитай structure-guide.md §1-2, §4.1.

- Естественные разрывы в дуге → границы файлов
- Ветвление сценариев → подпапки
- Порядок нарратива → нумерация
- Предпосылки файла = раскрытое в предыдущих звеньях

kebab-case, NN-префиксы, макс. 4 уровня, 3+ файлов → подпапка.

**Для серий:** как файл N заканчивается → мотивация N+1. Для каждого файла — конкретная под-дуга, мотивация, вход.

## Шаг 6: Интеграция

Прочитай structure-guide.md §11, styleguide.md §8.5.
Для каждого затронутого файла — что меняется.

## Чекпоинт

### Диалог с автором

Представь дизайн и объясни ключевые решения: почему такая точка входа, почему такая дуга, где главная сложность для читателя. Спроси: это совпадает с тем, что вы хотели? Что-то смущает?

### Валидация

1. Граница знаний — это действительно всё?
2. Мотивация — создаёт любопытство?
3. Точка входа — доступна при ТОЛЬКО предпосылках?
4. Дуга — история, где каждый шаг создаёт следующий?
5. Структура — разрывы в правильных местах?
6. Интеграция — одобрить?

## Запись

Запиши в `wip/<slug>-design.md`:

```
---
phase: design
status: approved
topic: <тема>
files: [конкретные пути файлов из «Файловая структура из дуги»]
---

# Design: <тема>

## Черновик объяснения
(абзац-объяснение, главная сложность, момент понимания)

## Перспектива читателя
(ожидания, вопросы, расхождения с черновиком)

## Грубый эскиз
(домен, слой, scope, пол/потолок)

## Педагогический дизайн

### Граница знаний
(знает / не знает)

### Мотивация
(черновик текста)

### Точка входа
(черновик первого абзаца)

### Сценарий
(конкретная ситуация)

### Дуга
(цепочка причин и следствий)

### Карта деталей
(деталь → шаг дуги)

### Связи
(предпосылки, prev, соседи)

## Валидация
(PASS/FAIL)

## Файловая структура из дуги
(пути, нумерация, предпосылки, prev/next)

## (если серия) Дизайн файлов
(для каждого: под-дуга, мотивация, вход)

## Integration plan
(для каждого файла — что меняется)
```

Предложи `/note-draft <slug>`.
