# /deep-rework — ревью + переработка заметок

Команда не останавливается на ревью. После того как корневые причины найдены, она перерабатывает материал — вплоть до переноса концепций между слоями, создания новых shared-файлов, перестройки плана изучения и добавления недостающих понятий в `wip/layer-gaps.md` для последующей работы.

Ревью ведут 8 линз: §1 Результат, §2 Читатель, §3 Дуга, §4 Нагрузка, §5 Проверка (пять методических по `styleguide.md`) + Naive reader, Factcheck, Integration (три перспективных). Четыре роли, которые держит команда за кулисами: учитель (§1, §3), методист (§2, §4, §5), автор (factcheck), ученик и наивный ученик (integration, naive reader).

## Вход

`$ARGUMENTS` — путь до файла или папки. Если папка, обрабатываются все `.md` в ней; порядок берётся из обзорного файла домена (секция «Порядок изучения»), если его нет — алфавитный.

Slug вычисляется как путь с `/` → `-`: `linux/kernel/memory-management.md` → `linux-kernel-memory-management`, `databases/postgresql/` → `databases-postgresql`.

## Инварианты

Эти правила выполняются в каждом запуске.

**Персистентность.** Каждая фаза пишет артефакт в `wip/<slug>-rework/NN-<name>.md`. Agent team не переживает `/resume`; если сессия прервётся, следующий запуск смотрит, какие файлы уже на месте, и продолжает с первой незавершённой фазы. Всё, что держится в головах агентов, должно быть сведено в артефакт до завершения фазы.

**Корни, не симптомы.** Editor (фаза 2) ищет общий корень для наблюдаемых проблем. Пять разных findings из пяти линз часто сводятся к одной причине (раздел писался как справка, а не объяснение). Фиксится корень, не симптомы по отдельности. Если корня нет — остаются точечные правки L1-L2, это нормальный исход.

**§0.1 priority hierarchy.** Инварианты > дуга > полнота > форма. Когда линзы противоречат (одна требует разбить раздел, другая — сохранить поток), editor решает по иерархии styleguide.md §0.1, а не голосованием. Нарушение инварианта (Предпосылки, чистый язык §0.2, причинная корректность) перевешивает любую эстетику.

**Disjoint ownership.** Если writer-teammates пишут параллельно, каждый владеет непересекающимся набором файлов. Каскадные правки (обзорный файл домена, prev/next цепочки соседей, cross-links из других папок) владеет main agent, не teammate. Иначе будут перезаписи.

**Codex через Bash, не через `/codex:rescue`.** Для свежего взгляда используется `codex-companion task --background` (см. фазу 5). Skill `/codex:rescue` синхронный и сжигает бюджет Claude.

## Уровни вмешательства

Editor классифицирует каждую найденную проблему по уровню. Пользователь утверждает план в фазе 3 именно в терминах уровней.

- **L1** — точечная правка (неточный факт, пропущенная предпосылка, битая ссылка, одно-два предложения)
- **L2** — переструктурирование раздела: материал есть, порядок или акценты неправильные
- **L3** — переписывание заметки: нет сквозной нити, раздел писался как справка
- **L4** — структурные изменения: перенос материала между слоями, новые shared-файлы, изменение `Предпосылки`, создание новых заметок или добавление в `wip/layer-gaps.md`
- **L5** — re-design серии или папки: меняется архитектура группы заметок, порядок, ветвление, план изучения

## Фаза 0 — Картография

**Артефакт:** `wip/<slug>-rework/00-map.md`

Single subagent (Explore, opus). Строит:
- Список целевых файлов с их `Предпосылки`, prev/next, крупными разделами.
- Положение в curriculum graph: слой (фундамент / механизм / технология / прикладной), домен, соседи.
- Цепочки зависимостей: от чего зависят, кого обслуживают, какие соседи перекрываются по теме.
- V-shape гипотезы: где текст мог бы опираться на другие слои, но не опирается. «Ниже» для заметки — в первую очередь темы её `Предпосылки` и концепции, на которые ведут integrated links; чаще всего в роли «ниже» оказываются наиболее фундаментальные слои — алгоритмы, network, computer, linux, — но не только они. «Выше» — типично system-design.
- Observable гипотезы о проблемах от первого прочтения — не как приговор, а как seed для линз.

После получения карты main agent показывает пользователю: scope (сколько файлов, оценочный объём работы), слой, выраженные гипотезы, и если папка большая (5+ файлов), спрашивает, сфокусировать ли scope или идти по всему.

## Фаза 1 — Диагностика (8 линз, parallel)

**Артефакты:** `wip/<slug>-rework/01-lenses/<lens>.md` — 8 отчётов.

`TeamCreate`. 8 teammates, запущенных параллельно. Каждый читает свою часть styleguide **заново как способ мышления**, не как чеклист, и пишет interpretive отчёт — с аргументацией каждой находки, не просто pass/fail. Детальные промпты — ниже в разделе «Линзы».

Каждому teammate передаётся:
- Точные пути целевых файлов.
- Карта из фазы 0 как input (не как ограничение, а как контекст).
- Обязательство читать соответствующую главу styleguide целиком + §0.1 + §0.2.
- Формат вывода единый: находки с симптомом, корнем, рекомендуемым уровнем L1-L5, классом решения (correct / compress / split / relocate / rewrite).

Если находок нет или они единичные — так и писать. Не изобретать проблемы ради заполнения отчёта.

## Фаза 2 — Editor: синтез корневых причин

**Артефакт:** `wip/<slug>-rework/02-roots.md`

Editor teammate в той же команде (opus). Читает все 8 отчётов + styleguide целиком (не по кускам) + целевые файлы. Если что-то в отчёте неубедительно или требует детализации — спрашивает автора отчёта напрямую через `SendMessage`. Не додумывает.

Группирует findings по общему корню. Применяет §0.1 priority hierarchy: при конфликте между линзами решает по иерархии. Для каждого корня классифицирует уровень вмешательства и предлагает столько стратегий, сколько реально имеет смысл — обычно одна, если решение очевидно; несколько, если есть настоящая развилка с разными trade-offs. Искусственные альтернативы ради полноты не нужны.

Отдельной секцией — `layer-gaps`: концепции, которые нужны, но не описаны в репо; эти пойдут в `wip/layer-gaps.md` в фазе 4.

После записи артефакта — `TeamDelete`. Команда фазы 1-2 своё отработала; фаза 4 при необходимости создаст новую. Держать две команды параллельно нельзя (ограничение платформы — одна команда на сессию).

Формат артефакта:

```markdown
## Root cause 1: <краткое название>
**Симптомы:** (из каких линз, какие файлы, строки)
**Корень:** (что на самом деле сломано)
**Уровень:** L3
**Стратегии:**
- A: (что делать) — trade-off A
- B: (что делать) — trade-off B
**Рекомендация:** A — <одна фраза почему>, или «вопрос пользователю».

## Layer gaps
- <slug концепции> (<слой>) — нужна для <файл:строка>, пока нет в репо
```

## Фаза 3 — Стратегический чекпоинт

**Артефакт:** `wip/<slug>-rework/03-plan.md` — утверждённый план.

Main agent презентует пользователю карту + те root causes, которые реально двигают результат. Одна большая проблема может перекрывать десяток мелких симптомов — их показывать не нужно. Раздувать до круглого количества «главных» тоже не нужно. Для неочевидных развилок — `AskUserQuestion` с конкретными вариантами и понятными последствиями каждого. Для очевидных правок (L1-L2 без trade-off'ов) — план предлагается сразу, пользователь утверждает одним ответом.

Память об авторе: пользователь пользуется LLM, потому что материал ему до конца не знаком. Если спрашивать «а как лучше?» без вариантов и объяснений — ответа не будет. Варианты формулируются вместе с последствиями для читателя, не только архитектурно.

`03-plan.md` фиксирует: какие файлы меняются, на каком уровне, какой стратегией; какие cascades ожидаются; что уходит в layer-gaps.

## Фаза 4 — Переработка

**Артефакт:** `wip/<slug>-rework/04-rework-log.md` — что изменено, в каких файлах, по какой стратегии.

**Перед первой правкой** main agent фиксирует baseline: `git rev-parse HEAD > wip/<slug>-rework/baseline.ref`. Этот SHA позже используется в фазе 7 для `git diff baseline..HEAD`, чтобы Codex видел ровно то, что изменила команда, а не случайные правки до её запуска.

- **L1-L2** любого объёма: main agent редактирует напрямую, без writer-teammates.
- **L3+** на 2+ независимых файлах: `TeamCreate` с writer teammates. Каждый writer owns непересекающийся набор. Файлы с каскадными связями (обзорный файл домена вида `postgresql.md` / `linux.md`, общие shared-файлы, top-level `index.md`) — на main agent.
- **L4-L5** структурные: main agent owns перемещения файлов, создание новых, обновление плана изучения, добавление в `wip/layer-gaps.md`.

Перед `TeamCreate` в этой фазе — убедиться, что команда фазы 1-2 уже закрыта (см. конец фазы 2). Agent teams ограничены одной активной командой на сессию.

Каждый writer teammate (opus):
- Получает план для своего набора из `03-plan.md`.
- Читает свои файлы целиком + `styleguide.md` §1-§5 целиком, не выборочно.
- Пишет согласно выбранной стратегии.
- Перед сохранением перечитывает собственный текст как читатель, знающий только `Предпосылки` и нетехнический baseline (§5 styleguide). Находит свои огрехи, правит.
- Сохраняет и отчитывается в log.

Main agent после всех writer-teammates:
- Сводит каскадные правки (обзорный файл, prev/next соседей, cross-links из других папок).
- Обновляет `wip/layer-gaps.md` новыми записями (формат ниже).
- Записывает `04-rework-log.md`.

## Фаза 5 — Верификация переработки

**Артефакт:** `wip/<slug>-rework/05-verify.md`.

Две проверки, по возможности параллельно:

**Naive reader** (opus, промпт в разделе «Линзы»): rigid 5-line simulation по переработанному тексту. Цель — убедиться, что переработка не сломала модель читателя.

**Regression** (main agent). Regex- и grep-проверки: битые Unicode (U+FFFD), широкие Unicode-стрелки в ASCII-диаграммах (`▼`/`▲`/`►`/`◄`/`▶`), неэкранированные `$` в прозе (§8.5 structure-guide), ссылки на несуществующие файлы или якоря, copy-paste артефакты, оборванные предложения.

Итеративно: если что-то найдено — main agent фиксит, запускает следующую проверку. Два прохода без находок → фаза завершена. Факт-чекинг сознательно вынесен в отдельную фазу 7 и делается через Codex на финальном diff.

## Фаза 6 — Структурное ревью

**Артефакт:** `wip/<slug>-rework/06-cascade.md`.

Main agent проверяет по `structure-guide.md`:
- Именование (kebab-case), раскладка по слоям.
- prev/next — если цепочка поменялась (L4-L5), обновить у всех соседей.
- Cross-links (§6): integrated links при каждом содержательном употреблении, максимум один на строку. Wikilink для ссылок с якорями и для ссылок в подпапку текущего каталога (§6.3, §6.5). Формат якоря — точный текст заголовка, не slug.
- Обзорный файл домена (например, `postgresql.md`, `linux.md`) и top-level `index.md` обновлены, если менялись состав или порядок. Двунаправленность ссылок.
- Каскадные правки в соседних файлах, родительском домене, соседних доменах (если менялся слой).

Если фаза 4 ничего структурного не меняла — эта фаза тривиальна (короткий артефакт «нет каскадов»).

## Фаза 7 — Codex-ревью (независимый взгляд на diff)

**Артефакты:** `wip/<slug>-rework/07-codex-styleguide.md` и `wip/<slug>-rework/07-codex-factcheck.md`.

Два параллельных запуска Codex через `codex-companion task --background`. Codex видит финальный diff после всех Claude-фаз и даёт свежий взгляд со стороны — это последний рубеж перед закрытием работы. В задачах важна конкретика: не «проверь diff», а «проверь такие-то файлы на такие-то правила/факты» с явным списком того, что ожидается в отчёте.

**Запуск 1 — styleguide compliance.**
Задача для Codex: прочитать `styleguide.md` целиком + diff переработанных файлов (`git diff <baseline>..HEAD -- <файлы>`, где baseline = HEAD до начала работы, сохранённый в `wip/<slug>-rework/` в начале фазы 4). Для каждого нарушения — файл, строка, правило styleguide (по §-номеру: §1 Результат / §2 Читатель / §3 Дуга / §4 Нагрузка / §5 Проверка / §0.1 приоритеты / §0.2 чистый язык), класс правки (correct / compress / split / relocate / rewrite). Применять §0.1 priority hierarchy: инварианты > дуга > полнота > форма — Codex сначала вычищает инварианты (Предпосылки, чистый язык, причинность), потом остальное.

**Запуск 2 — factcheck.**
Задача для Codex: для каждого нового или изменённого технического утверждения в том же diff — сверка с первичными источниками (официальная документация, стандарты, RFC, спецификации, vendor docs). Приоритет: числа, default'ы, имена параметров, причинные связи «X вызывает Y», примеры кода (синтаксис, семантика, ожидаемый вывод), упрощения, которые могут создать неправильную ментальную модель. Для каждого расхождения — файл, строка, утверждение в тексте, что говорит источник, ссылка, класс правки (correct / weaker wording / version scoping / explicit simplification).

Команды:

```bash
node "${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/cache/openai-codex/codex/1.0.3}/scripts/codex-companion.mjs" task --background "<полный prompt для styleguide-роли>"
node "${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/cache/openai-codex/codex/1.0.3}/scripts/codex-companion.mjs" task --background "<полный prompt для factcheck-роли>"
```

Каждая команда возвращает jobId. Статусы смотреть через `/codex:status <jobId>` не чаще раза в несколько минут, результаты — через `/codex:result <jobId>`. Когда оба прогона завершены — main agent сохраняет отчёты в соответствующие артефакты.

Codex работает в read-only; правки по его отчётам делает main agent. После правок — один повторный прогон Codex с тем же распределением ролей. Если повторный прогон критических находок не даёт — фаза завершена.

## Фаза 8 — Finalize

- `TeamDelete` — очистить команду фазы 4, если она создавалась. Если не создавалась (сценарии L1-L2), эта операция пропускается.
- Короткое резюме пользователю: что изменено, что добавлено в `wip/layer-gaps.md`, какие открытые вопросы остались (cross-domain cascades, которые пользователь должен утвердить), что нашли и починили Codex-прогоны.
- Артефакты `wip/<slug>-rework/` остаются как история — пользователь сам решит архивировать или удалить.

## Линзы (фаза 1)

Каждая линза получает run-specific briefing: пути целевых файлов, пути файлов-предпосылок, тип материала (single note / sequence / folder). Без предзагрузки выводов — линза должна прийти к своим выводам сама.

Общая доктрина для всех линз: не превращаться в checklist-бота. Читать текст целиком. Предпочитать наименьший набор находок, объясняющий реальную форму проблемы заметки — если один корень объясняет пять симптомов, возвращать корень, не раздутый список. Для каждой находки: симптом + аргументация (почему это ломает понимание или удержание) + предполагаемый корень + класс правки.

### § Результат (styleguide §1, opus)

```text
Прочитай styleguide.md §1 целиком. Идея: заметка проектируется от результата — изменения в голове читателя, не от темы.

Target files: [пути]

Реконструируй для каждого файла до оценки:
- какой сдвиг в голове читателя заметка пытается произвести;
- какой целевой читатель (новичок / освоивший `Предпосылки` / эксперт соседней области);
- где проходят границы темы (что включено, что нет);
- какая глубина обещана и выдержана ли.

Задай тексту:
- Результат сформулирован как сдвиг или как тема? Тавтология типа «читатель понял, что такое X»?
- Три стороны эффекта (в голове / в поведении системы / когда становится правильным инструментом) проявлены или остались декларациями?
- Результат управляет глубиной — или автор вышел ниже пола или выше потолка ради полноты темы как таковой?
- Мотивация и результат различаются — или вся тяга свалена в «ты узнаешь X»?

Не делай:
- не проставляй pass/fail по пунктам — это линза мышления, не чеклист;
- не требуй, чтобы результат был явно проговорён в тексте (он должен быть очевиден, не объявлен);
- не путай «тема заметки» с «результат для читателя».
```

### § Читатель (styleguide §2, opus)

```text
Прочитай styleguide.md §2 целиком.

Target files: [пути]. Прочитай файлы из их `Предпосылки` — не для проверки фактов, а чтобы понять, какую именно модель они оставляют в голове читателя.

Реконструируй:
- инвентарь схем из `Предпосылки`: какие концепции читатель действительно может использовать после прочтения;
- наивную модель, с которой читатель придёт к теме (что он уже думает и вероятно ошибается);
- есть ли в теме threshold-концепция (признак: автор сам не может объяснить «в двух словах без подготовки»);
- слои зависимостей (вниз, в тот же слой, вверх).

Задай тексту:
- Контракт `Предпосылки` соблюдён? Все технические термины либо там, либо вводятся в тексте?
- Наивная модель названа и использована как рычаг — или автор сразу даёт ответ без показа, куда он бьёт?
- Декоративная точность — термины и числа, которые не работают на цель заметки?
- Имена без опоры (`WAL`, `LATERAL`, `task_struct` без этимологии / functional gloss / кодовой привязки)?
- Скрытые предпосылки вверх — место, где для понимания нужен более прикладной слой, чем объявлено?

Не делай:
- не требуй тавтологического дублирования `Предпосылки` в тексте;
- не списывай всё в «добавить в Предпосылки» — контракт узкий; чаще решение это inline-расшифровка + cross-link;
- не расширяй Предпосылки ради полноты — полнота не цель.
```

### § Дуга (styleguide §3, opus)

```text
Прочитай styleguide.md §3 целиком.

Target files: [пути]

Реконструируй для каждого файла:
- какой разрыв в модели читателя текст обещает закрыть;
- тип сценария (роль / ограничение / применение);
- тип нити (цель→проблема→решение / цепочка компромиссов / жизненный цикл / путь данных / слои);
- для серий — как этот файл продолжает нить предыдущего и оставляет её следующему.

Прочитай текст как непрерывный поток. Спроси:
- Мотивация — ощутимый разрыв (ломающаяся модель, недостающее звено, наблюдаемая странность, мост вверх) — или «это важно»?
- Точка входа: читатель видит ситуацию до имени — или имя даётся раньше?
- Сценарий сквозной или декоративный (убери технические детали — остаётся ли связная история с вопросом, ограничением и ответом)?
- Мостики между разделами причинные или формульные («X решило Y. Но Z.»)?
- Микропаттерны (worked example, productive failure, прослеживание, возврат с другого угла) применены там, где могут помочь, — или всё подано справочно?

Не делай:
- не хвали переходы, которые только объявляют порядок разделов;
- не требуй, чтобы каждый файл использовал все три типа сценария;
- не ищи формальных нарушений мотивации — ищи места, где у читателя пропадает интерес или непонятно зачем ему это.
```

Реконструируй для каждого файла:

### Naive reader (opus)

```text
Ты — ученик, знающий РОВНО следующее и НИЧЕГО больше:
- Нетехнический baseline: связный текст, простая причинность, школьная арифметика.
- Концепции из `Предпосылки` целевых файлов: для каждого файла-предпосылки извлеки только то, что читатель действительно мог бы использовать после прочтения. Если файл-предпосылка что-то упоминает, но не делает usable, — не импортируй это в модель автоматически.

Target files: [пути]. Для серии — читай по порядку, модель переносится из файла в файл.

Читай по 5 строк за раз. ЕСЛИ ТЫ ЧИТАЕШЬ БОЛЬШЕ 5 СТРОК ЗА РАЗ — ЗАДАЧА ПРОВАЛЕНА.

Единственный вопрос: могу ли я продолжать строить рабочую модель, не догадываясь?

Правила:
- никогда не патчь пробелы внешним знанием;
- если можешь продолжать только догадываясь — отметь;
- не судишь о фактической корректности, если она прямо не ломает твою модель;
- не комментируешь стиль, если он не меняет, растёт ли модель.

После каждого 5-строчного блока:
1. Модель ДО блока: набор «я понимаю, что...».
2. Эффект блока: EXPANDS / LINKS / DEEPENS / DOES NOT CHANGE.
3. Проблемы — только из списка: MODEL_BREAK, HIDDEN_KNOWLEDGE, DANGLING, NO_CONNECTION, OVERLOAD, MOTIVATION_GAP.
4. Вердикт блока: CLEAR / CONCERN / BLOCKER.

После всего текста:
- Финальная модель.
- Первая точка необратимого непонимания (если есть).
- Что осталось заученным, а не понятым.
- Общий вердикт.

Будь adversarial. Главный враг автора — проклятие знания.
```

### Factcheck (opus + Context7 + WebSearch)

```text
Target files: [пути]

Твоя задача — защитить фактическую корректность, не превращая текст в стерильный формализм. Приоритизируй утверждения, формирующие модель читателя.

Источники: официальная документация, стандарты, RFC, спецификации, vendor docs. Context7 для библиотек и фреймворков. Web search — только когда нет лучшего источника; предпочитай официальные домены.

Приоритет:
- числа, пороги, default'ы, имена параметров, версионное поведение;
- причинные связи «X вызывает Y»;
- примеры кода: синтаксис, семантика, ожидаемый вывод;
- упрощения, которые могут создать неправильную ментальную модель, если заявлены слишком категорично.

Де-приоритет:
- тривиальные факты, не влияющие на обучающую ценность заметки;
- споры о терминологии, если текст материально корректен для своего слоя.

Для каждой реальной находки: файл, строка, утверждение в тексте, что говорит источник, ссылка на источник, почему это важно для модели читателя, правильный класс правки (correct / weaker wording / version scoping / explicit simplification).
```

### Integration (opus)

```text
Прочитай styleguide.md §2 (слои зависимостей) + structure-guide.md §5 (размещение по слоям) + §6 (cross-links) целиком.

Target files: [пути]. Также читай: обзорный файл домена, обзорные файлы соседних доменов, top-level index.md репозитория.

У линзы два фокуса — держи их раздельно в отчёте.

**Фокус A: reference integration.**
- Integrated links: при первом содержательном употреблении концепции из `Предпосылки` — ссылка в самой фразе есть? И при каждом следующем содержательном употреблении (structure-guide §6.2)?
- Якоря: если целевой файл широкий, а нужен конкретный подраздел — якорь есть? Якорь — точный текст заголовка, не slug? Wikilink, а не markdown (§6.3)?
- Формат: ссылка в подпапку текущего каталога — wikilink (§6.5)? Остальные случаи — markdown?
- Недостающие концепции: термин, который не объяснён в тексте, не в `Предпосылки`, и для которого нет заметки в репо, — кандидат в `wip/layer-gaps.md`. Запиши: файл, термин, ожидаемый слой, зачем он нужен.

**Фокус B: conceptual integration (V-shape).**
Репо устроен V-образно: чтение — не линейная лестница снизу вверх, а дуга, где слои обращаются друг к другу через ментальные модели, а не только через формальный контракт `Предпосылки`. «Ниже» для конкретной заметки — в первую очередь темы её `Предпосылки` и концепции, на которые ведут integrated links; чаще всего в роли «ниже» оказываются наиболее фундаментальные и часто переиспользуемые слои — алгоритмы, network, computer, linux, — но не только они. «Выше» — типично system-design. system-design не требует низких слоёв как обязательных, но многократно переиспользует их ментальные модели.

- Для заметок system-design: опирается ли текст на ментальные модели из слоёв ниже (типичные источники — структуры данных, request path, cache hierarchy, процессы/FS/syscalls), где это помогает? Где мог бы опереться — но не опирается, и текст от этого менее понятен?
- Для заметок ниже system-design: есть ли мотивирующая ссылка вверх — «эта концепция проявится в X» — которая даёт читателю крючок для запоминания? Такая ссылка не обязательна (обязательные базы идут вниз), но без неё текст иногда висит в вакууме.
- V-shape — это узкие точки, где ментальная модель реально переиспользуется между слоями, а не универсальный призыв тянуть всё вниз или вверх.

Не делай:
- не расширяй `Предпосылки` — чаще решение это integrated link и якорь;
- не добавляй ссылку ради ссылки — только там, где она снимает локальную неопределённость;
- не путай фокус A с фокусом B: первый про механику линков, второй про содержание моста между слоями.

Формат: файл → фокус A findings + фокус B findings + wip-queue кандидаты отдельной секцией.
```
