## Зачем нужен пул соединений

Puma в clustered mode запускает несколько воркер-процессов, в каждом — несколько потоков. При 3 воркерах по 5 потоков приложение обрабатывает до 15 запросов одновременно. Каждый из этих потоков может обращаться к Redis: читать кеш, проверять rate limit, публиковать в Pub/Sub.

Один объект `Redis.new` — это одно TCP-соединение с сервером. Если несколько потоков используют один объект без синхронизации, их команды перемешаются в одном сокете и ответы перепутаются. Причина в том, как Ruby отпускает [GVL](../../ruby/ruby-concurrency.md#gvl-почему-потоки-не-ускоряют-cpu-код) (Global VM Lock — глобальная блокировка интерпретатора, которая позволяет только одному потоку исполнять Ruby-код в каждый момент). GVL не защищает от чередования Redis-команд: при каждом I/O-вызове (`send`, `recv` по сокету) поток отпускает GVL и засыпает в ядре. В этот момент другой поток получает GVL, формирует свою команду и тоже вызывает `send` на том же сокете. Результат — в TCP-потоке перемежаются байты двух разных команд, и Redis не может разобрать ни одну.

Два варианта: один объект с внутренним мьютексом (потоки ждут друг друга — теряем конкурентность) или пул из нескольких соединений — по одному на поток.

## connection_pool

Гем `connection_pool` создаёт заданное количество соединений и выдаёт каждому потоку своё на время блока.

```ruby
# config/initializers/redis.rb
require 'connection_pool'

REDIS = ConnectionPool.new(size: ENV.fetch('RAILS_MAX_THREADS', 5).to_i + 2, timeout: 3) do
  Redis.new(url: ENV.fetch('REDIS_URL', 'redis://localhost:6379/0'))
end
```

Размер пула — `RAILS_MAX_THREADS + небольшой запас`. Puma с 5 потоками — минимум `size: 5`. Запас в 1–2 соединения нужен, если Redis используется из фоновых потоков (таймеры, колбэки).

Использование — через `with`:

```ruby
REDIS.with do |conn|
  conn.get('user:123:name')
end
```

`with` берёт свободное соединение из пула, передаёт в блок и возвращает обратно после выполнения. Если все соединения заняты, поток ждёт до `timeout` секунд и поднимает исключение.

## Ruby-клиенты для Redis

Стандартный клиент — гем `redis` (redis-rb). Он покрывает все команды Redis, стабилен и поддерживается. Для большинства Rails-проектов этого достаточно.

```ruby
# Gemfile
gem 'redis', '~> 5.0'
```

Опциональная оптимизация — гем `hiredis-client`. Это C-расширение, которое заменяет Ruby-парсер протокола RESP (REdis Serialization Protocol — бинарный формат, которым клиент и сервер обмениваются командами и ответами) на реализацию на C. На больших payload'ах (bulk-строки, длинные списки) прирост достигает ~30%. На мелких GET/SET разница незаметна, потому что основное время уходит на сетевой round-trip, а не на парсинг.

```ruby
# Gemfile
gem 'redis', '~> 5.0'
gem 'hiredis-client'
```

redis-rb автоматически использует hiredis-client, если гем установлен.

`REDIS_URL` следует формату `redis://host:port/db_number`. Номер базы (от 0 до 15 по умолчанию) — способ логически разделить ключи внутри одного инстанса. Разные номера баз изолируют пространства ключей, но разделяют одну и ту же память и CPU.

## Несколько инстансов Redis

Один инстанс Redis обслуживает и кеш, и сессии, и Sidekiq — но у этих задач разные требования к сохранности данных и поведению при нехватке памяти. Если Redis для кеша вытеснит ключ Sidekiq-очереди, задача потеряется. Разделение на инстансы изолирует эти гарантии.

Кеш страниц и фрагментов — данные, которые можно пересчитать. Персистентность не нужна: при рестарте кеш прогреется заново. Политика вытеснения `allkeys-lru` — Redis сам удаляет давно неиспользуемые ключи при нехватке памяти. Если Redis для кеша упадёт, приложение продолжит работать, просто медленнее (запросы пойдут в PostgreSQL).

Сессии — данные с TTL, потеря которых означает разлогин пользователей. [AOF](../../databases/redis/persistence/01-aof.md) с `appendfsync everysec` даёт потерю максимум секунды данных при падении. Политика `volatile-ttl` — при нехватке памяти Redis удаляет ключи с наименьшим оставшимся TTL (самые старые сессии).

Sidekiq — очереди задач. Потеря означает потерю незавершённых джобов. [RDB-снимки](../../databases/redis/persistence/00-rdb.md) достаточны: Sidekiq при рестарте перечитает очереди. Политика `noeviction` — Redis отказывает в записи, если память кончилась, вместо того чтобы удалять задачи из очереди.

```ruby
# config/initializers/redis.rb
require 'connection_pool'

REDIS = ConnectionPool.new(size: ENV.fetch('RAILS_MAX_THREADS', 5).to_i + 2, timeout: 3) do
  Redis.new(url: ENV.fetch('REDIS_URL', 'redis://localhost:6379/0'))
end

REDIS_CACHE = ConnectionPool.new(size: ENV.fetch('RAILS_MAX_THREADS', 5).to_i + 2, timeout: 3) do
  Redis.new(url: ENV.fetch('REDIS_CACHE_URL', 'redis://localhost:6380/0'))
end

# Sidekiq настраивает пул самостоятельно через REDIS_SIDEKIQ_URL
```

Три переменные окружения — `REDIS_URL`, `REDIS_CACHE_URL`, `REDIS_SIDEKIQ_URL` — указывают на разные порты или разные серверы. Каждый инстанс настраивается независимо в `redis.conf`: свой `maxmemory`, своя политика вытеснения, свои параметры персистентности.
