# Клиенты и соединения

**Предпосылки:** [Redis: архитектура](../../databases/redis/index.md), [TCP](../../networking/transport/01-tcp.md) (соединение), GIL в Ruby, Puma (worker'ы + потоки).

## Ruby-клиенты для Redis

Стандартный клиент — гем `redis` (redis-rb). Он покрывает все команды Redis, стабилен и поддерживается. Для большинства Rails-проектов этого достаточно.

```ruby
# Gemfile
gem 'redis', '~> 5.0'
```

Опциональная оптимизация — гем `hiredis-client`. Это C-расширение, которое заменяет Ruby-парсер протокола RESP на реализацию на C. На больших payload'ах (bulk-строки, длинные списки) прирост достигает ~30%. На мелких GET/SET разница незаметна, потому что основное время уходит на сетевой round-trip, а не на парсинг.

```ruby
# Gemfile
gem 'redis', '~> 5.0'
gem 'hiredis-client'
```

redis-rb автоматически использует hiredis-client, если гем установлен.

## GIL и I/O-конкурентность

GIL (Global Interpreter Lock) не позволяет двум Ruby-потокам исполнять Ruby-код одновременно. Но при I/O-операции (сетевой запрос к Redis, чтение файла, запрос в БД) GIL освобождается. Пока один поток ждёт ответа от Redis, другой поток может отправить свой запрос.

Если Puma настроен на 5 потоков, все 5 могут одновременно ожидать ответа от Redis. Каждый ожидающий поток держит TCP-соединение открытым. Один объект `Redis.new` — это одно TCP-соединение. Если несколько потоков используют один объект без синхронизации, команды перемешаются в одном сокете и ответы перепутаются.

Два варианта: либо один объект с внутренним мьютексом (потоки ждут друг друга — теряем конкурентность), либо пул из нескольких соединений.

## connection_pool

Гем `connection_pool` решает проблему: он создаёт заданное количество соединений и выдаёт каждому потоку своё на время блока.

```ruby
# config/initializers/redis.rb
require 'connection_pool'

REDIS = ConnectionPool.new(size: ENV.fetch('RAILS_MAX_THREADS', 5).to_i + 2, timeout: 3) do
  Redis.new(url: ENV.fetch('REDIS_URL', 'redis://localhost:6379/0'))
end
```

Размер пула — `RAILS_MAX_THREADS + небольшой запас`. Puma с 5 потоками → минимум `size: 5`. Запас в 1–2 соединения нужен, если Redis используется из фоновых потоков (таймеры, колбэки).

Использование — через `with`:

```ruby
REDIS.with do |conn|
  conn.get('user:123:name')
end
```

`with` берёт свободное соединение из пула, передаёт в блок и возвращает обратно после выполнения. Если все соединения заняты, поток ждёт до `timeout` секунд и поднимает исключение.

## Конфигурация Rails-приложения

Минимальная настройка — один инициализатор и переменная окружения:

```ruby
# config/initializers/redis.rb
require 'connection_pool'

REDIS = ConnectionPool.new(size: ENV.fetch('RAILS_MAX_THREADS', 5).to_i + 2, timeout: 3) do
  Redis.new(url: ENV.fetch('REDIS_URL', 'redis://localhost:6379/0'))
end
```

`REDIS_URL` следует формату `redis://host:port/db_number`. Номер базы (от 0 до 15 по умолчанию) — способ логически разделить ключи внутри одного инстанса. Разные номера баз изолируют пространства ключей, но разделяют одну и ту же память и CPU.

## Несколько инстансов Redis

На практике для разных задач запускают отдельные инстансы Redis. Причина — разные требования к [персистентности](../../databases/redis/persistence/01-aof.md) и [политике вытеснения](../../databases/redis/memory/01-eviction.md).

Кеш страниц и фрагментов — данные, которые можно пересчитать. Персистентность не нужна: при рестарте кеш прогреется заново. Политика вытеснения `allkeys-lru` — Redis сам удаляет давно неиспользуемые ключи при нехватке памяти. Если Redis для кеша упадёт, приложение продолжит работать, просто медленнее (запросы пойдут в PostgreSQL).

Сессии — данные с TTL, потеря которых означает разлогин пользователей. AOF с `appendfsync everysec` даёт потерю максимум секунды данных при падении. Политика `volatile-ttl` — при нехватке памяти Redis удаляет ключи с наименьшим оставшимся TTL (самые старые сессии).

Sidekiq — очереди задач. Потеря означает потерю незавершённых джобов. RDB-снимки достаточны: Sidekiq при рестарте перечитает очереди. Политика `noeviction` — Redis отказывает в записи, если память кончилась, вместо того чтобы удалять задачи из очереди.

```ruby
# config/initializers/redis.rb
require 'connection_pool'

REDIS = ConnectionPool.new(size: ENV.fetch('RAILS_MAX_THREADS', 5).to_i + 2, timeout: 3) do
  Redis.new(url: ENV.fetch('REDIS_URL', 'redis://localhost:6379/0'))
end

REDIS_CACHE = ConnectionPool.new(size: ENV.fetch('RAILS_MAX_THREADS', 5).to_i + 2, timeout: 3) do
  Redis.new(url: ENV.fetch('REDIS_CACHE_URL', 'redis://localhost:6380/0'))
end

# Sidekiq настраивает пул самостоятельно через REDIS_SIDEKIQ_URL
```

Три переменные окружения — `REDIS_URL`, `REDIS_CACHE_URL`, `REDIS_SIDEKIQ_URL` — указывают на разные порты или разные серверы. Каждый инстанс настраивается независимо в `redis.conf`: свой `maxmemory`, своя политика вытеснения, свои параметры персистентности.
