# Контейнеры

**Предпосылки:** [пространства имён и контрольные группы](namespaces-and-cgroups.md) (namespaces, cgroups, clone/unshare), [режимы процессора и системные вызовы](../foundations/cpu-modes-and-syscalls.md) (syscall, прерывание, переход в kernel mode).

← [Пространства имён и контрольные группы](namespaces-and-cgroups.md)

[[linux/containers/namespaces-and-cgroups#Пространства имён: что процесс видит|Пространства имён]] отвечают за видимость: [процесс](../foundations/processes.md) видит только своё дерево процессов, свою сеть и свои монтирования. [[linux/containers/namespaces-and-cgroups#Контрольные группы: сколько процесс может потратить|Контрольные группы]] отвечают за лимиты: сколько CPU и памяти он может забрать у системы. Но после предыдущей заметки остаётся практический вопрос: как собрать эти разрозненные механизмы в один запускаемый сервис?

Контейнер не добавляет в ядро новую сущность. Это обычный [процесс](../foundations/processes.md), вокруг которого контейнерная среда исполнения (runtime) собирает корневую [файловую систему](../foundations/filesystems.md), изоляцию, ресурсные лимиты и дополнительные ограничения безопасности. Поэтому `docker run` — не запуск «мини-VM», а автоматическая сборка уже знакомых примитивов в один воспроизводимый запуск.

## docker run: от команды до процесса

В упрощённом виде `docker run -d --memory=512m -p 8080:80 nginx` делает следующее:

```text
docker run -d --memory=512m -p 8080:80 nginx
  |
  v
Проверка/скачивание образа --> корневая файловая система из образа (overlay FS)
  |
  v
clone(CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | ...) --> новые пространства имён
  |
  v
виртуальная пара интерфейсов (veth) --> отдельная сеть контейнера
  |
  v
cgroup: memory.max = 512 МБ --> лимиты CPU и памяти
  |
  v
seccomp profile --> фильтр на системные вызовы
  |
  v
capabilities drop --> урезаны root-привилегии
  |
  v
pivot_root --> корневая файловая система контейнера становится /
  |
  v
exec("nginx") --> PID 1 внутри контейнера
```

Контейнер здесь не отдельный объект ядра, а результат этой сборки: образ даёт корневую [файловую систему](../foundations/filesystems.md), [[linux/containers/namespaces-and-cgroups#Создание пространств имён: системные вызовы|пространства имён]] скрывают чужие ресурсы, cgroups ставят лимиты, [[linux/containers/containers#Seccomp-BPF: фильтрация системных вызовов|seccomp]] и [capabilities](../foundations/permissions-and-capabilities.md) сужают допустимые действия, а затем runtime вызывает [[linux/foundations/processes#exec(): замена программы|`exec()`]] целевой программы. Обычно всё это укладывается в сотни миллисекунд; если образ уже скачан, заметная часть времени уходит не на изоляцию, а на старт самого приложения. Каждый шаг разобран ниже.

## Контейнер --- это не виртуальная машина

Виртуальная машина эмулирует аппаратуру целиком: гипервизор (KVM --- Kernel-based Virtual Machine, Xen, VMware) создаёт виртуальный процессор, виртуальную память, виртуальные устройства и загружает внутри полноценное ядро гостевой ОС. Два ядра --- хост и гость --- работают одновременно, и между пользовательским [процессом](../foundations/processes.md) внутри VM (Virtual Machine) и железом лежат два слоя привилегий. Запуск VM --- это загрузка ОС: инициализация ядра, systemd, драйверы --- от 5 до 30 секунд. Накладные расходы на память --- от 200-500 МБ на каждый экземпляр только под ядро и системные процессы гостя.

Контейнер работает иначе. Внутри контейнера нет своего ядра --- [процесс](../foundations/processes.md) использует ядро хоста напрямую. `docker run ubuntu sleep 60` не запускает Ubuntu с её ядром --- он создаёт обычный процесс с PID 1 внутри нового PID namespace, которому ядро хоста показывает изолированную картину мира. [Системные вызовы](../foundations/cpu-modes-and-syscalls.md) из контейнера обрабатываются тем же ядром, что обслуживает хост. Запуск контейнера --- это `clone()` с набором флагов `CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWCGROUP` плюс настройка cgroup. User namespace (`CLONE_NEWUSER`) по умолчанию не используется в стандартном Docker с root-демоном --- он добавляется в rootless-режиме (Podman, rootless Docker). Ядро уже запущено, инициализация не нужна --- контейнер стартует за 100-500 миллисекунд.

Архитектурная разница видна в количестве слоёв между приложением и железом:

```text
VM                                    Контейнер
+---------------------------+         +---------------------------+
| Приложение                |         | Приложение                |
+---------------------------+         +---------------------------+
| Библиотеки гостевой ОС   |         | Библиотеки (overlay FS)   |
+---------------------------+         +---------------------------+
| Гостевое ядро             |         | (ядро хоста напрямую)     |
+---------------------------+         +---------------------------+
| Гипервизор (KVM/Xen)     |         | namespaces + cgroups      |
+---------------------------+         +---------------------------+
| Ядро хоста                |         | Ядро хоста                |
+---------------------------+         +---------------------------+
| Железо                    |         | Железо                    |
+---------------------------+         +---------------------------+
```

Отсюда фундаментальное различие в модели безопасности. VM изолирует через аппаратную границу: гостевое ядро не может обратиться к памяти хоста, потому что гипервизор контролирует таблицы страниц через EPT (Extended Page Tables — расширенные таблицы страниц, Intel) или NPT (Nested Page Tables — вложенные таблицы страниц, AMD). Контейнер изолирует через программные абстракции ядра: namespaces, cgroups, seccomp, [capabilities](../foundations/permissions-and-capabilities.md). Граница тоньше --- уязвимость в ядре хоста потенциально даёт выход из контейнера.

## Overlay FS: файловая система образа

`docker run` начинает с подготовки [файловой системы](../foundations/filesystems.md) из образа.

Контейнеру нужна корневая [файловая система](../foundations/filesystems.md): `/bin`, `/lib`, `/etc` со всеми утилитами и библиотеками. Можно скопировать полный образ Ubuntu (~78 МБ) для каждого контейнера, но при 100 контейнерах на одном хосте это ~7,8 ГБ одинаковых файлов. Overlay FS решает эту проблему, позволяя нескольким контейнерам разделять общую базу, сохраняя при этом независимость записи.

Overlay FS (overlay filesystem) объединяет два каталога в один видимый: нижний слой `lowerdir` доступен только для чтения, верхний слой `upperdir` принимает все изменения. [Процесс](../foundations/processes.md) видит объединённое представление через точку монтирования `merged`:

```text
merged (то, что видит контейнер)
  |
  +--- /bin/bash        <-- из lowerdir (read-only)
  +--- /etc/hostname    <-- из upperdir (изменён контейнером)
  +--- /lib/...         <-- из lowerdir (read-only)
  +--- /tmp/app.log     <-- из upperdir (создан контейнером)
```

Когда [процесс](../foundations/processes.md) читает файл, overlay FS ищет его сначала в `upperdir`, затем в `lowerdir`. Когда процесс записывает в файл из `lowerdir`, overlay FS выполняет copy-up (копирование наверх — в записываемый слой): копирует весь файл из `lowerdir` в `upperdir` и применяет изменения к копии. Оригинал в `lowerdir` остаётся нетронутым. Copy-up копирует файл целиком, даже если процесс изменил один байт --- поэтому запись в большой файл (лог на 500 МБ, база SQLite) вызывает неожиданный всплеск I/O и потребления диска в `upperdir` при первой модификации. Повторные записи в тот же файл уже работают с копией в `upperdir` и не вызывают copy-up.

Удаление файла из `lowerdir` создаёт в `upperdir` специальный whiteout-файл (файл-заглушка, «затирающий» оригинал) --- маркер, скрывающий оригинал из объединённого представления. При удалении каталога создаётся opaque-маркер --- его содержимое из `lowerdir` перестаёт быть видимым, но сам каталог остаётся.

Монтирование overlay FS --- один [системный вызов](../foundations/cpu-modes-and-syscalls.md):

```bash
mount -t overlay overlay \
  -o lowerdir=/var/lib/docker/overlay2/abc123/diff,\
     upperdir=/var/lib/docker/overlay2/xyz789/diff,\
     workdir=/var/lib/docker/overlay2/xyz789/work \
  /var/lib/docker/overlay2/xyz789/merged
```

`workdir` --- служебный каталог, который overlay FS использует для атомарных операций copy-up (переименование через промежуточный файл). Он должен находиться на том же разделе, что и `upperdir`.

Эффект: 100 контейнеров на базе Ubuntu разделяют один `lowerdir` размером ~78 МБ. Каждый контейнер занимает в `upperdir` только свои изменения --- обычно от нескольких килобайт до нескольких мегабайт. Суммарное потребление диска: ~78 МБ + 100 * ~5 МБ = ~578 МБ вместо ~7,8 ГБ.

## Образы и слои

Docker-образ (image) --- это стек слоёв, каждый из которых является `lowerdir` для [[linux/containers/containers#Overlay FS: файловая система образа|overlay FS]]. Образ собирается из Dockerfile — текстового файла с инструкциями сборки. Каждая инструкция создаёт новый слой --- diff относительно предыдущего состояния [файловой системы](../foundations/filesystems.md):

```dockerfile
FROM ubuntu:22.04          # слой 1: базовая Ubuntu (~78 МБ)
RUN apt-get update && \
    apt-get install -y nginx  # слой 2: добавлены файлы nginx (~25 МБ)
COPY app.conf /etc/nginx/   # слой 3: один конфигурационный файл (~1 КБ)
```

Три инструкции --- три слоя. При `docker pull` каждый слой скачивается отдельно и идентифицируется по SHA256-хешу его содержимого. Если на хосте уже есть слой `ubuntu:22.04` от другого образа, Docker не скачивает его повторно. Слои read-only и разделяются между всеми образами, которые их используют.

При `docker run` Docker создаёт тонкий read-write слой поверх стека read-only слоёв образа --- это `upperdir` контейнера. [[linux/containers/containers#Overlay FS: файловая система образа|Overlay FS]] поддерживает несколько `lowerdir`, объединяя их снизу вверх:

```text
upperdir (read-write, контейнер)   <-- /tmp/app.log, изменённые файлы
lowerdir (слой 3, read-only)       <-- /etc/nginx/app.conf
lowerdir (слой 2, read-only)       <-- /usr/sbin/nginx, /etc/nginx/...
lowerdir (слой 1, read-only)       <-- /bin, /lib, /usr (базовая Ubuntu)
```

Слои экономят не только диск, но и page cache. Ядро кеширует страницы файлов из `lowerdir` один раз, и все 100 контейнеров читают эти страницы из одного кеша. Без слоёв у каждого контейнера были бы свои копии `/bin/bash` в page cache.

Порядок слоёв в Dockerfile влияет на эффективность кеширования при сборке. Docker кеширует слои: если инструкция и её входные данные не изменились, слой берётся из кеша. Если изменить ранний слой --- все последующие пересобираются. Поэтому инструкции, которые меняются редко (установка системных пакетов), ставятся раньше, а часто меняющийся код приложения --- позже:

```dockerfile
FROM ruby:3.3                  # слой 1: меняется раз в месяцы
COPY Gemfile Gemfile.lock ./   # слой 2: меняется при обновлении зависимостей
RUN bundle install             # слой 3: пересобирается только при изменении Gemfile
COPY . .                       # слой 4: пересобирается при каждом деплое
```

Если поставить `COPY . .` перед `RUN bundle install`, каждое изменение кода будет пересобирать зависимости --- минуты вместо секунд.

## Сеть контейнера

[[linux/containers/containers#Overlay FS: файловая система образа|Overlay]] смонтирован, [процесс](../foundations/processes.md) запущен в новых namespaces --- но network namespace пуст.

runc (программа, которая непосредственно создаёт namespaces, настраивает cgroups и запускает [процесс](../foundations/processes.md) контейнера) создаёт пару виртуальных Ethernet-интерфейсов (veth pair) --- два связанных сетевых интерфейса, где [[networking/foundations/ip-and-routing#Пакет|пакет]], отправленный в один конец, появляется на другом. Один конец помещается в [[linux/containers/namespaces-and-cgroups#Network namespace: собственный сетевой стек|network namespace]] контейнера как `eth0`, другой подключается к bridge-интерфейсу `docker0` на хосте. Bridge работает как виртуальный [[networking/foundations/ethernet-and-switching#Коммутатор: изоляция трафика|L2 (канальный уровень)-коммутатор]]: контейнеры на одном хосте общаются между собой через `docker0` без выхода в хостовую сеть. Если нужно проследить следующий уровень глубины --- как пакет потом проходит через bridge, маршрутизацию, [[linux/kernel/network-stack#Netfilter и правила фильтрации|netfilter]] и [[linux/kernel/network-stack#TCP: от сегмента к данным|TCP]] внутри ядра Linux, --- это разбирается в [сетевом стеке](../kernel/network-stack.md).

Контейнер получает [[networking/foundations/ip-and-routing#IP-адрес: адрес, отражающий местоположение|IP-адрес]] из [[networking/foundations/ip-and-routing#Маска подсети|подсети]] bridge (обычно 172.17.0.0/16). Флаг `-p 8080:80` превращается в правило [[networking/infrastructure/firewalls#Linux: iptables и nftables|iptables]]: DNAT (Destination NAT) перенаправляет входящий трафик с порта 8080 хоста на порт 80 контейнера. Обратный трафик проходит через SNAT (Source NAT), чтобы ответы контейнера выглядели как ответы хоста для внешних клиентов. Сами механизмы DNAT/SNAT подробно разобраны в [[networking/foundations/nat#SNAT и DNAT|NAT]]; здесь важна именно их контейнерная сборка в Linux.

Настройка сети --- одна из самых затратных частей создания контейнера: создание veth pair, подключение к bridge, настройка [[networking/infrastructure/firewalls#Linux: iptables и nftables|iptables]] --- но всё это укладывается в единицы миллисекунд.

## Cgroup-лимиты

Сеть настроена. До запуска [процесса](../foundations/processes.md) нужно ограничить, сколько ресурсов он может потратить. Docker создаёт cgroup и записывает ограничения из флагов командной строки: `--memory=512m` превращается в `memory.max = 536870912`, `--cpus=1.5` --- в `cpu.max = 150000 100000` (150 мс процессорного времени из каждых 100 мс). PID контейнерного процесса добавляется в эту cgroup.

Если [процесс](../foundations/processes.md) превысит лимит памяти, OOM killer [[linux/programming/memory-management#Cgroups: OOM без системного ущерба|сработает внутри cgroup]]: процесс получит [[linux/programming/signals#Действия по умолчанию|SIGKILL]], exit code 137, и `docker logs` покажет «Killed». Остальная система не затронута. При превышении CPU-квоты поведение иное: [планировщик](../foundations/scheduler.md) throttle-ит процесс (вставляет принудительные паузы до конца периода), но не убивает его.

## Seccomp-BPF: фильтрация системных вызовов

Namespaces изолируют видимость, cgroups ставят ресурсные лимиты, [файловая система](../foundations/filesystems.md) готова --- но [процесс](../foundations/processes.md) по-прежнему вызывает [системные вызовы](../foundations/cpu-modes-and-syscalls.md) ядра хоста напрямую.

Из ~380 [системных вызовов](../foundations/cpu-modes-and-syscalls.md) Linux (x86-64) контейнеру реально нужны ~200: читать файлы, работать с сетью, создавать процессы. Вызовы вроде `reboot()`, `kexec_load()` (загрузка нового ядра), `mount()` (монтирование файловых систем хоста), `clock_settime()` (изменение системного времени) --- опасны, если контейнер скомпрометирован.

Seccomp (Secure Computing mode) позволяет [процессу](../foundations/processes.md) установить фильтр на собственные [системные вызовы](../foundations/cpu-modes-and-syscalls.md). В режиме seccomp-BPF фильтр --- это программа на BPF (Berkeley Packet Filter), загружаемая через `prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, ...)` или `seccomp(SECCOMP_SET_MODE_FILTER, ...)`. Фильтр получает номер системного вызова и его аргументы, и возвращает решение: `SECCOMP_RET_ALLOW` (разрешить), `SECCOMP_RET_ERRNO` (вернуть ошибку), `SECCOMP_RET_KILL_PROCESS` (завершить процесс), `SECCOMP_RET_TRACE` (передать отладчику) или `SECCOMP_RET_LOG` (разрешить, но записать в лог).

Фильтр работает в ядре и проверяется на каждом [системном вызове](../foundations/cpu-modes-and-syscalls.md). Накладные расходы минимальны: BPF-программа выполняется за наносекунды, потому что это простой линейный массив инструкций без циклов. Фильтр устанавливается один раз и действует необратимо: [процесс](../foundations/processes.md) не может ослабить свой собственный seccomp-фильтр, только ужесточить. Это свойство критично для контейнеров --- даже если атакующий получил контроль над процессом внутри контейнера, он не может снять фильтр. Потомки наследуют фильтр родителя, и `fork()`/`exec()` не сбрасывают его.

Docker по умолчанию применяет seccomp-профиль, блокирующий около 44 системных вызовов. Среди них:

- `reboot`, `kexec_load` --- перезагрузка и замена ядра
- `mount`, `umount2` --- монтирование файловых систем (контейнер получает [[linux/containers/containers#Overlay FS: файловая система образа|overlay FS]] через [[linux/containers/containers#pivot_root: замена корневой файловой системы|pivot_root]], дополнительные монтирования запрещены)
- `clock_settime`, `clock_adjtime` --- изменение системного времени хоста
- `swapon`, `swapoff` --- управление подкачкой
- `create_module`, `init_module`, `delete_module` --- загрузка модулей ядра
- `ptrace` --- отладка чужих процессов (по умолчанию запрещён, разрешается флагом `--cap-add SYS_PTRACE`)

Когда приложение вызывает заблокированный [syscall](../foundations/cpu-modes-and-syscalls.md), ядро возвращает `EPERM`. Приложение, не ожидающее этой ошибки от `clock_settime()`, может упасть с непредсказуемым стеком — именно поэтому профиль нужно тестировать перед деплоем.

Профиль хранится в JSON и передаётся при создании контейнера. Структура профиля --- массив правил, где каждое правило указывает имена [системных вызовов](../foundations/cpu-modes-and-syscalls.md) и действие:

```json
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "syscalls": [
    {
      "names": ["read", "write", "open", "close", "stat", "fstat"],
      "action": "SCMP_ACT_ALLOW"
    },
    {
      "names": ["clone"],
      "action": "SCMP_ACT_ALLOW",
      "args": [
        { "index": 0, "value": 2114060288, "op": "SCMP_CMP_MASKED_EQ" }
      ]
    }
  ]
}
```

`defaultAction: SCMP_ACT_ERRNO` означает, что все не перечисленные вызовы возвращают ошибку. Правило для `clone` использует маску на аргументах: разрешает `clone()` только без namespace-флагов (`CLONE_NEWUSER`, `CLONE_NEWPID`, `CLONE_NEWNET` и др.), предотвращая создание новых пространств имён изнутри контейнера. Можно заменить профиль собственным: `docker run --security-opt seccomp=my-profile.json ...`, или отключить полностью: `--security-opt seccomp=unconfined` --- но это снимает важный слой защиты.

## Capabilities: дробление root-привилегий

Seccomp фильтрует вызовы по имени. Но многие вызовы --- `mount()`, `ptrace()` --- легитимны для одних контейнеров и опасны для других. Системный контейнер мониторинга должен уметь монтировать cgroup-файловые системы; обычный веб-сервер --- нет. Фильтровать по имени вызова недостаточно, нужен более тонкий механизм.

[Capabilities](../foundations/permissions-and-capabilities.md) дробят привилегии root на ~40 независимых флагов --- механизм детально разобран в той же заметке. Здесь важно, как Docker использует их в контейнерном контексте.

Docker по умолчанию запускает контейнер лишь с частью из ~40 [capabilities](../foundations/permissions-and-capabilities.md) -- включая `CAP_NET_RAW` для `ping` и `CAP_NET_BIND_SERVICE` для порта 80. Отброшенные включают `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE`, `CAP_SYS_MODULE` (загрузка модулей ядра), `CAP_SYS_BOOT` (перезагрузка), `CAP_SYS_TIME` (изменение часов). Добавить capability: `docker run --cap-add SYS_PTRACE ...` для контейнера с отладчиком. Убрать из набора по умолчанию: `docker run --cap-drop NET_RAW ...` если `ping` не нужен и хочется уменьшить поверхность атаки.

Посмотреть текущие [capabilities](../foundations/permissions-and-capabilities.md) контейнера можно через `docker exec <container> cat /proc/1/status | grep Cap`. Поля `CapPrm` (permitted), `CapEff` (effective) и `CapInh` (inheritable) содержат битовые маски. Утилита `capsh --decode=<hex>` расшифровывает маску в человекочитаемые имена.

Флаг `--privileged` снимает все ограничения: все [capabilities](../foundations/permissions-and-capabilities.md), отключённый [[linux/containers/containers#Seccomp-BPF: фильтрация системных вызовов|seccomp]], доступ ко всем устройствам хоста через `/dev`. Контейнер с `--privileged` может монтировать диск хоста, загружать модули ядра и изменять сетевые настройки --- фактически это root на хосте. Используется для системных контейнеров (сбор метрик, управление сетью), но в остальных случаях создаёт дыру в изоляции.

## pivot_root: замена корневой файловой системы

[[linux/containers/containers#Overlay FS: файловая система образа|Overlay]] смонтирован, namespaces созданы, [capabilities](../foundations/permissions-and-capabilities.md) урезаны --- но [процесс](../foundations/processes.md) всё ещё видит [файловую систему](../foundations/filesystems.md) хоста. runc вызывает `pivot_root()`, атомарно заменяя корень процесса на overlay-монтирование. `pivot_root()` отличается от `chroot()`: chroot меняет только корневой каталог, но старая файловая система остаётся доступной через `..` относительно точки монтирования --- атакующий с shell внутри контейнера может выполнить `cd /proc/1/root` и выйти на файловую систему хоста. `pivot_root()` позволяет полностью размонтировать старую файловую систему --- после этого процесс не имеет путей к файлам хоста. Затем runc вызывает [[linux/foundations/processes#exec(): замена программы|`exec("nginx")`]], и процесс контейнера начинает выполнять целевую программу. С точки зрения nginx он работает в обычной системе: видит `/etc/nginx/nginx.conf`, слушает порт 80, имеет PID 1.

Теперь все слои сборки готовы. Такая изоляция через механизмы ядра даёт другой набор свойств, чем альтернатива --- виртуальные машины.

## Контейнер и VM: сравнение

```text
                    Контейнер                   Виртуальная машина
+------------------+---------------------------+---------------------------+
| Ядро             | общее с хостом             | своё (гостевое)           |
+------------------+---------------------------+---------------------------+
| Изоляция         | namespaces + cgroups +     | аппаратная (гипервизор,   |
|                  | seccomp + capabilities     | EPT/NPT)                  |
+------------------+---------------------------+---------------------------+
| Запуск           | 100-500 мс                 | 5-30 секунд               |
+------------------+---------------------------+---------------------------+
| Overhead памяти  | ~5-20 МБ (процесс +       | 200-500 МБ (ядро +        |
|                  | overlay diff)              | системные процессы)       |
+------------------+---------------------------+---------------------------+
| Overhead CPU     | ~0% (нативные syscalls)    | 1-5% (VMX transitions)    |
+------------------+---------------------------+---------------------------+
| Плотность        | сотни на хосте             | десятки на хосте          |
+------------------+---------------------------+---------------------------+
| Граница          | программная (ядро хоста)   | аппаратная (гипервизор)   |
| безопасности     |                            |                           |
+------------------+---------------------------+---------------------------+
| Совместимость    | только Linux-процессы      | любая ОС (Windows,        |
|                  | (то же ядро)               | FreeBSD, Linux)           |
+------------------+---------------------------+---------------------------+
```

Контейнеры выигрывают по плотности и скорости запуска. VM выигрывают по глубине изоляции и совместимости с разными ОС. На практике выбор зависит от модели угроз: для внутренних сервисов одной команды достаточно контейнеров; для запуска недоверенного кода --- VM или их гибрид.

## Podman: контейнеры без демона

Docker работает через центральный демон `dockerd`, который слушает [[linux/programming/sockets#Unix domain sockets: локальный обмен без сетевого стека|Unix-сокет]] `/var/run/docker.sock` и выполняет все операции от имени root. Это удобно, но означает, что любой [процесс](../foundations/processes.md) с доступом к сокету может создавать привилегированные контейнеры --- фактически получая root на хосте.

Podman (Pod Manager) использует те же механизмы ядра --- namespaces, cgroups, [[linux/containers/containers#Overlay FS: файловая система образа|overlay FS]], [[linux/containers/containers#Seccomp-BPF: фильтрация системных вызовов|seccomp]], [capabilities](../foundations/permissions-and-capabilities.md) --- но без центрального демона. Каждый вызов `podman run` напрямую запускает container runtime (среда исполнения контейнеров — conmon + runc/crun). Контейнер становится дочерним [процессом](../foundations/processes.md) вызывающего пользователя, а не демона.

Главное следствие --- rootless-контейнеры. Podman использует user namespaces для запуска контейнеров от непривилегированного пользователя. Внутри контейнера [процесс](../foundations/processes.md) видит себя как root (UID 0), но на хосте он отображается на непривилегированный UID (например, 100000) через маппинг в `/etc/subuid` и `/etc/subgid`. Даже если процесс выйдет из контейнера, он окажется пользователем без привилегий. Docker тоже поддерживает rootless-режим (с версии 20.10), но в Podman это режим по умолчанию.

Отсутствие демона влияет на жизненный цикл контейнера. В Docker контейнер --- дочерний [процесс](../foundations/processes.md) `dockerd`: если демон перезапустится, контейнер осиротеет (на практике Docker использует containerd, который переживает рестарт `dockerd`). В Podman контейнер --- дочерний процесс conmon (container monitor), а conmon привязан к вызывающему пользователю. Systemd-интеграция через `podman generate systemd` создаёт unit-файл для контейнера, и systemd берёт на себя перезапуск при сбоях.

CLI (Command Line Interface) Podman совместим с Docker: `podman run`, `podman build`, `podman images` работают так же. Переход сводится к `alias docker=podman` в большинстве случаев.

## Выход из контейнера и усиление изоляции

Rootless-контейнеры сужают последствия взлома на уровне демона. Но остаётся более глубокая проблема: программная граница контейнера --- это ядро хоста. Все [системные вызовы](../foundations/cpu-modes-and-syscalls.md) контейнера обрабатываются одним ядром, и уязвимость в нём потенциально даёт полный выход из изоляции. Это не теоретическая угроза: CVE (Common Vulnerabilities and Exposures)-2016-5195 (Dirty COW) позволял записывать в read-only маппинги через race condition в обработчике copy-on-write, CVE-2020-14386 --- целочисленное переполнение в обработчике AF_PACKET, приводящее к записи за пределы буфера, позволяло повысить привилегии из контейнера до root на хосте.

Для сценариев с недоверенным кодом (CI/CD --- Continuous Integration / Continuous Delivery --- с произвольными пользовательскими скриптами, serverless-платформы) существуют два подхода к усилению изоляции.

### gVisor: прокси-ядро в userspace

gVisor (Google) --- Между контейнером и ядром хоста встаёт [процесс](../foundations/processes.md) `runsc` (Sentry), который перехватывает [системные вызовы](../foundations/cpu-modes-and-syscalls.md) контейнера и реализует их самостоятельно, обращаясь к реальному ядру только для базовых операций (файловый ввод-вывод, сеть). Из ~380 системных вызовов Linux gVisor реализует ~274 --- достаточно для большинства приложений. Поверхность атаки на ядро хоста сокращается радикально: контейнер не может вызвать уязвимый syscall, если gVisor его не проксирует. Цена --- overhead 5-30% на интенсивных системных вызовах (файловый ввод-вывод, создание процессов).

### Firecracker: microVM на базе KVM

Firecracker (Amazon) --- microVM (микровиртуальная машина), лёгкая VM, запускаемая за 125 мс. Firecracker --- это минимальный VMM (Virtual Machine Monitor) на базе KVM, эмулирующий только пять устройств: virtio-net (виртуальная сеть), virtio-block (виртуальный диск), virtio-vsock (связь VM←→хост), serial console и минимальный контроллер клавиатуры. Никакого USB, GPU, звука --- минимальная поверхность атаки. Каждый контейнер (или функция в AWS Lambda) запускается внутри отдельной microVM с собственным ядром. Изоляция аппаратная --- через EPT, как у обычной VM --- но overhead минимален благодаря легковесности VMM. Потребление памяти --- от 5 МБ на microVM.

Оба подхода комбинируются с контейнерными инструментами: gVisor интегрируется с Docker/containerd через runtime `runsc`, Firecracker --- через Kata Containers или собственный API. Google Cloud Run использует gVisor, AWS Lambda и Fargate --- Firecracker. Ориентир при выборе: gVisor подходит, когда важна syscall-совместимость с Linux без смены образа; Firecracker --- когда нужна аппаратная граница для недоверенного кода с нестандартными или непредсказуемыми [системными вызовами](../foundations/cpu-modes-and-syscalls.md).

Спектр решений выстраивается по глубине изоляции и цене overhead: обычный контейнер (namespaces + cgroups + [[linux/containers/containers#Seccomp-BPF: фильтрация системных вызовов|seccomp]]) < rootless-контейнер (+ user namespace) < gVisor (+ userspace-ядро) < Firecracker/microVM (+ аппаратная виртуализация). Каждый шаг добавляет слой защиты и миллисекунды к запуску, мегабайты к потреблению памяти, проценты к overhead на [системных вызовах](../foundations/cpu-modes-and-syscalls.md).

> [!info]- Задача: контейнер с --privileged и -v /:/host --- что может сделать процесс внутри?
> **Частая ошибка:** считать, что контейнер --- это изоляция. `--privileged` снимает seccomp, даёт все [capabilities](../foundations/permissions-and-capabilities.md), открывает доступ к устройствам. `-v /:/host` монтирует корневую FS хоста.
>
> **Последствия:**
> ```bash
> # внутри контейнера:
> chroot /host        # переключиться на FS хоста
> mount -t proc proc /proc  # доступ к /proc хоста
> nsenter -t 1 -m -u -i -n -p -- /bin/bash  # войти в namespaces PID 1 хоста
> ```
> Процесс получает полный root-доступ к хосту. `--privileged` + bind mount корня = отсутствие изоляции. Единственный допустимый сценарий --- системные контейнеры (мониторинг узла, сетевые агенты), и даже тогда стоит ограничиться конкретными capabilities вместо `--privileged`.
