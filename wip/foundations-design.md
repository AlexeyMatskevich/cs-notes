# Design: foundations/

## Грубый эскиз

- **Домен:** `foundations/` — новый корневой домен
- **Слой:** фундамент (ниже всех существующих доменов)
- **Scope:** серия из 6 файлов + index
- **Пол:** школьная математика (десятичная система, степени, логика «да/нет»). Ниже пола: физика полупроводников — не спускаемся, кроме одного предложения про транзистор как мотивацию
- **Потолок:** архитектура процессора (computer/), сетевые протоколы (networking/), языки программирования (programming/) — только cross-link вверх

## Педагогический дизайн (целая серия)

### 1. Граница знаний

**Читатель знает (baseline):** десятичную систему, степени, школьную арифметику, «да/нет» в бытовом смысле, что компьютер существует и «что-то вычисляет».

**Читатель НЕ знает:** бит, байт, двоичная система, hex, signed/unsigned, two's complement, overflow, побитовые операции, IEEE 754, ASCII/Unicode/UTF-8, endianness.

**Предпосылки серии:** нет (baseline = школьная математика).

### 2. Слой

Фундамент — абсолютно нижний слой. Все домены (programming/, computer/, databases/, networking/) ссылаются сюда.

### 3. Мотивация

**Источник:** недостающее звено.

Электронный переключатель различает два состояния: ток есть или тока нет. Из этого физического ограничения компьютер строит всё: числа, текст, изображения, звук. Как два состояния порождают миллиарды значений? И почему инженеры выбрали именно эти конструкции — почему 8 бит в байте, почему отрицательные числа хранятся «наизнанку», почему 0.1 + 0.2 ≠ 0.3?

### 4. Точка входа

В десятичной системе десять цифр (0–9), и из них складываются все числа. Это привычно — человек считает десятками, потому что у него десять пальцев. Но электронный переключатель, из которого собран любой процессор, различает только два состояния: ток проходит или не проходит. Два состояния — значит, две цифры: 0 и 1.

### 5. Тип сценария

**Сценарий роли** для всей серии: какая работа должна быть выполнена? Нужно представить все виды данных (числа, текст, цвета) используя элементы с двумя состояниями. Каждый файл отвечает «какая задача?» и показывает инженерное решение с его компромиссами.

### 6. Дуга

```
Физическое ограничение: переключатель = два состояния
  → Как представить больше двух? → Группировка → бит, байт (почему 8?)
    → Как из байтов получить числа? → Unsigned
      → Нет отрицательных → Знаковый бит? Ломает сложение
        → Two's complement: единая схема, один ноль
          → Числа есть. Нужно работать с отдельными битами → AND/OR/XOR/shift
            → Дискретные покрыты. А дроби?
              → Фиксированная точка: просто, но диапазон мал
                → Плавающая: IEEE 754 — компромисс диапазон/точность
                  → Числа есть. А текст?
                    → ASCII хватает для английского → А остальные языки?
                      → Кодовые страницы: хаос → Unicode → UTF-8
                        → Числа из нескольких байтов → В каком порядке?
                          → Little-endian vs big-endian
```

## Валидация

1. **Тест первых двух абзацев:** «Десятичная → десять пальцев → переключатель → два состояния → две цифры.» Понятно при baseline. **PASS**
2. **Тест дуги:** «Два состояния → группируем → считаем → отрицательные → биты → дроби → текст → порядок.» Связная история. **PASS**
3. **Тест на порядок документации:** отличается от учебника (побитовые после integers, endianness последним). **PASS**

## Дизайн каждого файла

### binary-and-bytes.md

**Предпосылки:** нет
**Мотивация:** недостающее звено — внутри компьютера два состояния, как из них всё?
**Тип сценария:** роль — какая работа выполняется (кодирование информации)
**Вход:** «В десятичной системе десять цифр — потому что десять пальцев. Электронный переключатель различает два состояния. Две цифры: 0 и 1.»

**Под-дуга:**
1. Физическая причина двоичной → бит (binary digit)
2. Позиционная нотация в двоичной, перевод dec↔bin
3. Арифметика в двоичной (сложение с переносом)
4. Одного бита мало → группировка → байт (почему 8? IBM System/360, 1964)
5. Степени двойки: КБ/МБ/ГБ, путаница KiB/KB
6. Hex как удобная запись (4 бита = 1 hex-цифра, таблица)
7. Ключевой инсайт: `01000001` = 65 = 'A' — одни биты, разная интерпретация

**Мост к 01:** «Из битов и байтов записываются числа — но пока только натуральные. Как записать отрицательное?»

**Детали на шагах:**
- Шаг 1: транзистор (1 предложение), определение бита
- Шаг 2: таблица позиций (128, 64, 32, 16, 8, 4, 2, 1), пошаговый перевод 42 → 00101010
- Шаг 3: пример 0011 + 0101 = 1000 с carry
- Шаг 4: IBM System/360 как поворотная точка (до него были 6-, 7-, 9-битные байты)
- Шаг 5: таблица 2¹⁰ = КБ, 2²⁰ = МБ, 2³⁰ = ГБ; заметка про 1000 vs 1024
- Шаг 6: таблица 0000→0, ..., 1111→F; пример 0xDEADBEEF
- Шаг 7: ASCII-диаграмма «одни биты — три интерпретации»

**Оценка объёма:** ~2500–3000 слов

### integers.md

**Предпосылки:** [binary-and-bytes](../foundations/binary-and-bytes.md) (бит, байт, двоичная система, hex)
**Мотивация:** ограничение — unsigned хватает для 0–255, но нет отрицательных
**Тип сценария:** ограничение — где unsigned перестаёт работать
**Вход:** «Восемь бит дают 256 вариантов (0–255). Для маленьких положительных — хватает. Но температура бывает ниже нуля, координата — левее начала, баланс — в минусе.»

**Под-дуга:**
1. Unsigned: прямое двоичное, диапазон 0..2ⁿ−1
2. Двоичное сложение (carry) — пошагово
3. Нужны отрицательные → наивный подход: знаковый бит
4. Проблемы sign-magnitude: два нуля (+0, −0), сложение ломается (нужна отдельная схема)
5. One's complement: инвертируем биты → ещё два нуля, end-around carry
6. Two's complement: мод 2ⁿ арифметика → единая схема сложения, один ноль
7. Почему «инвертируй и прибавь 1» работает (вывод из 2ⁿ − |x|)
8. Диапазон: −2ⁿ⁻¹..2ⁿ⁻¹−1, асимметрия
9. Overflow и wrap-around (uint8: 255+1 → 0; int8: 127+1 → −128)
10. Стандартные ширины: int8/16/32/64, uint8/16/32/64

**Мост к 02:** «Целое число — цепочка битов. Но иногда нужно работать не с числом целиком, а с конкретным битом внутри.»

**Детали на шагах:**
- Шаг 2: ASCII-диаграмма столбиковое сложение в двоичной
- Шаг 4: таблица sign-magnitude для 3 бит, показать два нуля
- Шаг 6: «числовая ось на циферблате» — модулярная арифметика как часы
- Шаг 7: пошаговый вывод: −5 в int8 = 256 − 5 = 251 = 11111011
- Шаг 9: таблица диапазонов int8..int64

**Оценка объёма:** ~2500–3000 слов

### bitwise-operations.md

**Предпосылки:** [binary-and-bytes](../foundations/binary-and-bytes.md), [integers](../foundations/integers.md)
**Мотивация:** недостающее звено — нужны инструменты для работы с отдельными битами
**Тип сценария:** роль — какую работу выполняют побитовые операции
**Вход:** «До сих пор число — единое значение: складывали, сравнивали, записывали. Но бывает, что важен конкретный бит: включен ли флаг, есть ли разрешение, установлен ли признак.»

**Под-дуга:**
1. NOT — инверсия всех бит (связь с one's complement из 01)
2. AND — «оба единицы» → применение: выделить биты через маску
3. OR — «хотя бы одна единица» → применение: установить бит
4. XOR — «ровно одна единица» → применение: переключить бит; свойство a⊕a=0
5. Сдвиги: left shift = ×2, right shift = ÷2; arithmetic vs logical shift
6. Составные операции: маски для выделения / установки / сброса / переключения
7. Практика: упаковка нескольких значений в один байт (type: 4 бита + encoding: 4 бита — как в Redis)
8. Практика: Unix permissions (rwx = 3 бита × 3 группы = 9 бит)

**Мост к 03:** «Побитовые операции — инструменты для дискретных значений. Но температура, координата, расстояние — дробные числа. Целых бит для них недостаточно.»

**Детали на шагах:**
- Шаги 1–4: таблицы истинности + побитовый пример (8-битные числа)
- Шаг 5: пример 00001010 << 2 = 00101000 (10 → 40)
- Шаг 6: формулы — set: `x | (1 << n)`, clear: `x & ~(1 << n)`, toggle: `x ^ (1 << n)`, check: `(x >> n) & 1`
- Шаг 7: ASCII-диаграмма упаковки двух 4-битных значений в байт
- Шаг 8: `chmod 755` → `111 101 101` → rwxr-xr-x

**Оценка объёма:** ~2000–2500 слов

### floating-point.md

**Предпосылки:** [binary-and-bytes](../foundations/binary-and-bytes.md), [integers](../foundations/integers.md)
**Мотивация:** ограничение — целые не могут представить дроби
**Тип сценария:** ограничение — где integers перестают работать
**Вход:** «36.6° температуры, 3.14 для площади круга — целых чисел недостаточно. Нужен способ записать дробную часть теми же битами.»

**Под-дуга:**
1. Двоичные дроби (0.1₂ = 0.5, 0.01₂ = 0.25, ...) — позиционная нотация после точки
2. Фиксированная точка: 8 бит целой + 8 бит дробной → просто, но диапазон мал
3. Научная нотация: ±M × 10ᵉ → аналогия для двоичной: ±M × 2ᵉ
4. IEEE 754: sign (1 бит) + exponent + mantissa
5. float32: 1+8+23, float64: 1+11+52
6. Нормализация: ведущая 1 всегда есть → скрытый бит (бесплатный бит точности)
7. Bias экспоненты: 127 для float32 (почему не two's complement — чтобы сравнение как unsigned)
8. Пошаговый пример: разобрать 0.15625 в float32
9. Спецзначения: ±0 (sign bit), ±∞ (exponent=FF, mantissa=0), NaN (exponent=FF, mantissa≠0)
10. Денормализованные (subnormals): exponent=0, постепенное исчерпание (gradual underflow)
11. Почему 0.1 + 0.2 ≠ 0.3: 0.1₁₀ = бесконечная двоичная дробь → округление → накопление ошибки
12. Практические следствия: сравнение с epsilon, не хранить деньги во float

**Мост к 04:** «Числа — целые и дробные — записаны в битах. Но компьютер работает и с текстом. Как из битов получить буквы?»

**Детали на шагах:**
- Шаг 1: таблица позиций после точки (2⁻¹ = 0.5, 2⁻² = 0.25, ...)
- Шаг 2: ASCII-диаграмма фиксированной точки, показать ограничение диапазона
- Шаг 4: ASCII-диаграмма раскладки float32 на биты (1 | 8 | 23)
- Шаг 8: пошаговый walkthrough: 0.15625 → 0.00101₂ → 1.01 × 2⁻³ → sign=0, exp=124, mantissa=01000...
- Шаг 11: пошаговый walkthrough: 0.1₁₀ → 0.0001100110011...₂ (бесконечная)

**Оценка объёма:** ~3500–4000 слов (самый плотный файл)

### text-encoding.md

**Предпосылки:** [binary-and-bytes](../foundations/binary-and-bytes.md) (бит, байт, hex)
**Мотивация:** недостающее звено — биты кодируют числа, но экран показывает буквы
**Тип сценария:** роль — кто превращает байты в символы
**Вход:** «Экран отображает буквы, знаки пунктуации, иероглифы. Каждый символ занимает место в памяти — значит, записан теми же байтами. Какое число соответствует какой букве?»

**Под-дуга:**
1. Идея: таблица «число → символ» (код)
2. Телеграф → код Бодо (5 бит, 32 символа, shift-режимы)
3. ASCII: 7 бит, 128 символов, управляющие + печатные, хватает для английского
4. Проблема: 128 символов, а языков — сотни
5. Кодовые страницы: ISO 8859, Windows-1251 → каждая расширяет верхние 128 → несовместимость, мохибай
6. Unicode: единый каталог, code point (U+XXXX), planes (BMP + 16 дополнительных)
7. Code point ≠ байты → нужна кодировка (encoding)
8. UTF-32: просто (4 байта = 1 code point), расточительно (4× для ASCII)
9. UTF-16: 2 байта для BMP, 4 для остальных (суррогатные пары)
10. UTF-8: переменная 1–4 байта, ASCII-совместимость, доминирует в интернете
11. Как UTF-8 кодирует (побитовая схема: 0xxxxxxx, 110xxxxx 10xxxxxx, ...)
12. BOM (Byte Order Mark): U+FEFF, зачем нужен для UTF-16, необязателен для UTF-8
13. Нормализация: «é» = U+00E9 или U+0065 + U+0301 → NFC/NFD, сравнение строк
14. Grapheme clusters: флаг 🇯🇵 = два code point, «видимый символ» ≠ code point ≠ байт

**Мост к 05:** «И числа, и текст — последовательности байтов. Когда число занимает несколько байтов, возникает вопрос: в каком порядке их хранить?»

**Детали на шагах:**
- Шаг 3: фрагмент ASCII-таблицы (A=65, a=97, 0=48)
- Шаг 5: пример: слово «привет» в Windows-1251 vs ISO 8859-5 → мусор при неправильной кодовой странице
- Шаг 6: карта Unicode planes (BMP: 0000–FFFF, дополнительные: 10000–10FFFF)
- Шаг 10: таблица byte-length для UTF-8 (ASCII=1, кириллица=2, китайские=3, эмодзи=4)
- Шаг 11: побитовая разборка буквы «Щ» (U+0429) → UTF-8
- Шаг 14: таблица «байты vs code points vs grapheme clusters» для строки с эмодзи

**Оценка объёма:** ~3000–3500 слов

### endianness.md

**Предпосылки:** [binary-and-bytes](../foundations/binary-and-bytes.md), [integers](../foundations/integers.md)
**Мотивация:** наблюдаемая странность — одно число, байты в разном порядке
**Тип сценария:** ограничение — многобайтовое число требует соглашения о порядке
**Вход:** «Число 0x00000001 занимает четыре байта. В памяти x86 оно хранится `01 00 00 00`, а в сетевом пакете — `00 00 00 01`. Те же байты, зеркальный порядок. Не ошибка — два разных соглашения.»

**Под-дуга:**
1. Многобайтовое число → какой байт первый? (проблема)
2. Big-endian: старший первый (MSB first), «тупоконечники» (Gulliver)
3. Little-endian: младший первый (LSB first), x86
4. Почему x86 выбрал little-endian (проще наращивать разрядность; младший байт всегда по одному адресу)
5. Mixed/bi-endian: ARM (переключается), middle-endian (PDP-11)
6. Где стреляет: файловые форматы (ELF header), сетевые протоколы (network byte order = big-endian), сериализация (protobuf, JSON не зависят)
7. Конвертация: htonl/ntohl/htons/ntohs
8. BOM в UTF-16 как маркер endianness (связь с 04)

**Завершение серии:** обзорный абзац — вся цепочка от бита до порядка байтов; ссылки наружу.

**Детали на шагах:**
- Шаг 1: ASCII-диаграмма: число 0x01020304 в памяти (4 ячейки, два варианта)
- Шаг 4: диаграмма: расширение int16 → int32 (в little-endian младший байт остаётся на месте)
- Шаг 6: пример из ELF: `e_ident[EI_DATA]` = 1 (little) или 2 (big)
- Шаг 7: псевдокод конвертации

**Оценка объёма:** ~1500–2000 слов (самый компактный файл)

## Общие соглашения для серии

- **Примеры:** таблицы, ASCII-диаграммы, пошаговые расчёты. Без привязки к языку программирования.
- **`<details>`:** для продвинутых подробностей (доказательства, edge cases, историческая справка)
- **Фокус:** «почему именно так» — каждое инженерное решение через альтернативу и компромисс
- **Тон:** styleguide §7.3 — проза по умолчанию, конкретика, «почему, а не только что»
- **Антипаттерн серии:** «школьный учебник» (определение → формула → упражнение). Вместо этого: проблема → наивное решение → почему ломается → правильное решение → чего стоит.
