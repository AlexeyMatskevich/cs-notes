На протяжении всего курса мы писали код вроде `salary = 1500`. Процессор таких слов не понимает. Ему нужны инструкции низкого уровня. Значит, между исходным кодом и выполнением всегда есть этап перевода.

Исходный код — это текст, который пишет программист. Процессор умеет выполнять машинный код. Вопрос в том, как добраться от одного до другого. Каждый следующий подход возник из ограничений предыдущего.

## Компиляция заранее

Самое прямолинейное решение — перевести весь текст программы в машинный код до запуска. Такой подход называется ahead-of-time (AOT — «заблаговременно», до запуска) компиляцией. Компилятор берёт исходный код и создаёт файл с инструкциями для конкретной платформы (платформа — конкретная комбинация процессора и операционной системы):

```text
исходный код -> компилятор -> машинный код -> запуск
```

Пример на C:

```bash
$ gcc file.c -o program
$ ./program
```

То же делает Rust:

```bash
$ rustc file.rs
$ ./file
```

Результат — файл, который процессор выполняет напрямую, без посредников. Многие ошибки ловятся ещё до запуска, а выполнение обычно быстрое.

Но у этого подхода есть цена. После каждого изменения код нужно перекомпилировать. И главное: бинарный файл привязан к платформе — программа, собранная для Linux на x86, не запустится на macOS или на ARM без пересборки.

## Виртуальная машина

Привязка к платформе — серьёзное ограничение. Если нужно запускать одну программу на разных операционных системах и процессорах, каждый раз пересобирать её под каждую платформу неудобно.

Выход — перевести код не в машинный код процессора, а в байткод (bytecode — инструкции, закодированные побайтно) для виртуальной машины (virtual machine) — программы, которая ведёт себя как отдельный компьютер: у неё свой набор инструкций и своя модель памяти, но работает она поверх настоящего процессора:

```text
исходный код -> байткод -> виртуальная машина -> выполнение
```

В Ruby при запуске `ruby file.rb` происходит несколько шагов:

1. исходный код читается;
2. Ruby переводит его во внутренний байткод;
3. виртуальная машина Ruby исполняет этот байткод.

В Java шаги разделены на две команды:

```bash
$ javac Main.java
$ java Main
```

`javac` создаёт `.class`-файлы с байткодом JVM. Команда `java` запускает этот байткод на виртуальной машине Java.

Одна и та же промежуточная форма может работать на разных платформах — достаточно, чтобы на каждой из них была своя виртуальная машина. Часть работы уже сделана заранее, поэтому это не то же самое, что прямое построчное исполнение.

Цена — дополнительный слой между кодом и процессором, и модель запуска становится сложнее: есть не только программа, но и VM, которая её исполняет.

## Прямая интерпретация

И компиляция, и виртуальная машина требуют отдельного шага перевода до того, как программа начнёт работать. Но иногда важнее другое — мгновенная обратная связь: изменил строку, сразу увидел результат.

Интерпретатор читает код и исполняет его без отдельного сохранённого артефакта:

```text
исходный код -> интерпретатор -> выполнение
```

Так работали ранние версии BASIC: строка вводилась, сразу разбиралась и выполнялась. Для обучения это было удобно — цикл «написал -> увидел результат» максимально короткий.

Чистая интерпретация сегодня встречается реже как основной массовый путь, но сама идея важна: код можно не переводить целиком заранее.

## Это другая ось, чем статическая и динамическая типизация

Модель выполнения и момент проверок — не одно и то же.

Например:

- C: ahead-of-time компиляция + много проверок до запуска;
- Rust: ahead-of-time компиляция + ещё больше проверок до запуска;
- Java: виртуальная машина + статическая типизация, большая часть типовых ошибок ловится до запуска `java`;
- Ruby: виртуальная машина + динамическая типизация, многие проверки происходят уже во время выполнения.

То есть нельзя просто сказать: “VM значит ошибки только в runtime” или “компиляция значит язык статический”. Это разные свойства языка и среды выполнения.

## Время компиляции и время выполнения

**Время компиляции** — момент, когда код переводится и проверяется до запуска.

**Время выполнения** — момент, когда программа уже работает.

Это важно, потому что часть ограничений из курса относится именно ко времени компиляции:

- статическая проверка типов;
- проверка владения в Rust;
- отказ собрать программу при явном нарушении контракта.

А часть проблем относится ко времени выполнения:

- исключения;
- отсутствие файла;
- неверный ввод пользователя;
- ошибки, которые проявляются только на реально дошедшем до них пути выполнения.

## Почему это важно на практике

| Подход | Что получается после перевода | Что это даёт |
|--------|-------------------------------|--------------|
| AOT-компиляция | машинный код | быстрый запуск и выполнение, но нужна перекомпиляция |
| Виртуальная машина | байткод | переносимость и дополнительный слой оптимизаций |
| Прямая интерпретация | нет отдельного артефакта | простой цикл “изменил -> запустил”, но меньше заранее сделанной работы |

На практике границы размываются. Многие VM используют JIT (just-in-time — «в момент выполнения»): часто выполняемый байткод дополнительно переводится в машинный код во время работы. Но для базовой модели этого достаточно: есть код, есть форма перевода, есть момент, когда выполняются проверки.

## Исторический контекст

В начале 1950-х сама идея компилятора казалась спорной: многие программисты привыкли писать машинный код вручную. В 1952 году команда Грейс Хоппер создала A-0 — один из первых компиляторов. FORTRAN сделал компиляцию массовой. BASIC сделал массовым немедленный запуск для обучения. Java популяризовала виртуальную машину как переносимый слой исполнения.

Эти подходы не отменяют друг друга. Они отвечают на разные практические требования: скорость выполнения, скорость обратной связи, переносимость, ранние проверки.
