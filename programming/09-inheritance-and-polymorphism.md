Один класс удобен, пока все объекты ведут себя одинаково. Но это заканчивается быстро. Например, в магазине появляются разные способы доставки: самовывоз, обычный курьер, экспресс-доставка. У каждого свой срок и своя цена.

Первый рабочий вариант обычно выглядит так: в коде хранят признак `kind`, а дальше в нескольких функциях пишут ветвление по этому признаку. Вот [пример](examples/09-delivery-dispatch.rb). Если хотите запустить его без установки Ruby, используйте web runner из [index](index.md). Здесь неважно вручную перечислить все ветки. Важно увидеть, как одно различие по `kind` начинает течь сразу в подписи, цену и срок.

## Когда ветвление расползается

В этом примере одно и то же различие уже повторяется три раза:

- `delivery_label` решает, как назвать способ доставки;
- `delivery_price` решает, сколько он стоит;
- `delivery_eta` решает, какой срок показать.

Пока способов доставки мало, это ещё можно читать. Но как только появляется новый `locker delivery`, правку нужно внести сразу во все три функции. Потом рядом обычно появляются ещё `delivery_refundable?`, `delivery_tracking_label`, `delivery_warning_text`, и то же ветвление течёт дальше по файлу.

Проблема не в самом `if`. Проблема в том, что знание о различиях между видами доставки больше не живёт в одном месте. Оно уже размазано по нескольким функциям, и при каждой новой правке нужно вспоминать, все ли такие места остались согласованными.

## Наследование

Наследование позволяет вынести общую часть в базовый класс, а различия оставить в дочерних:

```ruby
class DeliveryMethod
  attr_reader :label

  def initialize(label)
    @label = label
  end
end

class Pickup < DeliveryMethod
  def initialize
    super("Самовывоз")
  end

  def price(order_total)
    0
  end

  def eta
    "сегодня"
  end
end

class Courier < DeliveryMethod
  def initialize
    super("Курьер")
  end

  def price(order_total)
    300
  end

  def eta
    "2 дня"
  end
end
```

`Pickup < DeliveryMethod` означает, что `Pickup` наследует общую часть от `DeliveryMethod`. Метка `label` и механизм инициализации не копируются в каждый класс заново.

Наследование полезно тогда, когда у сущностей действительно есть общий каркас и общая форма поведения.

## Полиморфизм

После этого внешний код может работать с разными объектами через один и тот же набор сообщений:

```ruby
methods = [Pickup.new, Courier.new]
order_total = 2400

methods.each do |method|
  puts method.label + ": " + method.price(order_total).to_s + ", " + method.eta
end
```

Здесь цикл не ветвится по типу. Он просто вызывает `label`, `price` и `eta` у каждого объекта. Для `Pickup` и `Courier` результат будет разный, но форма вызова одна и та же.

Это и есть полиморфизм: один и тот же внешний вызов, разное поведение в зависимости от конкретного объекта.

Польза здесь опять не для процессора, а для чтения и развития программы. Внешний код знает меньше подробностей о разновидностях сущностей. При добавлении нового вида доставки чаще всего достаточно добавить новый класс, а не переписывать старый dispatcher.

## Когда это уместно

Наследование и полиморфизм не нужны автоматически всякий раз, когда объектов больше одного.

Они окупаются, когда:

- у объектов есть общий контракт;
- внешний код должен обрабатывать их одинаковым образом;
- ветвление по виду объекта уже повторяется в нескольких местах.

Если общего контракта нет, искусственная иерархия только усложнит код.

Даже хорошая иерархия классов не убирает другую проблему: объекты всё ещё можно менять по ходу работы программы. Когда изменений много, становится трудно восстанавливать их историю.
