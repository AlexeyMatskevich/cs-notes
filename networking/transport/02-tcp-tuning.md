# TCP Tuning

**Предпосылки:** [TCP](01-tcp.md) (соединение, handshake, окно, congestion control, завершение).

Для передачи файлов настройки TCP по умолчанию работают хорошо. Но для интерактивных приложений — SSH, Redis, real-time API — поведение TCP может вызывать неожиданные задержки. Проблема не в TCP как таковом, а в том, что его параметры оптимизированы для общего случая, а не для конкретного профиля нагрузки.

## Nagle и TCP_NODELAY: задержки при малых сообщениях

Представим сценарий: Redis-клиент отправляет команду `GET user:123` — всего 14 байт. TCP-сегмент с 14 байтами полезных данных и 20+ байт заголовка — неэффективно. **Алгоритм Nagle** решает эту проблему: если есть неподтверждённый сегмент, мелкие данные накапливаются в буфере и отправляются одним сегментом, когда придёт ACK или буфер заполнится.

Для bulk-передачи это отличная оптимизация — меньше пакетов, выше утилизация сети. Для интерактивных приложений — катастрофа. Redis-клиент отправляет команду, Nagle задерживает её на время RTT (ждёт ACK предыдущего сегмента), сервер получает команду с задержкой, отвечает, клиент отправляет следующую команду — снова задержка. Вместо сотен тысяч операций в секунду — тысячи.

**TCP_NODELAY** — [опция сокета](../../linux/programming/03-sockets.md), отключающая алгоритм Nagle. Данные отправляются немедленно, без накопления. Redis, SSH, игровые серверы, биржевые терминалы — все устанавливают `TCP_NODELAY`.

Цена: больше мелких пакетов в сети. Но для приложений, чувствительных к латентности, это приемлемый компромисс.

## Delayed ACK: вторая половина проблемы

Наgle — на стороне отправителя. На стороне получателя есть симметричная оптимизация: **Delayed ACK**. Вместо немедленного подтверждения каждого сегмента получатель ждёт до 40 ms, надеясь совместить ACK с ответными данными (piggybacking).

Nagle + Delayed ACK вместе создают патологическую ситуацию: отправитель ждёт ACK, чтобы отправить следующие данные (Nagle), а получатель ждёт данных, чтобы отправить ACK (Delayed ACK). Результат — задержка 40 ms на каждом обмене. `TCP_NODELAY` разрывает этот deadlock.

## SO_KEEPALIVE: обнаружение мёртвых соединений

TCP-соединение может существовать бесконечно без обмена данными — это by design. Но если удалённая сторона упала (выдернули кабель, процесс убит, машина перезагрузилась), локальная сторона об этом не узнает. Соединение висит, занимая ресурсы.

**SO_KEEPALIVE** — опция сокета, включающая периодические проверочные пакеты. Три параметра (на Linux):

- `tcp_keepalive_time` — через сколько секунд бездействия начать проверку (по умолчанию 7200 = 2 часа).
- `tcp_keepalive_intvl` — интервал между проверочными пакетами (по умолчанию 75 секунд).
- `tcp_keepalive_probes` — сколько неответов считать обрывом (по умолчанию 9).

По умолчанию обнаружение мёртвого соединения занимает 2 часа + 9 × 75 секунд ≈ 2 часа 11 минут. Для сервера баз данных или брокера сообщений это слишком долго — обычно `tcp_keepalive_time` снижают до 60–300 секунд.

## Socket buffers: пропускная способность

Каждый TCP-сокет имеет буферы отправки и приёма. Размер буфера ограничивает количество неподтверждённых данных "в полёте". Для соединения с высоким bandwidth и высоким RTT (длинный "толстый канал") маленький буфер становится бутылочным горлышком: отправитель заполняет буфер быстрее, чем приходят ACK.

Оптимальный размер буфера = bandwidth × RTT (bandwidth-delay product, BDP). Для канала 1 Gbps с RTT 100 ms: BDP = 125 MB/s × 0.1s = 12.5 MB. По умолчанию буфер сокета значительно меньше.

Современные ОС используют автонастройку буферов (TCP autotuning), но верхняя граница определяется системными параметрами (`net.core.rmem_max`, `net.core.wmem_max` на Linux). Для серверов с высокопропускными соединениями имеет смысл увеличить эти лимиты.

## Listen backlog: очередь входящих соединений

Когда сервер вызывает `listen()`, ядро создаёт две очереди для входящих соединений. **SYN queue** — соединения в процессе рукопожатия (получен SYN, отправлен SYN-ACK, ждём ACK). **Accept queue** — полностью установленные соединения, ожидающие, пока приложение вызовет `accept()`.

Параметр `backlog` в `listen(fd, backlog)` ограничивает размер accept queue. Если очередь заполнена, ядро отбрасывает новые SYN-пакеты (клиент получает таймаут) или отправляет RST.

При всплесках нагрузки (например, после рестарта сервера, когда все клиенты переподключаются одновременно) маленький backlog приводит к отказам. Типичные значения для production-серверов: 128–4096. Nginx по умолчанию использует 511; для высоконагруженных систем рекомендуется увеличить.

## TIME_WAIT: последствия закрытия

После четырёхстороннего закрытия TCP-соединения сторона, инициировавшая закрытие (отправившая первый FIN), переходит в состояние **TIME_WAIT** на 2 × MSL (Maximum Segment Lifetime, обычно 60 секунд). Это нужно, чтобы запоздавшие пакеты от старого соединения не были ошибочно приняты новым соединением на том же порту.

Проблема: HTTP-сервер, который закрывает соединения после каждого запроса, накапливает тысячи сокетов в TIME_WAIT. Каждый занимает запись в таблице ядра и порт. На Linux `net.ipv4.tcp_tw_reuse` позволяет переиспользовать TIME_WAIT-сокеты для новых исходящих соединений (безопасно, если используются TCP timestamps). Включение `keep-alive` на HTTP-уровне (что делает HTTP/1.1 по умолчанию) радикально уменьшает количество TIME_WAIT — соединения не закрываются после каждого запроса.
