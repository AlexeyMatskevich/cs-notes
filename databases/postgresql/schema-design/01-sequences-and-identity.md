# SERIAL/IDENTITY и sequence — генерация id без иллюзий

**Предпосылки:** SQL DDL (CREATE/ALTER TABLE), [MVCC](../concurrency/00-mvcc.md) (COMMIT/ROLLBACK и параллельность), [блокировки](../concurrency/03-locks.md) (почему ожидания появляются там, где их «не видно»).

Почти в каждом приложении есть таблицы с авто‑id. На вид это «техническая деталь», но именно вокруг генерации id часто появляются ложные ожидания: «id без дырок», «id отражает порядок событий», «ROLLBACK вернёт всё как было». В PostgreSQL источник id — sequence, и у него другие гарантии: он оптимизирован на параллельность и скорость, а не на «красивые числа».

## Два способа объявить авто‑id: SERIAL и IDENTITY

`SERIAL` — исторический синтаксический сахар: на самом деле это `integer/bigint` + `DEFAULT nextval(...)` + отдельный объект sequence.

```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL
);
```

`IDENTITY` — стандартный SQL‑способ, появившийся позже. По сути он тоже использует sequence, но объявляется как часть колонки.

```sql
CREATE TABLE users (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL
);
```

Для прикладного кода ключевое одинаково: id берётся через sequence и `nextval`.

## Что такое sequence

Sequence — отдельный объект базы данных, который выдаёт возрастающие числа.

Главная операция — `nextval(seq)`:

- атомарно получает следующий номер,
- сдвигает внутренний счётчик вперёд,
- возвращает номер вызывающей транзакции.

Эта операция должна быстро работать в условиях высокой конкуренции, иначе любое `INSERT` в горячую таблицу будет упираться в генерацию id.

## Почему появляются «дырки» в id

Самое важное: вызов `nextval()` **не откатывается** вместе с транзакцией.

```sql
BEGIN;
INSERT INTO users(email) VALUES ('a@example.com'); -- допустим, id=100
ROLLBACK;

INSERT INTO users(email) VALUES ('b@example.com'); -- id будет 101, а не 100
```

Дыра образуется по двум причинам:

1. **Откат транзакции.** Номер уже выдан, но строка не сохранилась.
2. **Параллельные вставки.** Две транзакции берут номера «вперемешку». Даже если обе закоммитятся, последовательность id отражает только порядок выдачи номеров, а не реальный порядок «кто раньше завершился».

Это не баг и не «недостаток PostgreSQL». Это цена за параллельность: если бы sequence откатывался, то при ROLLBACK пришлось бы «возвращать» номер назад, а при конкуренции это означало бы дополнительные блокировки и проблемы с уникальностью.

## Почему id не равен порядку событий

Часто id используют как прокси времени: «больше id → позже произошло». Это работает, пока:

- вставки идут из одного потока,
- транзакции короткие и не конфликтуют,
- нет ретраев.

В реальной системе это ломается:

- транзакция T1 получила `id=100`, но ждёт блокировку и коммитится поздно,
- транзакция T2 получила `id=101` и коммитится быстро.

Снаружи первым появится `id=101`, хотя номер больше.

Если приложению нужен «порядок событий», это отдельная модель данных: `created_at`, логический sequence на уровне домена, или отдельный механизм упорядочивания.

## BY DEFAULT vs ALWAYS: кто имеет право задавать id

У `IDENTITY` есть два режима:

- `GENERATED BY DEFAULT AS IDENTITY` — можно явно вставить `id`, иначе будет `nextval`.
- `GENERATED ALWAYS AS IDENTITY` — явная вставка `id` запрещена (если не использовать override).

Это важно, когда приложение иногда загружает данные извне и хочет сохранить «оригинальные id». В режиме ALWAYS база защищает от случайных вставок id и тем самым от конфликтов.

## Транзакции, блокировки и производительность

`nextval` — это точка синхронизации: много вставок в одну и ту же таблицу вызывают `nextval` много раз. PostgreSQL делает эту операцию максимально дешёвой, но конкуренция всё равно может проявляться как ожидание.

При этом практический эффект обычно другой: sequence снимает необходимость держать «глобальный счётчик» в приложении и защищает от гонок при генерации id. Это ровно тот случай, когда проще и надёжнее отдать инвариант базе, чем пытаться удержать его в коде.

## Практические правила

1. Не ожидайте «id без дырок». Это нормально и неизбежно.
2. Не используйте id как «время» или «порядок событий» без отдельного поля времени/порядка.
3. Если приложение должно запрещать ручную установку id, используйте `GENERATED ALWAYS`.
4. Если нужно загружать внешние id, используйте `BY DEFAULT` и контролируйте конфликты через `PRIMARY KEY/UNIQUE`.
