# Ограничения (constraints) — целостность данных в базе

**Предпосылки:** SQL DDL (CREATE/ALTER TABLE), [B-tree](../indexes/00-btree.md) (индексы и уникальность), [блокировки](../concurrency/03-locks.md) (row/table locks и ожидания).

Ограничения нужны не «для красоты схемы», а чтобы база данных сама удерживала инварианты, на которые опирается код. Если инвариант не закреплён в базе, он рано или поздно ломается: из‑за гонок, багов, новых сервисов, ручных правок или просто из‑за того, что один путь записи забыл проверку.

В PostgreSQL ограничения — это часть контракта данных. Они влияют не только на корректность, но и на производительность и параллелизм: одни ограничения требуют индексов, другие добавляют проверки на запись, третьи создают ожидания блокировок между транзакциями.

## Два класса инвариантов

Полезно сразу разделять два типа правил:

**Инварианты строки (row-level).** Их можно проверить, глядя на одну строку: `amount >= 0`, `email IS NOT NULL`, `status IN (...)`.

**Инварианты связей (cross-row / cross-table).** Их нельзя проверить по одной строке: «у пользователя уникальный email», «у заказа есть существующий user_id», «переговорка не может быть забронирована дважды на пересекающиеся интервалы».

В PostgreSQL первый класс обычно выражается `NOT NULL`/`CHECK`, второй — `PRIMARY KEY`/`UNIQUE`/`FOREIGN KEY`/`EXCLUDE`.

## PRIMARY KEY и UNIQUE: уникальность как индекс

`PRIMARY KEY` и `UNIQUE` закрепляют правило «дубликатов быть не должно».

```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL UNIQUE
);
```

Ключевое следствие: в PostgreSQL уникальность обеспечивается через индекс. `UNIQUE`‑ограничение создаёт уникальный индекс (обычно B-tree) и проверяет уникальность при вставке/изменении.

Это связывает корректность с I/O: при `INSERT/UPDATE` база должна проверить, что в индексе нет конфликтующей записи, а затем записать новую запись в индекс (и в [WAL](../durability/00-wal.md)). На маленьких таблицах это незаметно, но на горячих таблицах с частыми вставками уникальность — реальная стоимость, за которую вы получаете стабильный контракт данных.

### UNIQUE и NULL

`UNIQUE` не запрещает несколько `NULL` (потому что `NULL` не равен `NULL` в терминах SQL‑логики).

```sql
CREATE TABLE emails (
  email TEXT UNIQUE
);
-- Можно вставить несколько строк с NULL:
INSERT INTO emails(email) VALUES (NULL), (NULL);
```

Если вам нужен «уникальный и не пустой», это всегда связка `NOT NULL` + `UNIQUE`.

### Частый паттерн: уникальность «с учётом soft delete»

Если записи «удаляются» через флаг, часто нужна уникальность только среди активных:

```sql
CREATE UNIQUE INDEX users_email_active_uq
ON users(email)
WHERE deleted_at IS NULL;
```

Это не `UNIQUE CONSTRAINT`, а частичный уникальный индекс, но по смыслу он выполняет ту же работу: держит инвариант, на который опирается код.

## FOREIGN KEY: ссылка на существующие данные

`FOREIGN KEY` закрепляет правило «ссылка должна указывать на существующую строку».

```sql
CREATE TABLE orders (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id)
);
```

Это защищает от «осиротевших» строк: заказ не может ссылаться на несуществующего пользователя.

### Почему индекс на дочерней колонке FK почти всегда нужен

Для корректности FK достаточно индекса на **родительской** стороне (`users(id)`), и он уже есть из‑за `PRIMARY KEY`.

Но для производительности почти всегда нужен индекс на **дочерней** стороне (`orders(user_id)`).

Причина проста: когда вы удаляете или меняете `users.id`, PostgreSQL должен проверить, нет ли в `orders` строк, которые ссылаются на этот `users.id`. Без индекса это превращается в scan по `orders`, и чем больше `orders`, тем больше ненужной работы и тем больше времени держатся блокировки.

Поэтому практическое правило для приложений такое: если есть `FOREIGN KEY (orders.user_id) → users(id)`, то индекс на `orders(user_id)` обычно обязателен.

```sql
CREATE INDEX orders_user_id_idx ON orders(user_id);
```

### ON DELETE / ON UPDATE: что делать с дочерними строками

FK задаёт поведение при удалении/изменении родительской строки:

- `RESTRICT`/`NO ACTION` (по умолчанию): запретить, если есть ссылки.
- `CASCADE`: удалить/обновить дочерние строки автоматически.
- `SET NULL` / `SET DEFAULT`: разорвать ссылку в дочерней строке.

Выбор здесь про смысл данных. `CASCADE` удобен, но опасен как «скрытая массовая запись»: одно удаление может превратиться в тысячи `DELETE` и неожиданно стать дорогой транзакцией.

### FK и ожидания блокировок

FK — не просто «проверка существования». Он создаёт связь между транзакциями.

Когда одна транзакция вставляет строку в `orders` и ссылается на `users(id)`, PostgreSQL должен гарантировать, что в этот момент другая транзакция не удалит или не поменяет ключ пользователя так, чтобы ссылка стала недействительной. Для этого при проверке FK используются row‑level locks на строке родителя (см. режимы `FOR KEY SHARE` и связанные конфликты в [блокировках](../concurrency/03-locks.md)).

Если эти ожидания неожиданны для приложения, они проявляются как «зависшие INSERT/UPDATE», хотя код выглядит безобидно.

## CHECK и NOT NULL: инварианты одной строки

`NOT NULL` и `CHECK` держат правила, которые можно проверить на одной строке.

```sql
CREATE TABLE payments (
  id BIGSERIAL PRIMARY KEY,
  amount_cents BIGINT NOT NULL CHECK (amount_cents >= 0),
  currency TEXT NOT NULL CHECK (currency IN ('USD', 'EUR', 'RUB'))
);
```

Обычно это самый дешёвый способ защитить доменные инварианты: проверка происходит в момент `INSERT/UPDATE`, и вы не можете записать «мусор», на который потом будет падать бизнес‑логика.

Если проверка сложная и в ней участвуют функции, важно помнить: `CHECK` должен быть детерминированным по смыслу. Если условие зависит от текущего времени или внешних таблиц, оно начинает вести себя как триггер с побочными эффектами и может неожиданно ломать повторяемость транзакций.

## EXCLUDE: «запретить пересечения»

Иногда уникальности по значению недостаточно. Типичный пример: бронирования не должны пересекаться по времени для одной переговорки.

```sql
CREATE TABLE bookings (
  room_id BIGINT NOT NULL,
  during TSRANGE NOT NULL
);

ALTER TABLE bookings
ADD CONSTRAINT bookings_no_overlap
EXCLUDE USING gist (
  room_id WITH =,
  during  WITH &&
);
```

Это ограничение говорит: «для одинакового `room_id` диапазоны `during` не могут пересекаться». Технически оно опирается на индекс (обычно GiST) и на операторы, которые умеют проверять пересечение (см. [GiST](../indexes/02-gist.md)).

## DEFERRABLE: когда проверять ограничения

По умолчанию ограничения проверяются немедленно на каждом операторе.

Иногда удобнее отложить проверку до конца транзакции: например, вы переставляете ссылки в нескольких строках и в середине транзакции данные «временно» неконсистентны, но к `COMMIT` всё снова согласовано.

Для этого ограничения можно сделать `DEFERRABLE` и внутри транзакции перевести в режим `DEFERRED`.

Это сильный инструмент, но он меняет точку, где вы ловите ошибку: вместо «ошибка на конкретном INSERT» вы получите «ошибка на COMMIT». В коде это обычно значит, что обработка ошибок и retry должны быть рассчитаны на такую задержку.

## Практические правила для приложений

Если свести всё к нескольким привычкам, чаще всего работают такие:

1. Почти у каждой таблицы должен быть `PRIMARY KEY`.
2. У каждого `FOREIGN KEY` почти всегда должен быть индекс на дочерней колонке.
3. `UNIQUE` без `NOT NULL` редко делает то, что «кажется» по смыслу.
4. `CHECK` — лучший способ закрепить простые доменные правила прямо в данных.
5. Если правило связывает несколько строк (уникальность/ссылки/пересечения), считайте, что у него всегда есть стоимость в параллелизме и I/O — и это нормально, потому что стоимость покупает корректность.
