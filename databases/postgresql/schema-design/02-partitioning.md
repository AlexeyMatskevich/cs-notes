# Декларативное партиционирование

**Предпосылки:** SQL DDL (PARTITION BY), [планировщик запросов](../query-processing/00-planner.md) (selectivity и выбор плана), [B-tree](../indexes/00-btree.md) (индексы и порядок), [EXPLAIN](../query-processing/03-explain.md) (как увидеть pruning и сканы по партициям).

Сервис аналитики записывает события: клики, просмотры, покупки. За год накопилось 500 млн строк в таблице `events` — 120 ГБ данных, B-tree индекс по `created_at` занимает 15 ГБ. Запрос «события пользователя за сегодня» (`WHERE user_id = 42 AND created_at >= '2026-02-13'`) проходит через индекс, но [VACUUM](../maintenance/00-vacuum.md) на 120 ГБ таблице занимает минуты, REINDEX — десятки минут с блокировкой записи. Проблема не в скорости чтения, а в управляемости: удаление данных старше 90 дней через `DELETE` создаёт миллионы dead tuples и bloat.

Партиционирование решает эту проблему: вместо одной огромной таблицы — набор помесячных таблиц. Удаление старых данных — `DROP TABLE events_2025_11`, мгновенная операция без dead tuples.

## Как устроена партиционированная таблица

```sql
CREATE TABLE events (
  id BIGSERIAL,
  created_at TIMESTAMP NOT NULL,
  user_id BIGINT NOT NULL,
  payload JSONB NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE events_2026_02 PARTITION OF events
FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

В DDL нет `PRIMARY KEY(id)` — это не случайность. PostgreSQL требует, чтобы [уникальные ограничения](00-constraints.md) на партиционированной таблице включали ключ партиционирования. `UNIQUE(id)` без `created_at` невозможен: уникальность проверяется только внутри одной партиции, а не по всей таблице. Допустимый вариант — `PRIMARY KEY(id, created_at)`.

Для приложения таблица остаётся `events`: INSERT и SELECT пишутся как обычно. PostgreSQL сам выбирает нужную партицию при вставке и отфильтровывает лишние при чтении — если запрос даёт ему такую возможность.

## Partition pruning

Partition pruning — отбрасывание партиций, которые заведомо не содержат нужных строк. Возвращаемся к сценарию: аналитик запрашивает события за один день.

```sql
SELECT *
FROM events
WHERE created_at >= '2026-02-10'
  AND created_at <  '2026-02-11';
```

PostgreSQL читает только `events_2026_02`, потому что остальные месяцы не пересекаются с диапазоном. При 12 месячных партициях это 1/12 данных — вместо 120 ГБ сканируется ~10 ГБ, вместо 15 ГБ индекса — ~1.25 ГБ. Если данные за 3 года и 36 партиций — 1/36, то есть ~3.3 ГБ вместо 120 ГБ.

Pruning бывает двух видов. **Plan-time pruning** работает, когда границы известны из текста запроса (литералы): планировщик исключает партиции ещё при построении плана и может точнее оценить стоимость. **Runtime pruning** — когда условие зависит от параметра (`$1`) и значение станет известно только при выполнении. Оба механизма отсеивают партиции, но plan-time делает это раньше. Это следствие той же проблемы, что и parameter sensitivity в [prepared statements](../query-processing/05-prepared-statements.md): generic plan для prepared statement может включить все партиции в узел `Append` и полагаться на runtime pruning — корректно, но планировщик работает с худшей оценкой стоимости.

В EXPLAIN это видно по узлу `Append`. Если plan-time pruning сработал, в плане остаётся одна-две партиции и строка `Subplans Removed: N`:

```
Append (actual rows=8543)
  -> Index Scan using events_2026_02_created_at_idx on events_2026_02
       Index Cond: (created_at >= '2026-02-10' AND created_at < '2026-02-11')
  Subplans Removed: 11
```

Если pruning не сработал — все 36 партиций, фактически 36 отдельных сканов.

## Индексы на партициях

Партиционирование не отменяет индексы — оно меняет их масштаб. Вместо одного B-tree на 15 ГБ появляются 12 индексов по ~1.25 ГБ. Каждый помещается в буферный кеш целиком гораздо чаще, чем один огромный. REINDEX и VACUUM становятся локальными — можно обслужить одну партицию, не трогая остальные.

Но это не бесплатно: планировщик должен выбрать план внутри каждой релевантной партиции. Запрос с диапазоном в 6 месяцев на месячных партициях — это 6 детей `Append`, каждый со своим index scan. При десятках и сотнях партиций planning time становится ощутимым даже для OLTP-запросов, которые должны выполняться за миллисекунды.

Уникальность через всю партиционированную таблицу тоже ограничена. Глобальный уникальный ключ должен включать ключ партиционирования. Если партиционируете по `created_at`, то `UNIQUE(email)` на всю таблицу невозможен — одинаковый email может оказаться в разных партициях, и PostgreSQL не проверяет уникальность между ними. Нужен `UNIQUE(email, created_at)` или пересмотр схемы.

## Retention: мгновенное удаление старых данных

Главный операционный выигрыш партиционирования — удаление целых партиций вместо массового `DELETE`. `DELETE FROM events WHERE created_at < '2025-12-01'` на 500 млн строк создаёт десятки миллионов dead tuples, нагружает [WAL](../durability/00-wal.md) и VACUUM на часы. `DROP TABLE events_2025_11` — мгновенная DDL-операция. Каждая партиция — это отдельный [relfilenode](../storage/03-physical-layout.md) со своими файлами main-форка, FSM и VM в каталоге `base/<dboid>/`. DROP удаляет эти файлы на уровне ОС: ни dead tuples, ни bloat, ни нагрузки на VACUUM.

## Цена партиционирования

Партиционирование не является бесплатным ускорителем. Помимо накладных расходов планировщика (описанных выше), есть ещё несколько ограничений.

PostgreSQL не создаёт будущие партиции автоматически. Если `events_2026_03` не существует к 1 марта — INSERT в март упадёт с ошибкой. Создание партиций — задача кода приложения, миграций или расширения pg_partman.

Запросы без фильтра по ключу партиционирования сканируют все партиции. Это превращает преимущество в недостаток: вместо одного Seq Scan по 120 ГБ — 36 отдельных Seq Scan, каждый с собственным overhead на открытие файлов и инициализацию.

Партиционирование делит данные внутри одного сервера. Разделение данных между серверами — [шардинг](../../../system-design/sharding.md) — решает другую задачу: масштабирование ёмкости и пропускной способности записи.

## Типовые ошибки в запросах

Партиционирование ускоряет только запросы, дающие планировщику шанс отфильтровать партиции. Условие на ключ партиционирования, «спрятанное» в выражении (`WHERE extract(month FROM created_at) = 2`), не позволяет вывести диапазон — pruning не срабатывает. Правильная форма — `WHERE created_at >= '2026-02-01' AND created_at < '2026-03-01'`.

Запрос без фильтра по ключу (`SELECT * FROM events WHERE user_id = 42` без ограничения по `created_at`) сканирует все партиции. Слишком широкий диапазон — например, за целый год на месячных партициях — тоже сводит выигрыш к минимуму: 12 партиций = 12 отдельных сканов, pruning ничего не отбросил. Инженерная дисциплина: почти каждый запрос к партиционированной таблице обязан явно ограничивать диапазон ключа партиционирования.
