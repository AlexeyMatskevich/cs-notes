# Декларативное партиционирование — как управлять большими таблицами

**Предпосылки:** SQL DDL (PARTITION BY), [планировщик запросов](../query-processing/00-planner.md) (selectivity и выбор плана), [B-tree](../indexes/00-btree.md) (индексы и порядок), [EXPLAIN](../query-processing/03-explain.md) (как увидеть pruning и сканы по партициям).

Партиционирование в PostgreSQL нужно не «для красоты схемы», а чтобы держать большие таблицы в управляемой форме: быстрее отсеивать ненужные данные, уменьшать стоимость индексов и не превращать каждый запрос по времени в scan по миллиарду строк.

Главная идея проста: вместо одной огромной таблицы мы храним несколько меньших, и запросы должны читать только те части, которые реально пересекаются с условием.

## Что такое партиционирование

Партиционированная таблица — это «логическая» таблица, которая физически состоит из набора дочерних таблиц‑партиций. Строки раскладываются по партициям по правилу `PARTITION BY`.

Чаще всего партиционируют по времени:

```sql
CREATE TABLE events (
  id BIGSERIAL PRIMARY KEY,
  created_at TIMESTAMP NOT NULL,
  user_id BIGINT NOT NULL,
  payload JSONB NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE events_2026_02 PARTITION OF events
FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

Для приложения таблица остаётся `events`: `INSERT` и `SELECT` пишутся как обычно. PostgreSQL сам выбирает нужную партицию при вставке и должен уметь «выкинуть» лишние партиции при чтении.

## Pruning: почему партиционирование может ускорить SELECT

**Partition pruning** — это отбор подмножества партиций, которые могут содержать строки, удовлетворяющие условиям запроса.

Если запрос ограничивает `created_at` на конкретный диапазон, партиционирование по `created_at` позволяет вообще не читать большинство партиций.

```sql
SELECT *
FROM events
WHERE created_at >= '2026-02-10'
  AND created_at <  '2026-02-11';
```

Идеальная картина: PostgreSQL читает только `events_2026_02`, потому что другие месяцы не пересекаются с диапазоном.

## Два режима pruning: при планировании и в рантайме

Pruning бывает двух видов:

**Plan-time pruning.** Лишние партиции отбрасываются ещё на этапе планирования, если границы известны из текста запроса (литералы).

**Runtime pruning.** Лишние партиции отбрасываются во время выполнения, если условие зависит от параметров (`$1`) и значение станет известно только в момент выполнения.

Это важно по той же причине, что и parameter sensitivity: форма запроса влияет на то, насколько рано оптимизатор может сделать «правильный» выбор.

## Как увидеть pruning в EXPLAIN

В плане для партиционированной таблицы обычно видно `Append`/`Merge Append` над дочерними таблицами.

Если pruning сработал, список дочерних таблиц будет коротким: в `Append` окажется только несколько партиций.

Если pruning не сработал, `Append` будет содержать почти все партиции, и вы фактически делаете N отдельных сканов.

## Индексы на партициях: что меняется

Партиционирование не отменяет индексы. Оно меняет их масштаб:

- вместо одного огромного индекса вы получаете набор меньших индексов — по одному на партицию;
- маленькие индексы чаще помещаются в кеш;
- операции `REINDEX` и `VACUUM` становятся локальными по партициям.

Обычно это выигрыш, но есть и цена: планировщик должен выбирать планы внутри каждой партиции, а запрос с широким диапазоном может сканировать десятки партиций и десятки индексов.

### Уникальность и ключ партиционирования

В PostgreSQL уникальность через всю партиционированную таблицу имеет важное ограничение: глобальная уникальность должна быть выразима через структуру партиций.

Практическое следствие: если вы хотите `UNIQUE` на партиционированной таблице, обычно в уникальный ключ приходится включать ключ партиционирования.

Это напрямую влияет на дизайн: например, если партиционируете по `created_at`, то «уникальный `email` на всю таблицу» не реализуется как простой уникальный индекс на партициях, потому что одинаковый `email` может оказаться в разных партициях.

## Что партиционирование НЕ делает автоматически

Партиционирование не является автоматическим «ускорителем всего».

Типичные ожидания, которые не оправдываются:

1. **«Партиции заменят индекс».** Нет. Pruning может убрать часть данных целиком, но внутри выбранной партиции всё равно нужен эффективный доступ (индексы, селективные фильтры).
2. **«Партиции сами будут создаваться».** PostgreSQL не создаёт будущие партиции автоматически — это должен делать код/миграции.
3. **«Старые данные сами исчезнут».** Если нужен retention, вы обычно удаляете партиции как таблицы (`DROP TABLE events_2024_01`) — это мгновенно по сравнению с массовым `DELETE`.

## Типовые ошибки в запросах

Партиционирование ускоряет только те запросы, которые дают оптимизатору шанс отфильтровать партиции.

Частые ошибки:

- Условие на ключ партиционирования «спрятано» в выражении, и оптимизатор не может вывести диапазон.
- Запрос не содержит фильтра по ключу партиционирования, хотя логически он подразумевался (например, забыли ограничение по времени).
- Фильтр по времени задаётся так, что диапазон слишком широкий, и всё равно приходится читать десятки партиций.

Поэтому для партиционированных таблиц часто появляется инженерная дисциплина: почти каждый запрос обязан явно ограничивать диапазон партиционирования.
