# Hash Index

**Предпосылки:** [хеш-таблица](../../algorithms-and-data-structures/linear/05-hash-table.md), [B-tree](00-btree.md).

**Hash Index** — индекс на основе хеш-таблицы.

**Hash** — от английского "рубить, крошить". Хеш-функция "измельчает" вход произвольной длины в число фиксированного размера.

## Мотивация: когда B-tree избыточен

B-tree поддерживает порядок ключей. Это даёт range scan, сортировку, операторы <, <=, >=, >.

Порядок ключей — это практическая вещь: B-tree умеет «пройти» ключи по возрастанию или убыванию и тем самым часто обслуживает `ORDER BY` без отдельной сортировки. Hash‑индекс такого порядка не хранит: ключи «размазаны» по bucket'ам, поэтому ни range scan, ни «бесплатного» `ORDER BY` у него нет.

```sql
-- B-tree может эффективно выдать результат в порядке ключа:
SELECT * FROM users ORDER BY email LIMIT 10;

-- И так же эффективно обходит диапазон:
SELECT * FROM users WHERE email >= 'a' AND email < 'b';

-- Hash‑индекс не ускоряет эти запросы: у него нет упорядоченного обхода ключей.
```

Если нужно только равенство (=), вся работа по поддержанию порядка — накладные расходы без пользы.

Теоретически хеш-таблица даёт O(1) для точечных запросов против O(log N) у B-tree. На практике разница меньше — B-tree с данными в кеше очень быстр. Но для определённых сценариев Hash может быть выгоднее.

## Структура Hash Index в PostgreSQL

Внутри это хеш‑таблица, разложенная по страницам: ключ → hash → bucket → список ссылок на строки.

```text
Meta Page (страница 0)
  - параметры и метаданные индекса

Bucket Pages
  - основные страницы bucket'ов (bucket ≈ корзина)
  - bucket_num определяется по hash ключа

Overflow Pages
  - если bucket переполнен, записи «вытекают» в цепочку overflow страниц
  - это дисковый аналог chaining в обычной хеш‑таблице

Bitmap Pages
  - служебные страницы для учёта свободных overflow страниц
```

Рост индекса устроен через **linear hashing**: число bucket'ов увеличивается постепенно (split «по одному»), без полного пересоздания индекса.

## Что хранится в записи

```text
Hash code (4 байта) — результат хеш‑функции
TID (6 байт) — указатель на строку в heap
```

**Hash code** — число, полученное применением хеш-функции к ключу.

**Важно:** в индексе хранится хеш ключа, а не «отсортированные ключи» как в B-tree. Из‑за коллизий совпадение hash code даёт только кандидата — поэтому после индекса обычно нужен recheck в heap.

## Поиск

Запрос: WHERE email = 'alice@example.com'

```text
Шаг 1: Вычисляем hash('alice@example.com') → например, 0x7A3B2C1D

Шаг 2: Определяем bucket
  bucket_num = hash_code % num_buckets

Шаг 3: Читаем bucket page
  Для каждой записи сравниваем hash code
  Если совпал — кандидат

Шаг 4: Если есть overflow pages — читаем их тоже

Шаг 5: Recheck в heap
  Hash code совпал, но возможна коллизия (разные ключи с одинаковым hash code)
  Идём в heap и проверяем реальное значение ключа
```

**Почему recheck обязателен:** индекс не хранит сам ключ — не может отличить 'alice@example.com' от другой строки с тем же hash code.

## Вставка

```text
Шаг 1: Вычисляем hash(key)
Шаг 2: Находим bucket
Шаг 3: Ищем место в bucket page
  Если место есть — вставляем
  Если нет — используем цепочку overflow страниц
Шаг 4: При росте индекса PostgreSQL постепенно сплитит bucket'ы (linear hashing)
```

## Ограничения Hash Index

**Нельзя использовать для UNIQUE constraint.** Из‑за коллизий совпадение hash ещё не означает совпадение ключей, а уникальность требует точного сравнения ключей внутри индекса.

**Только равенство.** Никаких диапазонов, LIKE, регулярных выражений.

## История и надёжность

**До PostgreSQL 10:** Hash index не писался в [WAL](../durability/00-wal.md). При crash — индекс повреждён, нужен REINDEX. Непригоден для production.

**PostgreSQL 10+:** Hash полностью поддерживает WAL. Можно использовать на production.

## Сравнение Hash и B-tree

| Характеристика | Hash | B-tree |
|----------------|------|--------|
| Поддерживаемые операторы | Только = | =, <, <=, >, >=, BETWEEN |
| Range scan | Нет | Да |
| ORDER BY | Нет | Да |
| Сложность поиска | O(1) амортиз. | O(log N) |
| Размер индекса | Обычно меньше (только hash+TID) | Обычно больше (ключ+TID) |
| Recheck | Всегда нужен | Не нужен |
| UNIQUE | Не поддерживает | Поддерживает |

## Когда использовать Hash

Реалистичные сценарии:

1. Колонка с очень длинными значениями (URL, длинные строки), только поиск по равенству, не нужна уникальность

2. Таблица с огромным количеством точечных запросов, память ограничена, важен размер индекса

На практике большинство случаев покрывается B-tree. Hash — нишевый инструмент.

## Синтаксис

    CREATE INDEX idx_email_hash ON users USING hash(email);

По умолчанию (без USING) PostgreSQL создаёт B-tree.

Hash — нишевый инструмент для точечных запросов. Для огромных append-only таблиц с естественной корреляцией данных существует самый компактный тип индекса — [BRIN](04-brin.md).
