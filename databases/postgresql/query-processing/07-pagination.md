# Пагинация: `LIMIT/OFFSET` vs keyset (seek)

**Предпосылки:** [B-tree](../indexes/00-btree.md) (порядок ключей и range scan), [EXPLAIN](03-explain.md) (как читать план), базовые `SELECT/WHERE/ORDER BY`.

Пагинация кажется простым UI‑требованием: «покажи ещё 50 элементов». Но на уровне базы данных это всегда вопрос о двух вещах:

1. **Какой порядок считать “следующим”.** Без стабильного `ORDER BY` страницы будут прыгать.
2. **Сколько работы нужно сделать, чтобы добраться до нужного места.** Это определяет, будет ли “страница 2000” работать за миллисекунды или за секунды.

## Стабильный порядок: без него пагинация не существует

Если запрос не фиксирует порядок, база имеет право возвращать строки в любом порядке, который удобен текущему плану. Поэтому первая техническая привычка такая:

```sql
-- Плохо: порядок не задан, страницы будут «гулять»
SELECT * FROM posts LIMIT 50;

-- Хорошо: порядок фиксирован
SELECT * FROM posts ORDER BY created_at DESC LIMIT 50;
```

Дальше важно сделать порядок **детерминированным**. Если `created_at` не уникален, добавьте tie‑breaker:

```sql
SELECT *
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Теперь «следующая страница» имеет ясный смысл: это строки “меньше” последней строки предыдущей страницы по паре `(created_at, id)`.

## OFFSET‑пагинация: простая, но становится дороже с номером страницы

Классический вариант:

```sql
SELECT *
FROM posts
WHERE created_at >= now() - interval '30 days'
ORDER BY created_at DESC, id DESC
LIMIT 50 OFFSET 5000;
```

### Что в ней хорошего

- можно прыгнуть на произвольную страницу (по номеру),
- форма запроса простая,
- легко реализуется в любом ORM.

### Что в ней ломается

1. **Стоимость растёт с OFFSET.** Чтобы вернуть 50 строк после `OFFSET 5000`, базе обычно нужно пройти первые 5000 строк в выбранном порядке и отбросить их. Даже если используется индекс, это всё равно работа.

2. **Страницы дрейфуют при вставках/удалениях.** OFFSET описывает позицию «N‑я строка в текущем порядке». Если между запросами появились новые строки или какие‑то строки исчезли, позиции сдвигаются: пользователь может увидеть дубликаты или пропуски между страницами.

OFFSET‑пагинация подходит, когда:

- таблица небольшая,
- пользователь редко уходит далеко,
- данные мало меняются во время навигации,
- или вам принципиально нужен «переход на страницу N».

## Keyset‑пагинация (seek): стабильнее и масштабируется по глубине

Keyset‑пагинация не говорит «пропусти N строк». Она говорит «начни после вот этой границы».

### Базовый вариант для “следующей страницы”

Пусть первая страница:

```sql
SELECT id, created_at, title
FROM posts
WHERE created_at >= now() - interval '30 days'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Запоминаем ключ последней строки страницы, например:

```text
last_created_at = 2026-01-31 12:00:00
last_id = 123456
```

Следующая страница:

```sql
SELECT id, created_at, title
FROM posts
WHERE created_at >= now() - interval '30 days'
  AND (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Здесь важны сразу две вещи:

1. Сравнение идёт по той же паре, по которой задан `ORDER BY`.
2. Используется строгий `<`, чтобы не получить дубликат последней строки.

### Почему это быстрее на «дальних» страницах

B-tree хранит ключи в порядке. Условие вида `(created_at, id) < (...)` делает запрос похожим на «начни сканирование индекса от конкретного места и иди дальше 50 строк». Поэтому стоимость становится примерно O(page_size), а не O(offset).

### Индекс под keyset‑пагинацию

Чтобы это работало предсказуемо, нужен индекс, который совпадает с порядком:

```sql
CREATE INDEX posts_created_at_id_idx
ON posts (created_at DESC, id DESC);
```

Если вы возвращаете дополнительные колонки и хотите уменьшить походы в heap, часто помогает `INCLUDE` (см. covering indexes в [B-tree](../indexes/00-btree.md)).

## «Назад» и произвольные страницы

Keyset‑пагинация идеально подходит для «вперёд» (infinite scroll, лента, лог). Но у неё есть ограничения:

- переход на «страницу 2000» без дополнительной структуры сделать нельзя: у вас нет границы, от которой начинать;
- “назад” обычно реализуют отдельным запросом с обратным сравнением и обратным `ORDER BY`, а затем разворачивают результат в приложении.

Если UI требует «перейти на страницу N», OFFSET остаётся самым простым вариантом. Часто делают смешанный подход: keyset для обычной навигации и отдельный “jump” для редких случаев, где пользователю действительно нужен номер страницы.

## Как проверить на своей базе

1. Создайте индекс под порядок, если его нет.
2. Возьмите один и тот же фильтр и сравните:
   - `LIMIT 50 OFFSET 100000`
   - keyset‑вариант с `(created_at, id) < (...)`
3. Смотрите `EXPLAIN (ANALYZE, BUFFERS)`:
   - сколько строк/страниц прочитано,
   - есть ли заметный `shared read` (диск),
   - не появился ли `Sort` (значит, порядок не поддерживается индексом).
