# Практические паттерны параллельного доступа

**Предпосылки:** [уровни изоляции](02-isolation-levels.md), [блокировки](03-locks.md).

В приложении проблемы проявляются как конкретные сценарии: read → compute → write, отчёты, списания, очереди задач. Выбор защиты зависит от того, какие данные должны быть согласованы и может ли приложение безопасно повторить транзакцию.

## 7 паттернов: какой уровень изоляции нужен

Каждый паттерн диктует минимальный уровень защиты.

**Паттерн 1: Простые независимые операции**

Записываемое значение не зависит от прочитанного. Нет цепочки read → compute → write.

```sql
UPDATE users SET status = 'active' WHERE id = 5;
UPDATE products SET name = 'Widget' WHERE id = 42;
```

**Уровень:** READ COMMITTED (дефолт) — достаточен.

**Почему:** Нет зависимости read → write. Даже если другая транзакция изменила строку — мы просто записываем своё значение поверх.

**Паттерн 2: Read-Modify-Write в SQL (атомарная модификация)**

Читаем и вычисляем новое значение **внутри одного SQL-оператора**.

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 5;
UPDATE products SET stock = stock - 1 WHERE id = 42;
UPDATE posts SET likes_count = likes_count + 1 WHERE id = 99;
```

**Уровень:** READ COMMITTED — достаточен.

**Почему:** При конфликте PostgreSQL перечитает строку и **пересчитает выражение** с новым значением. Если balance был 200, другая транзакция изменила на 150, PostgreSQL вычислит 150 - 100 = 50.

**Критично:** Работает только если вся логика в одном UPDATE. Как только вычисление выносится в приложение — паттерн ломается.

**Паттерн 3: Read-Modify-Write в приложении**

Читаем значение в приложение, вычисляем там, записываем результат.

```ruby
# ОПАСНЫЙ паттерн
user = User.find(5)                     # SELECT → balance = 100
new_balance = user.balance - 10         # Вычисляем в Ruby: 90
user.update(balance: new_balance)       # UPDATE SET balance = 90

# Если между SELECT и UPDATE другая транзакция изменила balance на 80,
# мы запишем 90, потеряв изменение (должно быть 70)
```

**Уровень:** REPEATABLE READ — минимально необходим.

**Почему:** На REPEATABLE READ PostgreSQL обнаружит: строка изменена транзакцией, невидимой в нашем snapshot → ошибка сериализации → приложение ловит и повторяет.

**Альтернативы без повышения уровня:**
1. Переписать на атомарный UPDATE (паттерн 2)
2. Использовать `SELECT ... FOR UPDATE` для явной блокировки

**Паттерн 4: Проверка условия перед записью (одна строка)**

Читаем строку, проверяем условие в приложении, записываем в **ту же строку**.

```ruby
# ОПАСНЫЙ паттерн
account = Account.find(5)               # SELECT → balance = 100
if account.balance >= 100
  account.update(balance: account.balance - 100)
end

# Если между SELECT и UPDATE баланс стал 50 — спишем в минус
```

**Уровень:** REPEATABLE READ — минимально необходим.

**Почему:** Та же проблема read-modify-write. Решение то же: REPEATABLE READ выдаст ошибку при конфликте.

**Альтернатива — атомарная проверка в SQL:**
```sql
UPDATE accounts SET balance = balance - 100
WHERE id = 5 AND balance >= 100;
-- Проверить affected rows!
```

**Паттерн 5: Cross-row инварианты (UPDATE разных строк)**

Инвариант связывает несколько строк. Транзакции читают общие данные, но пишут в **разные строки**.

```sql
-- Инвариант: минимум 1 дежурный врач
-- T1:
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- видит 2
UPDATE doctors SET on_call = false WHERE id = 1;    -- "останется 1"

-- T2 (параллельно):
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- видит 2
UPDATE doctors SET on_call = false WHERE id = 2;    -- "останется 1"

-- Результат: 0 дежурных. Инвариант нарушен.
```

**Уровень:** SERIALIZABLE — необходим.

**Почему:** REPEATABLE READ ловит конфликты только когда две транзакции пишут **одну строку**. Здесь строки разные (id=1 и id=2), конфликта записи нет. Это **write skew**.

SERIALIZABLE отслеживает зависимости через SIREAD locks: "T1 читала данные, которые T2 изменила" + "T2 читала данные, которые T1 изменила" = цикл → одна откатывается.

**Альтернатива:** FOR UPDATE на всех связанных строках (заблокировать всех врачей перед проверкой).

**Паттерн 6: Cross-row инварианты (INSERT)**

Инвариант ограничивает количество строк. Транзакции проверяют и вставляют **новые строки**.

```sql
-- Инвариант: очередь ≤ 10 человек
-- T1:
SELECT COUNT(*) FROM queue;  -- видит 9
INSERT INTO queue (...);     -- "ещё можно"

-- T2 (параллельно):
SELECT COUNT(*) FROM queue;  -- видит 9
INSERT INTO queue (...);     -- "ещё можно"

-- Результат: 11 строк. Инвариант нарушен.
```

**Уровень:** SERIALIZABLE — необходим.

**Почему:** INSERT создаёт новые строки — нет конфликта с существующими. REPEATABLE READ не поможет. Это write skew с фантомами.

**Паттерн 7: Cross-row инварианты (DELETE)**

Инвариант требует минимальное количество строк. Транзакции проверяют и удаляют **разные строки**.

```sql
-- Инвариант: минимум 3 товара на складе
-- T1:
SELECT COUNT(*) FROM inventory WHERE product = 'X';  -- видит 4
DELETE FROM inventory WHERE id = 101;                -- "останется 3"

-- T2 (параллельно):
SELECT COUNT(*) FROM inventory WHERE product = 'X';  -- видит 4
DELETE FROM inventory WHERE id = 102;                -- "останется 3"

-- Результат: 2 товара. Инвариант нарушен.
```

**Уровень:** SERIALIZABLE — необходим.

**Почему:** Та же логика — разные строки, REPEATABLE READ не ловит.

## Сводная таблица паттернов

| Паттерн | Пример | Минимальный уровень |
|---------|--------|---------------------|
| Независимые операции | `SET status = 'active'` | READ COMMITTED |
| Read-modify-write в SQL | `SET balance = balance - 100` | READ COMMITTED |
| Read-modify-write в приложении | Ruby: `balance - 100` → UPDATE | REPEATABLE READ |
| Проверка + запись (одна строка) | `if balance >= 100 then UPDATE` | REPEATABLE READ |
| Cross-row + UPDATE разных строк | Дежурные врачи | SERIALIZABLE |
| Cross-row + INSERT | Ограничение очереди | SERIALIZABLE |
| Cross-row + DELETE | Минимальный запас | SERIALIZABLE |

## Два архитектурных подхода

Определив паттерн и минимальный уровень, выбираем **как** защищаться.

Мы знаем: параллельные транзакции могут конфликтовать. Вопрос: когда платить за защиту?

**Оптимистичный подход:** «Скорее всего конфликта не будет». Работаем параллельно, не блокируя друг друга. Если конфликт всё-таки случился — откатываемся и повторяем. Платим только когда конфликт реально произошёл.

Название «оптимистичный» — потому что мы *оптимистично* предполагаем, что конфликтов не будет.

**Пессимистичный подход:** «Конфликт вероятен, лучше перестраховаться». Блокируем данные заранее, до начала работы. Конкуренты ждут в очереди. Платим всегда, даже если конфликта не было бы.

Название «пессимистичный» — потому что мы *пессимистично* предполагаем худшее и защищаемся заранее.

**Это не вопрос «что лучше»** — это выбор, зависящий от характера нагрузки.

## Оптимистичный: REPEATABLE READ / SERIALIZABLE + retry

```ruby
def with_retry(isolation:, max_attempts: 3)
  attempts = 0
  begin
    ActiveRecord::Base.transaction(isolation: isolation) do
      yield
    end
  rescue ActiveRecord::SerializationFailure
    attempts += 1
    retry if attempts < max_attempts
    raise
  end
end

with_retry(isolation: :repeatable_read) do
  user = User.find(5)
  user.update(balance: user.balance - 100)
end
```

**Характеристики:**
- Транзакции не блокируют друг друга до момента записи
- При конфликте — откат и повтор
- При высокой конкуренции: много откатов, потерянная работа

**Когда выбирать:**
- Конфликты редкие
- Транзакции длинные (не хочешь держать блокировку)
- Читаешь много, меняешь мало

## Пессимистичный: FOR UPDATE

```ruby
ActiveRecord::Base.transaction do
  user = User.lock("FOR UPDATE").find(5)
  user.update(balance: user.balance - 100)
end
```

**Характеристики:**
- Блокировка берётся при SELECT
- Конкуренты ждут в очереди
- Каждая транзакция завершается успешно (если нет deadlock)

**Когда выбирать:**
- Конфликты частые
- Транзакции короткие
- Работаешь с конкретными известными строками

## Hot spot: когда выбор критичен

**Hot spot** — ситуация, когда много транзакций конкурируют за одни и те же данные.

**Пример:** Баланс популярного пользователя. 100 транзакций в секунду списывают/начисляют деньги одному user_id.

**Оптимистичный подход (REPEATABLE READ + retry):**
```text
T1: читает balance=1000, вычисляет 900
T2: читает balance=1000, вычисляет 900
T3: читает balance=1000, вычисляет 900
T1: коммитит → balance=900
T2: конфликт → откат → retry → читает 900 → коммитит 800
T3: конфликт → откат → retry → конфликт → откат → retry...
```

При высокой конкуренции: каскад откатов, потерянная работа, latency растёт экспоненциально.

**Пессимистичный подход (FOR UPDATE):**
```text
T1: FOR UPDATE → блокирует строку
T2: FOR UPDATE → ждёт в очереди
T3: FOR UPDATE → ждёт в очереди
T1: коммитит
T2: получает блокировку, работает, коммитит
T3: получает блокировку, работает, коммитит
```

Каждая транзакция ждёт, но каждая завершается с первой попытки. Пропускная способность предсказуема.

**Вывод для hot spot:** FOR UPDATE лучше. Очередь эффективнее каскада откатов.

## Когда REPEATABLE READ лучше FOR UPDATE

**Сценарий:** Генерация отчёта. Читаем 100k строк, делаем вычисления, записываем результат в одну строку.

**FOR UPDATE на 100k строк:**
- Блокируем все строки на время отчёта
- Другие транзакции не могут их обновлять — ждут
- Пропускная способность системы падает

**REPEATABLE READ:**
- Работаем со snapshot — никого не блокируем
- Другие транзакции свободно читают и пишут
- Если кто-то изменил ту одну строку результата — получим ошибку и retry
- Один retry для одной строки — приемлемо

**Вывод:** Для длинных read-heavy транзакций REPEATABLE READ лучше — не блокирует систему.

## Сравнение подходов

| Критерий | FOR UPDATE (пессимистичный) | REPEATABLE READ (оптимистичный) |
|----------|---------------------------|--------------------------------|
| Конфликты частые (hot spot) | Лучше | Каскад откатов |
| Конфликты редкие | Лишние блокировки | Лучше |
| Транзакция короткая | Лучше | Приемлемо |
| Транзакция длинная | Блокирует других | Лучше |
| Читаем много, пишем мало | Блокируем лишнее | Лучше |
| Нужна гарантия успеха | Всегда успешно* | Требует retry |
| Простота кода | Нет retry логики | Требует try/catch |

*При условии отсутствия deadlock

## Третий путь: атомарный SQL

```ruby
User.where(id: 5).update_all("balance = balance - 100")

# С проверкой условия:
affected = User.where("id = 5 AND balance >= 100")
               .update_all("balance = balance - 100")
raise InsufficientFunds if affected == 0
```

**Характеристики:**
- Вся логика в одном SQL-операторе
- PostgreSQL сам перечитывает и пересчитывает при конфликте
- READ COMMITTED достаточен
- Нет retry, нет явных блокировок

**Когда выбирать:**
- Логика достаточно простая для SQL
- Высокая конкуренция

## Когда возникает вопрос выбора

Ты пишешь код, который читает данные, принимает решение на их основе, и записывает результат. Классический read-modify-write.

```ruby
user = User.find(5)
if user.balance >= 100
  user.update(balance: user.balance - 100)
end
```

Этот код работает в тестах. Но в production параллельные запросы могут создать lost update. Нужна защита. Какой подход выбрать?

## Цена каждого уровня изоляции

| Уровень | Память | CPU | Риск откатов | Влияние на VACUUM |
|---------|--------|-----|--------------|-------------------|
| READ COMMITTED | Минимум (snapshot на оператор) | Минимум | Низкий | Минимум |
| REPEATABLE READ | Snapshot на транзакцию | Чуть выше | При конфликте записи | Long-running транзакции мешают |
| SERIALIZABLE | Snapshot + SIREAD locks | Отслеживание зависимостей | При любом опасном цикле | То же + память на locks |

**Почему long-running транзакции мешают VACUUM:**

[VACUUM](../maintenance/00-vacuum.md) удаляет dead tuples — старые версии строк. Но он не может удалить версию, если хоть одна транзакция ещё может её видеть через snapshot.

Транзакция на REPEATABLE READ/SERIALIZABLE держит snapshot на всё время работы. Пока она активна — все версии строк, существовавшие на момент старта, должны оставаться. VACUUM видит: «есть активный snapshot» — и не трогает старые версии.

Результат: bloat (таблицы разбухают), производительность падает.

## Чеклист выбора

1. **Можно выразить логику в атомарном SQL?** → READ COMMITTED + атомарный UPDATE. Это проще всего — нет retry, нет явных блокировок.

2. **Инвариант затрагивает несколько строк?** (например, «минимум 1 дежурный») → SERIALIZABLE или FOR UPDATE на всех связанных строках. Атомарный SQL не поможет — проблема в зависимости между строками.

3. **Конфликты частые?** (hot spot — много транзакций на одни данные) → FOR UPDATE (пессимистичный). Оптимистичный подход будет постоянно откатываться.

4. **Конфликты редкие?** → REPEATABLE READ (оптимистичный). Большинство транзакций пройдут без отката.

5. **Готов к retry-логике?** → Нет → FOR UPDATE. Да → REPEATABLE READ / SERIALIZABLE.

## Сводка: что защищает от чего

| Аномалия | READ COMMITTED | + FOR UPDATE | REPEATABLE READ | SERIALIZABLE |
|----------|----------------|--------------|-----------------|--------------|
| Dirty read | ✓ | ✓ | ✓ | ✓ |
| Non-repeatable read | ✗ | ✓ | ✓ | ✓ |
| Phantom read | ✗ | ✗ | ✓ | ✓ |
| Lost update | ✗* | ✓ | ✓ | ✓ |
| Write skew | ✗ | ✓** | ✗ | ✓ |

*READ COMMITTED защищает при атомарном SQL (`balance = balance - 100`), не защищает при read-modify-write в приложении.

**FOR UPDATE защищает от write skew, только если заблокировать все связанные строки.

Паттерны описывают правильные подходы. [Распространённые ошибки](05-common-mistakes.md) показывают, что бывает, когда эти подходы игнорируются.
