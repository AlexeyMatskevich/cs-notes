# Очереди задач в PostgreSQL: `FOR UPDATE SKIP LOCKED`

**Предпосылки:** [блокировки](03-locks.md) (row-level locks, очереди ожидания, deadlock), [практические паттерны](04-patterns.md) (пессимистичный подход и hot spots).

Очередь задач — типичный компонент бэкенда: отправить email, пересчитать кеш, обработать webhook, прогнать биллинг. Самый наивный вариант — `SELECT ... LIMIT 1`, потом `UPDATE status='processing'`. Но как только воркеров становится больше одного, появляется гонка: два воркера могут выбрать одну и ту же задачу, и работа будет выполнена дважды.

PostgreSQL даёт простой инструмент для «раздачи задач без гонок» прямо на уровне SQL: `SELECT ... FOR UPDATE` и модификаторы `SKIP LOCKED` / `NOWAIT`.

## Проблема: два воркера забирают одну задачу

Пусть есть таблица:

```sql
CREATE TABLE jobs (
  id BIGSERIAL PRIMARY KEY,
  run_at TIMESTAMP NOT NULL,
  status TEXT NOT NULL, -- queued/processing/done/failed
  payload JSONB NOT NULL
);
```

Наивная логика воркера:

```sql
BEGIN;

SELECT id
FROM jobs
WHERE status = 'queued' AND run_at <= now()
ORDER BY run_at
LIMIT 1;

UPDATE jobs SET status = 'processing' WHERE id = $id;

COMMIT;
```

Если два воркера выполняют этот код параллельно, оба могут увидеть одну и ту же строку в первом SELECT, а затем оба попробуют обновить её. В лучшем случае один будет ждать блокировку и в конце обновит уже «не ту» строку, в худшем — вы получите двойную обработку из‑за логики приложения вокруг транзакций.

## Решение: блокировать выбранную строку при чтении

`SELECT ... FOR UPDATE` берёт row‑level lock на выбранные строки. Это превращает «выбрать» и «пометить как processing» в одну атомарную операцию на уровне конкурентного доступа: пока воркер держит блокировку, другой воркер не сможет «забрать» ту же задачу.

Практический шаблон:

```sql
BEGIN;

WITH next_job AS (
  SELECT id
  FROM jobs
  WHERE status = 'queued' AND run_at <= now()
  ORDER BY run_at
  FOR UPDATE
  LIMIT 1
)
UPDATE jobs
SET status = 'processing'
WHERE id IN (SELECT id FROM next_job)
RETURNING *;

COMMIT;
```

Если воркер получил строку в `RETURNING`, значит он действительно «забрал» задачу. Если `RETURNING` пустой — задачи нет.

## `SKIP LOCKED`: не ждать, а брать следующую

Проблема с чистым `FOR UPDATE` в очереди такая: если самый ранний job заблокирован (например, воркер долго обрабатывает или упал в середине транзакции), остальные воркеры будут ждать эту строку и не смогут взять следующие задачи.

`SKIP LOCKED` решает это для очередей: «если строка заблокирована, пропусти её и попробуй следующую».

```sql
WITH next_job AS (
  SELECT id
  FROM jobs
  WHERE status = 'queued' AND run_at <= now()
  ORDER BY run_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs
SET status = 'processing'
WHERE id IN (SELECT id FROM next_job)
RETURNING *;
```

Эта форма превращает таблицу `jobs` в многопотребительскую очередь без централизованного диспетчера.

### Цена `SKIP LOCKED`

`SKIP LOCKED` сознательно жертвует строгой справедливостью. Если ранняя задача постоянно заблокирована, воркеры будут обрабатывать более поздние.

Для очередей это обычно допустимо, если вы отдельно контролируете stuck‑задачи (например, через `processing_started_at` и таймаут) и умеете перекидывать их обратно в `queued`.

## `NOWAIT`: если заблокировано — сразу ошибка

`NOWAIT` — другой режим: «не ждать блокировку, а сразу завершиться ошибкой».

Это полезно, когда ожидание само по себе вредно (например, API‑запрос должен быстро ответить, даже если ресурс занят), но для очередей чаще подходит именно `SKIP LOCKED`, потому что ошибка — это лишний шум и лишняя логика ретраев.

## Почему нужен `ORDER BY`

Если очередь должна быть более‑менее FIFO (по `run_at` или по `id`), порядок нужно зафиксировать:

```sql
ORDER BY run_at, id
```

Без `ORDER BY` PostgreSQL не обязан возвращать строки в каком‑то стабильном порядке, и очередь будет вести себя хаотично.

## Индекс для очереди

Очередь обычно фильтруется по `status` и `run_at` и сортируется по `run_at`.

Чтобы воркер не делал scan по всей таблице `jobs`, обычно нужен индекс, который поддерживает эту форму запроса. Для простого случая:

```sql
CREATE INDEX jobs_queue_idx
ON jobs(status, run_at, id);
```

Это индекс «под форму доступа», а не «потому что индексы всегда полезны».

## Что делать с идемпотентностью

Даже при `SKIP LOCKED` приложение должно быть рассчитано на повторы. Причины повторов:

- воркер получил задачу, выполнил внешний эффект (например, отправил письмо), но упал до `COMMIT`;
- транзакция откатилась из‑за ошибки, а задача снова стала видимой;
- вы сами вернули задачу в `queued` по таймауту, хотя внешний эффект уже произошёл.

Поэтому для очередей обычно вводят доменную идемпотентность: уникальный ключ эффекта, запись “уже отправлено”, `ON CONFLICT DO NOTHING` и т.п.
