# Распространённые ошибки параллельного доступа

**Предпосылки:** [уровни изоляции](02-isolation-levels.md), [блокировки](03-locks.md), [паттерны](04-patterns.md).

Эти ошибки — следствие непонимания механизмов MVCC, блокировок и уровней изоляции. Каждая связана с конкретным заблуждением о том, как работает PostgreSQL.

## Ошибка 1: FOR UPDATE без необходимости

**Заблуждение:** «FOR UPDATE — это безопасность, лишним не будет».

```ruby
User.lock("FOR UPDATE").find(5)  # просто читаем, не меняем
```

**Реальность:** FOR UPDATE — это блокировка. Другие транзакции, которые хотят изменить эту строку, будут ждать. Если ты не меняешь данные — ты зря держишь очередь.

## Ошибка 2: REPEATABLE READ / SERIALIZABLE без retry

**Заблуждение:** «Я поставил высокий уровень изоляции — теперь всё безопасно».

```ruby
ActiveRecord::Base.transaction(isolation: :serializable) do
  # ...
end
# Ошибка сериализации не обработана!
```

**Реальность:** REPEATABLE READ и SERIALIZABLE работают по оптимистичному принципу. Они не предотвращают конфликты — они их обнаруживают. При конфликте транзакция откатывается с ошибкой. Если приложение не ловит ошибку и не повторяет — данные просто не сохранятся.

## Ошибка 3: Игнорировать affected rows

**Заблуждение:** «UPDATE выполнился без ошибки — значит данные обновились».

```ruby
User.where("id = 5 AND balance >= 100").update_all("balance = balance - 100")
# Не проверили результат!
```

**Реальность:** Вспомним поведение READ COMMITTED при конфликте: PostgreSQL перечитывает строку и проверяет WHERE заново. Если условие больше не выполняется (balance уже < 100) — UPDATE успешен, но 0 строк изменено. Деньги не списались, а код продолжает работать как будто всё хорошо.

## Ошибка 4: Блокировать в разном порядке

**Заблуждение:** «Deadlock — это что-то редкое и экзотическое».

```text
T1: lock(row_1), lock(row_2)
T2: lock(row_2), lock(row_1)  → DEADLOCK
```

**Реальность:** Вспомним: каждый UPDATE автоматически берёт блокировку. Если две транзакции обновляют одни и те же строки в разном порядке — deadlock неизбежен при достаточной нагрузке. PostgreSQL обнаружит и откатит одну транзакцию, но это потерянная работа.

**Решение:** Сортируй ресурсы перед блокировкой. Всегда.

## Ошибка 5: Думать, что REPEATABLE READ = эксклюзивный доступ

**Заблуждение:** «Я на REPEATABLE READ — другие транзакции не смогут изменить мои данные».

```ruby
transaction(isolation: :repeatable_read) do
  user = User.find(5)
  sleep(10)  # другая транзакция меняет и коммитит
  user.update(...)  # получим ошибку сериализации
end
```

**Реальность:** REPEATABLE READ не блокирует данные. Другие транзакции свободно читают и пишут. REPEATABLE READ лишь гарантирует: ты увидишь согласованный snapshot И получишь ошибку при попытке записать в строку, изменённую после твоего snapshot.

Это **обнаружение** конфликта, не **предотвращение**. Для эксклюзивного доступа нужен FOR UPDATE.

## Ошибка 6: Долгие транзакции на REPEATABLE READ

```ruby
transaction(isolation: :repeatable_read) do
  generate_huge_report  # 30 минут
end
```

**Почему опасно:** Вспомним как работает [MVCC](00-mvcc.md). [VACUUM](../maintenance/00-vacuum.md) удаляет dead tuples — старые версии строк. Но он не может удалить версию, если хоть одна транзакция ещё может её видеть через свой snapshot.

Транзакция на REPEATABLE READ держит snapshot 30 минут. Все версии строк, существовавшие на момент старта, должны оставаться — вдруг транзакция их прочитает. VACUUM видит: «есть активный snapshot от 30 минут назад» — и не трогает старые версии.

За 30 минут накопились тысячи dead tuples. VACUUM не может их удалить. Таблица разбухает (bloat). После завершения транзакции VACUUM уберёт мусор, но таблица уже выросла — место не освобождается автоматически.

**Решение:** Для длинных read-only операций используй READ COMMITTED. Каждый оператор создаёт свежий snapshot, старые версии не держатся.

## Ошибка 7: Долгий SELECT блокирует ALTER TABLE

**Заблуждение:** «SELECT ничего не блокирует, это же просто чтение».

```sql
SELECT * FROM huge_table;  -- 10 минут, держит ACCESS SHARE
ALTER TABLE huge_table ...;  -- ждёт ACCESS EXCLUSIVE
```

**Реальность:** SELECT берёт ACCESS SHARE. ALTER TABLE требует ACCESS EXCLUSIVE. Они несовместимы — миграция ждёт.

**Скрытая проблема:** ALTER TABLE в ожидании блокирует ВСЕ последующие запросы к таблице — даже SELECT. PostgreSQL ставит их в очередь за ALTER TABLE.

**Решения:** `lock_timeout` на DDL, `CREATE INDEX CONCURRENTLY`, вынос аналитики на реплику, `idle_in_transaction_session_timeout`.

Ошибки параллельного доступа проявляются в рантайме. Но есть и более фундаментальная проблема: каждый UPDATE создаёт dead tuples, и без регулярного [VACUUM](../maintenance/00-vacuum.md) таблица разбухает.
