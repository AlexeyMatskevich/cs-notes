# Шардирование: когда одной базы мало

**Предпосылки:** [репликация](00-replication.md), [партиционирование](../schema-design/02-partitioning.md), базовая идея [хеширования](../../algorithms-and-data-structures/linear/05-hash-table.md).

Пока данные и нагрузка помещаются на один узел, почти все проблемы решаются внутри одного PostgreSQL: индексы, кеш, партиции, реплики для чтений. Но иногда упираются в предел одной машины: объём данных, пропускная способность записи или стоимость вертикального масштаба.

Шардирование решает задачу иначе: хранить данные не в одном PostgreSQL, а в нескольких независимых кластерах, распределив строки по «шардам».

## Шардирование vs партиционирование

Эти слова похожи, но последствия разные.

**Партиционирование** — один PostgreSQL, одна точка записи, один WAL, один контур транзакций. Таблица логически одна, физически — набор партиций, а оптимизатор умеет отбрасывать ненужные партиции (pruning).

**Шардирование** — несколько PostgreSQL. У каждого шарда свой WAL, свои блокировки и свои транзакции. Запросы, которым нужны данные из нескольких шардов, становятся распределёнными.

## Что даёт шардирование

Шардирование обычно выбирают ради двух вещей:

1. **Ёмкость по данным.** Можно хранить больше, чем влезает на один узел.
2. **Пропускная способность записи.** Можно писать параллельно в разные шарды, если нагрузка распределена по ключу.

## Цена: распределённые запросы и «глобальные» гарантии

Как только данные находятся на разных узлах, появляются две новые сложности.

**1) Запросы, которые «собирают всё».** `JOIN`, `GROUP BY`, `ORDER BY`, глобальный `LIMIT/OFFSET` по всем данным — теперь это либо fan-out (опрос всех шардов), либо заранее подготовленные агрегаты/индексы, либо отказ от таких запросов.

**2) Гарантии, которые раньше давал один узел.** В одном PostgreSQL уникальность, внешние ключи и транзакции работают как единый контракт. В шардированном мире «уникальность по всей системе» и «атомарность через несколько узлов» требуют отдельного механизма и обычно становятся дороже.

## Шард-ключ: по чему распределять строки

Шардирование почти всегда строится вокруг одного поля — **shard key**. Это значение, по которому система понимает, на каком шарде лежит строка.

Хороший shard key обычно:

- есть в большинстве запросов (чтобы можно было маршрутизировать запрос на один шард);
- имеет много различных значений (чтобы нагрузка распределялась);
- не создаёт горячих точек (например, «все записи текущего дня» на одном шарде);
- стабилен (если shard key часто меняется, строки придётся «перевозить» между шардами).

## Как распределяют данные

Самые частые схемы:

**Range-based sharding.** Диапазоны значений живут на разных шардах (например, по времени). Плюс — легко «отсечь» старые данные. Минус — риск hot shard, если новые данные всегда попадают в один диапазон.

**Hash-based sharding.** Шард определяется по `hash(key) % N`. Плюс — равномерность. Минус — при изменении числа шардов меняется распределение, и приходится массово переносить данные.

**Consistent hashing.** Вариант хеш‑распределения, где добавление/удаление шарда влияет только на часть ключей, а не на все сразу. Это упрощает постепенное расширение кластера, но добавляет сложности в маршрутизации и балансировке.

## Перебалансировка (resharding)

Добавить новый шард — значит изменить функцию распределения и переместить часть данных. Это тяжёлая операция:

- нужно копировать много строк и индексов,
- нужно обеспечивать согласованность во время переезда,
- нужно поддерживать маршрутизацию на старое и новое место, пока миграция не завершится.

Поэтому шардирование — это не только «разложили данные», но и постоянная задача управления распределением.
