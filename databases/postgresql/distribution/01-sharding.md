# Шардирование в PostgreSQL

**Предпосылки:** [шардинг](../../../system-design/sharding.md) (shard key, resharding), [репликация](00-replication.md), [партиционирование](../schema-design/02-partitioning.md), базовая идея [хеширования](../../algorithms-and-data-structures/linear/05-hash-table.md).

Репликация решает проблему отказов и разгружает чтения, но не помогает, когда система упирается в пределы одного сервера. Допустим, сервис доставки еды обрабатывает 50 000 заказов в сутки. Таблица `orders` — 200 млн строк, 80 ГБ. Primary обслуживает 3000 запросов/сек на чтение и 500 транзакций/сек на запись. Реплики забирают часть чтений, но все 500 записей/сек всё равно идут в один primary. При росте до 2000 записей/сек primary упирается в CPU и I/O — реплики не помогут, потому что запись не масштабируется горизонтально через репликацию.

Шардирование решает эту проблему: данные разносятся по нескольким независимым кластерам PostgreSQL, каждый обслуживает свою долю записей.

## Как выглядит система после шардирования

```text
client -> app/router -> shard 0 (PostgreSQL + replicas)
                   |-> shard 1 (PostgreSQL + replicas)
                   |-> shard 2 (PostgreSQL + replicas)
                   |-> shard 3 (PostgreSQL + replicas)
```

При 4 шардах каждый обслуживает ~125 записей/сек вместо 500. При росте до 2000 записей/сек — 500 на шард, что один PostgreSQL выдерживает комфортно.

## Партиционирование vs шардирование

Партиционирование и шардирование оба делят таблицу на части. Разница — где проходит граница.

**Партиционирование** делит таблицу *внутри одного PostgreSQL*. Один журнал, одна точка записи, один контур транзакций: JOIN, UNIQUE, FOREIGN KEY работают как обычно. Меняется масштаб доступа — планировщик может не читать лишние партиции.

**Шардирование** делит данные *между несколькими PostgreSQL*. У каждого шарда свой журнал, свои блокировки и свои транзакции. Всё, что требует данных из разных шардов, перестаёт быть одним SQL-запросом и становится задачей распределённой системы.

## Shard key: что определяет маршрутизацию

Для сервиса доставки самые частые запросы — «заказы конкретного пользователя»: история, текущий статус, оплата. Естественный shard key — `user_id`. Маршрутизация: `shard = hash(user_id) % N`. Все заказы одного пользователя оказываются в одном шарде — запросы по user_id всегда попадают в один шард без scatter-gather.

Запрос «заказы пользователя 42» идёт в один конкретный шард. Запрос «все заказы за сегодня по всем пользователям» (отчёт для бизнеса) не содержит user_id и требует опроса всех 4 шардов, сбора результатов и агрегации в приложении — это 4 параллельных запроса + merge на стороне клиента. При 100 шардах — 100 запросов. Cross-shard запросы добавляют N round-trips к общему времени, поэтому аналитику обычно выносят в отдельное хранилище (data warehouse, OLAP).

## Что становится сложнее

**Cross-shard запросы.** GROUP BY, ORDER BY, JOIN между данными разных пользователей — всё это «обойти все шарды и собрать». Запрос, который на одном PostgreSQL занимал 50 мс, может стать 200 мс из-за N round-trips и merge.

**Ограничения целостности.** UNIQUE и FOREIGN KEY работают внутри одного шарда. «Email уникален по всем пользователям» требует либо отдельного lookup-сервиса, либо включения shard key в ключ уникальности.

**Транзакции.** Обычная транзакция PostgreSQL атомарна внутри одного кластера. Перевод бонусов от пользователя A (shard 0) к пользователю B (shard 2) — две независимые транзакции без атомарности между ними. Приложение должно явно решать, что делать при частичном успехе. Без координации чтение между шардами становится eventually consistent — [модели консистентности](../../../system-design/01-consistency-models.md) описывают спектр промежуточных гарантий.

**Операционная сложность.** Миграции, VACUUM, бэкапы, мониторинг — всё умножается на количество шардов. 4 шарда — терпимо. 100 шардов — нужна автоматизация.

## Как шардируют PostgreSQL на практике

У PostgreSQL нет встроенного шардинга. Два основных подхода:

**На уровне приложения.** Приложение само выбирает шард по shard key и держит несколько пулов соединений. Максимальная гибкость, но вся логика маршрутизации и scatter-gather — ответственность разработчика. Запросы без shard key требуют явной инженерной дисциплины.

**Распределённый слой.** Citus добавляет координатор (принимает запросы) и воркеры (хранят данные). Координатор хранит правила распределения и может распараллеливать часть запросов. Снижает цену ручной маршрутизации, но накладывает ограничения на модель данных и типы эффективных запросов.
