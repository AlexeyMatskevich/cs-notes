# Шардирование в PostgreSQL: когда одного кластера мало

**Предпосылки:** [распределение данных](../../distribution.md) (что такое шардинг и shard key), [репликация](00-replication.md), [партиционирование](../schema-design/02-partitioning.md), базовая идея [хеширования](../../algorithms-and-data-structures/linear/05-hash-table.md).

Репликация решает проблему отказов и иногда разгружает чтения, но почти не помогает, когда упираются в пределы *одной* машины: объём данных не помещается или запись/обновления стали слишком тяжёлыми для одного primary (узла записи). В этот момент появляется идея шардинга: не держать весь набор данных в одном PostgreSQL, а разделить его на части и разнести по нескольким независимым кластерам.

В терминологии PostgreSQL «кластер» — это один экземпляр PostgreSQL со своим набором файлов (data directory). В шардинге таких кластеров становится несколько, и каждый из них отвечает только за свой «кусок» данных.

Важно: у PostgreSQL нет встроенного механизма шардинга. Ядро не умеет само распределять строки по нескольким узлам и автоматически маршрутизировать запросы между ними. Поэтому шардирование в PostgreSQL обычно делают на уровне приложения или через внешний распределённый слой (например, Citus).

## Как выглядит система после шардинга

Если упростить, приложение получает два слоя вместо одного:

```text
client → app/router → shard A (PostgreSQL) → (опционально реплики)
                 ↘→ shard B (PostgreSQL) → (опционально реплики)
                 ↘→ shard C (PostgreSQL) → (опционально реплики)
```

Ключевой новый компонент — маршрутизация: по входному запросу нужно понять, в какой шард идти. Обычно это делается по shard key (см. [распределение данных](../../distribution.md)).

## Партиционирование и шардирование — похожие слова, разные последствия

Партиционирование и шардирование похожи тем, что «делят таблицу на части». Разница в том, где проходит граница.

**Партиционирование** делит одну большую таблицу *внутри одного PostgreSQL*. У вас остаётся один журнал изменений, одна точка записи и один контур транзакций: `JOIN`, `UNIQUE`, `FOREIGN KEY` и обычные транзакции работают так же, как без партиций. Меняется в основном масштаб: вместо одной огромной таблицы — несколько меньших, и оптимизатор может не читать лишнее.

**Шардирование** делит данные *между несколькими PostgreSQL*. У каждого шарда свой журнал изменений, свои блокировки и свои транзакции. Всё, что требует данных из разных шардов, перестаёт быть «одним SQL-запросом к одной базе» и превращается в задачу распределённой системы.

## Shard key в PostgreSQL: что именно делает приложение

Представим сервис заказов, где самые частые запросы выглядят так: «покажи заказы конкретного пользователя». Тогда естественный shard key — `user_id`.

Схема «одинаковая таблица на каждом шарде» выглядит примерно так:

```text
shard 0: orders(...)
shard 1: orders(...)
shard 2: orders(...)
```

А маршрутизация в приложении — так:

```text
shard = hash(user_id) % N
```

Дальше приложение выбирает соединение с нужным шардом (например, из пула соединений) и выполняет запрос.

Запрос с `user_id=42` идёт в один конкретный шард. А запрос «посчитать заказы за сегодня» не содержит `user_id` и, значит, потребует опросить все шарды и сложить результат (или заранее поддерживать отдельную агрегированную таблицу).

## Что становится сложнее

Проблема шардинга не в том, что «сложно настроить». Сложность в том, что привычные гарантии и удобства одного PostgreSQL оказываются локальными — внутри одного шарда.

**Запросы “по всем данным”.** `GROUP BY`, `ORDER BY`, отчёты «за весь день по всем пользователям», поиск по всей таблице — всё это либо становится “обойти все шарды и собрать”, либо требует отдельных агрегированных таблиц, которые поддерживаются фоновыми задачами.

**Ограничения целостности.** `UNIQUE` и `FOREIGN KEY` PostgreSQL гарантирует внутри одного кластера. «Глобальная уникальность» по всем шардам требует отдельного решения, либо такого выбора shard key, при котором нужная уникальность становится локальной (например, ключ уникальности включает shard key).

**Транзакции.** Обычная транзакция PostgreSQL атомарна только внутри одного кластера. Если бизнес‑операция затрагивает два шарда, вам нужен дополнительный уровень координации в приложении (и нужно явно решать, что делать при частичном успехе).

**Миграции и обслуживание.** Любое изменение схемы, настройка `VACUUM`, бэкапы и мониторинг становятся задачей “умножить на количество шардов”.

## Как шардируют PostgreSQL на практике

Обычно встречаются два подхода.

**Шардирование на уровне приложения.** Приложение само выбирает шард по shard key и держит несколько пулов соединений. Это даёт максимальную гибкость, но требует дисциплины: запросы без shard key (или с несколькими значениями shard key) становятся отдельной инженерной задачей.

**Распределённый слой поверх PostgreSQL.** Например, Citus добавляет “координатор” (узел, куда подключаются клиенты) и “воркеры” (узлы с данными). Координатор хранит правила распределения и может распараллеливать часть запросов по воркерам. Это снижает цену ручной маршрутизации, но накладывает ограничения на модель данных и на типы запросов, которые будут эффективны.
