# Распределённые блокировки

**Предпосылки:** [String](../data-structures/00-string.md), [Lua-скрипты](../atomicity/02-lua-scripting.md), [репликация](../distribution/00-replication.md).

## Базовая блокировка: SET NX EX

`SET lock:resource NX EX 30` — атомарная команда, которая устанавливает ключ только если он не существует (NX), с TTL 30 секунд (EX). Если команда вернула OK — блокировка захвачена. Если nil — ресурс занят другим процессом, и клиент должен повторить попытку после случайной задержки (random backoff), чтобы избежать конкуренции нескольких клиентов за одну блокировку.

```redis-cli
SET lock:order:42 "owner-abc-123" NX EX 30
-- → OK (блокировка получена)
-- → nil (ресурс уже заблокирован)
```

TTL необходим для защиты от мёртвых блокировок: если процесс, захвативший блокировку, упал и не освободил её, TTL гарантирует автоматическое освобождение.

## Проблема: удаление чужой блокировки

Если работа заняла больше TTL, блокировка истекает. Другой процесс захватывает блокировку. Первый процесс завершает работу и выполняет `DEL lock:order:42` — удаляя блокировку второго процесса. Теперь третий процесс тоже может захватить блокировку, и два процесса работают параллельно.

## Решение: уникальный идентификатор + Lua-скрипт

При захвате блокировки в значение записывается уникальный идентификатор (UUID, PID + thread ID + random). При освобождении Lua-скрипт атомарно проверяет, что значение совпадает, и только тогда удаляет:

```redis-cli
-- захват:
SET lock:order:42 "process-a-uuid-xyz" NX EX 30

-- освобождение (атомарно через Lua):
EVAL "
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
  else
    return 0
  end
" 1 lock:order:42 "process-a-uuid-xyz"
```

Без Lua между `GET` и `DEL` может вклиниться другая команда — Lua гарантирует атомарность.

## Проблема: единственный Redis

Если Redis — один инстанс, при его падении все блокировки теряются. Начиная с Redis 3.2, AOF записывает абсолютные timestamps для TTL, поэтому при восстановлении из AOF просроченные ключи корректно удаляются. Однако при `appendfsync everysec` (по умолчанию) до секунды данных может не попасть в лог, и блокировка, записанная прямо перед падением, просто исчезнет. При failover на реплику блокировка может отсутствовать — асинхронная репликация могла не успеть передать её.

## Redlock: распределённая блокировка

Алгоритм Redlock (предложен Salvatore Sanfilippo, автором Redis) использует N независимых Redis-инстансов (обычно 5, на разных машинах, без репликации между ними). Клиент захватывает блокировку на каждом инстансе, фиксируя время. Если блокировка успешно получена на большинстве инстансов (≥ N/2 + 1) и суммарное время захвата меньше TTL — блокировка считается захваченной. Иначе — клиент освобождает блокировку на всех инстансах и повторяет попытку.

Redlock защищает от падения отдельных Redis-инстансов: даже если 2 из 5 упали, блокировка всё ещё действует на 3 оставшихся.

## Fencing tokens: защита от потери блокировки

Даже с Redlock возможна ситуация: процесс A получил блокировку, затем произошла длительная пауза (GC-пауза в JVM или Go, задержка сети, swap) длиной в TTL, блокировка истекла, процесс B получил блокировку, процесс A «проснулся» и продолжил работу, считая что блокировка активна. Оба процесса выполняют защищённую операцию.

Fencing token — монотонно возрастающий номер, который выдаётся при захвате блокировки. Защищаемый ресурс (база данных, внешний сервис) проверяет fencing token: если пришёл запрос с token меньше последнего принятого — запрос отклоняется. Это переносит проверку на сторону ресурса и не зависит от корректности блокировки.

Redis не предоставляет fencing tokens из коробки. Их реализуют через `INCR` отдельного ключа при захвате блокировки, а полученное значение передают ресурсу.

## На практике

Для большинства случаев (идемпотентные операции, координация между процессами одного приложения) достаточно базовой блокировки `SET NX EX` + Lua для освобождения на одном Redis. Redlock нужен, когда потеря блокировки при падении Redis приводит к реальным последствиям (двойные платежи, повреждение данных). Fencing tokens нужны, когда даже Redlock не даёт достаточных гарантий (финансовые операции, критичные системы).

Martin Kleppmann в статье «How to do distributed locking» (2016) критикует Redlock и рекомендует fencing tokens как единственный надёжный механизм. Salvatore Sanfilippo опубликовал ответ в защиту Redlock. Дискуссия не завершена однозначно — выбор зависит от требований к корректности.
