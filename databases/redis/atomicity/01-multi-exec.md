# MULTI/EXEC

**Предпосылки:** [Атомарность одной команды](00-single-command.md).

## Зачем нужны транзакции

Одна команда атомарна, но иногда нужно выполнить несколько команд как единое целое. Без транзакций между командами клиента A могут вклиниться команды клиента B:

```text
Клиент A: GET balance       → 100
Клиент B: GET balance       → 100
Клиент A: SET balance 80    (списал 20)
Клиент B: SET balance 70    (списал 30, но от старого 100)
-- Результат: 70. Должно быть 50.
```

## MULTI/EXEC: атомарный пакет команд

`MULTI` начинает транзакцию. Все последующие команды не выполняются немедленно — Redis помещает их в очередь и отвечает `QUEUED`. `EXEC` выполняет все накопленные команды атомарно: между ними не может вклиниться команда от другого клиента. `DISCARD` отменяет транзакцию, очищая очередь.

```redis-cli
MULTI
SET balance 80                -- → QUEUED
INCR login_count              -- → QUEUED
SET status "active"           -- → QUEUED
EXEC                          -- выполнить все три атомарно
-- → ["OK", 1, "OK"]
```

## Нет rollback

MULTI/EXEC гарантирует атомарность выполнения, но не целостность в случае ошибки. Принципиальное отличие от SQL-транзакций: Redis не откатывает транзакцию при ошибке в одной из команд. Если `INCR` применена к строковому значению — эта команда вернёт ошибку, но остальные команды в транзакции выполнятся успешно. Redis-авторы объясняют это тем, что ошибки в транзакции — это ошибки программирования (неправильный тип данных), а не конкурентные конфликты, и rollback усложнил бы реализацию без практической пользы.

Ошибки синтаксиса (несуществующая команда, неправильное количество аргументов) обнаруживаются на этапе `QUEUED`, и Redis откажется выполнять `EXEC` целиком.

## Ограничение: нет условий внутри транзакции

Отсутствие rollback — не единственное ограничение. Команды в очереди не имеют доступа к результатам друг друга. Нельзя написать «если GET вернул X, то SET Y» — потому что GET выполнится только при EXEC, а к тому моменту все команды уже в очереди. Для условной логики нужен [Lua-скрипт](02-lua-scripting.md).

## WATCH: проверить, потом записать

Часто нужен паттерн «прочитать значение, решить на его основе что делать, записать результат» — но без гарантии, что значение не изменилось между чтением и записью. `WATCH` решает это: клиент начинает «наблюдать» за ключами. Если между `WATCH` и `EXEC` другой клиент изменил наблюдаемый ключ, `EXEC` возвращает nil — транзакция не выполнена. Клиент может повторить попытку.

```redis-cli
WATCH balance
-- прочитать текущее значение
GET balance                   -- → "100"
-- подготовить транзакцию на основе прочитанного
MULTI
SET balance 80
EXEC
-- → ["OK"] если balance не изменился
-- → (nil) если другой клиент изменил balance между WATCH и EXEC
```

Такой подход называется оптимистичной блокировкой: WATCH не мешает другим клиентам читать или писать — он лишь отклоняет транзакцию, если обнаружен конфликт. При высокой конкуренции за один ключ количество повторных попыток может расти. В таких случаях Lua-скрипт может быть эффективнее — он выполняется атомарно без повторов.

`UNWATCH` снимает наблюдение за всеми ключами без выполнения транзакции. После `EXEC` или `DISCARD` наблюдение снимается автоматически — явный `UNWATCH` не нужен.

## MULTI/EXEC + pipelining

MULTI/EXEC обеспечивает атомарность, но не экономит сетевые задержки: MULTI, каждая команда и EXEC отправляются отдельными сообщениями, что означает несколько round-trip'ов по сети. MULTI/EXEC хорошо комбинируется с [pipelining](../architecture/02-pipelining.md): клиент отправляет MULTI, все команды и EXEC одним пакетом. Это даёт и атомарность (MULTI/EXEC), и экономию на сетевых задержках (pipelining).
