# RDB — снимки данных

**Предпосылки:** [Что такое Redis](../architecture/00-what-is-redis.md), процесс (fork), файловая система.

## Проблема: данные в памяти не переживают рестарт

Redis хранит всё в RAM. При остановке, перезагрузке или падении сервера все данные теряются. RDB (Redis Database Backup) — первый из двух механизмов персистентности. Он периодически сохраняет полный снимок всех данных в компактный бинарный файл `dump.rdb`.

## Как работает BGSAVE

Команда `BGSAVE` (или автоматический триггер по расписанию) запускает сохранение снимка. Redis вызывает `fork()`, создавая дочерний процесс. Дочерний процесс получает копию адресного пространства родительского и последовательно записывает все данные в файл. Родительский процесс продолжает обрабатывать команды.

Дочерний процесс записывает данные во временный файл, а по завершении атомарно заменяет старый `dump.rdb` через `rename()`. Это гарантирует, что на диске всегда находится целостный снимок — даже если Redis упадёт во время сохранения, старый `dump.rdb` останется нетронутым.

Благодаря copy-on-write (CoW) операционной системы `fork()` не копирует всю память физически. Дочерний и родительский процесс разделяют страницы памяти, пока один из них не изменит данные. При записи ОС копирует только изменённую страницу (обычно 4 КБ). На практике это означает, что во время BGSAVE Redis потребляет дополнительную память пропорционально объёму изменений, а не полному объёму данных. Если за время сохранения изменилось 10% данных — потребление вырастет примерно на 10%.

## Автоматическое сохранение

Ручной вызов `BGSAVE` непрактичен для production — Redis умеет запускать снимки автоматически. Расписание настраивается через директивы `save` в конфигурации:

```conf
save 900 1        -- снимок если 1+ ключ изменился за 15 минут
save 300 10       -- снимок если 10+ ключей за 5 минут
save 60 10000     -- снимок если 10000+ ключей за 1 минуту
```

Redis проверяет условия в фоновом цикле и запускает BGSAVE, когда хотя бы одно условие выполнено. `save ""` отключает автоматическое сохранение.

## Характеристики RDB

Автоматическое сохранение определяет частоту снимков, но не влияет на формат файла и скорость загрузки. Файл `dump.rdb` компактен: данные сериализованы в бинарном формате с LZF-сжатием (опционально). Загрузка при старте быстрая — Redis просто десериализует файл в память. Для 10 ГБ простых данных (строки, маленькие хеши) загрузка занимает секунды; для сложных структур (большие sorted set, stream) — дольше.

Главный недостаток — окно потери данных. Если Redis упал через 10 минут после последнего снимка, все изменения за эти 10 минут потеряны. Размер окна определяется расписанием `save` — от минуты до 15 минут в стандартной конфигурации.

## Когда RDB полезен, даже при наличии AOF (журнала команд)

Клонирование: скопировать `dump.rdb` на другой сервер и запустить Redis — полный клон за секунды. AOF-файл того же объёма данных может быть в 5–10 раз больше и требует «проигрывания» всех команд при загрузке.

Бэкап: один файл с чексуммой, удобно копировать в S3 или другое хранилище.

Репликация: при первичной синхронизации мастер генерирует RDB и отправляет его реплике — подробнее в [разделе репликации](../distribution/00-replication.md).

Страховка: AOF — текстовый лог, который может повредиться при некорректном завершении. RDB — бинарный файл с CRC64 чексуммой, повреждение легко обнаружить.

Для минимизации окна потери данных Redis предоставляет [AOF](01-aof.md) — журнал всех команд записи.
