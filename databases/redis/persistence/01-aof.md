# AOF — журнал команд

**Предпосылки:** [RDB](00-rdb.md), fsync, понятие write-ahead log.

## Идея: записывать каждую команду

AOF (Append Only File) записывает каждую команду записи в конец лог-файла. При перезапуске Redis «проигрывает» лог от начала до конца, восстанавливая состояние. Это аналог WAL в PostgreSQL, но с важным отличием: Redis пишет лог после выполнения команды (не до), поэтому AOF — не write-ahead log в строгом смысле.

## Три режима fsync

Запись в файл и `fsync` (сброс из буфера ОС на диск) — разные вещи. `write()` может вернуть управление, пока данные ещё в page cache ОС. Только `fsync()` гарантирует, что данные на физическом диске.

**`appendfsync always`** — `fsync` после каждой записи. Максимальная надёжность: при падении теряется максимум одна команда. Минимальная производительность: каждая команда ждёт завершения дискового I/O.

**`appendfsync everysec`** — `fsync` раз в секунду (по умолчанию). Компромисс: при падении теряется не более секунды данных. Фоновый поток выполняет `fsync`, основной поток не блокируется.

**`appendfsync no`** — Redis не вызывает `fsync` явно, полагаясь на ОС (Linux по умолчанию сбрасывает dirty pages каждые ~30 секунд). Максимальная производительность, но при сбое можно потерять данные за десятки секунд.

## AOF rewrite: сжатие лога

Три режима fsync контролируют надёжность, но не размер файла. AOF-файл растёт с каждой командой. Тысяча `INCR counter` превращается в тысячу строк, хотя текущее состояние — одно число. AOF rewrite создаёт новый файл, содержащий минимальный набор команд для восстановления текущего состояния. Вместо тысячи INCR — один `SET counter 1000`.

Rewrite запускается автоматически (когда файл вырос в `auto-aof-rewrite-percentage` раз от базового размера, по умолчанию 100%) или вручную командой `BGREWRITEAOF`. Как и BGSAVE, rewrite выполняется дочерним процессом через `fork()` с copy-on-write. Пока дочерний процесс пишет новый файл, родительский продолжает дописывать новые команды и в старый AOF, и в специальный буфер. После завершения rewrite буфер дописывается в новый файл, и новый файл заменяет старый. Начиная с Redis 7.0 AOF хранится как набор файлов (multi-part AOF): базовый файл + инкрементальные файлы, что упрощает rewrite и уменьшает риск потери данных при сбое во время перезаписи.

## Гибрид: RDB + AOF (Redis 4.0+)

AOF rewrite сжимает лог, но загрузка через «проигрывание» команд всё равно медленнее, чем десериализация бинарного RDB. Гибридный формат объединяет преимущества обоих подходов. Начиная с Redis 4.0 при rewrite Redis записывает RDB-снимок в начало нового AOF-файла, а после него — только команды, поступившие во время rewrite. При загрузке Redis быстро десериализует RDB-часть и затем «проигрывает» хвост из команд. Это даёт быструю загрузку (от RDB) и минимальное окно потери (от AOF). Включается директивой `aof-use-rdb-preamble yes` (по умолчанию включено).

## Рекомендуемая конфигурация

RDB, AOF и гибридный формат можно комбинировать в зависимости от требований к надёжности и производительности. Для большинства сценариев, где потеря данных нежелательна:

```conf
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
save 900 1          -- RDB как дополнительный бэкап
```

При загрузке Redis использует AOF (точнее). RDB остаётся для бэкапов и клонирования.

Если AOF-файл повреждён (например, из-за сбоя файловой системы), `redis-check-aof --fix` может обрезать файл до последней корректной записи. Параметр `aof-load-truncated yes` (по умолчанию) позволяет Redis при загрузке игнорировать обрезанный хвост AOF вместо отказа стартовать.

Для чистого кеша, где потеря данных допустима, можно отключить оба механизма (`appendonly no`, `save ""`). Redis работает быстрее без дискового I/O.

## Персистентность — на весь инстанс

Redis не позволяет настроить персистентность для отдельных ключей. Если одни данные требуют AOF, а другие нет — запускают несколько инстансов Redis с разными настройками.
