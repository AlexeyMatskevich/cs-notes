# Event loop

**Предпосылки:** [Что такое Redis](00-what-is-redis.md), процессы и потоки, системные вызовы (read, write), понятие file descriptor.

## Почему один поток

Многопоточный сервер тратит ресурсы на координацию: мьютексы, атомарные операции, context switch'и между потоками. Для in-memory хранилища, где каждая операция занимает наносекунды, накладные расходы на синхронизацию могут превысить стоимость самой операции. Redis выбирает другой путь: один поток обрабатывает все команды последовательно. Никаких гонок, никаких deadlock'ов, каждая команда атомарна по определению.

Однопоточность не означает «один поток на весь процесс». Redis использует дополнительные потоки для фоновых задач (сброс данных на диск, закрытие файловых дескрипторов, освобождение памяти больших объектов). Но главный цикл, который читает команды клиентов и выполняет их, работает строго в одном потоке.

## Как работает event loop

Один поток обрабатывает тысячи клиентов одновременно благодаря мультиплексору ввода-вывода. Сердце Redis — цикл событий на основе мультиплексора ввода-вывода. На Linux это `epoll`, на macOS — `kqueue`, на других системах — `select`. Redis абстрагирует различия в файле `ae.c` (ae — сокращение от «a simple event-driven programming library»).

Цикл работает так. Redis регистрирует в `epoll` файловые дескрипторы всех клиентских соединений. Вызов `epoll_wait` блокируется до тех пор, пока хотя бы на одном дескрипторе не появятся данные для чтения или готовность к записи. Когда `epoll_wait` возвращает список готовых дескрипторов, Redis обходит их по очереди: читает команду, выполняет её, записывает ответ в буфер. После обработки всех готовых событий — снова `epoll_wait`.

```text
epoll_wait → обработать готовые события → выполнить команды → записать ответы → epoll_wait
```

За один оборот цикла Redis может обработать команды от сотен клиентов. Между оборотами выполняются периодические задачи: проверка TTL ключей, обновление статистики, фоновое сохранение.

## Что блокирует event loop

Раз все команды выполняются в одном потоке, медленная команда задерживает всех остальных клиентов. Типичные источники блокировок:

`KEYS *` обходит всю таблицу ключей. При миллионе ключей это занимает десятки миллисекунд — все клиенты ждут. Безопасная альтернатива — `SCAN`, который возвращает ключи порциями и отдаёт управление event loop между итерациями.

`HGETALL` / `SMEMBERS` / `LRANGE 0 -1` на больших структурах — сериализация миллиона элементов блокирует цикл. На маленьких структурах (сотни элементов) эти команды безопасны.

`SORT` с внешними ключами (`BY`, `GET`) — загрузка и сортировка данных из разных ключей, сложность зависит от объёма.

Lua-скрипты (`EVAL`) выполняются атомарно: пока скрипт работает, никакие другие команды не обрабатываются. Длинный скрипт — длинная блокировка.

`DEL` большого объекта (список из миллионов элементов) в Redis до 4.0 блокировал event loop на время освобождения памяти. Начиная с Redis 4.0 команда `UNLINK` помещает освобождение в фоновый поток (`lazyfree`), а event loop продолжает работу.

## I/O threads (Redis 6.0+)

Однопоточная модель упирается в пропускную способность сети раньше, чем в CPU на выполнение команд. На современных серверах с быстрыми сетевыми картами (10/25/100 Gbit) узким местом становится не выполнение команд, а чтение данных из сокетов и запись ответов. Redis 6.0 добавил возможность переложить сетевой I/O на несколько потоков (`io-threads` в конфигурации). Выполнение команд по-прежнему происходит в основном потоке — это сохраняет однопоточную семантику и атомарность. I/O threads только читают данные из сокетов в буферы и записывают ответы из буферов в сокеты.

На типичных нагрузках до 100 000 ops/sec I/O threads не нужны — одного потока хватает. Они становятся полезны при высокой пропускной способности, когда парсинг протокола и сериализация ответов начинают занимать заметную долю CPU.

Батчинг команд через [pipelining](02-pipelining.md) снижает нагрузку на event loop с другой стороны — уменьшая количество системных вызовов и roundtrip'ов.
