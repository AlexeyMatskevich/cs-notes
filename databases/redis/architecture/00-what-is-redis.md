# Что такое Redis

**Предпосылки:** [ACID](../../postgresql/storage/00-acid.md), базовые структуры данных ([массив](../../../algorithms-and-data-structures/linear/01-array.md), [хеш-таблица](../../../algorithms-and-data-structures/linear/05-hash-table.md), [связный список](../../../algorithms-and-data-structures/linear/03-linked-list.md)).

## Главный вопрос при выборе хранилища

Любое приложение работает с данными разной ценности. Оформленный заказ, платёжная транзакция, документ пользователя — потеря любого из них приводит к финансовым или юридическим последствиям. Кеш тяжёлого запроса, онлайн-статус, счётчик непрочитанных уведомлений — при потере всё пересчитается за секунды.

Вопрос «если эти данные исчезнут — что произойдёт?» определяет выбор хранилища. Реляционная СУБД вроде PostgreSQL гарантирует ACID: данные переживут сбой, параллельный доступ не сломает консистентность. Redis работает в другой точке пространства компромиссов: данные живут в оперативной памяти, без тяжёлых блокировок и журналирования каждой операции.

## Что именно делает PostgreSQL при UPDATE

Чтобы понять, за счёт чего Redis быстрее, нужно видеть, что делает реляционная СУБД при простом `UPDATE counter SET value = value + 1`. PostgreSQL берёт блокировку строки (row-level lock), создаёт новую версию строки (MVCC — хранение версий строк для изоляции), журналирует изменение в WAL (write-ahead log — последовательный журнал для durability; `fsync` сбрасывает данные на диск), обновляет индексы, отпускает блокировку, а позже VACUUM (фоновая очистка) убирает старые версии. Каждый из этих шагов существует ради durability и изоляции — данные не потеряются при падении, параллельные транзакции не увидят промежуточных состояний.

Redis при `INCR counter` находит значение в хеш-таблице в RAM, увеличивает число и возвращает результат. Нет версий строк, нет тяжёлого журналирования каждой операции, нет блокировок на уровне сервера Redis. В результате в микробенчмарках на простых командах Redis обычно заметно быстрее, но точные цифры зависят от сети, диска, настроек WAL/персистентности и паттерна нагрузки.

## Redis — не база данных, а сервер структур данных

Определение «Redis — это NoSQL база данных» формально верно, но создаёт неправильные ожидания. Redis не хранит данные в таблицах, не поддерживает SQL, не даёт JOIN'ов и rollback'ов.

Redis — это структуры данных в памяти с сетевым доступом. Он предоставляет примитивы, которые знакомы любому программисту: строки (STRING), хеш-таблицы (HASH), списки (LIST), множества (SET), упорядоченные множества (SORTED SET). Разница с структурами данных внутри процесса приложения — данные в Redis доступны всем процессам и серверам по сети и переживают рестарт приложения (хотя не обязательно переживут рестарт самого Redis — это зависит от настроек [персистентности](../persistence/00-rdb.md)).

## CAP-теорема и позиция Redis

CAP важна для распределённых конфигураций, где есть сеть и несколько узлов. При сетевом разделении (partition) приходится выбирать между Consistency (все узлы видят одинаковые данные) и Availability (система продолжает отвечать). Redis в кластерном режиме по умолчанию делает упор на Availability: он старается продолжать отвечать, даже если часть узлов недоступна или реплика чуть отстала от мастера. Асинхронная репликация означает, что при падении мастера несколько последних операций могут потеряться.

Это не недостаток архитектуры, а осознанный выбор: для кеша, счётчиков и сессий потеря последней секунды данных — допустимая цена за скорость и доступность.

Однопоточная модель исполнения обеспечивает атомарность команд без блокировок — подробно об этом в [event loop](01-event-loop.md).
