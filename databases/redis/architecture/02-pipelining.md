# Pipelining

**Предпосылки:** [Event loop](01-event-loop.md), сеть (клиент/сервер, RTT).

## Проблема: RTT на каждую команду

Стандартный обмен между клиентом и Redis выглядит так: клиент отправляет команду, ждёт ответа, отправляет следующую. При RTT 0.1 мс внутри одного дата-центра и 100 командах на одну страницу — 10 мс уходит только на ожидание сети, хотя Redis выполняет каждую команду за микросекунды. При RTT 1 мс между зонами доступности потери вырастают на порядок.

## Pipelining: отправка без ожидания ответа

Pipelining — это отправка нескольких команд подряд, не дожидаясь ответа на каждую. Клиент записывает N команд в TCP-сокет одним или несколькими вызовами `write`, затем читает N ответов одним `read`. Redis читает доступные команды из буфера сокета и выполняет их последовательно (в зависимости от объёма данных это может занять один или несколько оборотов event loop).

```text
Без pipelining:              С pipelining:

клиент → SET a 1             клиент → SET a 1
клиент ← OK                           SET b 2
клиент → SET b 2                       SET c 3
клиент ← OK                 клиент ← OK
клиент → SET c 3                       OK
клиент ← OK                           OK

3 RTT                        1 RTT
```

При 100 командах pipelining сокращает общее время со 100 RTT до 1 RTT. На уровне Redis ничего не меняется — команды выполняются последовательно, как обычно. Выигрыш целиком за счёт сети.

## Pipelining vs MULTI/EXEC

Pipelining ускоряет отправку, но не меняет семантику выполнения. Pipelining — это оптимизация сетевого уровня. Команды в pipeline не образуют транзакцию: между ними могут вклиниться команды от других клиентов. Если клиент A отправил pipeline из `SET x 1; SET y 2`, а клиент B одновременно отправил `GET x`, клиент B может увидеть новое значение `x`, но старое значение `y`.

[MULTI/EXEC](../atomicity/01-multi-exec.md) — это атомарность на уровне сервера: все команды между MULTI и EXEC выполняются как единое целое, без вклинивания. MULTI/EXEC можно (и нужно) комбинировать с pipelining: отправить MULTI, команды и EXEC одним pipeline-запросом, получив и экономию RTT, и атомарность.

## Размер pipeline

Отправка миллиона команд одним pipeline создаст проблемы на стороне Redis — накопленные ответы займут много памяти. Буфер отправки и приёма ограничен. При очень длинном pipeline (десятки тысяч команд) Redis накапливает ответы в памяти, пока клиент их не прочитает. На практике хорошим размером считается 100–1000 команд за один pipeline. Если нужно выполнить 50 000 команд — их разбивают на серии по 500–1000.

```redis-cli
# redis-cli поддерживает пакетную отправку через --pipe:
# генерируем команды и отправляем pipeline
cat commands.txt | redis-cli --pipe
```

## Когда pipelining не помогает

Если каждая следующая команда зависит от результата предыдущей (например, прочитать значение, посчитать что-то, записать результат), pipelining бесполезен — нужен либо [Lua-скрипт](../atomicity/02-lua-scripting.md), либо логика на стороне клиента с несколькими roundtrip'ами.
