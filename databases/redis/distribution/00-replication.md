# Репликация

**Предпосылки:** [RDB](../persistence/00-rdb.md), [AOF](../persistence/01-aof.md), сеть (клиент/сервер).

## Master-replica: масштабирование чтения и отказоустойчивость

Один Redis-сервер ограничен памятью и CPU одной машины. Репликация позволяет создать копии (реплики) мастера: реплики содержат те же данные и могут обслуживать команды чтения, разгружая мастер. При падении мастера одна из реплик может занять его место.

Запись идёт только в мастер. Реплики по умолчанию read-only (`replica-read-only yes`). Данные на каждом сервере — полная копия, поэтому репликация не увеличивает объём доступной памяти, только пропускную способность чтения и отказоустойчивость.

Реплика подключается к мастеру командой `REPLICAOF host port` (или через конфигурацию `replicaof`). С этого момента начинается жизненный цикл репликации: получение полной копии данных, штатная потоковая передача команд, обработка разрывов.

## Полная синхронизация

При первом подключении реплики (или после длительного рассинхрона) происходит полная синхронизация. Мастер запускает `BGSAVE`, генерирует RDB-снимок и отправляет его реплике по сети. Пока снимок создаётся и передаётся, мастер буферизирует все новые команды записи. После загрузки снимка реплика получает буферизированные команды и выходит на текущее состояние.

Полная синхронизация — тяжёлая операция: `fork()` на мастере потребляет CPU и память. При активной записи copy-on-write может привести к тому, что процесс-потомок скопирует значительную часть страниц — на инстансе с 10 ГБ данных потребление RAM может вырасти почти вдвое. Передача RDB-файла занимает сеть. Redis поддерживает альтернативу — diskless-репликацию (`repl-diskless-sync yes`): мастер стримит RDB прямо в сокет реплики, минуя запись на диск. Это полезно, когда диск медленный, а сеть быстрая.

Полная синхронизация настолько дорога, что Redis старается избежать её при кратковременных разрывах связи.

## Частичная ресинхронизация и replication backlog

Чтобы понять, как Redis избегает полной синхронизации, нужны два понятия. Replication offset — это позиция в потоке команд записи; и мастер, и каждая реплика хранят своё значение offset. По нему можно определить, насколько реплика отстала. Replication backlog — кольцевой буфер последних команд записи, который мастер хранит в памяти (`repl-backlog-size`, по умолчанию 1 МБ).

Когда реплика переподключается, она сообщает мастеру свой replication offset и replication ID — уникальный идентификатор потока репликации. Если replication ID совпадает (реплика подключается к тому же мастеру или мастеру с тем же потоком данных) и пропущенные команды ещё есть в backlog, мастер отправляет только пропущенное — это частичная ресинхронизация, быстрая и дешёвая. Если пропущенных команд в backlog уже нет (реплика отсутствовала слишком долго или backlog переполнился) либо replication ID не совпадает (например, после failover мастер сменился и получил новый ID), Redis вынужден выполнить полную синхронизацию.

Replication ID важен при failover: когда реплика становится мастером, она получает новый replication ID. Остальные реплики, подключаясь к новому мастеру, видят другой ID. Redis хранит два ID (текущий и предыдущий), что позволяет провести частичную ресинхронизацию с репликами, которые раньше были подключены к тому же потоку данных. Но если состояние расходится сильнее — полная синхронизация неизбежна.

Размер backlog стоит подбирать исходя из объёма записи и допустимого времени отключения реплики: `repl-backlog-size = средний_объём_записи_в_секунду × допустимое_время_отключения`. Мастер создаёт backlog при подключении первой реплики. Если все реплики отключились, backlog сохраняется в течение `repl-backlog-ttl` секунд (по умолчанию 3600), после чего освобождается.

## Асинхронная репликация

Полная и частичная синхронизация доставляют данные, но штатная потоковая передача команд от мастера к репликам происходит асинхронно: мастер не ждёт подтверждения от реплик перед ответом клиенту. Это даёт низкую задержку записи, но создаёт окно потери данных. Если мастер упал сразу после ответа клиенту, клиент уже получил OK на свою запись, однако команда могла не дойти до реплик. После failover промоутированная реплика не будет содержать этих данных — с точки зрения клиента, подтверждённая запись пропала.

Асинхронность — осознанный компромисс: производительность за счёт гарантий. Для большинства сценариев это приемлемо, но для критичных операций Redis предлагает способ уменьшить окно потери.

## WAIT: синхронное подтверждение

Команда `WAIT numreplicas timeout` блокирует клиента до тех пор, пока указанное количество реплик не подтвердит получение всех предшествующих команд, или до истечения таймаута.

```redis-cli
SET order:789 "confirmed"
WAIT 1 5000
-- → 1 (одна реплика подтвердила)
-- или → 0 (таймаут 5 секунд истёк, ни одна реплика не подтвердила)
```

`WAIT` не превращает Redis в синхронно реплицируемую систему. Даже если `WAIT` вернул подтверждение от одной реплики, при failover может быть промоутирована другая реплика — та, которая не успела получить команду. Это возможно, потому что выбор реплики при failover зависит не только от replication offset, но и от доступности и приоритета. Тем не менее `WAIT` значительно сужает окно потери и полезен для операций, где потеря подтверждённой записи критична (например, подтверждение платежа).

## Каскадная репликация

При большом количестве реплик нагрузка на мастер растёт линейно: каждая реплика — это отдельный поток команд и, при полной синхронизации, отдельный RDB-снимок. Реплика может быть мастером для другой реплики (`REPLICAOF replica-host replica-port`), образуя цепочку или дерево. Типичная топология: мастер синхронизирует 2–3 реплики первого уровня, каждая из которых синхронизирует ещё несколько. Это снижает нагрузку на мастер, но увеличивает лаг репликации — команда проходит больше узлов, прежде чем дойдёт до реплики на конце цепочки. Для сценариев, где допустим лаг в единицы секунд (кеширование, аналитические запросы), это приемлемый компромисс.

Автоматический failover при падении мастера — задача [Sentinel](01-sentinel.md).
