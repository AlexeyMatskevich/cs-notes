# Cluster

**Предпосылки:** [Репликация](00-replication.md), [Sentinel](01-sentinel.md), хеш-функция.

## Проблема: данные не помещаются в один сервер

Sentinel обеспечивает отказоустойчивость, но не решает проблему масштабирования: все данные хранятся на каждом сервере, и объём ограничен RAM одной машины. Redis Cluster разделяет (шардирует) данные между несколькими узлами, позволяя хранить больше данных и обрабатывать больше команд параллельно.

## 16 384 слота

Redis Cluster делит пространство ключей на 16 384 слота (0–16 383). Каждый узел-мастер владеет подмножеством слотов. Принадлежность ключа к слоту определяется формулой: `slot = CRC16(key) mod 16384`.

```text
Node A: слоты 0–5460
Node B: слоты 5461–10922
Node C: слоты 10923–16383
```

Когда клиент отправляет команду, Redis вычисляет слот по ключу. Если текущий узел владеет этим слотом — выполняет команду. Если нет — отвечает редиректом.

## MOVED и ASK: перенаправление клиента

Клиент может отправить команду не на тот узел — Redis Cluster обрабатывает это через редиректы.

**MOVED** — постоянный редирект. Клиент отправил `GET user:123` на Node A, но слот этого ключа принадлежит Node B. Node A отвечает: `MOVED 5765 192.168.1.2:6379`. Клиент обновляет свою карту слотов и впредь обращается к Node B для этого слота.

**ASK** — временный редирект. Возникает во время миграции слота с одного узла на другой. Node A отвечает: `ASK 5765 192.168.1.2:6379`. Клиент перенаправляет один запрос на Node B (с префиксом `ASKING`), но не обновляет карту слотов — следующий запрос к этому слоту снова пойдёт на Node A.

Клиентские библиотеки кешируют карту «слот → узел» при подключении. Большинство запросов идут напрямую к нужному узлу, без редиректов. MOVED-ответ обновляет кеш, после чего клиент снова попадает правильно.

## Multi-key операции и hash tags

Шардирование по слотам означает, что ключи на разных узлах недоступны в одной операции. Команды, работающие с несколькими ключами (`MGET`, `MSET`, `SINTER`, `ZUNIONSTORE`), требуют, чтобы все ключи принадлежали одному слоту. Иначе Redis вернёт ошибку `CROSSSLOT`. Решение — hash tags: если ключ содержит фигурные скобки, слот вычисляется только по содержимому между первыми `{` и `}`.

```redis-cli
SET {user:123}:profile "..."       -- слот по "user:123"
SET {user:123}:settings "..."      -- тот же слот
MGET {user:123}:profile {user:123}:settings   -- работает
```

Hash tags нужно использовать осторожно: если слишком много ключей попадут в один слот, один узел получит непропорциональную нагрузку (hot spot).

## Cluster + репликация

Шардирование распределяет данные, но не защищает от падения узла — при потере мастера его слоты становятся недоступны. В production каждый мастер-узел имеет одну или несколько реплик. При падении мастера его реплика автоматически промоутируется — без Sentinel, механизм failover встроен в Cluster. Минимальная production-конфигурация: 6 узлов (3 мастера + 3 реплики).

```text
Master A (слоты 0–5460)      ← Replica A
Master B (слоты 5461–10922)  ← Replica B
Master C (слоты 10923–16383) ← Replica C
```

## Ограничения Cluster

Шардирование вносит ограничения, которых нет в одиночном Redis. Lua-скрипты и транзакции (MULTI/EXEC) работают только с ключами одного слота. `SELECT` (выбор базы данных) не поддерживается — Cluster использует только database 0. Pub/Sub в классическом виде рассылает сообщения на все узлы (broadcast), что может быть дорого — [sharded Pub/Sub](../data-structures/08-pub-sub.md) (Redis 7.0+) решает эту проблему.

## Добавление и удаление узлов

Кластер можно масштабировать без простоя. Добавление узла: новый узел подключается к кластеру через `CLUSTER MEET ip port`, затем часть слотов мигрирует на него. Миграция происходит онлайн, без простоя: слот помечается как MIGRATING на исходном узле и IMPORTING на целевом, затем Redis перемещает ключи по одному, используя `MIGRATE` (атомарно передаёт ключ на другой узел и удаляет локально). Во время миграции запросы к перемещаемым ключам обрабатываются через ASK-редиректы.

Удаление узла: сначала все его слоты мигрируют на другие узлы, затем узел удаляется из конфигурации кластера.

## Когда нужен Cluster

Cluster добавляет сложность (ограничения multi-key, hash tags, редиректы), поэтому использовать его стоит только при реальной необходимости. Одного Redis достаточно при объёме данных до RAM одного сервера, нагрузке до ~100 000 ops/sec и допустимом кратковременном простое при ручном failover (или Sentinel для автоматического). Cluster нужен, когда данные не помещаются в один сервер, требуется горизонтальное масштабирование записи или нужен встроенный автоматический failover без отдельного Sentinel.
