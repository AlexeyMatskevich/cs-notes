# Cluster

**Предпосылки:** [Репликация](00-replication.md), [Sentinel](01-sentinel.md), хеш-функция, [транзакции MULTI/EXEC](../atomicity/01-multi-exec.md).

## Проблема: данные не помещаются в один сервер

Sentinel обеспечивает отказоустойчивость, но не решает проблему масштабирования: все данные хранятся на каждом сервере, и объём ограничен RAM одной машины. Redis Cluster разделяет (шардирует) данные между несколькими узлами, позволяя хранить больше данных и обрабатывать больше команд параллельно.

## 16 384 слота

Redis Cluster делит пространство ключей на 16 384 слота (0–16 383). Каждый узел-мастер владеет подмножеством слотов. Принадлежность ключа к слоту определяется формулой: `slot = CRC16(key) mod 16384`. CRC16 — быстрая хеш-функция, которую Redis использует для распределения ключей по слотам.

```text
Node A: слоты 0–5460
Node B: слоты 5461–10922
Node C: слоты 10923–16383
```

Почему именно 16 384? Узлы кластера обмениваются информацией о состоянии через gossip-протокол (об этом ниже), и каждое сообщение содержит bitmap слотов, которыми владеет отправитель. При 16 384 слотах bitmap занимает 2 КБ — приемлемый размер для периодических сообщений между узлами. При значительно большем количестве слотов gossip-трафик вырос бы непропорционально. Практическое следствие: рекомендуемый максимум мастер-узлов — около 1000.

Когда клиент отправляет команду, Redis вычисляет слот по ключу. Если текущий узел владеет этим слотом — выполняет команду. Если нет — отвечает редиректом.

## MOVED и ASK: перенаправление клиента

Клиент знает формулу `CRC16(key) mod 16384`, но ему нужна карта «слот → узел». Если карта устарела после смены топологии или клиент подключился к произвольному узлу — нужен механизм перенаправления.

**MOVED** — постоянный редирект. Клиент отправил `GET user:123` на Node A, но слот этого ключа принадлежит Node B. Node A отвечает: `MOVED 5765 192.168.1.2:6379`. Клиент обновляет свою карту слотов и впредь обращается к Node B для этого слота. MOVED означает дополнительный round-trip на один запрос, но после обновления кеша карты слотов все последующие запросы идут напрямую, без лишних хопов. На практике первый запрос после смены топологии чуть дороже, далее overhead минимален.

**ASK** — временный редирект. Возникает во время миграции слота с одного узла на другой. Node A отвечает: `ASK 5765 192.168.1.2:6379`. Клиент перенаправляет один запрос на Node B, предварительно отправив команду `ASKING` — она сообщает целевому узлу, что тот должен принять запрос к слоту, который ему ещё не полностью принадлежит (состояние IMPORTING). Карту слотов клиент не обновляет — следующий запрос к этому слоту снова пойдёт на Node A. Миграция слота происходит онлайн, клиент видит чуть повышенный latency из-за ASK-редиректов, но downtime нет.

Клиентские библиотеки кешируют карту «слот → узел» при подключении. Большинство запросов идут напрямую к нужному узлу, без редиректов. MOVED-ответ обновляет кеш, после чего клиент снова попадает правильно.

## Multi-key операции и hash tags

Маршрутизация работает для одного ключа, но команды вроде `MGET` оперируют несколькими ключами. Если эти ключи попали в разные слоты и оказались на разных узлах, выполнить команду атомарно невозможно — Redis вернёт ошибку `CROSSSLOT`. Эта ошибка не является временной (в отличие от MOVED/ASK): retry не поможет, нужно менять схему ключей.

Решение — hash tags: если ключ содержит фигурные скобки, слот вычисляется только по содержимому между первыми `{` и `}`.

```redis-cli
SET {user:123}:profile "..."       -- слот по "user:123"
SET {user:123}:settings "..."      -- тот же слот
MGET {user:123}:profile {user:123}:settings   -- работает
```

Hash tags нужно использовать осторожно: если слишком много ключей попадут в один слот, один узел получит непропорциональную нагрузку.

## Gossip-протокол и cluster bus

Данные распределены по узлам, но узлы должны знать о состоянии друг друга: кто владеет какими слотами, кто жив, кто упал. Для этого узлы кластера обмениваются информацией через gossip-протокол — каждый узел периодически отправляет другим узлам сообщения с состоянием известных ему узлов (слоты, статус, epoch). Со временем информация распространяется по всему кластеру.

Gossip-сообщения передаются по отдельному TCP-соединению — cluster bus. Каждый узел слушает порт данных + 10000 (например, при стандартном 6379 cluster bus работает на порту 16379). Это важно при настройке: в firewall нужно открыть оба порта — порт данных для клиентов и порт cluster bus для межузлового общения.

## Failover: что происходит при падении узла

При падении мастера его слоты становятся недоступны — без защиты кластер теряет часть данных. Поэтому в production каждый мастер-узел имеет одну или несколько реплик. Минимальная production-конфигурация: 6 узлов (3 мастера + 3 реплики).

```text
Master A (слоты 0–5460)      ← Replica A
Master B (слоты 5461–10922)  ← Replica B
Master C (слоты 10923–16383) ← Replica C
```

Механизм failover встроен в Cluster — отдельный Sentinel не нужен. Обнаружение сбоя работает через gossip. Если узел не отвечает на `PING` в течение `cluster-node-timeout` (по умолчанию 15 секунд, аналог `down-after-milliseconds` в Sentinel), он помечается как PFAIL (probable fail) — это мнение одного узла. Когда majority мастеров согласны, что узел недоступен, он помечается как FAIL — это объективный консенсус, аналогичный переходу SDOWN → ODOWN в Sentinel.

После пометки FAIL начинается промоутирование реплики. Реплики упавшего мастера инициируют голосование: каждая реплика запрашивает голоса у оставшихся мастеров. Предпочтение получает реплика с наибольшим replication offset — та, у которой минимум потерь данных. Получив голоса majority мастеров, реплика промоутируется в мастер и берёт на себя слоты упавшего узла.

Во время failover клиенты получают ошибку `CLUSTERDOWN` на запросы к слотам упавшего мастера. Время недоступности складывается из `cluster-node-timeout` (обнаружение) + время на gossip-распространение FAIL + голосование и промоутирование — на практике от секунд до десятков секунд.

Если старый мастер вернулся после failover, он автоматически становится репликой нового мастера тех же слотов — ручное вмешательство не требуется.

Cluster поддерживает автоматическую миграцию реплик: если у одного мастера не осталось реплик, а у другого их больше одной, Cluster может перенести «лишнюю» реплику к мастеру без защиты. Это повышает устойчивость без участия оператора — функция, которой нет в Sentinel.

## Добавление и удаление узлов

Кластер работает, но нагрузка или объём данных может вырасти — нужна возможность добавлять узлы без остановки. Кластер масштабируется онлайн.

Типичный путь создания кластера — утилита командной строки:

```bash
redis-cli --cluster create \
  host1:6379 host2:6379 host3:6379 \
  host4:6379 host5:6379 host6:6379 \
  --cluster-replicas 1
```

Эта команда создаёт кластер из шести узлов, назначая каждому мастеру по одной реплике, и автоматически распределяет слоты. Для добавления узла к работающему кластеру: новый узел подключается через `CLUSTER MEET ip port`, затем часть слотов мигрирует на него.

Миграция происходит онлайн: слот помечается как MIGRATING на исходном узле и IMPORTING на целевом, затем Redis перемещает ключи по одному, используя `MIGRATE` (атомарно передаёт ключ на другой узел и удаляет локально). Во время миграции запросы к перемещаемым ключам обрабатываются через ASK-редиректы.

Удаление узла: сначала все его слоты мигрируют на другие узлы, затем узел удаляется из конфигурации кластера.

## Ограничения Cluster

Cluster даёт шардирование, встроенный failover и онлайн-масштабирование, но за это приходится платить ограничениями, которых нет в одиночном Redis.

Lua-скрипты и транзакции MULTI/EXEC работают только с ключами одного слота — Cluster не может координировать атомарную операцию между узлами. `SELECT` (выбор базы данных) не поддерживается — Cluster использует только database 0. Pub/Sub в классическом виде рассылает сообщения на все узлы (broadcast), что может быть дорого — [sharded Pub/Sub](../data-structures/08-pub-sub.md) (Redis 7.0+) решает эту проблему.

По умолчанию параметр `cluster-require-full-coverage` установлен в `yes`: если хотя бы один слот не покрыт ни мастером, ни репликой, весь кластер перестаёт принимать запросы. При `cluster-require-full-coverage no` кластер продолжает обслуживать покрытые слоты, но запросы к потерянным слотам вернут ошибку.

## Когда нужен Cluster

С учётом ограничений — когда Cluster оправдан, а когда достаточно одиночного Redis с Sentinel? Одного Redis достаточно при объёме данных до RAM одного сервера, нагрузке до ~100 000 ops/sec и допустимом кратковременном простое при failover (с Sentinel — автоматическом). Cluster нужен, когда данные не помещаются в один сервер, требуется горизонтальное масштабирование записи или нужен встроенный автоматический failover без отдельного Sentinel.
