# String

**Предпосылки:** [Что такое Redis](../architecture/00-what-is-redis.md), [event loop](../architecture/01-event-loop.md).

## Что хранит STRING

STRING — базовый тип данных Redis, на котором построены счётчики, кеши, блокировки и флаги. Одному ключу соответствует одно значение: строка, число или бинарные данные (до 512 МБ).

## Базовые операции

```redis-cli
SET user:123:name "John"          -- записать строку
GET user:123:name                 -- прочитать → "John"

SET session:abc "data" EX 3600    -- записать с TTL 1 час
TTL session:abc                   -- сколько секунд осталось

SET counter 0
INCR counter                      -- → 1 (атомарно: +1 и вернуть)
INCRBY counter 10                 -- → 11
DECR counter                      -- → 10

SETNX lock:order:42 "owner-1"    -- SET if Not eXists → 1 (захвачено) или 0
SET lock:order:42 "owner-1" NX EX 30  -- NX + TTL за одну команду
```

`INCR` возвращает новое значение. Это одна атомарная операция — увеличить и вернуть результат. В однопоточном event loop никакая другая команда не может вклиниться между чтением и записью.

Кодировки выбираются автоматически — клиент работает с единым набором команд независимо от внутреннего представления (подробнее — ниже).

## TTL: два механизма удаления

Многие применения STRING (кеш, сессии, блокировки) зависят от автоматического удаления ключей по времени. Redis удаляет истёкшие ключи двумя способами.

Lazy expiration: при любом обращении к ключу Redis проверяет, не истёк ли TTL, и если истёк — удаляет ключ и возвращает nil. Это гарантирует, что клиент никогда не получит данные с истёкшим TTL, но не освобождает память, если к ключу никто не обращается.

Active expiration решает эту проблему: 10 раз в секунду Redis выбирает случайные ключи из множества ключей с TTL и удаляет истёкшие. Если более 25% проверенных ключей оказались истёкшими, цикл повторяется немедленно — это адаптивный механизм, который ускоряется при массовом истечении.

## Практические применения

STRING — самая используемая структура Redis. Кеш с TTL (`SET ... EX`), атомарные счётчики (`INCR`), флаги и семафоры (`SET ... NX EX`) — все эти паттерны опираются на одну структуру данных. Паттерны rate limiting и distributed lock, построенные на STRING, подробно рассмотрены в разделе [паттернов](../patterns/01-rate-limiting.md).

Когда нужно хранить несколько связанных полей одного объекта, STRING становится неэффективным: каждый ключ несёт ~70 байт overhead (метаданные объекта + запись в глобальной хеш-таблице + запись в таблице TTL). Для объектов с полями лучше подходит [Hash](01-hash.md).

## Внутреннее устройство: SDS

Внутри Redis строки хранятся не как обычные C-строки, а как SDS (Simple Dynamic String, `src/sds.h`) — структура, которая хранит длину строки и количество свободного места в буфере. Это даёт O(1) на получение длины (вместо O(n) при обходе до нулевого байта) и позволяет хранить бинарные данные, включая нулевые байты. При добавлении данных SDS автоматически расширяет буфер: удваивает при маленьких размерах и добавляет по 1 МБ при больших (свыше 1 МБ).

## Три внутренние кодировки

Redis дополнительно оптимизирует представление значения в зависимости от содержимого и размера.

**int** — если значение можно представить как 64-битное целое число. Redis хранит число прямо внутри метаданных объекта, без выделения отдельной памяти под строку. Команды `INCR`, `INCRBY`, `DECRBY` работают с этой кодировкой арифметически, не конвертируя в строку и обратно.

**embstr** — для коротких строк (порог порядка 44 байт в типичных 64-bit сборках). Метаданные объекта и данные строки размещаются в одном непрерывном блоке памяти — это экономит одно выделение памяти и ускоряет доступ. Кодировка read-only: любая модификация (даже `APPEND`) конвертирует значение в raw.

**raw** — для строк длиннее 44 байт. Метаданные и данные строки хранятся в двух отдельных блоках памяти.

Проверить кодировку можно командой `OBJECT ENCODING key`. Подробнее о `redisObject` и системе кодировок — в [заметке о кодировках](../memory/00-encodings.md).
