# Hash

**Предпосылки:** [String](00-string.md), [хеш-таблица](../../../algorithms-and-data-structures/linear/05-hash-table.md).

## Зачем HASH, если есть STRING

При хранении объекта с полями отдельными STRING-ключами (`user:123:name`, `user:123:age`, `user:123:email`) каждый ключ несёт ~70 байт overhead: метаданные объекта, запись в глобальной хеш-таблице, запись в таблице TTL (если есть). Для объекта из 10 полей это ~700 байт служебных данных сверх полезной нагрузки.

HASH хранит все поля под одним ключом — один overhead на весь объект. Кроме экономии памяти, HASH даёт атомарное чтение всех полей (`HGETALL`) и атомарное обновление нескольких полей (`HSET key field1 val1 field2 val2`).

## Основные команды

```redis-cli
HSET user:123 name "John" age 30 email "john@example.com"
HGET user:123 name                    -- → "John"
HMGET user:123 name age               -- → ["John", "30"]
HGETALL user:123                      -- → {name: "John", age: "30", email: "..."}

HEXISTS user:123 name                 -- → 1
HKEYS user:123                        -- → ["name", "age", "email"]
HLEN user:123                         -- → 3

HINCRBY user:123 login_count 1        -- атомарный инкремент числового поля
HDEL user:123 temporary_field         -- удалить поле
```

`HGETALL` возвращает все поля и значения за одну команду. На маленьких хешах (десятки полей) это эффективно. На больших хешах (тысячи полей) ответ может занять мегабайты и заблокировать [event loop](../architecture/01-event-loop.md). Для итерации по большому хешу есть `HSCAN` — порционная выборка, аналог `SCAN` для ключей.

## TTL применяется к ключу, а не к полю

Redis позволяет установить TTL только на весь ключ целиком. Отдельные поля хеша не могут иметь собственный TTL. Это влияет на выбор между HASH и отдельными STRING-ключами: если нужно автоудаление отдельных полей — придётся использовать отдельные STRING-ключи или Lua-скрипт с периодической очисткой.

## Когда использовать HASH

HASH подходит для объектов, поля которых читаются и пишутся вместе или по отдельности: профили пользователей, настройки, состояние сессии. Если нужен порядок или приоритет — лучше подходят [List](02-list.md) или [Sorted Set](04-sorted-set.md).

## Две внутренние кодировки

При малом количестве полей Redis использует компактное представление, при большом — переключается на полноценную хеш-таблицу.

**listpack** (`src/listpack.c`) — компактная последовательная структура, где поля и значения хранятся друг за другом в одном непрерывном блоке памяти. Нет указателей, нет заголовков на каждый элемент — минимальный overhead. Поиск по полю — линейный (O(n)), но при малом количестве элементов это быстрее хеш-таблицы, потому что данные лежат рядом в памяти и процессор читает их из кеша, а не из разбросанных по памяти узлов.

**hashtable** (`src/dict.c`) — стандартная хеш-таблица с цепочками коллизий. O(1) на доступ по полю, но каждая запись требует отдельного выделения памяти под ключ и значение.

Redis автоматически переключает кодировку с listpack на hashtable, когда количество полей превышает `hash-max-listpack-entries` (по умолчанию 128) или размер любого поля/значения превышает `hash-max-listpack-value` (по умолчанию 64 байта). Обратное переключение не происходит — если хеш вырос, он остаётся в hashtable даже после удаления полей.
