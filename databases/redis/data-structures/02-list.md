# List

**Предпосылки:** [String](00-string.md), [связный список](../../../algorithms-and-data-structures/linear/03-linked-list.md).

## Quicklist: компромисс между списком и массивом

До Redis 3.2 списки хранились как ziplist (компактный последовательный массив элементов без указателей, маленькие списки) или linked list (большие). Оба варианта имели проблемы: ziplist при вставке в середину перемещал все последующие элементы (O(n) на копирование), linked list тратил по 3 указателя (prev, next, value) на каждый элемент — ~24 байта overhead.

Начиная с Redis 3.2, оба представления заменены на quicklist (`src/quicklist.c`) — двусвязный список, где каждый узел содержит listpack (ранее — ziplist). Это компромисс: listpack внутри узла даёт компактность и cache locality, связный список узлов даёт O(1) вставку в начало и конец. Размер listpack в каждом узле контролируется параметром `list-max-listpack-size` (по умолчанию -2, что означает до 8 КБ на узел).

Quicklist также поддерживает сжатие внутренних узлов алгоритмом LZF (`list-compress-depth`). Голова и хвост списка остаются несжатыми (к ним обращаются чаще всего), а средние узлы сжимаются для экономии памяти.

## Основные команды

Quicklist обеспечивает O(1) вставку и извлечение с обоих концов — основу для очередей и стеков.

```redis-cli
LPUSH queue:emails "job3"           -- вставить в начало (левый конец)
RPUSH queue:emails "job4"           -- вставить в конец (правый конец)

LPOP queue:emails                   -- забрать из начала
RPOP queue:emails                   -- забрать из конца

BRPOP queue:emails 5                -- блокирующий pop: ждать до 5 секунд
                                    -- если список пуст, соединение блокируется
                                    -- пока не появится элемент или не истечёт таймаут

LRANGE queue:emails 0 -1            -- все элементы (без удаления)
LRANGE queue:emails 0 9             -- первые 10
LLEN queue:emails                   -- длина списка

LTRIM queue:emails 0 99             -- оставить только первые 100 элементов
```

## BRPOP: ожидание без polling

`RPOP` возвращает nil, если список пуст, и клиенту приходится повторять запрос в цикле. `BRPOP` — ключевая команда для построения очередей. Клиент вызывает `BRPOP queue 0` (таймаут 0 — ждать бесконечно). Redis регистрирует клиента в списке ожидающих для данного ключа. Когда другой клиент выполняет `LPUSH queue item`, Redis находит первого ожидающего клиента и отдаёт ему элемент. Клиент не тратит CPU на polling, Redis не тратит ресурсы на пустые ответы.

`BRPOP` принимает несколько ключей: `BRPOP q1 q2 q3 0` — клиент ждёт элемент в любой из трёх очередей, получает первый появившийся.

## Паттерн: Capped List

Без ограничения размера список растёт бесконечно. Capped list решает эту проблему, храня только последние N записей (активность пользователя, логи, лента):

```redis-cli
LPUSH user:123:activity '{"action":"login","at":"2025-01-15T10:00:00Z"}'
LTRIM user:123:activity 0 99       -- оставить только последние 100
```

`LPUSH` + `LTRIM` — две команды, но на практике выполняются за микросекунды. Для строгой атомарности можно обернуть в [MULTI/EXEC](../atomicity/01-multi-exec.md) или [pipeline](../architecture/02-pipelining.md).

## Сложность операций

`LPUSH`, `RPUSH`, `LPOP`, `RPOP` — O(1). `LINDEX n` и `LINSERT` — O(n), потому что quicklist требует последовательного обхода узлов. `LRANGE start stop` — O(stop - start + S), где S — количество пройденных узлов до начала диапазона. Для случайного доступа по индексу List не подходит — лучше использовать [Sorted Set](04-sorted-set.md) с числовым score.

Если нужны уникальные элементы, а не упорядоченная последовательность, подходящая структура — [Set](03-set.md).
