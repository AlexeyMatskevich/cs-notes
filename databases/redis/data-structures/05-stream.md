# Stream

**Предпосылки:** [List](02-list.md), [Sorted Set](04-sorted-set.md).

## Проблема: надёжная доставка сообщений

LIST как очередь работает, но имеет ограничение: после `BRPOP` элемент исчез из Redis. Если обработчик упал после получения, но до завершения обработки — сообщение потеряно. Streams (Redis 5.0+) решают эту проблему: сообщения хранятся в append-only структуре, каждый получатель отслеживает свою позицию, а необработанные сообщения можно перечитать.

## Структура Stream

Stream — это append-only лог: сообщения только добавляются в конец, каждое получает автоматически сгенерированный ID вида `<millisecondsTime>-<sequenceNumber>` (например, `1700000000000-0`). ID монотонно возрастают — по ним можно читать поток с любой позиции. Каждое сообщение — набор полей (field-value пар), аналогичный [HASH](01-hash.md).

## Основные команды

Базовые операции со Stream — добавление сообщений, чтение по диапазону ID и блокирующее ожидание новых.

```redis-cli
-- добавить сообщение (* = автоматический ID)
XADD mystream * sensor_id 1234 temperature 23.5
-- → "1700000000000-0"

-- прочитать сообщения начиная с ID
XRANGE mystream 1700000000000-0 +          -- от конкретного ID до конца
XRANGE mystream - + COUNT 10               -- первые 10 сообщений

-- прочитать новые сообщения (блокирующий режим)
XREAD COUNT 10 BLOCK 5000 STREAMS mystream $
-- $ означает "только новые" (после последнего на момент вызова)

-- длина потока
XLEN mystream

-- обрезка: оставить не более 1000 сообщений
XTRIM mystream MAXLEN ~ 1000
-- ~ означает "приблизительно" — Redis может оставить чуть больше,
-- но выполнит обрезку эффективнее (без полного прохода)
```

## Consumer groups

`XREAD` доставляет каждое сообщение каждому читателю. Для распределения нагрузки между несколькими обработчиками нужны consumer groups. Consumer group позволяет нескольким обработчикам читать один поток параллельно, при этом каждое сообщение доставляется ровно одному обработчику в группе. Это аналог consumer group в Kafka.

```redis-cli
-- создать группу, начинающую с ID 0 (все существующие сообщения)
XGROUP CREATE mystream processors 0

-- обработчик worker-1 читает из группы
XREADGROUP GROUP processors worker-1 COUNT 10 BLOCK 5000 STREAMS mystream >
-- > означает "только непрочитанные этой группой"

-- подтвердить обработку
XACK mystream processors 1700000000000-0

-- посмотреть необработанные сообщения (pending)
XPENDING mystream processors
```

Жизненный цикл сообщения в consumer group: `XADD` добавляет сообщение в поток, `XREADGROUP` доставляет его конкретному обработчику и переводит в состояние pending (доставлено, но не подтверждено), `XACK` подтверждает обработку и удаляет из pending-списка. Если обработчик не вызвал `XACK` (например, упал), сообщение остаётся в pending-списке.

## Обработка сбоев: XCLAIM и XAUTOCLAIM

Если обработчик упал и не подтвердил сообщение, другой обработчик может «забрать» его себе с помощью `XCLAIM`:

```redis-cli
-- забрать сообщения, которые висят в pending больше 60 секунд
XCLAIM mystream processors worker-2 60000 1700000000000-0
```

Redis 6.2 добавил `XAUTOCLAIM`, который автоматически находит и перенаправляет зависшие сообщения:

```redis-cli
XAUTOCLAIM mystream processors worker-2 60000 0
-- найти все pending старше 60 секунд и отдать worker-2
```

## Сравнение с Pub/Sub и Kafka

В отличие от [Pub/Sub](08-pub-sub.md), где сообщения не сохраняются и теряются без подписчиков, Streams хранят историю и позволяют повторное чтение. Streams похожи на Kafka в базовом сценарии: append-only лог, consumer groups, offset-based чтение. Различия: Kafka шардирует топик на партиции и хранит данные на диске (retention на дни/недели), Redis хранит поток в памяти одного узла. Kafka рассчитан на терабайты данных и десятки тысяч сообщений в секунду на партицию, Streams — на сценарии, где данные помещаются в RAM и нужна микросекундная латентность. Для тяжёлых систем обработки событий Kafka остаётся правильным выбором; Streams подходят, когда уже есть Redis и нужна надёжная очередь без дополнительной инфраструктуры.

## Внутреннее устройство: radix tree

Внутри Redis поток хранится как radix tree (`src/rax.c`) — дерево, в котором узлы хранят общие префиксы ключей. Ключи в дереве — ID сообщений. Radix tree компактен для ключей с общими префиксами, а ID потока всегда имеют общий префикс миллисекунд. Значения в узлах — listpack'и, содержащие поля сообщений.
