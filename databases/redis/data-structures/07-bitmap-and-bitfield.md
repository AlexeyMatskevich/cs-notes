# Bitmap и Bitfield

**Предпосылки:** [String](00-string.md), побитовые операции.

Иногда нужно отслеживать бинарные состояния (был/не был, включён/выключён) для миллионов объектов. SET хранит каждый элемент как строку — при 10 миллионах пользователей это сотни мегабайт. Bitmap позволяет представить те же данные как массив бит, где один пользователь занимает ровно один бит, а побитовые операции дают пересечения и объединения за O(n) байт.

## Bitmap: строка как массив бит

Bitmap в Redis — не отдельный тип данных, а способ работать с отдельными битами внутри STRING. Строка в Redis — последовательность байт, и команды `SETBIT`/`GETBIT` обращаются к конкретному биту по его позиции (offset). Redis автоматически расширяет строку, если offset выходит за текущий размер.

```redis-cli
SETBIT daily:2025-01-15 1234 1      -- пользователь 1234 был активен
SETBIT daily:2025-01-15 5678 1      -- пользователь 5678 был активен
GETBIT daily:2025-01-15 1234        -- → 1
GETBIT daily:2025-01-15 9999        -- → 0 (не был)

BITCOUNT daily:2025-01-15           -- количество установленных бит (DAU)
```

## Экономия памяти

Один бит на элемент — радикальная экономия по сравнению со строковыми структурами. При 10 миллионах пользователей bitmap занимает 10 000 000 / 8 = 1.25 МБ. SET из 10 миллионов user_id занял бы сотни мегабайт. Bitmap эффективен, когда пользовательские ID — плотно распределённые числа. При разреженных ID (например, UUID) большая часть битов останется нулевой и bitmap будет расточительным — в таком случае лучше [HyperLogLog](06-hyperloglog.md) (если допустима погрешность) или SET (если нужен точный ответ).

## Побитовые операции между bitmap'ами

Отдельный bitmap отвечает на вопрос «был ли конкретный пользователь?», но часто нужны ответы вида «кто был активен и вчера, и сегодня?». Redis позволяет применять побитовые операции к нескольким bitmap'ам.

```redis-cli
-- пользователи, активные и 15-го, и 16-го января
BITOP AND active:both daily:2025-01-15 daily:2025-01-16
BITCOUNT active:both

-- пользователи, активные хотя бы в один из дней
BITOP OR active:any daily:2025-01-15 daily:2025-01-16
BITCOUNT active:any

-- пользователи, активные 15-го, но не 16-го (ушедшие)
BITOP NOT active:not:2025-01-16 daily:2025-01-16
BITOP AND active:churn daily:2025-01-15 active:not:2025-01-16
BITCOUNT active:churn
```

`BITOP` выполняется на стороне сервера за O(n), где n — длина самой длинной строки в байтах. Результат записывается в новый ключ.

`BITPOS key 0` — найти позицию первого нулевого бита (первый неактивный пользователь). `BITPOS key 1` — первый активный. Если ключ не существует, `BITPOS key 0` вернёт 0 (строка считается полностью нулевой). Если в строке нет 1-битов, `BITPOS key 1` вернёт -1. Это удобно для поиска свободных слотов.

## BITFIELD: несколько числовых полей в одной строке

Bitmap оперирует отдельными битами, но иногда нужно хранить компактные числовые значения (уровень, рейтинг, счётчик) без overhead'а отдельных ключей. `BITFIELD` (Redis 3.2+) позволяет хранить и обновлять несколько целых чисел разной разрядности в одной строке, обращаясь к ним по битовому смещению.

```redis-cli
-- хранить два поля: level (8 бит unsigned) и score (16 бит unsigned)
BITFIELD player:123 SET u8 0 42            -- level = 42 (биты 0-7)
BITFIELD player:123 SET u16 8 1500         -- score = 1500 (биты 8-23)
BITFIELD player:123 GET u8 0               -- → 42
BITFIELD player:123 INCRBY u16 8 100       -- score += 100 → 1600

-- с контролем переполнения
BITFIELD player:123 OVERFLOW SAT INCRBY u8 0 300
-- SAT = saturation: при переполнении останется на максимуме (255 для u8)
-- WRAP = wrap-around (по умолчанию): 255 + 1 = 0
-- FAIL = отклонить операцию при переполнении
```

## Типичные применения

Трекинг DAU/WAU/MAU: один bitmap на день, user_id как offset, `BITCOUNT` для подсчёта, `BITOP AND/OR` для пересечений и объединений. Feature flags: один бит на пользователя, мгновенная проверка через `GETBIT`. Bloom filter: несколько бит на элемент (Redis Bloom module реализует это, но базовый bitmap позволяет построить простой фильтр вручную).
