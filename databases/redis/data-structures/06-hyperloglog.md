# HyperLogLog

**Предпосылки:** [String](00-string.md), хеш-функция, понятие вероятностной структуры данных.

## Проблема: подсчёт уникальных элементов

Подсчёт уникальных значений (unique visitors, уникальных IP, уникальных запросов) в точном виде требует хранения всех ранее встреченных значений. SET справляется с этим, но при миллионах уникальных элементов каждый занимает память. Миллион строк средней длины в SET — десятки мегабайт. Для задач, где точный подсчёт не критичен и допустима погрешность, Redis предоставляет HyperLogLog.

## Как работает HyperLogLog

Экономия памяти в тысячи раз возможна благодаря статистическому свойству хеш-функций. HyperLogLog — вероятностный алгоритм, который оценивает кардинальность множества (количество уникальных элементов) по паттернам в хеш-значениях. Идея основана на наблюдении: если равномерно распределённое хеш-значение начинается с k нулевых бит, вероятность этого — 1/2^k. Чем длиннее цепочка ведущих нулей максимально наблюдённого хеша, тем больше уникальных элементов было добавлено.

Redis реализует HyperLogLog с 16 384 регистрами (2^14). Каждый элемент хешируется, первые 14 бит определяют номер регистра, оставшиеся биты используются для поиска самой длинной цепочки ведущих нулей. Каждый регистр хранит максимальную длину цепочки (6 бит, значения 0–63). Итоговая оценка — гармоническое среднее по всем регистрам с поправочными коэффициентами.

## Память и точность

16 384 регистра по 6 бит дают фиксированный объём памяти — 12 288 байт (~12 КБ) независимо от количества добавленных элементов. Для сравнения: [SET](03-set.md) с миллионом строк занял бы десятки мегабайт. При малом количестве элементов Redis использует более компактное sparse-представление, переключаясь на полное (dense) по мере роста.

Стандартная погрешность — 0.81%. При 1 000 000 уникальных элементов результат будет в диапазоне примерно 991 900–1 008 100.

## Команды

```redis-cli
PFADD visitors "user:1" "user:2" "user:3"    -- добавить элементы
PFADD visitors "user:1"                       -- дубликат не меняет оценку
PFCOUNT visitors                              -- → 3 (приблизительно)

-- объединение нескольких HLL (например, за разные дни)
PFADD visitors:2025-01-15 "user:1" "user:4"
PFADD visitors:2025-01-16 "user:2" "user:5"
PFMERGE visitors:total visitors:2025-01-15 visitors:2025-01-16
PFCOUNT visitors:total                        -- уникальные за оба дня
```

`PFADD` возвращает 1, если внутреннее представление изменилось (вероятно, новый элемент), и 0, если нет. `PFCOUNT` для одного ключа — O(1), для нескольких ключей Redis сначала выполняет merge.

## Типичные применения

Подсчёт уникальных посетителей за день/неделю/месяц: один HLL на временной интервал, `PFMERGE` для агрегации. Подсчёт уникальных поисковых запросов, уникальных IP в логах, уникальных событий в аналитике — везде, где допустима погрешность менее 1% ради экономии памяти в тысячи раз по сравнению с SET.

Для побитового трекинга (был/не был конкретный пользователь) с точным ответом лучше подходит [Bitmap](07-bitmap-and-bitfield.md).
