# Pub/Sub

**Предпосылки:** [Event loop](../architecture/01-event-loop.md), [List](02-list.md) (для сравнения).

## Fire-and-forget

[LIST](02-list.md) и [Stream](05-stream.md) доставляют сообщение одному получателю. Когда нужно отправить одно сообщение сразу всем заинтересованным клиентам, используется Pub/Sub — механизм вещания (broadcast) в Redis. Отправитель публикует сообщение в канал, все подписчики этого канала получают его одновременно.

Критическое свойство: сообщения не сохраняются. Если в момент публикации на канал никто не подписан — сообщение теряется. Если подписчик отключился и переподключился — он пропустил все сообщения за время отсутствия. Нет истории, нет подтверждения доставки, нет retry. Для надёжной доставки нужны [Streams](05-stream.md).

## Основные команды

Pub/Sub работает через пару операций: `SUBSCRIBE` на стороне получателя и `PUBLISH` на стороне отправителя.

```redis-cli
-- подписчик (в отдельном соединении):
SUBSCRIBE notifications:user:123
-- соединение переходит в режим подписки
-- клиент получает сообщения по мере поступления

-- подписка по шаблону:
PSUBSCRIBE notifications:*
-- получает сообщения из ВСЕХ каналов, начинающихся с "notifications:"

-- отправитель (в другом соединении):
PUBLISH notifications:user:123 '{"event":"new_message","from":"alice"}'
-- → 2 (количество подписчиков, получивших сообщение)
```

## Соединение в режиме подписки

Команда `SUBSCRIBE` переводит соединение в специальный режим. В этом режиме доступны только команды подписки (`SUBSCRIBE`, `UNSUBSCRIBE`, `PSUBSCRIBE`, `PUNSUBSCRIBE`, `PING`, `RESET`). Никакие другие команды (GET, SET, INCR) выполнить нельзя — Redis вернёт ошибку. Для обычных команд нужно отдельное соединение.

Это означает, что подписчик держит выделенное TCP-соединение на всё время подписки. При большом количестве подписчиков это увеличивает число открытых соединений на сервере Redis.

## Sharded Pub/Sub (Redis 7.0+)

Классический Pub/Sub не учитывает топологию кластера, что приводит к избыточному трафику. В [Redis Cluster](../distribution/02-cluster.md) (шардированный режим, где данные распределены по узлам через слоты) классический Pub/Sub рассылает сообщение на все узлы кластера, даже если подписчики есть только на одном. Это создаёт лавину избыточного трафика при большом количестве каналов. Sharded Pub/Sub (команды `SSUBSCRIBE`, `SUNSUBSCRIBE`, `SPUBLISH`) привязывает канал к конкретному слоту (по хешу имени канала), и сообщение обрабатывается только узлом, владеющим этим слотом. Подписчики подключаются к нужному узлу, отправители публикуют в нужный узел — трафик локализован.

## LIST vs Pub/Sub vs Stream

| Свойство | LIST | Pub/Sub | Stream |
|----------|------|---------|--------|
| Доставка | одному получателю | всем подписчикам | одному в группе / всем |
| Хранение | да, пока не заберут | нет | да, append-only лог |
| Подтверждение | `BRPOP` = получил | нет | `XACK` |
| Блокирующее чтение | `BRPOP` | `SUBSCRIBE` | `XREADGROUP BLOCK` |
| Повторное чтение | нет (элемент удалён) | нет | да (по ID) |

Pub/Sub подходит для real-time уведомлений, где потеря сообщения допустима: обновления статуса, уведомления UI, трансляция курсов валют. Для надёжных очередей задач — LIST или Stream. Подробнее о паттернах очередей — в [разделе очередей](../patterns/03-queues.md).
