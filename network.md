## Уровень 0: Базовые понятия

### Что такое сеть

**Сеть** — способ передачи данных между компьютерами без физического переноса носителя. Название происходит от того, что связи между множеством соединённых компьютеров образуют структуру, похожую на рыболовную сеть.

### Бит и байт

**Бит** (от английского "binary digit" — двоичная цифра) — минимальная единица информации. Бит принимает только два значения: 0 или 1.

Почему два значения? Это самый простой способ что-то различить. Лампочка либо горит (1), либо не горит (0) — никакой неоднозначности.

Любая информация в компьютере представлена как последовательность битов.

**Байт** — группа из 8 битов. Один байт может хранить 2⁸ = 256 различных значений (от 0 до 255).

### Среда передачи

Для передачи битов между компьютерами нужна **среда передачи** — физический путь для сигнала.

**Медный кабель.** По проводу пускается электрический ток. Разные уровни напряжения представляют 0 и 1.

**Оптоволокно.** Тонкая стеклянная нить, по которой передаётся свет. Есть свет — 1, нет света — 0. Свет быстрее и не подвержен электромагнитным помехам.

**Радиоволны (Wi-Fi).** Передача через воздух. Передатчик создаёт радиоволну с определёнными характеристиками, приёмник распознаёт биты.

### Синхронизация

При передаче последовательности битов возникает проблема: как получатель узнает, где заканчивается один бит и начинается другой?

**Синхронизация** (от греческого "syn" — вместе, "chronos" — время) — договорённость между отправителем и получателем о том, когда считывать каждый бит.

Решения включают тактовый сигнал (отдельный провод, который "тикает") или специальные методы кодирования, где сам сигнал содержит информацию о границах битов.

## Уровень 1: Локальная сеть

### Сетевой интерфейс

**Сетевой интерфейс** (сетевая карта, NIC — Network Interface Card) — устройство, которое:
- Преобразует данные из памяти компьютера в электрические/оптические сигналы для отправки
- Преобразует входящие сигналы обратно в данные

Слово "интерфейс" происходит от латинского "inter" (между) и "facies" (лицо, поверхность) — "поверхность соприкосновения", место, где компьютер "встречается" с сетью.

### MAC-адрес

Когда несколько компьютеров подключены к общей сети, нужен способ указать, кому предназначено сообщение.

**MAC-адрес** (Media Access Control — управление доступом к среде) — уникальный идентификатор сетевого интерфейса.

Формат: `00:1A:2B:3C:4D:5E` — 6 байт (48 бит) в шестнадцатеричной записи.

MAC-адрес **прошит в сетевую карту на заводе**:
- Первые 3 байта — идентификатор производителя
- Последние 3 байта — серийный номер устройства

### Кадр (Frame)

Данные упаковываются в структуру с чётко определёнными полями — **кадр** (frame — "рамка", "каркас").

Структура Ethernet-кадра:

```
┌─────────────────┬─────────────────┬──────────┬───────────────┬─────────┐
│ MAC-адрес       │ MAC-адрес       │ Тип/     │ Данные        │ Контр.  │
│ получателя      │ отправителя     │ Длина    │ (payload)     │ сумма   │
│ (6 байт)        │ (6 байт)        │ (2 байта)│ (46-1500 байт)│ (4 байта)│
└─────────────────┴─────────────────┴──────────┴───────────────┴─────────┘
```

**MAC-адрес получателя** — кому предназначен кадр. Сетевая карта принимает кадр только если адрес совпадает с её собственным (или это широковещательный адрес).

**MAC-адрес отправителя** — от кого кадр. Нужен для ответа.

**Payload** (полезная нагрузка) — собственно передаваемые данные.

**Контрольная сумма (CRC)** — число для проверки целостности данных.

### Контрольная сумма

При передаче биты могут "испортиться" из-за помех.

**Контрольная сумма** (checksum) — число, вычисленное по определённому алгоритму на основе данных.

Механизм:
1. Отправитель вычисляет контрольную сумму и добавляет к кадру
2. Получатель вычисляет сумму заново по полученным данным
3. Если результаты совпадают — данные целы; если нет — кадр отбрасывается

**CRC** (Cyclic Redundancy Check) — конкретный алгоритм в Ethernet. Обнаруживает ошибки, но не исправляет их.

### Ethernet

**Ethernet** — стандарт (протокол), описывающий формат кадров, MAC-адреса, способы кодирования сигналов.

Название от слова "ether" (эфир) — данные распространяются через общую среду, как волны через эфир.

Эволюция скоростей: 10 Mbps → 100 Mbps → 1 Gbps → 10 Gbps → 100 Gbps.

### Коллизии

**Коллизия** (от латинского "collisio" — столкновение) — ситуация, когда два устройства передают одновременно и их сигналы смешиваются.

Ранний Ethernet использовал **CSMA/CD** (Carrier Sense Multiple Access with Collision Detection):
1. Слушай перед отправкой — не передаёт ли кто-то другой?
2. Если коллизия случилась — прекрати передачу, подожди случайное время, попробуй снова

### Коммутатор (Switch)

В современных сетях проблема коллизий решена через **коммутатор**.

**Коммутатор** — устройство с множеством портов. Каждый компьютер подключён к своему порту.

Принцип работы:
1. Компьютер A отправляет кадр компьютеру B
2. Коммутатор принимает кадр
3. Смотрит на MAC-адрес получателя
4. Отправляет кадр только в порт, где находится B

Коммутатор **учится**: запоминает, в каком порту какой MAC-адрес, анализируя адреса отправителей входящих кадров.

Если адрес получателя неизвестен — **flooding** (затопление): кадр отправляется во все порты.

## Уровень 2: Межсетевое взаимодействие

### Почему MAC-адресов недостаточно

Проблема масштабирования: коммутатор не может хранить миллиарды MAC-адресов всех устройств в мире.

Проблема структуры: MAC-адрес — просто серийный номер. По нему невозможно понять, где находится устройство географически или топологически.

Нужна система адресации, которая отражает структуру сети и позволяет иерархически искать путь.

### IP-адрес

**IP** (Internet Protocol — межсетевой протокол). "Inter" — между, "net" — сеть. Протокол для связи между разными сетями.

IP-адрес (версия 4): `192.168.1.25` — четыре числа от 0 до 255, разделённые точками. Каждое число — один байт. Итого 4 байта = 32 бита.

**Ключевое отличие от MAC:**
- MAC-адрес прошит в железо, не меняется
- IP-адрес назначается и может меняться в зависимости от того, к какой сети подключено устройство

IP-адрес отражает **где устройство находится в структуре сетей**, а не что это за устройство.

### Сетевая и хостовая части

IP-адрес состоит из двух частей:

**Сетевая часть** (network part) — идентифицирует сеть.

**Хостовая часть** (host part) — идентифицирует устройство внутри сети.

**Хост** (host — "узел") — любое устройство с IP-адресом.

Пример для `192.168.1.25` с маской `/24`:
- `192.168.1` — сетевая часть
- `25` — хостовая часть

### Маска подсети

**Маска подсети** (subnet mask) определяет границу между сетевой и хостовой частями.

Формат: `255.255.255.0` или `/24`

В битах `255.255.255.0`:
```
11111111.11111111.11111111.00000000
```

Где единицы — сетевая часть, где нули — хостовая часть.

`/24` означает "первые 24 бита — сетевая часть".

Маска позволяет быстро определить: находится ли другой адрес в той же сети?

```
192.168.1.25/24  хочет связаться с  192.168.1.100
Сеть: 192.168.1.x                   Сеть: 192.168.1.x
                   → Одна сеть, можно отправить напрямую

192.168.1.25/24  хочет связаться с  192.168.2.50
Сеть: 192.168.1.x                   Сеть: 192.168.2.x
                   → Разные сети, нужен роутер
```

### Роутер (маршрутизатор)

**Роутер** (router, от "route" — маршрут) — устройство, соединяющее разные сети.

Роутер подключён к нескольким сетям одновременно. У него несколько сетевых интерфейсов, каждый с IP-адресом в своей сети.

Пример:
- Интерфейс 1: `192.168.1.1` — сеть A
- Интерфейс 2: `192.168.2.1` — сеть B
- Интерфейс 3: `10.0.0.1` — сеть C (интернет)

Когда роутер получает пакет, он смотрит на IP-адрес получателя и решает, в какой интерфейс отправить дальше.

### Роутер vs Коммутатор

**Коммутатор** работает с MAC-адресами, внутри одной сети (Layer 2).

**Роутер** работает с IP-адресами, между сетями (Layer 3).

### Пакет (Packet)

На уровне IP данные упаковываются в **пакеты**.

Упрощённая структура:

```
┌─────────────┬────────────┬─────────────┬───────────────┐
│ Заголовок   │ IP-адрес   │ IP-адрес    │ Данные        │
│ (версия,    │ отправителя│ получателя  │ (payload)     │
│ TTL, etc.)  │ (4 байта)  │ (4 байта)   │               │
└─────────────┴────────────┴─────────────┴───────────────┘
```

### Инкапсуляция

**Инкапсуляция** (encapsulation) — помещение данных одного уровня внутрь структуры другого уровня.

IP-пакет помещается внутрь Ethernet-кадра как payload:

```
Ethernet-кадр:
┌─────────────┬─────────────┬───────────────────────────────┬─────────┐
│ MAC-адрес   │ MAC-адрес   │ IP-пакет                      │ CRC     │
│ получателя  │ отправителя │ (целиком, как данные)         │         │
└─────────────┴─────────────┴───────────────────────────────┴─────────┘
```

Два уровня адресов решают разные задачи:
- **IP-адрес** — куда в конечном счёте должны попасть данные
- **MAC-адрес** — какому устройству передать прямо сейчас (следующий хоп)

### Шлюз по умолчанию

**Шлюз по умолчанию** (default gateway) — IP-адрес роутера, которому отправляется всё, что не предназначено для локальной сети.

"Gateway" — "ворота" из локальной сети во внешний мир.

Базовые сетевые настройки:
1. IP-адрес (например, `192.168.1.25`)
2. Маска подсети (например, `255.255.255.0`)
3. Шлюз по умолчанию (например, `192.168.1.1`)

### ARP

**ARP** (Address Resolution Protocol — протокол разрешения адресов) — протокол для определения MAC-адреса по известному IP-адресу.

"Resolution" — "выяснение", "определение".

Механизм:
1. Компьютер отправляет **широковещательный** кадр на MAC `FF:FF:FF:FF:FF:FF` (все устройства в сети получат)
2. ARP-запрос: "У кого IP `192.168.1.1`? Ответьте свой MAC"
3. Роутер с этим IP отвечает: "Это я, мой MAC — `AA:BB:CC:DD:EE:FF`"
4. Результат кешируется

### Путь пакета через сеть

Компьютер `192.168.1.25` отправляет данные серверу `142.250.74.46` (внешний адрес).

**Шаг 1:** Проверка — локальная сеть или нет?
- Моя сеть: `192.168.1.x`
- Получатель: `142.250.74.46`
- Не совпадает → отправляем на шлюз по умолчанию

**Шаг 2:** Формирование IP-пакета
- IP отправителя: `192.168.1.25`
- IP получателя: `142.250.74.46`

**Шаг 3:** ARP для шлюза
- Нужен MAC роутера
- ARP-запрос → получаем MAC

**Шаг 4:** Формирование Ethernet-кадра
- MAC отправителя: свой MAC
- MAC получателя: MAC роутера
- Данные: IP-пакет

**Шаг 5:** Роутер принимает кадр
- Извлекает IP-пакет
- Смотрит в **таблицу маршрутизации** (routing table)
- Определяет, куда отправить дальше

**Шаг 6:** Роутер создаёт новый кадр
- Новые MAC-адреса (для следующего сегмента сети)
- Тот же IP-пакет внутри

**IP-адреса не меняются** на протяжении всего пути. **MAC-адреса меняются** на каждом хопе.

**Шаг 7:** Цепочка роутеров (10-20 штук)
- Каждый роутер повторяет процесс

**Шаг 8:** Последний роутер доставляет кадр серверу

### TTL (Time To Live)

**TTL** — счётчик переходов (несмотря на название "время жизни").

Защита от бесконечных петель при неправильной маршрутизации.

Механизм:
1. При создании пакета TTL = 64 (или 128)
2. Каждый роутер уменьшает TTL на 1
3. Когда TTL = 0, пакет уничтожается

## Уровень 3: Транспортный уровень

### Проблема: несколько приложений

IP-адрес идентифицирует машину, но на машине работает множество приложений: браузер, почта, мессенджер. Как понять, какому приложению предназначены данные?

### Порт

**Порт** (port — "гавань") — число от 0 до 65535, идентифицирующее приложение.

Почему 65535? Порт хранится в 16 битах, 2¹⁶ = 65536.

Приложение "слушает" на определённом порту (**привязка к порту**, binding). Все данные, приходящие на этот порт, отдаются этому приложению.

Полный адрес приложения = IP + порт. Записывается: `192.168.1.25:8080`

Эта комбинация называется **сокет** (socket — "гнездо").

### Известные порты

| Порт | Протокол |
|------|----------|
| 80   | HTTP     |
| 443  | HTTPS    |
| 22   | SSH      |
| 5432 | PostgreSQL |
| 6379 | Redis    |

Диапазоны:
- 0-1023 — "well-known", требуют привилегий
- 1024-49151 — "registered"
- 49152-65535 — "ephemeral" (временные, для исходящих соединений)

### Клиент и сервер

**Сервер** ждёт подключений на известном порту (например, 443).

**Клиент** инициирует подключение. Операционная система выделяет случайный эфемерный порт.

Пример соединения:
- Браузер: `192.168.1.25:52431` (случайный)
- Сервер: `142.250.74.46:443` (известный)

### UDP

**UDP** (User Datagram Protocol — протокол пользовательских датаграмм).

**Датаграмма** (datagram) — самодостаточная единица данных. "Data" + "-gram" (от греческого "запись").

Заголовок UDP — всего 8 байт:

```
┌────────────────┬────────────────┬──────────┬──────────┬─────────────┐
│ Порт           │ Порт           │ Длина    │ Контр.   │ Данные      │
│ отправителя    │ получателя     │          │ сумма    │             │
│ (2 байта)      │ (2 байта)      │ (2 байта)│ (2 байта)│             │
└────────────────┴────────────────┴──────────┴──────────┴─────────────┘
```

UDP **не гарантирует**:
- Доставку (данные могут потеряться)
- Порядок (могут прийти не по порядку)
- Отсутствие дублирования

Применение: видеозвонки, стриминг, онлайн-игры, DNS. Там, где скорость важнее надёжности.

### TCP

**TCP** (Transmission Control Protocol — протокол управления передачей).

TCP гарантирует:
- Данные дойдут
- Данные дойдут в правильном порядке
- Данные не продублируются
- Отправитель не перегрузит получателя

Цена: сложность и накладные расходы (минимум 20 байт заголовка).

Применение: HTTP, передача файлов, базы данных — везде, где нужна надёжность.

### TCP: Соединение

Фундаментальное отличие от UDP: TCP создаёт **соединение** (connection).

UDP — как отправка открыток: каждая независима.

TCP — как телефонный звонок: установка соединения → обмен данными → завершение.

Соединение — это **состояние**, хранимое на обоих концах.

### Трёхстороннее рукопожатие

**Handshake** (рукопожатие) — процедура установки соединения.

```
Клиент                          Сервер
   |                               |
   |  -------- SYN (seq=X) ------> |
   |                               |
   |  <---- SYN-ACK (seq=Y, ack=X+1) |
   |                               |
   |  -------- ACK (ack=Y+1) ----> |
   |                               |
   |     Соединение установлено    |
```

**SYN** (synchronize) — "хочу соединиться, мой начальный номер X".

**SYN-ACK** — "принял твой SYN, мой начальный номер Y".

**ACK** (acknowledge) — "принял твой SYN-ACK".

**Почему три шага?** Обе стороны должны убедиться, что связь работает в обе стороны. После двух шагов сервер не знает, дошёл ли его ответ до клиента.

### TCP: Сегмент

**Сегмент** (segment) — единица данных TCP. TCP "нарезает" поток данных на части.

Ключевые поля заголовка:

```
┌────────────────┬────────────────┬─────────────────┬─────────────────┐
│ Порт           │ Порт           │ Sequence Number │ Acknowledgment  │
│ отправителя    │ получателя     │ (номер послед.) │ Number (подтв.) │
│ (2 байта)      │ (2 байта)      │ (4 байта)       │ (4 байта)       │
├────────────────┴────────────────┴─────────────────┴─────────────────┤
│ Флаги (SYN, ACK, FIN, RST...), размер окна, контр. сумма...        │
├────────────────────────────────────────────────────────────────────┤
│ Данные (payload)                                                    │
└────────────────────────────────────────────────────────────────────┘
```

### Sequence Number

IP-пакеты могут приходить не в том порядке (разные маршруты).

**Sequence Number** — номер первого байта данных в сегменте.

Пример:
- Сегмент 1: seq=1000, 500 байт → байты 1000-1499
- Сегмент 2: seq=1500, 500 байт → байты 1500-1999

Если сегмент 2 придёт раньше — получатель положит его в буфер и подождёт сегмент 1.

### Acknowledgment

**Acknowledgment** (ACK) — подтверждение получения.

Получатель отправляет ACK с номером: "получил все байты до N, жду N и дальше".

Пример:
1. Отправитель: сегмент с байтами 1000-1499
2. Получатель: ACK = 1500
3. Отправитель: сегмент с байтами 1500-1999
4. Получатель: ACK = 2000

Если ACK не приходит в течение таймаута — **повторная передача** (retransmission).

### Таймаут

**Таймаут** (timeout) — время ожидания ACK.

TCP динамически вычисляет таймаут на основе **RTT** (Round-Trip Time — время туда-обратно). Быстрая сеть — короче таймаут. Медленная — длиннее.

### Окно (Window)

Проблема: отправитель может "завалить" получателя данными быстрее, чем тот успевает обрабатывать.

**Управление потоком** (flow control) через **окно** (window).

Получатель в каждом ACK сообщает размер окна: "у меня W байт свободного места".

Отправитель не отправляет больше неподтверждённых данных, чем размер окна.

Если получатель перегружен — окно уменьшается (вплоть до 0).

### Контроль перегрузки

Проблема: перегрузка сети (не получателя). Роутер перегружен, пакеты теряются.

**Congestion control** — адаптация к состоянию сети.

Принцип: потеря пакетов = сигнал перегрузки → замедлиться.

**Slow start**: начать с маленького окна перегрузки (cwnd), увеличивать экспоненциально при успешной доставке.

**Congestion avoidance**: после достижения порога — увеличивать линейно.

При потере: резкое уменьшение окна.

Алгоритмы: Tahoe, Reno, CUBIC, BBR.

### Завершение соединения

**Четырёхстороннее рукопожатие** (соединение полнодуплексное — каждая сторона завершает отдельно):

```
Клиент                          Сервер
   |                               |
   |  -------- FIN -------------> |  ("я закончил отправлять")
   |                               |
   |  <-------- ACK ------------- |  ("понял")
   |                               |
   |  <-------- FIN ------------- |  ("я тоже закончил")
   |                               |
   |  -------- ACK -------------> |  ("понял")
```

**FIN** (finish) — "больше не буду отправлять данные".

**RST** (reset) — грубое немедленное закрытие без церемоний.

### Полная инкапсуляция

```
┌─────────────────────────────────────────────────────────────────────┐
│ Ethernet-кадр                                                       │
│ ┌─────────────────────────────────────────────────────────────────┐ │
│ │ MAC-заголовок │ IP-пакет                                        │ │
│ │               │ ┌─────────────────────────────────────────────┐ │ │
│ │               │ │ IP-заголовок │ TCP-сегмент                  │ │ │
│ │               │ │              │ ┌───────────────────────────┐│ │ │
│ │               │ │              │ │ TCP-заголовок │ Данные   ││ │ │
│ │               │ │              │ │               │ (HTTP)   ││ │ │
│ │               │ │              │ └───────────────────────────┘│ │ │
│ │               │ └─────────────────────────────────────────────┘ │ │
│ └─────────────────────────────────────────────────────────────────┘ │

```

## Уровень 4: Прикладной уровень

### DNS

**DNS** (Domain Name System — система доменных имён) — распределённая база данных, переводящая имена в IP-адреса.

**Domain** (домен) — от латинского "dominium" (владение). "Территория" в пространстве имён.

### Структура доменного имени

`mail.google.com` читается справа налево:

- `com` — домен верхнего уровня (TLD — Top-Level Domain)
- `google` — домен второго уровня
- `mail` — поддомен (subdomain)

### DNS-запрос

Для определения IP-адреса `mail.google.com`:

1. **Локальный кеш** — проверка на компьютере
2. **Резолвер** — сервер провайдера или публичный (`8.8.8.8`, `1.1.1.1`)
3. **Корневой сервер** — "где найти информацию о `.com`?"
4. **TLD-сервер** — "где найти информацию о `google.com`?"
5. **Авторитативный сервер** — "какой IP у `mail.google.com`?"

**Авторитативный** (authoritative) сервер — владеет окончательной информацией о домене.

### DNS TTL

DNS-записи имеют **TTL** (Time To Live) — время кеширования.

Короткий TTL: быстрое распространение изменений, больше нагрузки.
Длинный TTL: меньше нагрузки, медленное распространение.

### Типы DNS-записей

| Тип   | Назначение                                    |
|-------|-----------------------------------------------|
| A     | IPv4-адрес                                    |
| AAAA  | IPv6-адрес                                    |
| CNAME | Псевдоним (указывает на другое имя)           |
| MX    | Почтовые серверы                              |
| TXT   | Произвольный текст (SPF, DKIM, верификация)   |
| NS    | Авторитативные серверы домена                 |

### HTTP

**HTTP** (HyperText Transfer Protocol — протокол передачи гипертекста).

**Гипертекст** — текст со ссылками. "Hyper" — "сверх". Выход за рамки линейного чтения.

### Модель запрос-ответ

1. Клиент отправляет **запрос** (request)
2. Сервер отправляет **ответ** (response)

Каждый запрос независим.

### Структура HTTP-запроса

```
GET /search?q=hello HTTP/1.1
Host: www.google.com
User-Agent: Mozilla/5.0
Accept: text/html

```

**Стартовая строка:**
- `GET` — метод
- `/search?q=hello` — путь + query string
- `HTTP/1.1` — версия протокола

**Заголовки** (headers) — пары "ключ: значение".

**Пустая строка** — разделитель.

**Тело** (body) — данные (в GET обычно отсутствует).

### HTTP-методы

| Метод  | Назначение                        | Идемпотентный |
|--------|-----------------------------------|---------------|
| GET    | Получить данные                   | Да            |
| POST   | Отправить данные, создать ресурс  | Нет           |
| PUT    | Заменить ресурс целиком           | Да            |
| PATCH  | Частично обновить                 | Нет (обычно)  |
| DELETE | Удалить                           | Да            |
| HEAD   | Только заголовки (без тела)       | Да            |
| OPTIONS| Узнать поддерживаемые методы      | Да            |

### Идемпотентность

**Идемпотентный** (idempotent) — от латинского "idem" (тот же) + "potent" (сила).

Операция, которую можно выполнить много раз с тем же результатом.

- `GET /users/123` — идемпотентный (всегда тот же пользователь)
- `DELETE /users/123` — идемпотентный (после первого удаления — пользователя уже нет)
- `POST /users` — не идемпотентный (каждый раз новый пользователь)

Важно при сетевых ошибках: идемпотентные методы можно безопасно повторить.

### Структура HTTP-ответа

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1234

<!DOCTYPE html>
<html>...</html>
```

**Строка статуса:** версия + код + текст.

### Коды статуса

| Диапазон | Категория        | Примеры                          |
|----------|------------------|----------------------------------|
| 1xx      | Информационные   | 100 Continue                     |
| 2xx      | Успех            | 200 OK, 201 Created, 204 No Content |
| 3xx      | Перенаправления  | 301 Moved Permanently, 302 Found, 304 Not Modified |
| 4xx      | Ошибки клиента   | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity |
| 5xx      | Ошибки сервера   | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout |

### Важные заголовки

**Запрос:**
- `Host` — домен (обязателен в HTTP/1.1)
- `Authorization` — учётные данные
- `Content-Type` — тип данных в теле
- `Accept` — ожидаемый тип ответа
- `Cookie` — куки

**Ответ:**
- `Content-Type` — тип данных
- `Content-Length` — размер тела
- `Set-Cookie` — установить куку
- `Cache-Control` — инструкции кеширования
- `Location` — URL для редиректа

### Cookies и сессии

HTTP — **stateless** (без состояния). Сервер не помнит предыдущие запросы.

**Cookie** — данные, которые сервер просит браузер сохранить и отправлять с каждым запросом.

Механизм:
1. Сервер: `Set-Cookie: session_id=abc123; HttpOnly; Secure`
2. Браузер сохраняет
3. При следующих запросах: `Cookie: session_id=abc123`
4. Сервер идентифицирует клиента

**Атрибуты cookies:**
- `HttpOnly` — недоступна из JavaScript (защита от XSS)
- `Secure` — только по HTTPS
- `SameSite` — ограничение межсайтовых запросов (защита от CSRF)
- `Max-Age` / `Expires` — время жизни

**Сессия** (session) — данные на сервере, связанные с session ID из куки.

### HTTPS и TLS

HTTP передаёт данные открытым текстом.

**HTTPS** = HTTP поверх **TLS** (Transport Layer Security).

TLS обеспечивает:
1. **Шифрование** — данные нечитаемы для перехватчика
2. **Аутентификация** — подтверждение подлинности сервера
3. **Целостность** — данные нельзя незаметно изменить

### TLS-рукопожатие (упрощённо)

1. **Client Hello** — "поддерживаю TLS X, алгоритмы Y"
2. **Server Hello** — "используем TLS X, алгоритм Y, вот сертификат"
3. **Проверка сертификата** — домен, подпись CA, срок действия
4. **Обмен ключами** — создание симметричного ключа
5. **Защищённое соединение** — данные шифруются

**Сертификат** — документ: "это действительно example.com, публичный ключ такой-то, подписано CA".

**CA** (Certificate Authority) — удостоверяющий центр, которому доверяют браузеры.

### Типы шифрования

**Асимметричное** — два ключа: публичный (шифрование) и приватный (расшифровка). Безопасно, но медленно.

**Симметричное** — один ключ для обоих операций. Быстро, но ключ нужно передать безопасно.

TLS: асимметричное для обмена симметричным ключом, затем симметричное для данных.

### Версии HTTP

**HTTP/1.0** — одно соединение = один запрос. Неэффективно.

**HTTP/1.1** — keep-alive (переиспользование соединения), но запросы последовательные. Head-of-line blocking.

**HTTP/2** — мультиплексирование (несколько запросов одновременно), сжатие заголовков, server push. Бинарный протокол.

**HTTP/3** — поверх QUIC (UDP с надёжностью и TLS). Решает head-of-line blocking на уровне TCP.

### REST

**REST** (Representational State Transfer) — архитектурный стиль для API.

Не протокол, а набор принципов.

**Ресурс** — сущность с идентичностью (пользователь, заказ, статья).

**URI** — идентификатор ресурса: `/users/123`

**Представление** — формат ресурса (JSON, XML, HTML).

**Методы HTTP = операции:**
- `GET /users` — список
- `GET /users/123` — конкретный
- `POST /users` — создать
- `PUT /users/123` — заменить
- `PATCH /users/123` — обновить частично
- `DELETE /users/123` — удалить

**Stateless** — сервер не хранит состояние клиента между запросами.

### Полный путь: от URL до страницы

1. **Парсинг URL:** протокол, хост, путь, query string
2. **DNS:** имя → IP-адрес
3. **TCP:** трёхстороннее рукопожатие
4. **TLS:** рукопожатие, шифрование
5. **HTTP-запрос:** отправка
6. **Обработка на сервере**
7. **HTTP-ответ:** получение
8. **Рендеринг:** парсинг HTML, загрузка ресурсов, отрисовка

## Модели OSI и TCP/IP

### Зачем нужны модели

Сетевое взаимодействие — сложная задача. Модель разбивает её на **уровни** (layers). Каждый уровень:
- Решает свою узкую задачу
- Предоставляет сервис уровню выше
- Не знает деталей других уровней

Преимущества:
- **Независимая разработка** — улучшение одного уровня не затрагивает другие
- **Взаимозаменяемость** — разные реализации на одном уровне
- **Упрощение понимания**

### Модель OSI

**OSI** (Open Systems Interconnection) — эталонная модель из 7 уровней.

```
┌─────────────────────────────────────────────────────────────────┐
│  Уровень 7: Прикладной (Application)                            │
│  HTTP, DNS, SMTP, FTP, SSH                                      │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 6: Представления (Presentation)                        │
│  Шифрование (TLS), сжатие, сериализация                         │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 5: Сеансовый (Session)                                 │
│  Управление диалогом, RPC                                       │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 4: Транспортный (Transport)                            │
│  TCP, UDP — порты, надёжность                                   │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 3: Сетевой (Network)                                   │
│  IP — маршрутизация между сетями                                │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 2: Канальный (Data Link)                               │
│  Ethernet, Wi-Fi — MAC-адреса, кадры                            │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 1: Физический (Physical)                               │
│  Биты, сигналы, кабели, разъёмы                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Уровни OSI подробно

**Уровень 1: Физический (Physical)**
- Задача: передача сырых битов по физической среде
- Единица данных: бит
- Примеры: спецификации кабелей, разъёмы RJ-45, оптика

**Уровень 2: Канальный (Data Link)**
- Задача: надёжная передача между непосредственно соединёнными устройствами
- Единица данных: кадр (frame)
- Примеры: Ethernet, Wi-Fi, MAC-адреса, коммутаторы

**Уровень 3: Сетевой (Network)**
- Задача: маршрутизация между разными сетями
- Единица данных: пакет (packet)
- Примеры: IP, роутеры, ICMP

**Уровень 4: Транспортный (Transport)**
- Задача: доставка данных между приложениями, надёжность
- Единица данных: сегмент (TCP) / датаграмма (UDP)
- Примеры: TCP, UDP

**Уровень 5: Сеансовый (Session)**
- Задача: управление диалогом между приложениями
- На практике: редко выделяется отдельно

**Уровень 6: Представления (Presentation)**
- Задача: преобразование форматов, шифрование, сжатие
- На практике: интегрирован в прикладной уровень

**Уровень 7: Прикладной (Application)**
- Задача: протоколы для приложений
- Примеры: HTTP, DNS, SMTP, SSH, FTP

### Модель TCP/IP

Практическая модель из 4 уровней:

```
        OSI                              TCP/IP
┌─────────────────────┐           ┌─────────────────────┐
│ 7. Application      │           │                     │
├─────────────────────┤           │                     │
│ 6. Presentation     │ ───────── │ 4. Application      │
├─────────────────────┤           │                     │
│ 5. Session          │           │                     │
├─────────────────────┼───────────┼─────────────────────┤
│ 4. Transport        │ ───────── │ 3. Transport        │
├─────────────────────┼───────────┼─────────────────────┤
│ 3. Network          │ ───────── │ 2. Internet         │
├─────────────────────┼───────────┼─────────────────────┤
│ 2. Data Link        │           │                     │
├─────────────────────┤ ───────── │ 1. Network Interface│
│ 1. Physical         │           │                     │
└─────────────────────┘           └─────────────────────┘
```

### OSI vs TCP/IP

**OSI** — теоретическая, для обучения и терминологии ("проблема на L2", "L7 балансировщик").

**TCP/IP** — практическая, описывает реальный интернет.

### Инкапсуляция по уровням

Спуск по стеку — каждый уровень добавляет заголовок:

```
[HTTP-данные]
       ↓
[TCP][HTTP-данные]
       ↓
[IP][TCP][HTTP-данные]
       ↓
[Eth][IP][TCP][HTTP-данные][CRC]
       ↓
     биты
```

Подъём по стеку — каждый уровень убирает свой заголовок:

```
     биты
       ↓
[Eth][IP][TCP][HTTP-данные][CRC]  → Канальный: убирает Eth
       ↓
[IP][TCP][HTTP-данные]            → Сетевой: убирает IP
       ↓
[TCP][HTTP-данные]                → Транспортный: убирает TCP
       ↓
[HTTP-данные]                     → Приложение
```

### PDU (Protocol Data Unit)

| Уровень       | Название единицы данных       |
|---------------|-------------------------------|
| Прикладной    | Данные, сообщение (message)   |
| Транспортный  | Сегмент / датаграмма          |
| Сетевой       | Пакет (packet)                |
| Канальный     | Кадр (frame)                  |
| Физический    | Биты (bits)                   |

### Устройства по уровням

| Уровень | Устройства                                      |
|---------|-------------------------------------------------|
| L1      | Репитер, хаб                                    |
| L2      | Коммутатор (switch), мост (bridge)              |
| L3      | Роутер (router)                                 |
| L4+     | Файрвол, балансировщик нагрузки, прокси         |

**L7 load balancer** — понимает HTTP, принимает решения на основе URL, headers, cookies.

### Принцип песочных часов

В середине — только IP. Это обеспечивает универсальность.

```
      HTTP   SMTP   DNS   ...
            \  |  /
             TCP UDP
               |
              IP          ← узкое место
             /  \
      Ethernet  Wi-Fi  LTE  ...
```

Любое приложение работает поверх IP. IP работает поверх любой физической сети.

### Сквозной принцип (End-to-End)

Умная логика — на концах (в приложениях). Сеть — "глупая", просто доставляет пакеты.

Надёжность, шифрование, проверка ошибок — делают конечные точки.
